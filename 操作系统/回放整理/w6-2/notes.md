## 1. 回顾：单处理器调度与算法评价

> 课件 第 58 页 · 讲解从 `05:12` 开始

### 单处理器调度算法回顾

单处理器调度的核心任务是：在多个就绪进程之间选择一个进程占用 CPU。前两次课的重点是多级反馈队列（Feedback）调度和 Windows 调度算法；而评价一个调度算法时，需要综合考察多个维度，包括公平性、响应时间、吞吐量、是否产生饥饿、是否支持抢占，以及算法对不同类型进程（如 I/O 密集型进程）的偏好等`▶ 05:12`。

### 评价调度算法的关键指标

- **选择函数**：决定按照什么标准从就绪队列中挑选下一个运行的进程。
- **决策模式**：分为**非抢占**（进程一旦获得 CPU 就一直运行到结束或阻塞）和**抢占**（可在特定时机被剥夺 CPU）。
- **吞吐量**：单位时间内完成的进程数量。
- **响应时间**：从提交请求到首次得到响应所经历的时间，对交互式系统尤为重要。
- **调度开销**：执行调度逻辑、进行上下文切换所付出的代价。
- **对进程的影响**：算法对长进程、短进程、I/O 密集型进程是否公平有利。
- **饥饿问题**：某些进程是否可能长期得不到调度。

> **老师强调**：评价调度算法不能只看单一指标，要综合公平性、响应时间、吞吐量、饥饿、抢占性以及对 I/O 密集型进程的偏好等要素`▶ 05:12`。

### 各调度算法的比较

| 调度算法 | 选择函数 | 决策模式 | 吞吐量 | 响应时间 | 开销 | 对进程的影响 | 饥饿问题 |
|---|---|---|---|---|---|---|---|
| **FCFS**（先来先服务） | max[w]（等待最久者优先） | 非抢占 | 不强调 | 可能很高，特别是当进程执行时间差别很大时 | 最小 | 对短进程不利；对 I/O 密集型进程不利 | 无 |
| **Round Robin**（时间片轮转） | 常数（按队列顺序轮流） | 抢占（时间片用完时） | 如果时间片小，吞吐量会很低 | 为短进程提供好的响应时间 | 最小 | 公平对待所有进程 | 无 |
| **SJF**（短作业优先） | min[s]（总服务时间最短者优先） | 非抢占 | 高 | 为短进程提供好的响应时间 | 可能较高 | 对长进程不利 | 可能 |
| **SRTN**（剩余时间最短优先） | min[s−e]（剩余服务时间最短者优先） | 抢占（新进程到达时） | 高 | 提供好的响应时间 | 可能较高 | 对长进程不利 | 可能 |
| **HRRN**（高响应比优先） | max((w+s)/s)（响应比最高者优先） | 非抢占 | 高 | 提供好的响应时间 | 可能较高 | 很好的平衡 | 无 |
| **Feedback**（多级反馈队列） | 见算法思想 | 抢占（时间片用完时） | 不强调 | 不强调 | 可能较高 | 可能对 I/O 密集型进程有利 | 可能 |

### 符号说明

- **w**：进程已经花费的**等待时间**。
- **e**：到目前为止，进程已经花费的**执行时间**。
- **s**：进程所需要的**总服务时间**，其中已经包含 e；因此剩余服务时间为 s−e。

### 要点理解

- **FCFS** 实现简单、开销最小，但平均等待时间对进程到达顺序和服务时间差异非常敏感，短进程可能被排在一个长进程之后而长时间等待；I/O 密集型进程在 I/O 完成后也要排在就绪队列末尾，同样吃亏。
- **Round Robin** 通过固定时间片轮流执行保证公平，没有饥饿；但时间片过小会导致频繁的上下文切换，使吞吐量下降，而时间片过大则会退化为类似 FCFS 的效果、响应变差。
- **SJF / SRTN** 都偏向短进程，能获得高吞吐量和好的响应时间；但长进程可能持续被后来的短进程"插队"，从而**可能饥饿**。SRTN 是 SJF 的抢占版本，在新进程到达时比较剩余时间。
- **HRRN** 的响应比 $(w+s)/s = 1 + w/s$：短作业初始响应比高，而长作业随着等待时间 w 增大，响应比也会逐渐升高，最终一定能被选中，因此**不会饥饿**，在长短进程之间取得了较好的平衡。
- **Feedback（多级反馈队列）** 不要求预先知道服务时间，而是根据进程的实际执行行为动态调整：进程用完时间片就被降到更低优先级队列，I/O 密集型进程因常因等待 I/O 而阻塞、往往能留在高优先级队列，所以该算法**可能对 I/O 密集型进程有利**；但低优先级队列中的进程在高负载下**可能饥饿**。

## 2. 多处理器调度的基本问题

> 课件 第 77–80 页 · 讲解从 `06:34` 开始

### 多处理器调度概述

多处理器调度研究多个处理器组成的多处理机系统中的进程调度问题。常见的多处理器硬件架构有两种`▶ 06:34`：

- **SMP（Symmetric Multiprocessing，对称多处理器）**：对称结构，所有 CPU 通过单条系统总线访问内存，不存在访问距离上的差异`▶ 06:34`。课件图示中，每个物理 CPU 可包含多个逻辑 CPU，各逻辑 CPU 经由系统总线互连并共享资源。
- **NUMA（Non-Uniform Memory Access，非一致内存访问）**：由多个节点组合而成，跨节点访问内存的距离更远、代价更高，调度时需要考虑这种访问距离差异`▶ 06:34`。

> **老师强调**：本次以 SMP 为例展开，NUMA 架构只需了解其特性即可`▶ 08:15`。

### SMP 调度的特征

在对称多处理器系统中：

- 每个处理器运行自己的调度程序，调度算法本身与单处理器调度差异不大`▶ 08:15`；
- 处理器之间可以进行负载共享；
- 由于多个调度程序会访问共享资源，必须通过**锁**等机制对共享资源的访问进行同步`▶ 08:15`。

### 多处理器调度算法设计要考虑的问题

与单处理器调度相比，多处理器调度不仅要决定**选择哪一个进程执行**，还需要决定**在哪一个 CPU 上执行**`▶ 09:33`。设计中主要关注以下问题。

#### 1. 进程迁移的开销

当进程在多个 CPU 之间迁移时，会带来额外开销，主要表现为：

- **高速缓存失效（Cache 失效）**：进程原 CPU 缓存中的数据用不上，新 CPU 缓存中没有所需数据；
- **TLB 失效**：地址翻译缓存的内容在新 CPU 上失效。

因此，调度的基本思路是**尽可能使进程总是在同一个 CPU 上执行**：如果进程上次在 CPU1 上执行、本次被调度到 CPU2，就会增加高速缓存失效和 TLB 失效；若尽量调度到原来的（或指定的）CPU 上，各种失效就会减少。

> **老师强调**：进程迁移能实现负载均衡，但会带来缓存失效、TLB 失效的额外开销，因此应尽量让进程固定在同一个 CPU 上运行`▶ 10:52`。

#### 2. 队列组织方式

- **全局（公共）就绪队列**：所有 CPU 从同一个队列中选取进程。缺点是所有 CPU 都要访问同一队列，必须加锁同步，容易形成性能瓶颈`▶ 09:33`。
- **每 CPU 独立就绪队列**：每个 CPU 维护自己的队列，可避免对单一队列的锁竞争；但可能出现各 CPU 队列长短不一、忙闲不均的情况，需要进行负载均衡`▶ 09:33 · 10:52`。

#### 3. 负载均衡

采用每 CPU 独立队列时，可能出现某个 CPU 队列中进程过多、而其他 CPU 空闲的情况，需要通过**进程迁移**把负载转移到空闲 CPU 上`▶ 10:52`。负载均衡与迁移开销之间存在权衡：迁移能均衡负载，却会引起缓存和 TLB 失效。

#### 4. 其他需要考虑的问题

老师补充指出，SMP 调度还需关注`▶ 10:52 · 13:56`：

- **亲和性（Affinity）**：进程倾向于在固定 CPU 上运行，以保留缓存热度；
- **缓存一致性（Cache Coherence）**：多个处理器缓存同一数据时需要保证一致性；
- **核间数据共享**：进程在不同核之间共享数据所带来的影响。

### 对称多处理器的进程分配

SMP 中进程到处理器的分配分为静态分配和动态分配两种方式。

| 对比项 | 静态进程分配 | 动态进程分配 |
|---|---|---|
| 分配方式 | 进程从开始到结束都被分配到一个固定的处理机上执行 | 进程在执行中可分配到任意空闲处理机执行 |
| 就绪队列 | 每个处理机有自己的就绪队列 | 所有处理机共享一个公共的就绪队列 |
| 调度开销 | 小 | 大 |
| 负载情况 | 各处理机可能忙闲不均，不考虑负载均衡 | 各处理机负载均衡 |
| 主要代价 | 负载不均衡 | 锁竞争、高速缓存失效、TLB 失效等 |

- **静态进程分配**：进程一旦分配就固定在一个处理器上，每个处理器维护独立队列，调度开销小，但无法应对处理器忙闲不均的问题`▶ 12:44`。
- **动态进程分配**：一方面可以通过进程迁移在处理器间实现负载均衡；另一方面，采用公共就绪队列时，空闲处理器可直接从队列中获取进程，天然保证负载均衡；但其代价是存在锁竞争以及 TLB 失效、高速缓存失效等额外开销`▶ 13:05`。

> **老师强调**：对称多处理器调度的核心问题就是缓存一致性、缓存亲和性、核间数据共享与负载均衡，以及它们与进程迁移开销之间的权衡`▶ 13:05 · 13:56`。

## 3. 缓存一致性、亲和性与负载均衡

> 课件 第 82–86 页 · 讲解从 `14:53` 开始

### 多核处理器系统面临的问题

在多核处理器中，缓存与主存的关系相比单核发生了变化，系统主要面临以下问题：

- **缓存一致性问题**：多个核心各自拥有缓存，如何保证它们看到的共享数据一致。
- **缓存亲和性问题**：让进程或线程尽量固定在同一个核心上运行，以复用该核心缓存中的数据。
- **核间数据共享**：多个核心之间需要共享和同步数据。
- **负载均衡**：如何把任务合理分配到多个核心上，避免有的核很忙、有的核空闲。

---

### 缓存一致性问题

#### 问题示例

假设有两个处理器 P1 和 P2，同时读取并修改共享数据 X，初始时：

- 内存中 X = 0
- P1 缓存中 X = 0
- P2 缓存中 X = 0

执行过程：

1. P1 执行 `X = X + 1`，P1 缓存中的 X 变为 1。
2. P2 执行 `X = X + 1`，P2 缓存中的 X 仍基于旧值 0，结果也变为 1。
3. 预期最终 X 应为 2，但由于两个缓存没有同步，最终结果可能错误。

> **老师强调**：若两个处理器缓存中的 X 初始都为 0，各自加 1 后预期结果应为 2；若缓存未同步，就会导致结果错误`▶ 14:53`。

#### 解决方法：MESI 协议

硬件通过 **MESI 协议**保证缓存一致性。该协议根据缓存行：

- 是否被修改；
- 是否与内存数据一致；

等状态来协调多个处理器缓存中的数据副本，从而避免共享数据不一致的问题`▶ 14:53`。

---

### 缓存亲和性问题

#### 基本思想

**缓存亲和性（Cache Affinity）**是指：在多核处理器系统中，让特定进程或线程尽可能长时间地在同一个处理器核心上运行。

这样做的好处是：

- 进程之前访问过的数据已经加载到该核心的缓存中；
- 继续在同一核心运行可以提高缓存命中率；
- 减少访问主存的次数；
- 提高数据访问速度和系统整体性能。

> **老师强调**：亲和性是指进程尽量固定在同一处理器上运行，以保证访问速度和整体性能；但负载均衡调度可能迁移进程、破坏亲和性，从而带来性能损失`▶ 16:21`。

---

### 缓存亲和性与负载均衡的权衡

缓存亲和性希望任务“留在原核”，负载均衡则可能把任务“迁到别的核”，二者存在矛盾：

- 保持亲和性：缓存命中率高，但可能导致各核心负载不均。
- 迁移任务：可以平衡负载，但任务在新核心上缓存未预热，会产生缓存不命中开销。

> **老师强调**：调度问题没有单一最优答案，需要综合权衡多种因素；任务迁移可以最小化整体计算时间，但会带来新的缓存未命中开销`▶ 17:04`。

#### 例子 1：多核并行计算 / 图像渲染

- 将一部分数据对应的计算任务分配到某个核心上；
- 该部分数据会被频繁访问，保留在核心缓存中可以提高访问速度；
- 但不同部分的计算量可能不均匀，导致各核心负载不同；
- 此时可能把负载较重核心上的任务转移到负载较轻的核心上，以最小化整体计算时间；
- 任务转移后，新核心缓存中没有相关数据，会带来额外的缓存不命中开销。

#### 例子 2：CDN 缓存

CDN 也体现了类似的“缓存亲和性 vs 负载均衡”思想：

- 按照用户或地区，将常访问的数据（如视频、商品详情页等）缓存到就近的 CDN 服务器上；
- 用户访问附近服务器时，可以更快获得内容；
- 当某地服务器负载较大时，可能将该地区用户请求路由到其他地区服务器；
- 跨地区访问会增加内容缓存不命中和网络访问开销。

> **老师强调**：CDN 缓存就近服务用户相当于缓存亲和性；服务器负载大时迁移请求相当于负载均衡，迁移同样会带来开销，二者始终存在矛盾`▶ 19:16`。

---

### 负载均衡：作业偷取（Work Stealing）

#### 核心思想

**作业偷取（Work Stealing）**让空闲处理器主动从忙碌处理器那里“偷取”任务来执行，从而使各个处理器的负载相对均衡。

> **老师强调**：作业偷取是任务被主动偷取的过程，是一种常见的调度优化手段`▶ 20:57`。

#### 基本流程

1. 初始时，任务按照一定策略分配到多个处理器的本地待执行队列（就绪队列）中。
2. 每个处理器优先执行自己本地队列中的任务。
3. 当处理器的本地待执行队列为空时，它可以访问其他处理器的待执行队列。
4. 空闲处理器从其他处理器队列中“偷取”任务执行。
5. 通过这种方式，让空闲核心也承担任务，达到整体负载均衡。

#### 优点

- 处理器优先处理本地队列任务，有利于保持缓存亲和性。
- 本地队列为空时才偷取任务，可以减少核心空闲时间。
- 空闲处理器主动找任务，能够较好地实现负载均衡。
- 适合任务量不均衡、任务执行时间不确定的并行场景。

#### 缺点

- 偷取任务时可能需要访问其他处理器的队列，带来同步和竞争开销。
- 被偷取的任务迁移到新处理器后，可能产生缓存不命中。
- 多个空闲处理器同时偷取时，需要保证队列操作的正确性。
- 任务迁移会在一定程度上破坏缓存亲和性。

> **老师强调**：处理器优先执行本地队列任务；本地队列为空时，主动从其他处理器的就绪队列窃取进程执行，以达到负载均衡的目的`▶ 20:04`。

## 4. 多处理器调度思想的系统案例

> 课件 第 87–88 页 · 讲解从 `21:07` 开始

本节通过两个真实系统案例，说明多处理器环境下"缓存亲和性 + 负载均衡"的调度思想如何在不同层面落地：Go 的 GMP 解决单机内协程如何调度到核心，YARN 解决集群中任务如何调度到节点。

### 案例一：Go 语言 GMP 调度器

GMP 是 Go 运行时系统的核心组件，负责管理和调度 Goroutine（协程），其角色类似于操作系统内核管理和调度进程/线程。

**三个核心概念**（由名称 GMP 而来）：

| 组成 | 含义 | 作用 |
|---|---|---|
| G | Goroutine，协程 | 被调度执行的用户任务 |
| M | Machine，内核线程 | 真正执行 Goroutine 的执行体 |
| P | Processor，处理器（逻辑处理器） | 持有本地 G 队列，是 G 与 M 之间的调度上下文 |

**体现的调度思想：**

- **数据/缓存亲和性优先**
  - 尽量把 Goroutine 调度到之前访问过相同数据的处理器上执行，保证亲和性、提升性能`▶ 21:07`。
  - 进一步地，尽量让 Goroutine 在之前执行它的那个 P 所绑定的 M（内核线程）上运行，从而保持缓存亲和性——同一核心的本地缓存中仍保留该协程用过的数据，缓存命中率更高。
- **每核本地队列 + 工作窃取（Work Stealing）**
  - 每个 P 都维护一个本地 Goroutine 队列，任务优先在本地排队、本地执行，减少跨核迁移。
  - 当某个 P 的本地队列为空时，它会尝试从其他 P 的本地队列中"窃取"Goroutine 来执行，以此在保持亲和性的同时实现负载均衡，避免有的核心空闲、有的核心积压`▶ 21:07`。

> **老师强调**：本地队列保证亲和性，窃取机制保证负载均衡，两者配合是多处理器调度的典型思路`▶ 21:07`。

### 案例二：Hadoop YARN

YARN 是 Hadoop 生态中的调度资源管理框架，把同样的调度思想从"单机多核"扩展到"多节点集群"。

**两类关键管理角色：**

| 组件 | 职责 |
|---|---|
| NodeManager（节点管理器） | 管理单个节点上的资源和容器（Container），与 HDFS 等分布式文件系统协作 |
| ResourceManager（资源管理器） | 收集各 NodeManager 上报的资源使用情况，协调任务的资源需求，并把任务分配到不同节点上 |

**体现的调度思想：**

- **数据本地性（节点级亲和性）**
  - NodeManager 与 HDFS 等分布式文件系统协作，保证数据在多个节点之间的缓存一致性。
  - 调度时将需要处理相同数据的任务分配到**已经存储有该数据的节点**上，使任务就近访问数据，减少网络传输，提高缓存利用率——这是把"缓存亲和性"思想用到了集群层面`▶ 22:37`。
- **基于全局资源信息的负载均衡**
  - ResourceManager 汇总各节点资源使用情况，将空闲节点纳入任务分配，把任务协调、分发到不同节点，避免节点间忙闲不均`▶ 22:37`。
- **多队列调度**
  - YARN 支持多队列调度，不同队列可以设置不同的资源分配策略，从而在多租户、多作业之间实现差异化的资源分配`▶ 22:37`。

### 两个案例的共同思想

| 维度 | Go GMP | Hadoop YARN |
|---|---|---|
| 调度层面 | 单机内，协程调度到核心/线程 | 集群内，任务调度到节点 |
| 被调度对象 | Goroutine（G） | 计算任务 / 容器 |
| 亲和性手段 | 调度到访问过相同数据的 P 及其绑定的 M | 任务分配到存储所需数据的节点 |
| 本地排队 | 每个 P 的本地 G 队列 | 节点本地数据与本地容器 |
| 负载均衡手段 | 空闲 P 从其他 P 窃取 G | ResourceManager 依据资源上报全局分配 |
| 差异化策略 | （由运行时调度逻辑控制） | 多队列、不同资源分配策略 |

> **老师总结**：从协程到集群任务，两个系统都遵循"优先保证数据/缓存亲和性，再通过窃取或全局调度平衡负载"的思路，它们是多处理器（及多节点）环境下调度思想的典型应用`▶ 21:07 · 22:37`。

## 5. 实时系统与实时调度算法

> 课件 第 89–93 页 · 讲解从 `24:15` 开始

### 实时系统概述

实时系统的核心特征是**以时间为关键参数**：任务请求到来后，系统必须在严格的时间范围内作出响应，并保证高可靠性，不能让任务饥饿`▶ 24:15`。

实时系统追求的目标：
- 对外部请求在严格时间范围内作出反应；
- 高可靠性。

典型应用：工业过程控制系统，如汽车装配线。

### 硬实时与软实时

| 类型 | 含义 | 例子 |
|---|---|---|
| **硬实时系统** | 某个动作绝对必须在规定的时刻或时间范围内完成，超时会造成严重后果 | 工业控制生产线的装配、拧螺丝环节，超时会引发生产问题`▶ 24:15` |
| **软实时系统** | 接受偶尔违反最终时限（截止时间） | 网络视频播放，短暂卡顿不影响整体观看体验`▶ 24:15` |

### 实时任务的分类与特点

- **周期性任务**：实时系统中最主要的任务类型，按固定周期反复到达`▶ 26:26`。
- **偶发性任务 / 非周期性任务**：随机出现的任务，系统也需处理`▶ 26:26`。

实时任务的根本特点是**确定性**：每个任务的完成时间（截止时间）是明确的，调度的关键就在于判断任务能否在截止时间之前完成。

### 可调度性

一个系统可能要响应多个周期性事件流。如果处理所需的 CPU 时间总量超过系统能力，就无法处理完所有事件。

设有 $m$ 个周期事件，事件 $i$：
- 以周期 $P_i$ 发生；
- 每次需要 $C_i$ 秒 CPU 时间处理。

则事件 $i$ 带来的 CPU 利用率为 $C_i/P_i$。系统可以处理该负载、即为**可调度**的条件是：

$$
\sum_{i=1}^{m} \frac{C_i}{P_i} \le 1
$$

即所有周期性任务的 CPU 利用率之和不超过 1（100%），才能保证所有任务在截止时间前完成`▶ 26:46`。

### 典型实时调度算法

实时调度的两类核心算法是 **RM（速率单调）** 和 **EDF（最早截止时间优先）**，多数嵌入式实时调度都是这两类算法或其变体`▶ 26:46 · 30:26`。

#### 速率单调（Rate-Monotonic，RM）

- **静态优先级**调度算法：任务优先级在运行前确定，运行期间不变。
- **前提条件**：
  - 所有任务都是周期性的；
  - 每个任务的执行时间已知。
- **优先级规则**：课件表述为"根据任务的周期性和执行时间分配优先级，执行时间较短的任务具有更高优先级"；讲解中强调"执行时间越短的任务，优先级越高，优先被调度"`▶ 28:09`。

#### 最早截止时间优先（Earliest Deadline First，EDF）

- **动态优先级**实时调度算法：优先级随运行情况不断变化。
- **优先级规则**：根据任务的最后期限（Deadline）和剩余执行时间分配优先级，**截止期越近（最先到期）的任务优先级越高**`▶ 30:26`。
- **优点**：
  - 可以在任务最后期限之前完成所有任务；
  - 具有较好的响应时间。
- **缺点**：
  - 实现复杂度较高，需要对每个任务的最后期限进行精确估计；
  - 任务的最后期限可能随时间变化，需要频繁计算各任务的截止时间，时间和空间开销都大于 RM`▶ 30:26`。

### RM 与 EDF 对比

| 对比项 | RM | EDF |
|---|---|---|
| 优先级类型 | 静态优先级 | 动态优先级 |
| 分配依据 | 执行时间越短优先级越高 | 截止时间越近优先级越高 |
| 前提 | 周期性任务、执行时间已知 | 需精确估计每个任务的截止时间 |
| 实现开销 | 较低 | 较高（频繁计算、更新优先级） |
| 优点 | 简单、开销小 | 可在截止期前完成全部任务，响应时间较好 |

> **老师强调**：实时调度算法的核心就是 RM、EDF 两类，多数嵌入式实时调度都是这两类或其变体`▶ 30:26`。

## 6. OpenEuler与Linux进程调度分类

> 课件 第 94–104 页 · 讲解从 `31:33` 开始

### CPU 调度的基本概念

操作系统需要合理安排多个进程的执行顺序，让它们轮换占用 CPU，从而保证并发性。

- 单 CPU 情况下：任一时刻只有一个进程处于执行状态，其他待运行进程处于就绪状态。
- 操作系统在适当时机中断当前进程，并从就绪进程中选择一个投入运行，这个过程称为 **CPU 调度（进程调度）**。
- 完成选择工作的程序称为 **调度程序（Scheduler）**。
- 调度程序依据 **调度策略（Scheduling Policy）** 决定“何时”以及“如何”选择新进程运行。
- 在多 CPU 或多核 CPU 系统中，调度还必须考虑核间的数据共享与数据同步。

openEuler 是对称多处理器（SMP）系统，其调度综合使用多种常见算法，主体调度器为 CFS`▶ 31:33`。

### 常见调度算法

| 算法 | 基本含义 |
|---|---|
| FIFO / FCFS | 先进先出 / 先来先服务，按进入就绪队列的顺序调度 |
| SJF | 最短进程优先，优先服务预计运行时间最短的进程 |
| RR（Round Robin，轮转） | 给每个进程分配时间片，时间片用完后轮换 |
| 优先级调度 | 按进程优先级高低选择运行进程 |

openEuler 使用了 **FIFO、轮转调度和优先级调度**，并将它们联合用于实时进程调度；普通进程则主要采用 CFS。

### CFS 调度

openEuler 中大部分进程是普通进程，普通进程更强调调度的公平性。

- openEuler 的核心调度策略之一是 **标准轮流分时调度策略**，其核心算法是 **CFS（Completely Fair Scheduler，完全公平调度器）**。
- CFS 同时使用了时间片和优先级概念，并引入 **虚拟运行时间（vruntime）**。
- 它根据当前系统负载和进程优先级，决定每个普通进程可获得的 CPU 使用比例。
- 目标不是让所有进程绝对等量运行，而是让普通进程按照权重相对公平地分享 CPU。

> **老师强调**：当前最新 Ubuntu 等系统已逐渐采用 EEVDF（课程中记作 EEVDS）调度器，但它是在 CFS 基础上针对未覆盖问题进行补充优化，核心思想仍源于 CFS，因此课程以 CFS 为核心讲解`▶ 35:34`。

### Linux 调度算法的演化

Linux 调度算法从早期版本到现在持续演进：

1. **Linux 2.4 时代**：调度核心主要基于优先级，优先级计算公式较复杂`▶ 35:34`。
2. 后续为了解决传统调度器开销大、公式复杂、可扩展性差等问题，出现了 **O(1)、SD、RSDL** 等改进方案`▶ 36:45`。
3. 最终形成并长期使用 **CFS**，其核心思想是让进程公平分享 CPU。
4. 最新发展中出现 EEVDF，在 CFS 基础上继续优化，但仍继承公平调度的基本思想`▶ 35:34`。

> **老师强调**：调度算法自身的开销也必须考虑。如果选择下一个进程的过程过于复杂，有时反而不如直接选择第一个就绪进程高效`▶ 36:45`。

公平分享、保证等调度算法的核心目标，是保障所有进程能够公平地使用 CPU 资源`▶ 37:53`

### 多核处理器系统结构

课件以 ARMv8 多核架构为例说明层次结构：

- 每个 Core 有自己的 **L1 Cache**；
- 一个 Cluster 内可以包含多个 Core，并共享或关联 **L2 Cache**；
- 多个 Cluster 通过 **Bus** 连接，并可共享 **L3 Cache**；
- L3 Cache 再与主存相连。

典型结构可概括为：

```text
Core 0 ── L1 Cache ─┐
                    ├── Cluster ── L2 Cache ──┐
Core 1 ── L1 Cache ─┘                         ├── Bus ── L3 Cache ── 内存
                                              │
                    ┌── Cluster ── L2 Cache ──┘
Core 2 ── L1 Cache ─┤
                    └── Core 3 ── L1 Cache
```

### 多核调度面临的问题

当缓存与主存的关系从单核扩展为多层、多核结构后，系统主要面临以下问题：

1. **缓存一致性问题**：多个核心的私有缓存中可能保存同一数据的多个副本，需要保证各副本与主存之间的一致性。
2. **缓存亲和性问题**：进程如果一直在同一 CPU 上运行，其缓存命中率通常更高；迁移到其他 CPU 可能导致原缓存失效。
3. **核间数据共享**：多个核心上的进程可能访问共享数据，需要同步机制。
4. **负载均衡**：不能让某些核心过载而另一些核心空闲，需要在各核心之间合理分配进程。

### 单队列调度

单队列调度指系统中所有就绪进程放在一个全局就绪队列中，由所有 CPU 共同从该队列取进程运行。

假设队列中有 A、B、C、D、E 五个就绪进程。

#### 策略一：每个 CPU 使用轮转调度

- 各 CPU 都从同一个全局队列中选择下一个进程。
- 进程可能在不同时间被调度到不同 CPU 上执行。
- 优点是实现简单、容易保持整体负载均衡。
- 缺点是进程会在 CPU 之间频繁转移，破坏 **缓存亲和性**。

#### 策略二：引入亲和度机制

- 调度器尽量让同一进程长期在同一个 CPU 上执行，以提高缓存命中率。
- 但为了维持负载均衡，某些进程仍不得不迁移。
- 课件例子中，为了兼顾各 CPU 负载，进程 E 的亲和性被牺牲。

因此，单队列调度的主要矛盾是：

> **负载均衡与缓存亲和性之间存在冲突**：迁移进程有利于均衡负载，但会损失缓存热度；保持进程不迁移有利于亲和性，但可能导致 CPU 负载不均。

### 多队列调度

openEuler 采用 **多队列调度策略**：每个 CPU 维护自己的就绪队列。

例如：

- CPU0 维护队列 Q0；
- CPU1 维护队列 Q1。

初始时：

```text
Q0: A -> C
Q1: B -> D
```

两个 CPU 分别在自己的队列上采用轮转调度：

- CPU0 运行 A、C；
- CPU1 运行 B、D。

这种方式有利于保持缓存亲和性，因为进程通常固定在某个 CPU 的队列中运行。

一段时间后，如果 A、C 都运行结束，则可能出现：

```text
Q0: NULL
Q1: B -> D
```

此时 CPU0 空闲，而 CPU1 仍有两个进程，系统出现 **负载失衡**。

因此，多队列调度的优点是天然具有较好的缓存亲和性，但必须额外解决各队列之间负载不均衡的问题。

### openEuler 中的迁移线程

解决多 CPU 负载不均衡最直接的方法是进行 **进程跨 CPU 迁移**。

例如将 CPU1 队列中的进程 D 迁移到 CPU0：

```text
迁移前：
CPU0: Q0 = NULL
CPU1: Q1 = B -> D

迁移后：
CPU0: Q0 = D
CPU1: Q1 = B
```

这样两个 CPU 各运行一个进程，实现负载均衡。

在 openEuler 中，每个处理器都有一个迁移线程，命名形式为：

```text
migration/CPUID
```

每个迁移线程都有一个由工作函数组成的 **停机工作队列**。迁移过程如下：

1. CPU0 向 CPU1 的停机工作队列添加一个工作函数，并唤醒 CPU1 上的迁移线程。
2. 迁移线程不会被普通进程抢占，因此会立即从停机工作队列中取出函数执行。
3. 该函数完成进程迁移，例如把进程 D 从 CPU1 迁移到 CPU0。
4. 迁移完成后，CPU0 与 CPU1 实现负载均衡。

迁移线程的高优先级和不可抢占性保证了负载均衡任务能够被及时执行。

### Linux 中进程分类与调度机制

Linux 将进程分为 **实时进程** 和 **普通进程** 两大类，分别采用不同调度路线。

| 分类 | 子类/特点 | 调度要求 | 调度策略 |
|---|---|---|---|
| 实时进程 | 要求尽快执行 | 调度延迟要求最高，就绪后应立即响应并执行 | FIFO、Round Robin |
| 普通进程 | 交互式进程 | 频繁睡眠/唤醒，对响应速度要求高 | CFS |
| 普通进程 | 批处理进程 | 后台运行，可忍受响应延迟 | CFS |

#### 实时进程

实时进程对调度延迟要求最高，要求立即响应并执行，调度策略为：

- **SCHED_FIFO**：先进先出；
- **SCHED_RR**：带时间片的轮转调度。

> **老师强调**：Linux 中所说的“实时进程”并非严格意义上的硬实时调度，本质上可理解为优先级高于普通用户进程的系统线程；它们要求尽快执行，主要用于优化系统响应和用户交互体验。实时进程与普通进程走不同的调度路线，采用简单的 FIFO 或时间片轮转，就绪后立即执行`▶ 32:07`。

课堂上还将 Linux 与 Windows 的优先级体系进行类比：

- Windows：零页线程优先级最低；可变优先级用户线程位于 1～15；实时线程位于 16～31。
- Linux：实时进程优先级高于普通用户进程，但并不等同于严格实时系统中的实时任务`▶ 32:07`。

#### 普通进程

普通进程使用 **CFS** 调度，进一步分为：

1. **交互式进程**
   - 经常处于睡眠状态，随后被事件唤醒；
   - 多为 I/O 型进程；
   - 典型表现是睡眠与唤醒频繁切换；
   - 对响应速度要求高，例如用户输入、终端操作、图形界面等。

2. **批处理进程**
   - 通常在后台运行；
   - 更关注持续占用 CPU 完成任务；
   - 能够忍受较高响应延迟；
   - 优先级通常较低。

> **老师强调**：调度算法重点关注交互式进程，因为它们频繁在睡眠和运行之间切换，对交互响应速度要求高；后续许多调度设计主要就是围绕这类进程展开`▶ 34:00`。

## 7. Linux 2.4调度器

> 课件 第 106–108 页 · 讲解从 `38:20` 开始

### 工作机制

Linux 2.4 调度器围绕 **runqueue（运行队列）、时间片、优先级** 三个要素工作`▶ 38:20`：

1. 调度时依次比较 runqueue 中所有就绪进程的优先级，选择优先级最高的进程运行。
2. 进程创建时被赋予一个时间片（即进程描述符中的 `counter` 字段）。
3. 每次时钟中断递减当前运行进程的时间片；当时间片减到 0 时，进程必须让出 CPU，等待重新分配时间片后才有机会运行`▶ 38:20`。
4. **只有当所有 RUNNING 进程的时间片都用完之后**，才统一重新计算所有进程的时间片，进入下一轮。这种设计保证每个进程都有机会执行。

整体轮转逻辑与轮转调度（RR）算法一致`▶ 38:20`。

### 优先级的决定：nice + counter

普通进程的优先级由两部分共同决定：

| 字段 | 含义 | 特点 |
|---|---|---|
| `nice` | 静态（负向）优先级 | 从 UNIX 沿用而来，课件取值范围 **-20 ~ 19**，**-20 优先级最高**；进程创建时可设定`▶ 40:08` |
| `counter` | 当前剩余时间片 | 每轮调度结束后重新计算，随调度动态变化；**counter 越大，优先级越高** |

即优先级是"时间片（counter）+ nice 静态优先级"的组合`▶ 40:08`。需要注意：

- 时间片指的就是 `counter` 值，每个进程的时间片可能不一样。
- 老师口述的范围为 -19~20，与课件的 -20~19 略有出入，复习时以课件表述 **-20 ~ 19、-20 最高** 为准。

### 交互式/I/O 型进程的优待

当所有 RUNNING 进程时间片用完后，调度器重新计算 **所有进程** 的 `counter`——不仅包括 RUNNING 进程，也包括处于睡眠状态的进程：

- 睡眠进程在睡眠期间 `counter` 不会递减；
- 重新计算时，它们原本次余的 `counter` 会被**叠加**到新值上，等效提高了优先级，从而能更快被调度`▶ 41:50`。

系统通过这种方式提高 I/O 型（交互式）进程的响应速度。

### 实时进程与普通进程的区别

- **实时进程**：`counter` 用完后会立刻重置 `counter`，然后重新放入就绪队列。
- **非实时（普通）进程**：必须等到 runqueue 中所有进程时间片都用完（队列为空）时，才统一重新计算 `counter`。

> 补充背景：**Linux 2.4 内核是非抢占式的**，这直接影响其实时性表现。

### 缺点

> **老师强调**：以下缺点以及"非抢占、高优先级实时进程无法立即抢占当前进程"是需要掌握的考点`▶ 43:08`。

1. **可扩展性不好**：调度时要遍历整个 runqueue 比较优先级，调度开销随队列中进程数量变化——100 个进程和 1000 个进程的开销差异明显`▶ 43:08`。
2. **高负载系统上调度性能低**：进程数增多时整体调度性能下降`▶ 43:08`。
3. **交互式进程优化不完善**：用睡眠时间长短来判定交互式进程并不合理——有些长睡眠进程并非交互式进程，界定不准确`▶ 42:37`。
4. **对实时进程支持不够**：内核非抢占，高优先级实时进程到来时无法立即抢占当前正在运行的进程`▶ 43:08`。

针对这些问题，Ingo Molnar 开发了新的 **O(1) 调度器** 来取代 Linux 2.4 的调度器。

## 8. O(1)调度器

> 课件 第 109–113 页 · 讲解从 `44:13` 开始

### 设计背景与改进点

O(1) 调度器针对 Linux 2.4 调度器做了两方面修改：

1. **进程优先级的计算方法**
2. **pick next（选择下一个运行进程）算法**

其核心目标是：让"选择下一个进程"这一操作的时间复杂度为常数 O(1)，与就绪进程数量无关。

---

### 优先级计算

#### 普通进程

- 引入**平均睡眠时间**来判断一个进程是否为**交互式进程（I/O 型进程）**。
- 平均睡眠时间越长，说明进程越频繁地等待 I/O、越偏向交互式，其 **bonus（奖励值）越大，动态优先级越高**`▶ 44:13`。
- 动态优先级通过经验公式计算，公式与静态优先级相关并附带经验值，理解难度较高`▶ 44:13`：

$$
\text{动态优先级} = \max(100,\ \min(\text{静态优先级} - \text{bonus} + 5,\ 139))
$$

并满足约束：

$$
\text{动态优先级} \le \frac{3 \times \text{静态优先级}}{4} + 28
$$

> 注意：Linux 中普通进程优先级数值范围为 100～139，**数值越小优先级越高**，因此 bonus 增大时公式中减去 bonus，优先级数值变小、实际优先级变高。

#### 实时进程

- 实时进程的优先级**不会被动态修改**。
- 实时进程的优先级**总是高于普通进程**，不受上述经验公式调整的影响`▶ 44:13`。

---

### pick next 算法：双队列结构

调度器为**每一个 CPU** 维护两个进程队列数组：

| 队列 | 含义 |
|------|------|
| `active`（活动数组） | 当前正在参与调度的就绪进程 |
| `expired`（过期数组） | 时间片已耗尽、等待下一轮的进程 |

- 两个数组都**按优先级索引**：数组中的每个元素保存指向"某一优先级进程队列"的指针。
- 选择进程时，直接从 `active` 数组中**当前最高优先级的非空队列里取第一个进程**，无需遍历所有进程，因此时间复杂度为 **O(1)**`▶ 45:50`。

#### 时间片用完时的处理

进程时间片变为 0 后，调度器先判断进程类型：

- **交互式进程或实时进程**：重置其时间片，并**重新插回 `active` 数组**，以便继续快速响应`▶ 45:50`。
- **普通（批处理型）进程**：从 `active` 数组移到 `expired` 数组，移入时调度器会为其**重置时间片**。

#### 防止交互式/实时进程长期占用

交互式进程和实时进程不能无限期留在 `active` 中：

- 当一个进程**占用 CPU 的累计时间超过某个固定上限**后，即使它是实时进程或交互式进程，也会被强制移到 `expired` 数组。
- 这保证了 `active` 数组在**有限时间内必然被清空**，从而避免其他进程饥饿`▶ 45:50`。

#### 队列切换

- 当 `active` 数组中的所有进程都被移入 `expired` 后，调度器**直接交换两个数组的指针**（`rq->active` 与 `rq->expired`）。
- 原来的 `expired` 成为新的 `active`，调度进入新一轮。
- 指针交换是常数时间操作，这也是调度整体能达到 O(1) 的关键之一。

工作机制可概括为：

```text
时间片用完 ──► 交互/实时进程：重置时间片，留在 active
           └─► 普通进程：移入 expired（同时重置时间片）
                          │
active 全部耗尽 ──► 交换 active 与 expired 指针（O(1)）
```

---

### O(1) 调度器的不足与后续

O(1) 调度器最终"昙花一现"，没有被长期使用，主要原因有`▶ 48:24`：

1. **交互式进程识别仍会失效**：尽管区分交互式进程与批处理进程的算法相比以前有较大改进，但在很多典型测试程序下性能仍会下降，导致交互式进程反应缓慢。
2. **代码难以阅读和维护**：动态优先级依赖平均睡眠时间和一些很难理解的经验公式来修正优先级、区分进程类型。

后续由 Con Kolivas 开发了**楼梯调度算法 SD（Staircase Deadline）**，以及其改进版本 **RSDL（Rotating Staircase Deadline）**，作为替代方案。

## 9. SD楼梯调度器

> 课件 第 114–115 页 · 讲解从 `49:04` 开始

### SD 楼梯调度器的基本思想

楼梯调度器（Staircase Scheduler，SD）与 O(1) 调度器有明显区别：它抛弃了动态优先级的概念，转而采用完全公平的思路。

其基本结构仍与 O(1) 调度器相似：

- 为每一个优先级维护一个进程就绪队列；
- 所有队列组织在 `active` 数组中；
- 选择下一个运行进程时，调度器直接从 `active` 数组中按优先级选取。

不同之处在于：SD 调度器不再区分 `active` 和 `expired` 两个数组。进程用完时间片后不会被移入 `expired` 数组，而是被加入 `active` 数组中低一个优先级的队列。

> **老师强调**：这里降低的是进程当前所在的调度队列级别，任务本身的优先级并没有改变。

### “下楼梯”式的降级过程

进程每次用完时间片，就下降一级：

1. 进程从与自身优先级对应的队列开始运行；
2. 用完时间片后，进入低一级优先级队列；
3. 再次用完时间片，再进入更低一级队列；
4. 如此逐级下降，就像“下楼梯”一样。

SD 的整体思路与多级反馈队列一致：优先级从高到低固定划分，调度器总是优先选择高优先级队列中的进程；进程用完时间片后逐级降级`▶ 49:04`。

但 SD 与传统多级反馈队列有两点关键区别：

| 对比点 | 传统多级反馈队列 | SD 楼梯调度器 |
|---|---|---|
| 新进程入口 | 通常进入最高优先级队列 | 进入自身初始优先级对应的队列 |
| 到达最低级后的处理 | 用完时间片后可能回到最高优先级队列 | 回到自身初始优先级的下一级队列 |

### 到达底部后的重新上升

当进程降到最低一级队列后，如果再次用完时间片，它不会回到最高优先级，也不会一直停留在最低级，而是回到其初始优先级的下一级队列。

假设某任务本身的优先级为 `P`，从第 `N` 级台阶开始下楼梯：

- 任务逐级下降，直到到达底部；
- 到达底部并再次用完时间片后，回到第 `N+1` 级台阶；
- 同时获得 `N+1` 倍的时间片。

可以理解为：进程完成一轮“下楼梯”后，不会直接回到最初的最高起点，而是从比初始优先级低一级的位置重新开始，并获得更长的执行时间。

### 为什么能避免饥饿

楼梯算法能够避免低优先级进程长期饥饿。

高优先级进程虽然一开始位于较高队列，可以优先获得 CPU，但它每次用完时间片都会逐级下降，最终会进入低优先级层级，与低优先级进程竞争 CPU。因此，低优先级进程最终能够获得执行机会。

> **老师强调**：该设计让高优先级进程最终会降到低优先级层级参与 CPU 竞争，从而避免低优先级进程长期饥饿`▶ 49:04`。

### 对交互式进程的支持

SD 调度器能够较好地照顾 I/O 型交互式进程。

当一个交互式进程进入睡眠状态时：

- 它的优先级和所在队列级别保持不变；
- 与它同等优先级的其他进程如果持续运行，会一步一步地下楼梯，进入较低优先级队列；
- 当交互式进程被唤醒时，它仍然留在较高的楼梯层；
- 因此，它可以更快地被调度器选中，从而缩短响应时间。

这相当于对未用完时间片的进程给予补偿：因为它睡眠时没有继续消耗时间片，所以不会被降级`▶ 52:02`。

> **老师强调**：交互式进程睡眠唤醒后仍保留原有优先级，而同级的其他进程会在运行中不断降级，因此能保证交互式进程的响应效率`▶ 49:04`。

### 实时进程的调度

SD 楼梯调度策略只用于普通进程。实时进程仍然采用原来的实时调度策略：

- FIFO（先来先服务）；
- Round Robin（时间片轮转）。

因此，实时调度与上述普通进程的楼梯调度机制相互独立`▶ 52:02`。

## 10. RSDL调度器

> 课件 第 116–118 页 · 讲解从 `52:27` 开始

### RSDL 调度器概述

RSDL（The Rotating Staircase Deadline Scheduler，旋转楼梯最终期限调度器）由 Con Kolivas 开发，是对 SD 调度器算法的改进。

- **核心思想**：仍然是"完全公平"，没有复杂的动态优先级调整策略，从而避免了优先级调整带来的额外开销`▶ 52:27`。
- **队列结构**：RSDL 重新引入了 expired 数组，借鉴了 O(1) 调度器的 active 与 expired 双数组结构，数组中的每个元素对应一个不同优先级的队列`▶ 52:27`。
- **调度目标**：在保持从最高优先级队列开始选择进程运行这一基本策略的同时`▶ 52:27`，防止高优先级进程长期占用 CPU 而导致低优先级进程饥饿。

### 两类时间配额

RSDL 引入了两个关键的时间配额指标：

| 配额 | 符号 | 含义 |
|---|---|---|
| 组时间配额 | Tg | 为每一个优先级分配，约束该优先级**所有进程**能够使用的总运行时间 |
| 进程时间配额 | Tp | 同一优先级内每个进程都相同，代表进程在当前优先级上单次可获得的运行时长 |

需要注意区分三个概念：进程原有的**时间片 time_slice**、同一优先级进程相同的**局部时间配额 Tp**、以及每个优先级组的**总时间配额 Tg**`▶ 55:06`。

### Minor rotation（小轮转）

当进程用完了自身的 Tp 时，就下降到下一优先级的进程组中，这一过程称为 **minor rotation**，与 SD 算法中的降级过程相同。

> **老师强调**：Tp 与进程的时间片 time_slice 不同，降级是由 Tp 用完触发的，而不是时间片用完触发的；时间片用完后进程会直接进入 expired 数组。一般有 **Tp < time_slice**。

具体来说，进程在每个优先级上只能运行一个 Tp，配额用完就降级继续运行；当累计运行时长超过自身的时间片后，进程才会被移入 expired 队列`▶ 55:06`。

### 对 SD 缺陷的改进：运行时间可预测

**SD 的问题**：低优先级进程必须等待所有高优先级进程执行完才能获得 CPU，因此低优先级进程的等待时间无法确定。

**RSDL 的解决办法**：当一个高优先级进程组用完了它的组时间配额 Tg 时，**无论该组中是否还有进程的 Tp 尚未用完**，所有属于该组的进程都会被强制降低到下一优先级进程组中。

这样一来，每个优先级组占用 CPU 的时间都有一个确定的上界（即 Tg），低优先级任务就可以在一个可以预计的未来得到调度，从而避免饥饿。整个机制的核心是通过多个时间指标的折中权衡来实现公平`▶ 55:06`。

### Major rotation（大轮转）

进程用完自己的时间片 time_slice 时，会被放入 expired 数组中**它初始优先级**对应的队列里。

当满足以下条件之一时触发 **major rotation**：
- active 数组为空（即 active 数组内的进程都用完了各自的时间片`▶ 55:06`）；
- 所有进程都降低到了最低优先级。

Major rotation 会**交换 active 数组和 expired 数组**（与 O(1) 调度器的切换逻辑类似`▶ 55:06`），所有进程都恢复到初始状态（即各自的初始优先级），重新开始 minor rotation 过程。

### 整体流程小结

1. 调度器从 active 数组的最高优先级非空队列中选取进程运行。
2. 进程每用完一次 Tp，就通过 minor rotation 降入下一级优先级队列。
3. 某优先级组的 Tg 用尽时，该组剩余进程被**整组强制降级**。
4. 进程累计运行超过 time_slice 后，进入 expired 数组的初始优先级队列。
5. active 为空或所有进程都降到最低优先级时，触发 major rotation，交换两个数组，进程恢复初始优先级，循环往复。

## 11. CFS核心思想与数据结构

> 课件 第 119–126 页 · 讲解从 `1:08:07` 开始

### CFS 调度器概述

CFS（Completely Fair Scheduler，完全公平调度器）是现在 Linux 内核采纳的调度器。它从 RSDL/SD 调度器中吸取了“完全公平”的思想，相比此前 O(1) 调度器和 Linux 2.4 版本调度器，具有以下特点：

- 不再跟踪进程的睡眠时间；
- 不再企图通过复杂规则区分交互式进程（I/O 型进程）；
- 目标是让所有进程公平地获得 CPU 时间`▶ 1:08:07`。

CFS 的核心机制可以概括为：

1. 每个进程维护一个**虚拟运行时间（vruntime）**，表示该进程运行了“多久”；
2. 调度器每次选择 **vruntime 最小**的进程运行；
3. vruntime 与进程实际运行时间成正比，与进程优先级（权重）成反比；
4. CFS 以 vruntime 为键值构造一棵红黑树，实现就绪进程的快速插入、更新和删除。

---

### CFS 算法概述

#### 1. 按权重比例分配运行时间

CFS 的核心思想是：**根据进程的优先级，按权重比例分配 CPU 运行时间**。

设一个调度周期内所有就绪进程都被调度一遍，则分配给某个进程的实际运行时间为：

$$
\text{分配给进程的运行时间}
= \text{调度周期} \times \frac{\text{进程权重}}{\text{所有进程权重之和}}
$$

其中，**调度周期**是指将所有处于 `TASK_RUNNING` 状态的进程都调度一遍所经历的时间。

例如，调度周期为 30ms，进程 A、B 的权重分别为 1 和 2，则`▶ 1:13:05`：

$$
T_A = 30 \times \frac{1}{1+2} = 10\text{ms}
$$

$$
T_B = 30 \times \frac{2}{1+2} = 20\text{ms}
$$

即 A 分到 10ms，B 分到 20ms，体现了高优先级（权重大）进程获得更多 CPU 时间。

#### 2. 虚拟运行时间 vruntime

为了用统一标准衡量不同权重进程的“运行进度”，CFS 对时钟进行抽象，为每个进程引入虚拟运行时间 `vruntime`：

$$
vruntime = \text{实际运行时间} \times \frac{NICE\_0\_LOAD}{\text{进程权重}}
$$

其中 `NICE_0_LOAD` 表示 nice 值为 0 的普通进程对应的基准权重。课堂上也将该公式表述为“实际运行时间 × nice值 / 进程权重”的形式`▶ 1:14:19`。

vruntime 表示的是进程的**运行进度**，而不是真实运行时长，可以理解为进程在自己计划获得的总运行时间中已经完成的百分比`▶ 1:09:47`。

将公式 1 代入公式 2：

$$
vruntime =
\left(\text{调度周期}\times\frac{\text{进程权重}}{\text{所有进程总权重}}\right)
\times\frac{NICE\_0\_LOAD}{\text{进程权重}}
$$

约去进程权重后得到：

$$
vruntime = \text{调度周期}\times\frac{NICE\_0\_LOAD}{\text{所有进程总权重}}
$$

可以看到，在一个调度周期内，所有进程得到的虚拟运行时间相同。也就是说，从 vruntime 的角度看，分配给所有进程的时间是一样的，这正是“完全公平”的含义。

#### 3. 权重对 vruntime 增长速度的影响

由公式可知：

- vruntime 与实际运行时间成正比；
- vruntime 与进程优先级（权重）成反比`▶ 1:12:06`。

因此，优先级越高、权重越大的进程，在相同实际运行时间内 vruntime 增长越慢；反之，低优先级进程的 vruntime 增长更快。

以两个权重不同的进程 A、B 为例：A 计划运行 10ms，B 计划运行 20ms，但二者都要通过运行完成自身 100% 的进度。若 A 实际运行 2ms，则完成 20%；B 实际运行 8ms，也完成 20% 左右的进度。若某个进程的进度落后于其他进程，它的 vruntime 就更小，随后会被优先调度，从而获得更多 CPU 时间`▶ 1:10:31`。

> **老师强调**：虚拟运行时间代表进程的运行进度，并非真实运行时长；不同权重进程完成“100%进度”所对应的实际运行时长不同`▶ 1:09:47 · 1:14:19`。

#### 4. 调度选择与红黑树组织

CFS 每次选择 **vruntime 最小**的进程投入运行。从宏观上看，所有进程的 vruntime 都在同时推进，只是增长速度因权重不同而不同。

为了快速找到 vruntime 最小的进程，CFS 维护一棵以 vruntime 为顺序的红黑树：

- 每个就绪进程对应红黑树中的一个节点；
- 节点的键值是该进程的 vruntime；
- 红黑树最左侧节点就是 vruntime 最小的进程；
- 红黑树支持高效的插入、删除和更新操作`▶ 1:12:24`。

进程调度过程如下：

1. 调度器选择红黑树最左侧节点对应的进程运行；
2. 该进程运行时，其节点从红黑树中删除；
3. 进程被抢占或切换下去时，更新它的 vruntime；
4. 若该进程仍处于就绪态，则根据新的 vruntime 重新插入红黑树；
5. 由于刚运行过的进程 vruntime 通常较大，重新插入时会靠近树的右侧；
6. 总体上，树中的节点随着调度不断从右侧迁移到左侧，红黑树也借此保持平衡。

> **老师强调**：学习 CFS 时，应先理解“完全公平”和虚拟运行时间的核心思想，再掌握红黑树等具体实现步骤`▶ 1:12:24`。

### CFS 重要数据结构

Linux 内核中的所有任务都通过 `task_struct` 结构表示。该结构完整描述了一个任务，包括任务当前状态、栈、进程标识、静态优先级和动态优先级等信息。

`task_struct` 主要通过两个成员与调度器关联：

- `sched_entity`：定义调度实体；
- `sched_class`：定义该进程所属的调度类。

#### 1. 主要结构关系

```c
struct cfs_rq {
    ...
    struct rb_root tasks_timeline;
    ...
};

struct task_struct {
    volatile long state;
    void *stack;
    unsigned int flags;
    int prio, static_prio, normal_prio;
    const struct sched_class *sched_class;
    struct sched_entity se;
    ...
};

struct sched_entity {
    struct load_weight load;
    struct rb_node run_node;
    struct list_head group_node;
    ...
};

struct rb_node {
    unsigned long rb_parent_color;
    struct rb_node *rb_right;
    struct rb_node *rb_left;
    ...
};
```

它们之间的关系可以概括为：

- `task_struct`：描述一个完整进程；
- `sched_entity`：进程参与 CFS 调度的实体，可嵌入红黑树；
- `rb_node`：红黑树节点，包含父节点、左右孩子等信息；
- `cfs_rq`：CFS 运行队列，通过 `tasks_timeline` 保存红黑树的根。

#### 2. `struct sched_entity`

`struct sched_entity` 是调度实体，简称 **SE**。它包含用于对单个任务或任务组进行调度的完整信息，例如：

- 负载权重 `load`；
- 对应的红黑树节点 `run_node`；
- 任务组成员链表 `group_node`。

在课堂讲解中，老师将其概括为任务结构中与红黑树节点相关的部分，包含单个任务或任务组的全部调度信息`▶ 1:17:09`。

#### 3. `struct sched_class`

`struct sched_class` 表示调度类，可以理解为实现调度功能的模块或模块链。

每种调度器模块都需要实现 `struct sched_class` 中规定的一组函数，内核通过这些函数完成进程入队、出队、选择下一个任务等调度操作。CFS 就是通过对应的调度类与通用调度框架协作工作的。

#### 4. `struct cfs_rq`

`struct cfs_rq` 表示 CFS 的运行队列。每个 CPU 运行队列都会有对应的 CFS 运行队列结构，用来保存与该 CPU 上 CFS 就绪进程相关的红黑树信息。

其中最重要的成员是：

```c
struct rb_root tasks_timeline;
```

它是 CFS 红黑树的根，所有处于 CFS 就绪状态的调度实体都按 vruntime 排列在这棵树中。

> **老师提示**：`task_struct` 等 Linux 数据结构较复杂，不需要记忆全部细节；重点理解调度实体 `sched_entity` 与红黑树节点的对应关系，能在结构中找到红黑树所在位置即可`▶ 1:16:58 · 1:17:09`。

---

### 本章小结

- CFS 是当前 Linux 使用的调度器，核心思想是完全公平；
- CFS 不再通过睡眠时间区分交互式进程，而是按进程权重比例分配 CPU 时间；
- 每个进程维护一个 vruntime，公式为：

$$
vruntime = \text{实际运行时间}\times\frac{NICE\_0\_LOAD}{\text{进程权重}}
$$

- 权重越大，相同实际运行时间内 vruntime 增长越慢；
- CFS 每次选择 vruntime 最小的进程运行；
- CFS 用红黑树组织就绪进程，最左侧节点就是下一个被调度的进程；
- `task_struct` 通过 `sched_entity` 接入 CFS 红黑树，通过 `sched_class` 使用具体调度模块；
- `cfs_rq` 中的 `tasks_timeline` 指向 CFS 红黑树的根。

## 12. CFS调度细节与典型场景

> 课件 第 127–136 页 · 讲解从 `1:18:44` 开始

### 几个关键问题

在进入具体调度场景之前，先明确 CFS 实现中容易混淆的四个问题：

- **新进程的 vruntime 初值不是 0**。若直接置 0，新进程的 vruntime 会过小，相当于拥有过高的运行优先权，因此需要特殊修正`▶ 1:18:44`。
- **休眠进程的 vruntime 在睡眠期间保持不变**，但在唤醒时并不会必然立刻抢占 CPU，而要由系统按规则判断`▶ 1:18:44`。
- **唤醒进程不会无条件抢占当前进程**，只有 vruntime 的优势达到一定门槛时才会触发重新调度，以避免频繁上下文切换`▶ 1:18:44 · 1:32:27`。
- **进程跨 CPU 迁移时，vruntime 的传递需要针对性处理**，因为不同 CPU 的 CFS 运行队列状态不同`▶ 1:18:44`。

> **老师强调**：新进程、睡眠唤醒、跨 CPU 迁移等都属于 CFS 必须处理的具体调度场景；CFS 与 Windows 调度类似，也要区分主动让出、被动等待、时间片用尽等情况`▶ 1:20:54`。

---

### 具体调度情景总览

CFS 主要分析以下四类场景：

1. 时钟中断
2. 主动调度
3. 进程唤醒
4. 进程创建

这些场景与进程三状态模型中的状态转换一致：新建进入就绪态、阻塞后唤醒回到就绪态、运行中可因时钟中断或主动调用 `schedule()` 而重新调度`▶ 1:33:19`。

---

### 情景一：时钟中断

时钟中断是 CFS 的核心调度触发场景，处理步骤如下：

1. **更新当前进程的运行信息**。
2. **计算 vruntime 增量**：
   - 将本次时钟中断间隔内进程实际占用 CPU 的时间，按照进程权值对应的比例换算成虚拟运行时间；
   - 再把该增量累加到进程原来的 vruntime 上。
3. **判断是否满足抢占条件**：
   - 如果当前进程在这一调度周期内的实际运行时间已经超过分配给它的时间配额，就设置需要调度的标记；
   - 随后主动触发一次进程调度；
   - 如果没有超过配额，则当前进程继续运行。

> **老师强调**：vruntime 不是等到时间片用尽时才一次性计算，而是**每一次时钟中断都会进行一次累加计算**`▶ 1:21:36`。

可以概括为：

```text
时钟中断
  → 更新实际运行时间
  → 折算并累加 vruntime
  → 判断是否超过本周期应得时间
      ├─ 超过：设置调度标记，触发调度
      └─ 未超过：当前进程继续运行
```

---

### 情景二：主动调度

#### 基本流程

当进程主动调用调度器让出 CPU 时，标准流程为：

1. 更新当前进程的运行信息；
2. 将当前进程插入 CFS 就绪队列对应的红黑树；
3. 选择下一个要运行的进程；
4. 将被选中的进程从红黑树中移出，使其投入运行。

常规情况下，红黑树中最左侧节点就是 vruntime 最小的就绪进程，但 CFS 并不总是机械地直接取最左节点`▶ 1:24:34`。

#### `last` 与 `next` 指针

每个 CFS 运行队列 `cfs_rq` 中有两个与调度选择密切相关的指针：

| 指针 | 含义 |
|---|---|
| `last` | 指向最近一次被调度出 CPU 的进程 |
| `next` | 指向被调度上 CPU 的进程，或调度器希望优先考虑的下一个进程 |

例如，进程 A 正在运行时被进程 B 抢占，则：

- `last` 指向 A；
- `next` 指向 B。

在选择下一个运行进程时：

1. 优先考虑 `next` 指向的进程；
2. 其次考虑 `last` 指向的进程；
3. 完成选择后清空这两个指针。

设置这两个指针是为了在抢占、让出等情况下优化进程选择，而不是每次都无条件重新选择红黑树最左节点`▶ 1:25:24`。

#### 抢占判断：`wakeup_preempt_entity`

主动调度中的优先选择通过类似下面的判断完成：

```c
wakeup_preempt_entity(cfs_rq->next, se)
wakeup_preempt_entity(cfs_rq->last, se)
```

该函数根据两个进程的 vruntime 差值判断能否抢占，返回值含义如下：

| 返回值 | 含义 | 是否允许抢占 |
|---|---|---|
| `-1` | 新进程的 vruntime 大于当前进程 | 不能抢占 |
| `0` | 新进程的 vruntime 虽小于当前进程，但差值未达到调度粒度 | 一般不能抢占 |
| `1` | 新进程的 vruntime 比当前进程小，且差值超过调度粒度 | 可以抢占 |

因此，即使某个进程的 vruntime 略小，也不一定能够抢占；CFS 设置了调度粒度，避免两个进程因极小的 vruntime 差异而频繁切换`▶ 1:25:24`。

---

### 情景三：进程创建

#### 新进程 vruntime 的初值

新进程的 vruntime **不是 0**。创建时的计算思路是：

- 以本 CPU 上 CFS 队列的 `min_vruntime` 为基准；
- 再加上新进程在一次调度周期中能够增加的 vruntime；
- 这相当于假设新进程在本轮调度中已经运行过一段时间。

可表示为：

```text
新进程 vruntime
  = cfs_rq->min_vruntime
  + 新进程一个调度周期可获得的 vruntime 增量
```

这样做可以防止新进程因为初值为 0 而长期占据红黑树最左侧，获得不合理的高优先级`▶ 1:27:22`。

#### `min_vruntime` 的含义

`min_vruntime` 是每个 CFS 运行队列各自维护的一个基准值：

- 它一般小于或等于该队列中所有就绪态进程的最小 vruntime；
- 它体现了当前运行队列中所有进程整体虚拟运行时间的下限；
- 它通常是一个单调向前推进、数值相对较小的基准。

它为新进程初始化、唤醒进程补偿等操作提供统一参考`▶ 1:27:22`。

#### 父子进程 vruntime 的交换

新进程的 vruntime 确定后，在特定条件下会交换父子进程的 vruntime，使子进程有机会更快运行。必须同时满足以下条件：

1. 系统参数 `sysctl` 设置为子进程优先运行；
2. `fork()` 出的子进程与父进程位于同一个 CPU；
3. 父进程不为空；
4. 父进程的 vruntime 小于子进程的 vruntime。

满足这些条件时交换二者的 vruntime，可以让刚创建的子进程优先获得 CPU；否则不交换`▶ 1:27:22`。

#### 创建后的处理流程

进程创建时完整流程为：

1. 更新并计算新进程的 vruntime；
2. 在满足条件时交换父子进程的 vruntime；
3. 将新建进程插入红黑树；
4. 调用 `wakeup_preempt_entity` 判断新进程能否抢占当前进程；
5. 如果满足抢占条件，则设置调度标记并随后调度；否则当前进程继续运行。

因此，**新建进程不会因为刚创建就一定立刻投入运行**`▶ 1:27:22`。

---

### 情景四：进程唤醒

进程唤醒通常发生在 I/O 操作完成、等待资源到达或从阻塞态返回时。

#### 为什么唤醒时要补偿 vruntime

进程睡眠期间不占用 CPU，其 vruntime 在睡眠期间基本保持不变。若系统中其他进程持续运行，它们的 vruntime 会不断增长，唤醒进程可能因为相对较小的 vruntime 而获得明显优势。为了让睡眠进程醒来后能较快得到响应，CFS 还会对其进行一定补偿：

```text
补偿后的候选 vruntime = min_vruntime - 某个值
```

这会降低唤醒进程的 vruntime，使其更容易被调度，适合响应 I/O 事件的交互型进程`▶ 1:30:11`。

#### 防止短睡眠进程获得额外优势

如果一个进程只睡眠了很短时间，就不应通过“睡眠—唤醒”获得额外 CPU 时间。因此 CFS 不会无条件使用 `min_vruntime - 某个值`，而是取以下两者中的较大值：

```text
唤醒后 vruntime
  = max(进程原来的 vruntime, min_vruntime - 补偿值)
```

这样可以达到两个目的：

- 对真正睡眠较久、等待 I/O 的进程给予一定调度补偿；
- 防止频繁短睡的进程通过补偿机制反复获得不公平的运行机会。

#### 唤醒后的抢占判断

唤醒处理流程为：

1. 调整唤醒进程的 vruntime；
2. 将该进程插入红黑树；
3. 判断是否满足抢占条件；
4. 只有 vruntime 优势达到阈值时，才设置抢占标志并触发重新调度。

> **老师强调**：唤醒进程不会一醒来就立刻切换。只有当它与当前进程的 vruntime 差值达到规定门槛时才抢占；如果差值不大，则不换人，以避免频繁上下文切换`▶ 1:30:11 · 1:32:27`。

---

### CFS 与进程状态转换

四类 CFS 调度场景可以对应到进程的三种基本状态：

```text
                 fork()
                  ↓
              ┌─────────┐
              │  就绪态  │
              └─────────┘
               ↑       │
        唤醒   │       │ schedule()：选出红黑树最左下结点
               │       ↓
              ┌─────────┐
  阻塞/等待 → │  运行态  │
              └─────────┘
                  │
                  ├─ 时钟中断：
                  │    1. 更新时间片信息
                  │    2. 检测是否满足抢占条件
                  │
                  ├─ 新建：
                  │    1. 计算 vruntime
                  │    2. 插入红黑树
                  │
                  └─ 唤醒：
                       1. 更新并补偿 vruntime
                       2. 插入红黑树
                       3. 判断是否抢占
```

各场景的核心区别如下：

| 场景 | vruntime 处理 | 是否立即切换 |
|---|---|---|
| 时钟中断 | 每次中断都按实际运行时间累加 vruntime | 超过当前周期应得时间才触发调度 |
| 主动调度 | 更新当前进程时间信息并放回红黑树 | 当前进程主动让出，选择下一进程 |
| 进程创建 | 以 `min_vruntime` 为基准初始化，必要时交换父子 vruntime | 抢占检查通过后才调度 |
| 进程唤醒 | 用 `min_vruntime - 补偿值` 与原 vruntime 取较大值 | 差值达到抢占门槛才切换 |

总体来看，CFS 虽然以“vruntime 最小者运行”为核心原则，但在实际实现中还必须处理新进程初始化、睡眠补偿、调度粒度、`last/next` 优化以及跨 CPU 等细节，以兼顾公平性、响应性和调度开销。

| NUMA | 非一致内存访问架构由多个节点组成，进程访问本节点内存和跨节点内存的代价不同。 |
| 缓存亲和性 | 让进程尽量固定在同一个处理器核心上运行，以复用该核心缓存中的数据并减少缓存失效。 |
| 缓存一致性 | 多个处理器缓存同一数据时，需要通过如 MESI 的机制保证各缓存和内存中的数据视图一致。 |
| 负载均衡 | 在多个处理器之间调整任务或迁移进程，使各处理器的工作负载尽量接近。 |
| 任务窃取 | 空闲处理器从忙碌处理器的本地任务队列中取出任务执行，以实现负载均衡。 |
| 硬实时 | 任务必须在规定时间内绝对完成，错过截止时间可能造成严重后果。 |
| 软实时 | 任务希望在截止时间前完成，但偶尔超时可以接受。 |
| 可调度性 | 在周期性实时任务集合中，各任务所需 CPU 时间之和满足限制时，系统才可能保证所有任务按时完成。 |
| RM | 速率单调算法是静态优先级实时调度算法，周期越短或执行时间越短的任务优先级越高。 |
| EDF | 最早截止时间优先算法根据任务截止时间动态分配优先级，截止时间最近的任务优先运行。 |
| nice值 | Linux 普通进程的静态优先级参数，数值越小优先级越高。 |
| O(1)调度器 | 通过 active 和 expired 两个按优先级组织的队列数组，使选择下一个进程的时间复杂度保持常数级。 |
| SD调度器 | 楼梯调度器让用完时间片的进程逐级降低调度层级，以减少饥饿并保留交互进程响应优势。 |
| RSDL | 旋转楼梯截止时间调度器在 SD 的降级思想上引入组时间配额和过期队列，使低优先级任务的等待时间更可预测。 |
| CFS | 完全公平调度器按进程权重比例分配 CPU，并选择虚拟运行时间最小的进程运行。 |
| 虚拟运行时间 | CFS 中用于表示进程运行进度的指标，与实际运行时间成正比、与进程权重成反比。 |
| 红黑树 | CFS 用红黑树按虚拟运行时间组织就绪进程，以便快速找到虚拟运行时间最小的进程。 |
| EEVDF | Linux 新版本中用于改进 CFS 的调度算法，在公平性之外进一步考虑延迟等因素。 |
