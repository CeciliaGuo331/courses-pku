> 课件 第 2–4 页 · 讲解从 `05:02` 开始

### 内存管理的演进：从物理内存到虚拟内存

虚拟内存并非一开始就存在，而是内存管理方式逐步抽象演进的结果：

1. **朴素内存管理阶段**：进程运行时按需分配其所需的全部实际物理内存。
2. **多道程序设计阶段**：多个进程共享内存，管理复杂度上升，需要解决：
   - 地址越界检查；
   - 内存空间不足；
   - 进程启动时内存需求与可用资源不匹配；
   - 通过内存压缩（memory compaction）腾挪可用空间等问题。
3. **第一次抽象：地址空间**：把进程看到的地址与实际物理内存隔离开。进程使用自己的地址空间，地址空间到物理内存的映射由系统完成，上层程序无需关心物理内存细节。
4. **进一步发展出虚拟内存**：在地址空间抽象之上，构造一个远大于实际物理内存的虚拟地址空间，使程序不必全部装入物理内存即可运行。

> **注意**：虚拟内存抽象并不适用于所有场景。小型嵌入式系统仍可能直接管理物理内存，采用按需分配的朴素方式`▶ 05:02`。

这种设计体现了计算机领域一条通用的软件工程思想：**遇到问题时，可以通过增加一个间接层来解决**。虚拟地址空间就是位于进程与物理内存之间的间接层，操作系统通过管理进程地址空间来间接管理物理内存，从而实现解耦，并提升灵活性、可扩展性、可维护性、安全性与性能`▶ 23:04`。

### X86-64 Linux 的虚拟地址空间大小

在 X86-64 架构下：

- 采用 **64 位虚拟地址形式**；
- 使用 **四级页表**；
- 标准页大小通常为 **4 KiB**；
- 结合页表项（PTE）和多级页表能表示的虚拟页号位数，Linux 在该架构上实际支持的虚拟地址空间大小为：

\[
2^{48}\text{ B}
\]

作为对比：

| 架构 | 典型虚拟地址空间大小 |
|---|---:|
| 32 位架构 | \(2^{32}\) B，即 4 GiB |
| X86-64（Linux 四级页表） | \(2^{48}\) B，即 256 TiB |

> **老师强调**：要能够结合 X86-64 的四级页表、4 KiB 页大小和 PTE 规格推导出 \(2^{48}\)；也可以自行推导 RISC-V 架构下最大支持的虚拟地址空间大小`▶ 08:35`。

需要注意：虽然虚拟地址是 64 位形式，但并不意味着全部 64 位都参与当前硬件的地址转换；实际可寻址范围还受页表级数和 CPU 实现限制。

### Linux 如何描述虚拟地址空间

进程创建时，操作系统会为其建立独立的虚拟地址空间，并分配相应的数据结构来描述其中真正有内容的区域`▶ 10:47`。

由于虚拟地址空间非常大（如 X86-64 下为 \(2^{48}\) B），不可能用一个巨大的连续数组逐字节描述整个空间。Linux 的做法是：

- 将地址空间中具有实际内容的区域抽象为一个个节点；
- 每个区域通常具有连续的虚拟地址范围、权限和映射来源；
- 使用链表、AVL 树（或红黑树等实际内核结构）把这些区域组织起来；
- 进程创建时初始化这些描述结构；
- 这一过程即完成了进程地址空间/虚拟内存的逻辑分配。

其中一个关键数据是 **PGD（Page Global Directory）**：

- PGD 是四级页表中的顶级页表，即一级页表；
- 其中保存顶级页表的基地址；
- 进程被调度上 CPU 运行时，该地址会被装入相应的硬件页表基址寄存器；
- 进程切换时，相关硬件上下文和进程状态必须保存与恢复，地址转换硬件才能定位到当前进程的页表`▶ 10:47 · 13:34`。

虚拟内存涉及的重要数据结构包括：

- 描述进程整体地址空间的结构；
- 描述各个虚拟内存区域的节点（如 `vm_area`）；
- 进程页表；
- 顶级页表基址 PGD；
- 页表项 PTE；
- 进程控制块 PCB（Linux 中为 `task_struct`）；
- 打开文件表等与内存映射相关的结构。

> **老师强调**：虚拟内存相关的主体数据结构是页表，必须重点掌握`▶ 14:04`。

### 地址转换：虚拟地址到物理地址的映射

虚拟内存学习的核心是 **地址转换（address translation）**，它是一个在程序运行时不断发生的动态过程`▶ 14:22`。

系统中存在两个不同的地址空间：

1. **虚拟地址空间**：进程发出指令和数据访问时使用的地址空间；
2. **物理内存空间**：实际内存条对应的地址空间。

CPU 执行程序时获得的地址都是虚拟地址。地址转换的作用，就是把 CPU 发出的虚拟地址映射为真实的物理地址，再访问实际内存单元`▶ 14:22`。

基本过程为：

```text
CPU 发出虚拟地址
        ↓
内存管理硬件查询页表
        ↓
得到物理页框号和页内偏移
        ↓
形成物理地址
        ↓
访问物理内存中的指令或数据
```

页内偏移在地址转换过程中保持不变，虚拟页号通过页表映射为物理页框号。

---

### 为什么需要 TLB

如果没有专门的加速机制，地址转换会显著降低访存性能：

- 单级页表下，需要先访问页表得到物理地址，再访问目标内存单元，至少需要 **2 次访存**；
- 在 X86-64 四级页表下，逐级访问页表后再访问最终数据，可能需要 **5 次访存**`▶ 15:04`。

这对每条指令都可能取指、访存的系统来说代价极高。因此硬件引入一种类似缓存的机制：

- **TLB（Translation Lookaside Buffer，转址旁路缓冲）**；
- 俗称 **快表**；
- 缓存最近使用的虚拟页号到物理页框号的映射；
- TLB 命中时无需逐级查询页表，从而加快地址转换`▶ 15:04`。

> **老师强调**：地址转换由硬件支持，而 TLB 是加快地址转换的关键机制`▶ 14:22 · 15:04`。

### 虚拟内存管理的目标

#### 1. 透明性

运行中的程序应感觉不到虚拟化的存在。程序使用虚拟地址访问指令和数据，地址转换、缺页处理、页面调入调出等工作都由操作系统和硬件在下层完成`▶ 20:29`。

#### 2. 效率

虚拟内存必须尽可能降低额外开销：

- 使用 TLB 加速地址转换；
- 优化页面调入速度；
- 在程序运行时完成动态地址重定位；
- 利用程序局部性减少低速外存访问`▶ 20:29 · 21:16`。

虚拟内存的核心思想可以概括为 **时间换空间**：

- 程序不需要在启动时全部装入内存；
- 需要某部分内容时，再从外存调入内存；
- 内存紧张时，可将暂不使用的页面换出到外存；
- 早期的交换（swapping/交换技术）是虚存的重要实现基础；
- 代价是增加运行时延迟，但获得了运行大程序和提高内存利用率的能力`▶ 21:16`。

#### 3. 保护

虚拟内存还提供内存保护，主要针对两类问题：

- **越界访问**：进程访问不属于自己地址空间或未定义区域的地址；
- **越权访问**：进程对页面执行不符合权限的操作，例如写只读页、执行不可执行页。

私有的虚拟地址空间天然隔离了不同进程的地址空间，但仍需要页表权限位等机制进行检查`▶ 22:31`。

### 虚拟页式存储

主流且管理相对简单的虚拟内存方案是 **页式虚拟存储（虚拟页式）**：

- 虚拟地址空间被划分为固定大小的虚拟页；
- 物理内存被划分为同样大小的物理页框；
- 页表记录虚拟页到物理页框的映射；
- 页面可以驻留在内存中，也可以暂存在外存中；
- 访问未驻留内存的页面时触发页故障，由操作系统调入页面。

现代虚拟地址空间建立在存储体系之上，由操作系统协调内存与外存共同工作`▶ 25:40`。

### 存储体系与虚拟内存的关系

虚拟内存能够良好运行，依赖于整个存储层次与程序局部性原理的配合。

典型存储层次从上到下为：

```text
CPU 寄存器
   ↓
Cache（高速缓存）
   ↓
内存（RAM）
   ↓
磁盘/外存（Disk）
```

其变化规律是：

- 速度逐级降低；
- 容量逐级增大；
- 单位成本逐级降低。

存储体系是在速度、成本和容量之间进行折中。结合程序的时间局部性和空间局部性，系统希望：

- 高频访问内容尽可能位于接近 CPU 的高速存储中；
- 全部程序和数据又能享有近似外存的大容量；
- 使虚拟内存的访问速度尽可能接近 CPU 取指所需速度，同时容量足够大`▶ 25:40`。

在课程给出的结构中：

- 上层是每个进程独立的虚拟地址空间（例如 32 位进程的 4 GiB 地址空间）；
- 虚拟地址空间具有固定布局；
- 虚拟页面的内容实际要么在内存中，要么在磁盘上；
- Cache 通常不由操作系统直接管理；
- 操作系统通过地址映射确定虚拟地址最终对应哪个物理存储位置；
- 虚存本身是一个抽象概念，但其内容最终必须落到实际物理存储中`▶ 27:42`。

### 三个核心概念

#### 1. 虚存（Virtual Memory）

虚存把物理内存与磁盘结合起来，向进程提供一个容量远大于实际物理内存的逻辑内存。这里的“内存”加引号，是因为它并不是与物理内存同等意义上的真实连续存储介质，而是操作系统通过映射和换入换出构造出的抽象空间`▶ 29:02`。

#### 2. 虚拟地址（Virtual Address）

虚拟地址是程序在虚存空间中引用指令或数据时使用的地址。它与实际物理地址不同，使用时必须经过地址转换映射为物理地址`▶ 29:02`。

虚拟地址空间的大小受两方面约束：

1. **CPU 寻址能力**：由字长等因素决定。例如 32 位字长最多只能表示 \(2^{32}\) 个地址，不可能覆盖 \(2^{48}\) 大小的空间；
2. **外存容量限制**：虚拟页面可放在磁盘等外存上，因此逻辑上也受可用磁盘容量限制；当前主流磁盘容量仍远达不到 \(2^{48}\) 对应的全部规模`▶ 29:02`。

#### 3. 虚拟内存区域（Area）

实际系统不会把整个巨大的虚拟地址空间作为一个统一对象管理，而是按照一个个 **area（区域）** 分段管理。每个区域通常表示一段连续虚拟地址范围，并具有自己的权限、用途和后备存储来源`▶ 29:02`。

### 页表项 PTE 与 Page Fault

页表的基本表项称为 **PTE（Page Table Entry，页表项）**。PTE 不只是保存物理页框号，还包含大量控制位，用来描述页面状态和访问权限，例如：

- 页面是否在物理内存中（有效/存在位）；
- 页面是否可写；
- 页面是否可读；
- 页面是否可执行；
- 是否允许用户态访问；
- 页面是否被访问过；
- 页面是否被写过（脏位）；
- 是否禁止缓存等硬件相关控制信息。

当硬件访问 PTE 时，如发现控制位状态不满足当前访问要求，就会触发 **Page Fault（页故障/缺页异常）**。

> **老师强调**：Page Fault 异常由硬件发出。硬件在查页表、检查 PTE 控制位时发现条件不满足，便陷入操作系统，由操作系统的异常处理程序完成后续处理`▶ 16:35`。

也就是说：

- **异常触发者**：硬件；
- **异常处理者**：操作系统；
- **判断依据**：PTE 中的存在位、权限位等控制位。

Page Fault 不一定表示错误。它既可能表示非法访问，也可能是虚拟内存正常工作的一部分，例如：

- 页面尚未调入内存；
- 写入写时复制的只读共享页；
- 第一次访问内存映射文件中的页面；
- 栈或堆需要自动扩展。

### 写时复制（Copy On Write, COW）

写时复制是一种优化 `fork()` 性能的技术，来源于 Unix，并在 Linux 中用于加快创建子进程的速度`▶ 17:50`。

#### 传统 fork 的问题

父进程拥有多种数据结构和资源，例如：

- PCB / `task_struct`；
- 打开文件表；
- 页表；
- `vm_area` 等地址空间描述结构；
- 代码、数据、堆栈对应的物理页。

传统 `fork()` 会把父进程地址空间中的数据完整复制到子进程，包括复制所有相关物理页。即使子进程随后立即调用 `exec()` 加载新程序，这些复制工作也可能被浪费，因此开销很大`▶ 17:50`。

#### COW 的做法

写时复制不立即复制物理页，而是：

1. 父子进程共享同一份物理内存页；
2. 将这些共享页在页表中标记为 **只读**；
3. 父子进程各自的页表暂时指向同一个物理页框；
4. 如果二者都只读取该页，则始终共享，不发生复制；
5. 当父进程或子进程尝试写入该页时，写入操作与只读权限冲突；
6. 硬件检测 PTE 后触发 Page Fault；
7. 操作系统在异常处理中分配新物理页，复制原页内容；
8. 修改触发写入一方的页表，使其指向新复制的页面并恢复可写权限；
9. 返回触发写入的指令重新执行。

> **老师强调**：COW 必须配合 Page Fault 才能实现。真正的复制动作不是在 `fork()` 时发生，而是延迟到某一方实际写入、并因只读 PTE 触发页故障之后才发生`▶ 17:50`。

#### 如果父子进程都只读，物理页会复制吗？

不会。若父子进程都只读取共享页面，该物理页一直共享，不需要复制。只有当某一方执行写操作时，被写入的那一页才会被复制；不同页面可以独立触发复制。

### 内存映射（mmap）

内存映射是虚拟内存中非常重要的底层支持机制，并且与写时复制密切相关，属于虚拟内存的高阶内容`▶ 19:52`。

通过 `mmap()`，进程可以把文件或其他对象映射到自己的虚拟地址空间中的某个区域。之后，程序可以像访问内存一样访问该区域，而不是显式调用 `read()`/`write()`。

#### 为什么第一次访问慢，之后可能很快？

建立映射时，操作系统通常只是：

- 创建描述该虚拟内存区域的数据结构；
- 设置相应页表项或暂不建立完整映射；
- 记录该区域的后备存储是哪个文件及偏移。

此时文件内容未必已经读入物理内存。第一次访问映射区域中的某个页面时：

1. CPU 访问虚拟地址；
2. 硬件查页表发现页面不在内存或映射尚未建立；
3. 触发 Page Fault；
4. 操作系统分配物理页；
5. 从文件中读取对应页面到内存；
6. 建立虚拟页到物理页框的映射；
7. 恢复用户程序执行。

因此第一次访问会经历缺页处理和磁盘 I/O，速度较慢。之后该页面已驻留内存，且 TLB/页表缓存可能命中，再次访问就可能像普通内存访问一样快。

#### 两个进程映射同一个文件时是否共享物理页？

多个进程 `mmap()` 同一个文件时，操作系统可以把同一文件页映射到它们各自的虚拟地址空间；底层可复用同一份物理页缓存。因此，即使不同进程中的虚拟地址不同，也可能访问同一个物理页框。具体可见性和一致性取决于映射类型（共享映射或私有映射）、访问权限以及操作系统的页缓存管理。

## 2. 虚拟页式存储与存储体系

> 课件 第 5–10 页 · 讲解从 `30:49` 开始

### 存储体系

现代计算机的存储层次由寄存器、Cache、内存和磁盘共同构成，由操作系统协调各存储器的使用。

构建存储体系的目的：

- **速度目标**：让进程所看到的"内存"速度尽量快，与 CPU 取指速度相匹配；
- **容量目标**：让"内存"容量尽量大，能够装下当前运行的程序与数据。

进程的地址空间（虚存）建立在这一存储层次之上，由操作系统通过虚拟存储技术把快速但容量小的内存与慢速但容量大的磁盘协调起来，对进程呈现出一个又快又大的"内存"。

### 相关术语辨识

- **虚拟存储技术**：进程运行时先将一部分装入内存，另一部分暂时保存在磁盘；当要执行的指令或访问的数据不在内存时，由操作系统自动完成将它们从磁盘调入内存的工作。
- **虚拟内存（虚存）**：把物理内存与磁盘结合起来使用，得到的一个容量很大的"内存"。
  - 程序引用内存所使用的地址与内存物理地址不同，可被自动转换成物理地址；
  - 虚存大小受计算机系统寻址机制和可用磁盘容量的限制。
- **虚拟地址空间**：分配给进程的虚拟内存。
- **虚拟地址**：虚拟内存中某一位置的地址，该位置可以被访问，仿佛它是内存的一部分。

对普通用户来说，虚拟地址等价于内存地址；但对操作系统学习者而言，它只是逻辑空间地址，必须经过地址转换才能访问实际物理内存`▶ 30:49`。

### 虚拟页式存储管理的基本思想

虚拟页式存储管理的核心思想包括：

1. **部分装入**：装载程序时，不是装入全部页面，而是装入几个甚至零个页面；
2. **动态调页**：进程执行时需要的页面不在内存，则动态装入所需页面；
3. **页面交换**：需要时，将内存中暂时不用的一些页面交换到磁盘，以便获得更多内存空间。

进程运行时不需要将整个地址空间全部装入内存，可一部分驻留内存、一部分保存在磁盘。当进程访问的指令或数据不在内存时，操作系统自动通过缺页（Page Fault）中断处理程序将目标页面从磁盘调入内存，处理完成后重新执行触发缺页的指令。现代系统甚至初始可以装入 0 个页面`▶ 31:15`。

#### 进程创建与首次缺页的实例

以 Hello World 程序的执行流程为例：

1. 在磁盘上找到对应可执行文件，先校验文件类型，仅可执行文件才能运行；
2. 通过文件首部信息，确定代码和数据在可执行文件中的相对位置（类似通过书籍目录找到对应章节的页码），再结合可执行文件的磁盘起始地址，计算出代码和数据对应的实际磁盘地址。这一步仅完成位置和地址计算，暂不将内容读入内存`▶ 32:37`；
3. 创建新进程，将可执行文件映射到进程结构中。创建进程的三个核心步骤是：分配 PID、创建 PCB（Linux 中通过 slab 机制分配 PCB）、分配地址空间。PCB 中会设置字段关联对应的可执行文件，甚至直接写入磁盘地址；
4. 完成映射后仍不把可执行文件内容读入内存，因此执行第一条指令时会立刻触发缺页异常，印证了初始装入 0 个页面的设计`▶ 34:40`。

进程执行时若所需页面不在内存，由硬件检测到页面缺失后触发缺页异常处理流程，动态装入对应页面`▶ 36:41`。x86 架构下，中断 14 号（int 14）是缺页异常处理入口`▶ 37:05`。

需要注意，Page Fault 的诱因不只有有效位为 0（页面不在内存）一种；发生缺页时通常需要执行内存置换操作`▶ 37:32`。

#### 资源转换的本质

缺页置换是操作系统中典型的"时间换空间"策略：用 CPU 时间和磁盘读取时间换取内存空间。与之相对的还有"空间换时间"的策略。操作系统在软件层面的核心矛盾就是时间与空间的权衡，这种权衡从早期算法复杂度设计阶段就已存在`▶ 37:32`。

### 请求调页与预先调页

虚拟页式存储管理通常有两种调页方式：

| 方式 | 做法 | 特点 |
|------|------|------|
| **请求调页（demand paging）** | 进程访问的页面不在内存时触发 Page Fault，再将该页面调入内存 | 按需加载 |
| **预先调页（prepaging）** | 提前预先装入部分即将用到的页面 | 利用局部性，减少后续缺页 |

实际计算机系统以请求调页为主、预先调页为辅。原因在于：从磁盘读取数据时，寻道时间远大于单页数据的传输时间，调入缺页时顺带调入相邻几页的时间成本几乎相同；结合程序局部性原理，能够降低后续的缺页概率。当前主流操作系统均采用这种混合方案`▶ 38:35`。

### 调页机制

进程的虚拟地址空间与物理地址空间相互分离，这是调页机制的基础。调页系统有 3 个重要策略（Coffman & Denning）：

1. **取页策略（fetch policy）**：系统何时把页面载入内存；
2. **放置策略（placement policy）**：系统把页面放在何处，即调入的页面分配到哪个空闲页框；
3. **置换策略（replacement policy）**：执行放置操作时若发生页框不足，如何选择从内存里"删除"的其他页框。

关于置换时的处理细节：若被选中的页面在内存中未被修改过，无需写回磁盘，可直接释放；若被修改过，则需要将其内容写回磁盘后再释放页框`▶ 40:54`。

### 虚拟地址到物理地址的转换

转换流程如下：

1. CPU 输出虚拟地址；
2. 交由内存管理单元（**MMU**，硬件部件，TLB 集成在该硬件芯片内）处理；
3. MMU 访问页表，通过虚拟页号查询对应的页表项；
4. 若有效位为 1（页面在内存中），得到物理页框号；
5. 将物理页框号与虚拟地址的**页内偏移**直接拼接，得到物理地址。

举例：若虚拟地址的高位页号为 `0010`，查询对应页表项，有效位为 1，得到物理页框号 `110`，将页框号 `110` 与页内偏移拼接即可得到物理地址`▶ 42:21`。

### 设计与实现时要解决的问题

虚拟页式存储管理在设计与实现中需要解决以下问题：

- 页表表项的设计；
- 如何处理页表巨大的问题；
- 地址重定位与快表（TLB）；
- 一种最常见的 Page Fault——缺页异常；
- 驻留集管理；
- 置换策略；
- 清除策略；
- 加载控制。

## 3. 页表项结构与控制位

> 课件 第 11–12 页 · 讲解从 `44:48` 开始

### 页表项（PTE）的基本设计

页表项是页表中用于记录一个虚拟页与物理页框映射关系及页面控制信息的数据结构。其大小与机器字长相关：32 位系统中页表项为 4 字节，64 位系统中为 8 字节。因此：

- 32 位系统：若页面大小为 4 KB，则一页可存放 `4 KB / 4 B = 1024` 个页表项；
- 64 位系统：若页面大小为 4 KB，则一页可存放 `4 KB / 8 B = 512` 个页表项。

> **老师强调**：单页能存放多少个页表项，与后续多级页表设计直接相关`▶ 44:48`。

页表项通常包含以下字段：页框号、有效位、访问位、修改位、保护位等。

| 字段 | 常见名称 | 作用 |
|---|---|---|
| 页框号 | 内存块号、物理页面号、页帧号、PFN | 保存虚拟页对应的物理页框编号 |
| 有效位 | 驻留位、中断位、Present、Valid | 表示页面当前在内存还是磁盘 |
| 访问位 | 引用位、Referenced、Accessed、A/R 位 | 表示页面在内存期间是否被访问过 |
| 修改位 | Dirty、Modified、M/D 位 | 表示页面装入内存后是否被修改过 |
| 保护位 | Protection、R/W/X 等 | 控制页面的读、写、执行权限 |

#### 页框号

页框号是页表项中最核心的字段，因为页表的根本作用就是完成**虚拟页号到物理页框号的映射**。页框号也可称为内存块号、物理页面号或页帧号，英文为 Page Frame Number，简称 PFN`▶ 45:31`。

#### 有效位

有效位在 x86 架构中常称为 Present 位，也叫驻留位或中断位，用于表示页面是否已经加载到内存：

- `P = 1`：页面在内存中；
- `P = 0`：页面不在内存中，可能仍在磁盘上。

当访问一个有效位为 0 的页面时，会触发缺页异常，由操作系统将所需页面调入内存`▶ 46:27 · 50:38`。

> **老师提醒**：口头作答时不要直接把字段叫作英文，应能说出“有效位”“驻留位”等中文名称；Valid、Present 是对应的英文字段名`▶ 46:27`。

#### 访问位

访问位也称引用位，可简称 A 位或 R 位。页面在内存期间一旦被读取或访问，硬件会将该位置为 1`▶ 47:13`。

访问位会被操作系统定期清零。其原因是：如果长期保留为 1，就无法判断页面最近是否仍在使用。清零后，若在下一次检查时该位仍为 0，说明这一段时间内页面没有被访问，因而可作为页面置换算法的依据`▶ 47:13`。

#### 修改位

修改位也称 Dirty 位或 Modified 位，可简称 D 位或 M 位，用于表示页面装入内存后是否被修改过`▶ 48:21`。

修改位同样服务于页面置换：

- 若页面未被修改，淘汰时通常不必写回磁盘；
- 若页面已经被修改，淘汰前必须将其写回磁盘，以保证磁盘上的副本是最新的。

#### 保护位

保护位用于设置页面的读、写、执行权限。现代系统通常将读、写、执行权限分开表示，而不是只区分简单的读写权限`▶ 48:39`。

早期系统没有独立的执行权限，栈上的数据也可能被当作指令执行，容易产生栈溢出攻击：攻击者向栈区注入恶意代码并直接执行。后来增加独立的执行位，使栈区不可执行，从而阻断这类攻击路径`▶ 48:39`。

### 页表项控制位的含义

#### P 位：有效位

P 位表示页面是否位于内存：

- `P = 1`：页面在内存；
- `P = 0`：页面在磁盘或尚未装入。

访问 `P = 0` 的页面会触发缺页异常`▶ 50:38`。

#### R/W 位：读写权限

R/W 位用于控制页面是否可写：

- 通常表示只读或可读写；
- 与执行权限等其他控制位组合，可以实现更细粒度的页面保护`▶ 50:38 · 1:05:01`。

#### U/S 位：用户态/内核态权限

U/S 位表示页面的特权级访问限制：

- U 表示 User，即用户态可访问；
- S 表示 Supervisor，即内核态访问。

当页面处于内核态权限下时，用户态程序不能访问该页面。若当前访问权限与页表项设置不匹配，会触发异常`▶ 50:38`。

#### A 位和 D 位

- A 位（Accessed）：页面被访问后置 1；
- D 位（Dirty）：页面被修改后置 1。

A 位和 D 位都可为页面置换算法提供依据：A 位反映最近是否被访问，D 位反映淘汰前是否需要写回磁盘`▶ 47:13 · 48:21`。

#### PWT 位：缓存写策略

PWT（Page Write Through）用于控制页面所在物理页框的缓存写策略：

- `PWT = 0`：通常对应 write back，即回写策略，修改后先写入 Cache，之后再滞后写回内存；
- `PWT = 1`：对应 write through，即直写策略，修改后立即同时写入 Cache 和内存。

老师说明，直写表示修改后立刻同步写回，回写表示修改后滞后写回；该知识点在组成原理和 ICS 课程中也出现过`▶ 50:38 · 52:33`。

#### PCD 位：禁止缓存

PCD（Page Cache Disable）用于控制页面内容是否允许进入 Cache：

- `PCD = 0`：允许缓存；
- `PCD ≠ 0` 或置 1：禁止缓存。

PCD 与 PWT 配合，共同确定该页的缓存策略`▶ 52:33`。

#### PS 位：大页控制

PS（Page Size）位用于指定页面大小。在 i386 中，该位置位时可支持 4 MB 大页，使页目录项可以直接映射一个较大的物理页面，而不必再经过下一级页表。

#### G 位：全局页标志

G 表示 Global，即全局页。全局页面通常用于长期驻留、多个进程共享的内核页面等场景，在地址空间切换时可避免相关 TLB 表项被频繁清除。

### 酷睿 i7 四级页表中的页表项

酷睿 i7 采用四级页表结构，通过逐级索引完成地址转换：

1. 一级页表项指向二级页表；
2. 二级页表项指向三级页表；
3. 三级页表项指向四级页表；
4. 最后一级页表项给出虚拟页对应的物理页框号。

前三级页表项主要负责定位下一级页表，最后一级页表项才最终完成虚拟页面到物理页面的定位，但前三级页表项的基本结构与通用页表项结构一致`▶ 49:45`。

- XD 即 Execute Disable，表示禁止执行；
- 设置 XD 位后，该页内容不能作为指令执行；
- 通过 XD 位与读写权限等控制位组合，可以设置页面是否只读、是否可执行等访问权限`▶ 1:05:01`。

MMU 查询页表时，不仅要根据 PFN 完成地址转换，还会检查当前操作是否符合页表项规定的权限。若页面不存在或访问权限不匹配，就会触发 page fault，即缺页异常或保护性异常`▶ 1:05:01`。

> **老师强调**：页表项最核心的作用仍然是保存对应的物理页框号；控制位则用于支持缺页处理、页面置换、访问保护和缓存控制`▶ 45:31 · 1:05:01`。

## 4. 多级页表结构与地址映射

> 课件 第 13–16 页 · 讲解从 `1:06:38` 开始

### 为什么需要多级页表

#### 单级页表的规模问题

以 **32 位系统、4 KB 页面、4 字节页表项**为例计算：

- 页面大小：$4\text{ KB}=2^{12}$ 字节，因此页内偏移占 12 位。
- 用户虚拟地址空间：$2\text{ GB}=2^{31}$ 字节。
- 一个进程的页数：

\[
\frac{2^{31}}{2^{12}}=2^{19}
\]

- 每个页对应一个 4 字节页表项，页表总大小：

\[
2^{19}\times 4\text{ B}=2^{21}\text{ B}=2\text{ MB}
\]

- 每个内存页大小为 4 KB，因此页表本身需要占用：

\[
\frac{2\text{ MB}}{4\text{ KB}}=2^9=512\text{ 页}
\]

也就是说，如果把一个进程的所有页表项组织成一个连续的一维数组，那么这个页表需要 **512 个连续的物理页**存放，这对每个进程来说代价过高，也不现实`▶ 1:06:38`。

在 64 位虚拟地址空间下，如果仍采用单级连续页表，页表规模会极其庞大。课件给出的规模是：

\[
\text{一张页表有 }33\,554\,432\text{ GB}
\]

因此，单级线性页表无法扩展到巨大的虚拟地址空间。

#### 稀疏地址空间造成浪费

进程的虚拟地址空间通常是 **稀疏使用**的：虽然虚拟地址空间很大，但真正有代码、数据、堆栈等内容的页面只占很少一部分。绝大多数虚拟页没有实际内容，如果仍为所有虚拟页连续分配页表项，会浪费大量内存；在 64 位地址空间中浪费更加严重`▶ 1:09:31`。

改进思路是：

- 页表页在内存中 **离散存放**，不要求连续；
- 只为实际使用的虚拟页分配对应的页表页；
- 没有使用的地址区域可以不分配下级页表`▶ 1:09:31`。

为了找到这些离散存放的页表页，需要再增加一层地址索引，即 **页目录（一级页表）**，由此形成两级或多级页表结构`▶ 1:10:39`。

> **老师强调**：多级页表的核心作用，是把原本要求连续存放的一维页表，改造成可以离散分配的树形结构，从而节省页表内存。

---

### 页表本身的存放

多级页表中的页表和普通页面一样存放在内存中，并且页表本身也可以映射到虚拟地址空间。进程运行时，只需要把当前用到的部分页表保存在内存中。

MMU 进行地址转换时，可以根据寄存器中的物理地址直接访问页表；但内核查询页表时不能方便地直接使用物理地址，因此系统会把物理内存中的页表反向映射到内核态虚拟地址空间，使内核能够通过虚拟地址访问页表`▶ 1:11:02`。

---

### 两级页表的设计思想

两级页表把原来的一维连续数组改造成树形结构：

- **顶级页表 / 页目录 / 一级页表**：相当于索引数组；
- **二级页表**：由页目录中的表项指向；
- **二级页表中的页表项**：指向真正的代码页或数据页；
- 各个二级页表页可以在内存中离散存放。

课件中的逻辑可以概括为：

```text
顶级页表（页目录）
      ├── 页目录项0 → 二级页表0 → 实际页面
      ├── 页目录项1 → 二级页表1 → 实际页面
      ├── 页目录项2 → 不存在或未分配
      └── ...
```

这样，顶级页表负责维护下级页表的顺序关系，二级页表页则不必连续存放`▶ 1:10:39 · 1:12:33`。

如果继续增加非叶子节点层，让二级页表指向更多下级页表，就可以扩展为三级、四级页表，以支持更大的虚拟地址空间`▶ 1:12:33`。

### 32 位两级页表的地址映射

#### 虚拟地址划分

页面大小为 4 KB，因此低 12 位是 **页内偏移**。32 位虚拟地址的高 20 位是虚拟页号，被平均划分为两个 10 位索引：

```text
31              22 21              12 11               0
┌──────────────────┬──────────────────┬──────────────────┐
│  页目录偏移       │    页表偏移       │    页内偏移       │
│     10 位        │     10 位        │     12 位        │
└──────────────────┴──────────────────┴──────────────────┘
```

- 高 10 位：索引 **页目录（一级页表）**；
- 中间 10 位：索引对应的 **二级页表**；
- 低 12 位：页面内部偏移。

#### 地址转换过程

设页目录的物理地址由页目录基址寄存器给出。转换步骤为：

1. 从 CR3 寄存器获得当前进程 **页目录的物理地址**；
2. 用虚拟地址高 10 位作为页目录索引，找到对应的页目录项；
3. 页目录项中存放某个二级页表的物理页框号；
4. 用中间 10 位在该二级页表中查找页表项；
5. 页表项给出实际物理页框号；
6. 将物理页框号与虚拟地址低 12 位页内偏移拼接，得到物理地址`▶ 1:13:51`。

可以表示为：

```text
虚拟地址
├── 页目录索引(10位)
│      ↓ 查页目录
│   二级页表基址
├── 页表索引(10位)
│      ↓ 查二级页表
│   物理页框号
└── 页内偏移(12位)
       ↓ 拼接
物理地址 = 物理页框号 × 页面大小 + 页内偏移
```

在 x86 架构中，页目录物理地址存放在 **CR3 寄存器**中，CR3 中保存的是物理地址，MMU 根据它完成页表查询`▶ 1:13:51`。

### Core i7 的四级页表结构

#### 基本参数

酷睿 i7 使用 **四级页表**，其主要参数为：

| 项目 | 参数 |
|---|---|
| 虚拟地址使用位数 | 48 位 |
| 页面大小 | 4 KB，即 $2^{12}$ 字节 |
| 页内偏移 | 12 位 |
| 页表项大小 | 8 字节 |
| 每个页表页可存放的表项数 | $4\text{ KB}/8\text{ B}=512=2^9$ |
| 每级索引位数 | 9 位 |
| 页表级数 | 4 级 |
| 虚拟地址空间大小 | $2^{48}$ |

> **老师强调**：必须牢记 32 位与 64 位架构的页表差异。32 位场景中页表项通常为 4 字节；Core i7 的 64 位四级页表中页表项为 8 字节`▶ 1:12:33 · 1:15:21`。

#### 虚拟地址划分

因为一个页表页可以存放 $2^9$ 个页表项，所以每一级索引需要 9 位。四级共需要：

\[
4\times 9=36\text{ 位}
\]

再加上 12 位页内偏移：

\[
36+12=48\text{ 位}
\]

因此虚拟地址划分为：

```text
47    39 38    30 29    21 20    12 11               0
┌─────────┬─────────┬─────────┬─────────┬──────────────┐
│ VPN 4   │ VPN 3   │ VPN 2   │ VPN 1   │  页内偏移     │
│  9 位   │  9 位   │  9 位   │  9 位   │   12 位      │
└─────────┴─────────┴─────────┴─────────┴──────────────┘
    L4        L3        L2        L1
```

课件中由高到低使用了 `VPN 3 / VPN 4 / VPN 2 / VPN 1` 等标注，并依次查询：

- L4 PTE；
- L3 PTE；
- L2 PTE；
- L1 PDE/PTE。

理解时应抓住本质：**四个 9 位字段依次索引四级页表，最后得到 40 位物理页框号，再与 12 位页内偏移拼接成物理地址。**

物理地址格式为：

```text
51                   12 11               0
┌──────────────────────┬──────────────────┐
│      物理页框号       │    页内偏移       │
│        40 位         │      12 位       │
└──────────────────────┴──────────────────┘
```

#### 四级查询过程

CR3 中存放最高级页表的物理地址。转换时：

1. CR3 提供最高级页表的物理页框号；
2. 用第一个 9 位索引查询最高级页表，得到下一级页表的物理页框号；
3. 用第二个 9 位索引查询第三级页表；
4. 用第三个 9 位索引查询第二级页表；
5. 用第四个 9 位索引查询最低一级页表，得到实际物理页框号；
6. 将物理页框号左移 12 位，并拼接页内偏移，得到物理地址`▶ 1:15:21`。

流程如下：

```text
CR3
 ↓
四级页表 ── VPN第1个9位 ──→ 三级页表
 ↓
三级页表 ── VPN第2个9位 ──→ 二级页表
 ↓
二级页表 ── VPN第3个9位 ──→ 一级页表
 ↓
一级页表 ── VPN第4个9位 ──→ 物理页框号
 ↓
物理页框号 + 页内偏移 ──→ 物理地址
```

#### 各级页表数量

在全部分配的理想情况下：

| 页表层级 | 数量 |
|---|---:|
| 最高一级页表 | 1 |
| 第二级页表 | $512$ |
| 第三级页表 | $512^2$ |
| 第四级页表 | $512^3$ |

只有最底层页表中的表项与进程实际虚拟页面一一对应；上层页表主要用于定位离散存放的下级页表`▶ 1:15:21`。

48 位虚拟地址空间大小为 $2^{48}$，已经足够使用，并且能够与硬件分页机制匹配，不需要额外用软件模拟更多级的地址转换`▶ 1:15:21`。

---

### 多级页表与进程切换

每个进程都有自己独立的一套页表，因此不同进程的相同虚拟地址可以映射到不同物理地址。即使多级页表节省了未使用区域的页表空间，已分配的页表本身仍会占用一定物理内存`▶ 1:17:28`。

进程切换时，上下文切换的关键动作之一就是切换地址空间：

- 当前进程的页目录物理地址存放在 CR3 中；
- 切换到另一个进程时，把目标进程的页目录物理地址装入 CR3；
- CR3 改变后，MMU 后续查询的就是新进程的页表`▶ 1:13:51 · 1:17:28`。

> **老师强调**：进程切换在分页机制中的本质，就是切换 CR3 寄存器中保存的页目录物理地址，从而切换当前进程的虚拟地址空间`▶ 1:17:28`。

## 5. 反向页表

> 课件 第 17–19 页 · 讲解从 `1:18:15` 开始

### 反向页表（反转/反置页表）

#### 提出背景：传统正向页表的问题

传统分页地址转换的思路是从**虚拟地址空间**出发：

- 虚拟地址 → 查页表 → 得到页框号 → 形成物理地址
- 每个进程拥有一张独立的页表，以虚拟页号 VPN 为索引查找物理页框号 PPN

这种方式下，页表占用的内存会随虚拟地址空间增大而增加；即使一个进程实际使用的物理页很少，仍可能需要一张很大的页表`▶ 1:18:15`。

而系统中的**物理内存总量是固定的**，反向页表正是利用这一特点设计的`▶ 1:18:15`。

#### 基本思路

反向页表反过来从**物理地址空间**出发：

- 整个系统只建立**一张全局页表**，而不是每个进程一张`▶ 1:18:52 · 1:19:12`
- 页表以**物理页框号 PPN 为索引**
- 每个页表项记录该物理页框当前被哪个进程的哪个虚拟页占用，即保存「PID + VPN」与 PPN 的映射关系`▶ 1:19:43`

由于不同进程的虚拟地址空间相互独立，不同进程可能使用相同的 VPN，因此仅凭 VPN 无法区分页面归属。页表项中必须加入**进程标识 PID**，用「PID + VPN」的组合唯一标识某个进程的虚拟页`▶ 1:19:43`。

#### 地址转换过程

进程运行时，CPU 只能得到当前进程的 VPN 和 PID，地址转换需要：

1. 用「VPN + PID」在全局反向页表中逐项查找
2. 找到 PID、VPN 均匹配且页表项有效的表项
3. 该表项的索引（或其中记录的 PPN）即对应物理页框号
4. 用 PPN 与页内偏移拼接得到物理地址`▶ 1:21:02`

这种逐项遍历、比对的方式远慢于正向页表依靠索引直接寻址，早期只能主要依靠软件检索，开销较大`▶ 1:21:02`。

#### 哈希优化

为降低线性查找开销，实际实现中引入哈希结构：

- 将虚拟地址的页号部分 VPN 与进程 PID 组合作为关键字
- 对「VPN + PID」计算散列值
- 用散列值定位反向页表中的表项或冲突链
- 不同键散列到同一位置时，采用**拉链法**解决冲突`▶ 1:23:00`

#### 特点与应用

| 项目 | 说明 |
|---|---|
| 页表数量 | 整个系统一张全局页表 |
| 索引依据 | 物理页框号 PPN |
| 表项关键标识 | PID + VPN |
| 查找方式 | 遍历比对，实际中常结合哈希和拉链 |
| 页表大小 | 与实际物理内存容量成固定比例 |
| 是否随进程数增长 | 否，与进程个数无关 |
| 应用架构 | PowerPC、UltraSPARC、IA-64 等 |

> **老师强调**：反向页表的大小只和物理内存容量成正比，与进程数量无关，这是它相对于传统每进程页表的主要优势`▶ 1:24:26`。

反向页表的实际实现需要相应硬件体系结构支持，PowerPC、SPARC、IA-64 等架构都采用过这种机制`▶ 1:24:26`。

## 6. 地址转换过程与异常类型

> 课件 第 20–24 页 · 讲解从 `1:25:12` 开始

### 地址转换的硬件背景

操作系统通过**地址空间**完成对存储的抽象：每个进程拥有独立的虚拟地址空间，物理内存容量可以远大于进程实际可见/可用的局部地址范围（课件中以 \(M \gg m\) 表示）。CPU、MMU、内存与磁盘控制器协同完成虚拟存储：

- CPU发出的是**虚拟地址**；
- **MMU（内存管理单元，Memory Management Unit）**负责把虚拟地址转换为物理地址；
- 内存接收并访问的是**物理地址**；
- 当所需页面不在内存时，操作系统可通过磁盘控制器等机制把页面调入内存。

典型访问路径为：

```text
CPU → MMU → 内存
        ↑
      页表/异常处理支持
```

课件示例中，虚拟地址被划分为**虚页号**和**页内偏移**。MMU以虚页号为索引查询页表，从页表项中获得物理页框号，再与页内偏移拼接形成物理地址。例如课件中虚拟地址 `8196` 经过页表映射后得到物理地址 `24580`。页表项中通常包含：

- 物理页框号；
- 页面是否在内存中的有效/存在位；
- 访问权限与保护位；
- 其他硬件或操作系统使用的标志位。

### 正常地址转换过程

在不考虑TLB、且页面访问正常的情况下，地址转换由硬件快速完成：

1. CPU给出虚拟地址；
2. MMU从虚拟地址中取出虚页号；
3. 以虚页号作为索引查询当前进程页表；
4. 若页面合法、在内存中且权限允许访问，则从页表项中获得物理页框号（PPN）；
5. 将物理页框号与虚拟地址中的页内偏移拼接，得到物理地址；
6. MMU把物理地址发送给内存完成访问。

> **老师强调**：正常无异常的地址转换过程由硬件完成；若页面已在内存，直接以序列号（虚页号）为索引查询页表得到PPN，再拼接物理地址，这是不考虑TLB时最快的转换流程`▶ 1:25:12`。

课件给出的硬件逻辑可概括为：

```c
if (虚拟页面不在内存 || 页面非法 || 访问被保护) {
    硬件产生异常；
    陷入操作系统；
    执行页面错误服务程序（Page Fault）；
} else {
    页框号 = 页表[虚页号];
    物理地址 = 页框号 拼接 页内偏移;
}
```

### 地址转换中的三类异常

地址转换并不是总能由硬件直接完成。硬件检查页表项时，可能遇到以下三类情况：

| 异常类型 | 含义 | 典型例子 |
|---|---|---|
| 虚拟页面不在内存 | 页面属于进程地址空间，但当前未驻留物理内存 | 页面被换出到磁盘，需要调入内存 |
| 页面非法 | 访问的地址不属于进程已分配、可管理的地址范围 | PC跳到未映射的空闲地址，访问不存在的地址 |
| 访问受保护 | 页面存在，但本次访问违反权限 | 写只读页、用户态访问内核页 |

其中，前两类可通过页表项中的存在位/有效位、非法或未映射状态进行判断；保护错误则由页表项中的访问权限位检查`▶ 1:26:09`。

### 页面非法与有效位为0

进程的虚拟地址空间中存在大量空闲、未分配区域。并不是所有虚拟地址都对进程有效。若指令的PC或数据访问指向这些未被VMA等进程地址空间结构管理的区域，就相当于访问了一个不存在的地址`▶ 1:26:50`。

当页表项有效位为0时，至少可能表示两种情况：

1. **页面合法但不在内存中**：页面属于进程，只是当前被换出或尚未加载；
2. **页面不属于进程可管理的已分配范围**：即访问了非法地址`▶ 1:26:50`。

因此，硬件只负责发现“无法正常完成转换”并陷入内核；具体原因需要操作系统在Page Fault处理程序中进一步判断。

### Page Fault及其恢复

无论触发原因是页面不在内存、地址非法、权限保护冲突，还是其他页访问异常，硬件都会统一产生 **Page Fault（页面错误/页面失效）**异常，使CPU从用户态陷入操作系统，并转入相应的页面错误处理程序`▶ 1:28:30`。

> **老师强调**：页面异常不一定意味着真正的程序错误。很多Page Fault只是正常虚拟内存机制中“需要内核介入”的事件，例如缺页时由内核把页面读入内存`▶ 1:28:30`。

对于可恢复的缺页异常，处理流程为：

1. 当前指令触发Page Fault；
2. 硬件保存触发异常的地址和处理器状态；
3. 进入操作系统内核的Page Fault处理程序；
4. 内核判断异常原因：
   - 若页面合法但不在内存，则分配物理页框并从磁盘读入页面，更新页表；
   - 若为权限问题或非法地址，则可能终止进程或发送相应信号；
5. 恢复现场；
6. **重新执行触发Page Fault的那条指令**，而不是直接执行下一条指令。

> **老师强调**：页面异常是可以恢复的。页面读入内存后，要回到触发Page Fault的指令重新执行；由于异常发生时PC可能已经指向后续指令，架构必须借助特殊寄存器保存异常状态和出错地址`▶ 1:29:12`。

在x86相关机制中，老师提到的控制寄存器包括：

- **CR3**：存放当前进程页表的基址；
- **CR4的特定位**：与分页等地址转换机制的启用/控制有关；
- **CR2**：记录触发Page Fault的线性地址，供内核查明是哪个访问导致异常`▶ 1:29:12`。

### 多级页表形式的地址映射

课件还给出了更复杂的地址转换机制：虚拟地址可被拆分成多个索引字段与偏移字段。以两级页表为例：

1. 虚拟地址中的**页目录索引**用于查找页目录项；
2. 页目录项给出对应页表的位置；
3. 虚拟地址中的**页表索引**用于查找页表项；
4. 页表项给出**页框号**；
5. 页框号与页内偏移相加/拼接，得到物理地址。

可以表示为：

```text
虚拟地址
├── 页目录索引 ──→ 页目录项 ──→ 页表
├── 页表索引   ──→ 页表项   ──→ 页框号
└── 页内偏移                     ↓
                           物理地址 = 页框号 + 偏移
```

多级页表使系统不必为整个庞大的虚拟地址空间连续分配全部页表，只有实际使用的地址范围才需要进一步建立下级页表，从而节省页表本身占用的内存。

## 7. TLB快表与地址转换加速

> 课件 第 25–28 页 · 讲解从 `1:31:27` 开始

### 快表（TLB）的引入

**问题背景**
- 使用页表进行地址转换时，需要两次或两次以上的内存访问：第一次访问页表获取物理页号，第二次才能访问目标数据/指令；多级页表（二级、三级、四级）的访存次数更多`▶ 1:31:27`。
- CPU 处理指令的速度远快于内存访问速度，多次访存使 CPU 性能得不到充分发挥`▶ 1:31:27`。

**解决思路**
- 利用**程序访问的局部性原理**，引入快表（TLB）来加快地址映射速度，从而改善系统整体性能。

### 快表是什么

- 快表（TLB，Translation Look-aside Buffers）本质上是一种**相联存储器（associative memory）**，采用 SRAM 实现，支持**按内容并行查找**，速度极快`▶ 1:32:17`。
- TLB 中保存的是**当前正在运行进程页表的一个子集**（部分页表项）。
- 工作原理：采用联想映射技术，按内容同时（并行）查找。
- **作用**：加快虚实地址转换速度，改善系统性能。

**不同架构下的 TLB 设计**`▶ 1:32:17`
- 可分为**指令 TLB（iTLB）**和**数据 TLB（dTLB）**。
- 也可像 CPU 缓存一样分级为 L1、L2、L3 级 TLB。

### 快表的大小与位置

- TLB 容量很小。以酷睿 i7 为例：L1 数据 TLB 约 64 项，指令 TLB 约 128 项，所有各级 TLB 合计约 512 项`▶ 1:34:30`。
- TLB 位于 **MMU（内存管理单元）旁**，与 CPU 集成在同一芯片上`▶ 1:34:30`。

### 快表的置换与刷新

**置换问题**
- 由于 TLB 容量很小，当 TLB 已满而又需要装入新表项时，必须使用**置换算法**淘汰旧表项（相关置换算法已在组成原理、ICS 中学过，后续还会讲解）`▶ 1:36:05`。

**刷新问题（重点）**

> **老师强调**：需要重点掌握 TLB 的刷新问题`▶ 1:36:05`。

- **进程切换导致 TLB 刷新**：传统方式下，上下文切换时会清空 TLB 的全部内容。切换后新进程运行初期会出现连续的 TLB 未命中（miss），直到 TLB 被逐步重新填满后才会出现命中（hit），导致性能下降`▶ 1:36:28`。
- 这属于上下文切换**间接开销**的一部分（间接开销还包括高速缓存 cache 的刷新成本）`▶ 1:36:28`。

**现代解决方案：PCID / ASID**`▶ 1:37:42`
- 现代硬件不再强制在进程切换时清空 TLB，而是为每个 TLB 表项附加一个**进程标识（PID）**：
  - **x86 架构**：PCID（Process Context IDentifier）
  - **RISC-V / AMD 架构**：ASID（Address Space IDentifier）
- 查找 TLB 时需要**同时匹配 PID 与页号标签（tag）**，确保命中的表项确实属于当前进程，从而避免进程切换时对 TLB 进行全量刷新。

### TLB 的使用（地址转换流程）

MMU 拿到虚拟地址后，**并行启动两路查找**`▶ 1:39:56`：

1. 一路用逻辑页号并行查找 **TLB**；
2. 另一路查找内存中的**页表**。

根据查找结果分情况处理：

| 情况 | 处理过程 |
|---|---|
| **TLB 命中** | 立即停止页表查找，直接从 TLB 得到物理地址，快速完成转换`▶ 1:39:56` |
| **TLB 未命中、页表命中** | 继续查页表得到物理地址，同时将该页表项填入 TLB（供后续访问命中）`▶ 1:39:56` |
| **TLB、页表均未命中** | 说明页面不在内存，触发 **Page Fault（缺页异常）**；由操作系统将缺页从磁盘加载到内存、修改页表等相关信息后，重新执行当前指令`▶ 1:39:56` |

- 整个过程中，**TLB 与页表的查找由硬件完成**，**缺页处理由操作系统完成**`▶ 1:39:56`。
- 缺页异常的衔接由 **CR2 寄存器**控制`▶ 1:39:56`。

### TLB 与高速缓存操作

得到物理地址之后，硬件还会继续访问高速缓存 cache（课件示意图简化了多级 cache 结构）`▶ 1:41:54`。

**完整的地址访问流程**`▶ 1:42:37`：

```
虚拟地址
   │
   ▼
并行查找 TLB 与页表  ──(都未命中/权限问题)──▶ 触发 Page Fault，陷入内核，由操作系统处理
   │（命中，得到物理地址）
   ▼
按物理地址访问 Cache
   │
   ├─ Cache 命中：直接获得数据
   └─ Cache 未命中：再访问内存
```

- 先根据物理地址访问 **cache**，未命中时再访问**内存**`▶ 1:42:37`。
- cache 与内存之间的访问全程由硬件完成；只有当 TLB、页表都未命中（或出现权限问题）时，才会触发 Page Fault 陷入内核，交由操作系统接管`▶ 1:42:37`。
- 只要前置环节（TLB、页表、cache）命中，硬件即可快速完成地址转换与数据访问`▶ 1:42:37`。

## 8. 缺页异常处理

> 课件 第 29 页 · 讲解从 `1:43:34` 开始

### 缺页异常的概念

缺页异常是 Page Fault（页错误/页面错误/页故障/页失效）的一种常见处理情形，其含义是：目标页尚未被读入内存，只需将该页调入内存即可完成处理。需要注意的是，"缺页"仅指代 Page Fault 中的这一种具体场景，二者不能完全等同`▶ 1:43:34`。

在地址映射（地址转换）过程中，硬件查询页表时会检查对应页表项的**驻留位**：若发现驻留位为 0，即所要访问的页不在内存中，便产生缺页异常，随即由操作系统执行缺页异常处理程序`▶ 1:44:28`。

### 缺页异常的处理流程

操作系统处理缺页异常的大致步骤如下：

1. **获取磁盘地址**：从当前进程的 PCB（进程控制块）中取得目标页的磁盘地址`▶ 1:45:03`。
   - 老师以之前 Hello World 的示例说明：该示例只完成了地址计算以及与 PCB 的映射关联，并没有实际的页面加载动作，因此访问时会触发 Page Fault`▶ 1:45:03`。
2. **寻找空闲页框并启动磁盘 I/O**：拿到磁盘地址后，CPU 通过 **DMA** 启动磁盘读操作，将目标页调入内存；在调入之前需先在内存中找到一个可用的空闲页框`▶ 1:46:13`。
3. 根据内存中是否有空闲页框，分两种情况处理（见下文）。

> **老师强调**：缺页异常处理流程虽短小，却覆盖了进程管理、内存管理、I/O 管理等操作系统的全部核心模块；读懂这部分代码是学习操作系统源码的关键，相关数据结构都包含在这一流程中`▶ 1:46:51`。

### 情况一：内存中有空闲页框

- 直接分配一个空闲页框；
- 将新调入的页面装入该页框；
- 修改页表中相应页表项：置上**驻留位**，并填写对应的**页框号**`▶ 1:46:51`。

### 情况二：内存中没有空闲页框

此时需要进行**页面置换**：

1. 按某种置换算法选择一个内存中的页面作为**牺牲页**；
2. 检查该牺牲页的修改位（**M 位 / D 位**）：
   - 若修改位为 1，说明该页在内存期间被修改过，需先将它**写回磁盘**；
   - 若未被修改过，则无需写回；
3. 腾出页框后，将其分配给新调入的页面，再更新相应页表项的驻留位和页框号`▶ 1:48:16`。

### 现代系统的补充做法

现代操作系统通常不会等到缺页发生时才发现内存中没有空闲页框，而是通过专门机制**始终维持一定数量的空闲页库存**。老师将其类比为家庭提前备好常备调味品，不会等用完了才去采购；此外系统还会**预取一些页面**，以进一步降低缺页带来的延迟`▶ 1:48:54`。

## 9. 驻留集管理

> 课件 第 30 页 · 讲解从 `1:50:22` 开始

### 驻留集的基本概念

驻留集管理要解决的核心问题是：**给每个进程分配多少个页框？**

- 在早期内存资源紧张时，系统不会按照进程申请的页框数足额分配，因此需要用"驻留集"作为系统为每个进程分配页框数量的指标`▶ 1:50:22`。
- 现代操作系统通常不再严格执行固定配额：进程申请多少页框，一般就分配多少；但系统会维护一个全局可用页框库存的下限，当库存不足时，会从超额占用页框的进程那里回收多余页框`▶ 1:50:22`。

### 驻留集大小的确定依据

驻留集配额的设置依据来自**缺页率与分配页框数之间的统计关系**`▶ 1:51:48`：

- 分配给进程的页框越多，缺页率越低；
- 但当页框数增加到一定程度后，缺页率的下降幅度会变得很小；
- 曲线上对应存在一个 **W 点（即后续要讲的工作集）**，当分配的页框数超过该点后，继续增加页框带来的收益很低`▶ 1:51:48`。

因此，驻留集管理的目标就是在"缺页率"和"内存利用率"之间取得平衡。

### 两种驻留集分配策略

| 策略 | 确定时机/方式 | 调整依据 | 特点 |
|---|---|---|---|
| **固定分配策略** | 进程创建时确定 | 不再动态调整 | 可根据进程类型（交互型、批处理型、应用类），或基于程序员、系统管理员的需要来确定 |
| **可变分配策略** | 运行过程中动态调整 | 根据缺页率评估进程的局部性表现 | 缺页率高 → 增加页框数；缺页率低 → 减少页框数；需要持续监控，存在系统开销 |

可变分配策略的具体调整逻辑：

- **缺页率高**：说明当前页框数不足以覆盖进程的局部工作集合，需要增加页框；
- **缺页率低**：说明进程占用的页框有富余，可以回收部分页框；
- 持续统计缺页率会带来额外的**系统开销**`▶ 1:51:48`。

> **老师强调**：目前主流操作系统采用的是**可变配额策略**，这个机制在系统内部一直存在，只是普通用户难以感知到它`▶ 1:51:48`。

驻留集管理的内容到此结束，接下来进入**页面置换算法**的学习`▶ 1:53:49`。

| 虚拟地址空间 | 操作系统为进程抽象出的地址范围，进程通过其中的虚拟地址访问指令和数据。 |
| 虚拟内存 | 把物理内存与磁盘结合起来形成的大容量逻辑内存，使程序不必全部装入内存即可运行。 |
| 虚拟页式存储管理 | 以页为单位进行虚拟存储管理，访问不在内存的页面时动态调页，必要时置换内存页。 |
| 请求调页 | 进程实际访问到不在内存的页面并触发缺页异常后，才把该页从磁盘调入内存。 |
| 预先调页 | 操作系统在调入所需页面时，提前把相邻或预计将要访问的页面一起装入内存。 |
| 页表项PTE | 记录虚拟页到物理页框映射关系及有效、访问、修改、保护等控制信息的数据结构。 |
| 页框号 | 物理内存中页框的编号，也称为物理页面号、页帧号或PPN/PFN。 |
| 有效位 | 标识页面当前是否驻留内存的控制位，也称为驻留位、Present位或Valid位。 |
| 访问位 | 记录页面是否被访问过的控制位，可供页面置换算法参考，并会被定期清零。 |
| 修改位 | 记录页面装入内存后是否被写过的控制位，也称为Dirty位；置换脏页前通常需要写回磁盘。 |
| 保护位 | 规定页面读、写、执行等访问权限的控制位，权限不匹配会触发Page Fault。 |
| 多级页表 | 把线性页表组织成树形层级结构，只为实际使用的虚拟地址区域分配页表空间。 |
| CR3 | x86中保存当前进程页目录或顶级页表物理基地址的控制寄存器，进程切换时会切换其内容。 |
| 反向页表 | 从物理页框出发建立的全局页表，用PID和虚拟页号共同标识映射关系，其大小主要取决于物理内存容量。 |
| 地址转换 | MMU根据虚拟地址和页表信息找到物理页框号，并与页内偏移拼接形成物理地址的过程。 |
| MMU | 内存管理单元，负责借助页表和TLB完成虚拟地址到物理地址的转换及权限检查。 |
| TLB | 快表是保存近期常用页表项的高速相联存储器，用于减少地址转换过程中的访存次数。 |
| PCID/ASID | 给TLB表项附加地址空间或进程标识的机制，可避免进程切换时简单清空全部TLB。 |
| Page Fault | 硬件在地址转换过程中发现页面不在内存、地址非法或权限不符等情况时触发的异常。 |
| 缺页异常 | Page Fault的一种常见情况，表示目标页面不在内存，需要操作系统从磁盘调入。 |
| 驻留集 | 某一时刻进程实际驻留在物理内存中的页框集合，其大小可固定分配或动态调整。 |
