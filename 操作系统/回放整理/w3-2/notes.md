## 2. 顺序程序、多道程序设计与并发环境

> 课件 第 7–9 页 · 讲解从 `19:41` 开始

### 1、顺序程序与顺序环境

**程序**是指令或语句的序列，体现某种算法。

**顺序环境**指：
- 计算机系统中只有一个程序在运行；
- 该程序独占系统中的所有资源；
- 该程序的执行不受外界影响。

早期六十多年前的计算环境就是串行顺序执行环境，没有并发，一次只执行一个任务，完成一个任务后再执行下一个。此时只需要一个程序计数器 PC，切换任务时只需将下一个程序的第一条指令地址送入 PC 即可`▶ 19:41`。

顺序环境具有以下特征：

| 特征 | 含义 |
| --- | --- |
| 程序执行的顺序性 | 程序按预定的指令次序依次执行 |
| 程序执行的封闭性 | 程序独占全部资源，执行过程不受外界其他程序干扰 |
| 程序执行结果的可再现性 | 只要初始条件相同，最终运行结果与程序的实际执行速度无关 |

> **老师强调**：在单道顺序执行环境中，程序具有封闭性；只要初始条件相同，程序的最终运行结果与实际执行速度无关，结果可以再现`▶ 21:51`。

### 2、多道程序设计（Multiprogramming）

**多道程序设计**是指允许多个程序同时进入内存并运行的技术。

- 其目的是打破单道模式下的资源闲置，提高系统整体效率`▶ 23:35`。
- 多个程序同时驻留内存，使内存管理、资源调度的复杂度显著上升`▶ 23:35`。
- 在只有单块物理 CPU 的硬件环境下，多道程序在内存中同时存在，相当于每个程序拥有一个虚拟 PC；这些虚拟 PC 与物理 PC 之间始终保持映射关系。
- 同一时刻只有一个程序能够获得物理 PC 的映射、真正占用 CPU 运行，其余程序暂时无法执行`▶ 25:03`。

### 3、并发环境与并发程序

**并发环境**：在一段时间间隔内，单处理器上有两个或两个以上的程序同时处于已经开始运行但尚未结束的状态，并且它们的执行次序不是事先确定的。

**并发程序**：在并发环境中执行的程序。

系统通过极快速的 CPU 上下文切换实现并发效果。对单个进程而言，它通常感知不到切换过程，会误认为自己始终独占 CPU 运行`▶ 26:03`。

#### 并发环境的特征

1. **程序执行结果的不可再现性**  
   多个并发程序的指令交错组合数量非常多，程序运行结果可能受执行次序影响；一旦出错，很难再次复现完全相同的执行序列`▶ 28:02`。

2. **程序执行的间断性**  
   程序不会一次性在 CPU 上运行到结束，而是呈现“执行——停——执行”的过程，频繁地在“上 CPU 运行”和“暂停下 CPU”之间交替切换`▶ 28:02`。

3. **资源共享**  
   多个并发程序需要共享内存、文件、CPU 等各类资源`▶ 28:02`。

4. **独立性和制约性**  
   每个进程独立完成自身任务，但进程之间会相互制约，其独立性会受到并发环境影响`▶ 28:02`。

5. **程序和计算不再一一对应**  
   多个程序并发执行、共享和竞争资源后，一个程序的执行过程不再等同于一个完全独立、封闭的计算过程。

> **老师强调**：资源竞争会产生制约。例如地铁空位、高铁最后一个座位，多个主体争抢同一稀缺资源时就会相互制约；操作系统设计必须解决这类问题`▶ 29:44`。

## 3. 进程概念、定义及进程分类

> 课件 第 10–11 页 · 讲解从 `30:27` 开始

### 进程的定义

进程（Process，又称任务 Task 或作业 Job）可以从多个角度理解：

- **程序的一次执行过程**：必须强调"一次"。同一个程序执行两次就是两个进程，类似影院同一正版数字拷贝，每播放一次消耗一次授权，对应一次独立的进程实例`▶ 30:27`。
- **正在运行程序的抽象**：进程本质上是对 CPU 的抽象。通过进程管理，单个物理 CPU 可以虚拟为多个并行的虚拟 CPU，每个进程对应一个虚拟 CPU`▶ 31:54`。
- **资源分配的单位**：操作系统的所有资源（内存、文件等）都以进程为单位分配，每个进程具有独立的地址空间`▶ 31:54`。
- **CPU 调度的对象**：在未引入线程之前，操作系统将 CPU 调度分配给进程`▶ 31:54`。

百科全书式的严谨定义为：

> 进程是具有独立功能的程序关于某个数据集合上的一次运行活动，是系统进行资源分配和调度的独立单位。

对定义中"某个数据集合"的理解：同一个编译器编译两个不同用户的代码，代码内容就是各自进程的专属数据集合，两次编译对应两个独立进程`▶ 33:01`。

> **老师强调**：课件中标色的内容需重点注意`▶ 33:01`。

需要注意的是，定义中"资源分配单位"是通用结论，但"调度单位"要区分场景：现代 Windows 系统中，**进程是资源分配单位，线程才是 CPU 调度的执行单位**，二者分工明确`▶ 33:01`。该定义来源于 1978 年在庐山召开的国内操作系统教学研讨会，由国内老一辈计算机教学工作者讨论制定；随着线程概念的引入，定义后续也有所发展`▶ 35:16`。

### 进程的作用、行为与分类

操作系统的运行架构分为内核与进程两部分。内核之上运行的进程按角色可分为系统进程和用户进程`▶ 36:31`：

| 分类       | 说明                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| **系统进程** | 承担操作系统功能，又称**精灵进程（守护进程）**。平时处于睡眠状态，被唤醒后才执行指定任务。典型例子是打印服务：所有用户的打印请求先进入排队队列，专门的系统进程监视队列，有任务时被唤醒执行打印，无任务时保持睡眠`▶ 38:12` |
| **用户进程** | 以类 Unix 系统为例，所有用户进程都从初始的"老祖宗"进程派生出家族树`▶ 36:31`                                                                      |

这类常驻内存的系统进程是早期的==**资源池化设计**，可以避免临时创建进程的开销==`▶ 39:23`。

按其他维度，进程还可以分类：

- **前台进程 / 后台进程**
- **CPU 密集型进程 / I/O 密集型进程**：按运行特征划分。这一分类以及系统进程优先级（高于用户进程）都是进程调度时的重要参考依据`▶ 39:23`。

### 进程之间的关系

- **UNIX 进程家族树**：以 init（Linux 中为 1 号进程）为根形成进程家族。杀死某个父进程后，其所有子孙进程也会随之终止，进程间关联紧密`▶ 40:16`。
- **Windows**：没有进程家族的概念，各进程地位相同，不存在这种父子绑定关系`▶ 40:16`。

### 进程与程序的区别

- 进程更能准确刻画**并发**，而程序不能。
- 程序是**静态**的，进程是**动态**的。
- 进程有生命周期，有诞生也有消亡，是**短暂**的；程序则相对**长久**。
- 一个程序可以对应多个进程（如同一程序执行两次产生两个进程）。
- 进程具有创建其他进程的功能。

## 4. 进程三种基本状态及转换

> 课件 第 12–13 页 · 讲解从 `40:55` 开始

### 进程的三种基本状态

不同操作系统的进程模型存在差异，但三状态模型是所有操作系统通用的基础模型`▶ 40:55`。

| 状态 | 英文 | 含义 |
|------|------|------|
| 运行态 | Running | 进程占有 CPU，并正在 CPU 上运行 |
| 就绪态 | Ready | 已经具备运行条件，但由于没有空闲 CPU，暂时不能运行 |
| 等待态 | Waiting / Blocked | 因等待某一事件（如完成 I/O）而暂时不能运行 |

关于三种状态的进一步说明：

- **就绪态**：进程在就绪队列中排队，等待被调度上 CPU；调度程序从就绪队列中挑选进程并分配 CPU`▶ 41:46`。
- **等待态**：又称阻塞态、封锁态、睡眠态（Linux、XV6 中多使用"睡眠态"这一称谓）。处于该状态的进程即使 CPU 空闲也无法获得 CPU，必须等待指定事件发生。例如父进程调用 `waitpid()` 等待子进程结束时，父进程就会进入阻塞态；等待读盘结果也是典型场景`▶ 41:46`。

### 进程状态之间的转换

进程在消亡之前，处于且仅处于某一种状态；不同操作系统设置的进程状态数目可能不同。

三个状态理论上存在 6 种转换，但实际只保留 **4 种**`▶ 44:02`：

```
              ① 调度选中
        ┌──────────────────►┐
        │                   │
     就绪态                 运行态
        ▲                   │
        │                   │
        └───────② 时间片到──┘
        ▲                   │
        │                   │ ③ 等待某事件
        │ ④ 事件发生         ▼
        └──────────────── 阻塞态
```

#### 四种合法转换

1. **就绪态 → 运行态**：进程在就绪队列中被调度程序选中，被调入 CPU 运行`▶ 44:02`。
2. **运行态 → 就绪态**：典型原因是**时间片到（超时）**。系统为每个进程分配限定运行的时间片段，运行时间一到就必须让出 CPU，回到就绪队列重新排队，避免单个进程长期独占 CPU，符合多进程并发运行的初衷。类比旋转木马：付费只能获得固定的游玩时长，时间到就必须离场`▶ 45:58`。
3. **运行态 → 阻塞态**：进程需要等待某一事件而主动放弃 CPU。
4. **阻塞态 → 就绪态**：进程等待的事件发生后，被唤醒并进入就绪队列。

#### 两种不存在的转换

> **老师强调**：不存在"阻塞态 → 运行态"，也不存在"就绪态 → 阻塞态"`▶ 44:02`。

- **阻塞态不能直接转为运行态**：阻塞进程等待的事件发生后，必须先进入就绪队列排队，才能获得 CPU，以此保证系统调度的确定性`▶ 44:02`。
- **就绪态不能直接转为阻塞态**：进程只有在运行时才能通过发起系统调用等方式进入阻塞，尚未获得 CPU 的就绪进程没有机会触发等待。

#### 就绪态的作用

进程不能直接占用 CPU，必须先排队，由调度程序决定哪个进程可以上 CPU，从而保证系统运行确定、可控`▶ 45:58`。

### 运行态转阻塞态的原因与完整过程

转换原因主要包括：

- 父进程调用 `wait`（如 `waitpid()`）等待子进程`▶ 47:30`；
- 进程执行慢速 I/O 类系统调用，如 `read`、`write` `▶ 47:30`。

系统调用可分为两类：一类（如 `fork`、`open`）不会导致进程阻塞；另一类属于慢速操作——因为 CPU 加内存的速度远快于 I/O，执行这类调用时进程需要等待`▶ 47:30`。**********

以 A 进程执行 `read` 系统调用为例，完整流程如下`▶ 47:30`：

1. A 进程在运行时发起 `read` 调用，立即暂停，保存硬件现场，通过中断描述符表找到系统调用入口；
2. 内核根据传入的系统调用号，查系统调用表定位 `read` 的处理逻辑，把 I/O 任务交给 DMA 完成；
3. A 进程需要等待 I/O 结果，由**运行态进入阻塞态**，CPU 转去运行其他进程（如 B 进程）；
4. DMA 完成 I/O 后触发中断，操作系统处理中断，发现 A 的 I/O 数据已返回，便将 A 进程**从阻塞态转为就绪态**；之后 A 需在就绪队列中等待调度，才能再次运行。

> **老师强调**：进程的状态转换与中断/异常处理机制密切相关。每次状态切换背后都对应一次中断或异常的处理流程，由该流程决定是否切换进程`▶ 47:30`。

## 5. 创建、终止、挂起及多状态模型

> 课件 第 14–16 页 · 讲解从 `52:07` 开始

### 进程的其他状态

在运行、就绪、阻塞三个基本状态之外，实际操作系统还可能引入创建态、终止态和挂起态。

#### 创建态（New）

- 操作系统已经完成创建一个进程所必要的工作，如分配 PID、建立 PCB。
- 但尚未同意该进程执行，原因通常是系统资源有限。
- 创建态是进程创建后、进入就绪态之前的过渡状态，相当于一道缓冲。
  - 老师用参观故宫作类比：需要先线上预约，但如果当日游客过多，即使已预约也要在门口等候；类似地，当就绪队列负载过重时，刚创建的进程不会直接进入就绪队列，而是停留在创建态，经过“提交”操作后才进入就绪态`▶ 52:07`。
- 创建态并不是所有操作系统都必须设置的，属于部分系统可选实现的状态；它用于在进程同意执行前提前完成准备工作`▶ 53:56 · 1:05:16`。

#### 终止态（Terminated）

- 进程终止执行后进入该状态。
- 在此状态中，系统可以完成一些数据统计工作，并进行资源回收。
- 进程并不是一结束就立刻消失，而是要先完成善后处理，之后才正式消亡。
  - 老师用本科毕业作类比：答辩完成后到领取毕业证之间的间隔期，就相当于终止态`▶ 54:17`。
- 所有主流操作系统都设置了终止态`▶ 54:17 · 1:05:16`。

#### 挂起态（Suspend）

- 挂起是指把一个进程从内存转到磁盘：进程不占用内存空间，其进程映像被交换到磁盘上。
- 引入挂起态的主要目的是调节系统负载。
- 过去内存资源紧张时，系统会把暂时不运行的进程交换到磁盘；进程并未终结，只是被暂停，当后续条件满足时可以再调入内存恢复执行`▶ 1:05:33`。
- 现代系统内存资源通常比较充足，因此这种状态在实际中已经很少使用`▶ 1:05:33`。

### 其他状态进程模型

William Stallings 给出了典型的五状态进程模型和七状态进程模型。

#### 五状态进程模型

在三状态模型基础上新增创建态和终止态：

1. 进程创建完成后停留在创建态；
2. 经过提交操作进入就绪态，加入就绪队列；
3. 调度后进入运行态；
4. 运行过程中可因等待事件进入阻塞态，事件发生后回到就绪态；
5. 时间片用完后由运行态回到就绪态；
6. 进程运行结束后先进入终止态，完成统计、资源回收等善后工作。

除新增的创建、终止状态外，其余状态流转逻辑与三状态模型一致`▶ 1:08:13`。

#### 七状态进程模型

七状态模型在五状态模型基础上增加两类挂起状态：

| 状态 | 含义 |
|---|---|
| 就绪挂起 | 就绪进程被临时换出到磁盘，不参与调度，用于降低就绪队列负载 |
| 阻塞挂起 | 等待事件的阻塞进程被换出到磁盘暂存 |

主要转换关系包括：

- 将就绪队列中过多的进程换出，使其从就绪态转为就绪挂起；
- 阻塞进程可被换出到磁盘，成为阻塞挂起；
- 阻塞挂起进程等待的事件完成后，先转为就绪挂起，之后再按需调入内存成为就绪态；
- 运行态进程时间片超时返回时，如果就绪队列负载过高，也可以直接换出成为就绪挂起`▶ 1:08:41`。

> **老师强调**：七状态模型主要用于内存紧张时的负载调节，在实际系统中很少使用`▶ 1:05:33 · 1:08:41`。

### Linux 进程状态

Linux 的进程状态命名与通用状态模型并不完全相同。

#### 运行相关状态：TASK_RUNNING

- Linux 中的 `TASK_RUNNING` 同时覆盖通用模型中的两种情况：
  - 进程处于就绪态，等待被调度；
  - 进程正在 CPU 上运行。
- 因此，不能简单地把 `TASK_RUNNING` 理解为只表示“正在运行”`▶ 1:10:21`。

#### 阻塞相关状态：睡眠态

Linux 中的阻塞态称为睡眠态，并分为两类：

| 类型 | 特点 |
|---|---|
| 浅度睡眠 | 可以接收信号，并由信号触发状态转换 |
| 深度睡眠 | 不响应外部中断/普通信号，通常等待某些特定事件完成 |

具体实现细节可根据需要查阅相关资料`▶ 1:10:21`。

#### 僵尸态：Zombie

- Linux 的 `zombie`（僵尸态）对应进程结束后仍需完成善后工作的阶段。
- 它与通用模型中的终止态作用相对应：进程已经结束，但相关数据结构或统计信息仍保留，等待父进程或系统回收`▶ 1:11:38`。

#### 停止态：Stop

- `stop` 状态主要用于跟踪和调试。
- 可配合 `ptrace`、`strace` 等调试工具：
  - 插入断点；
  - 跟踪运行流程；
  - 打印运行时状态。
- 进入该状态后，进程暂停执行，便于调试器控制`▶ 1:11:38`。

上述状态及其相互转换共同构成了 Linux 的进程模型`▶ 1:11:38`。

### 模型对比要点

> **老师强调**：学习时要明确各状态队列对应的进入条件，以及触发状态转换的操作`▶ 1:11:38`。

- 三状态模型：运行、就绪、阻塞。
- 五状态模型：在三状态基础上增加创建、终止，用于处理进程创建缓冲和结束善后。
- 七状态模型：在五状态基础上增加就绪挂起、阻塞挂起，用于把进程换出到磁盘以调节负载。
- Linux 模型：状态命名不同，`TASK_RUNNING` 同时表示就绪和运行；阻塞表现为深浅睡眠；`zombie` 对应终止善后；`stop` 服务于调试跟踪。

## 6. XV6进程状态与实验安排

> 课件 第 17 页 · 讲解从 `1:13:00` 开始

### XV6 进程状态模型

XV6 在内核中用枚举 `procstate` 定义进程状态，相关代码位于 `<kernel/proc.h>`，状态转换的实现主要在 `<kernel/proc.c>` 中：

```c
enum procstate {
    UNUSED,
    USED,
    SLEEPING,
    RUNNABLE,
    RUNNING,
    ZOMBIE
};
```

各状态含义如下：

| 状态 | 含义 |
|---|---|
| `UNUSED` | 进程控制块 PCB 未被使用，处于空闲状态 |
| `USED` | PCB 已被分配并完成初始化，对应进程创建前的准备阶段 |
| `SLEEPING` | 睡眠态 / 阻塞态，进程等待某事件发生 |
| `RUNNABLE` | 就绪态，进程已具备运行条件，等待被调度 |
| `RUNNING` | 运行态，进程正在 CPU 上执行 |
| `ZOMBIE` | 僵尸态，进程已退出，但尚未被父进程回收 |

老师指出，SV6 的核心进程状态主要包括四个：`Runnable`（就绪态）、`running`（运行态）、`sleep`（阻塞态）和 `zombie`（僵尸态），它们继承自 Unix/Linux 的进程状态体系`▶ 1:13:00`。

系统启动时会预先批量分配 PCB 并完成初始化，此时 PCB 处于未使用状态；`fork` 操作会把 PCB 从初始状态转换为就绪态。由于这一过程发生在进程正式创建之前，因此属于进程创建的准备阶段，不属于常规进程状态转换；核心的进程状态仍是上述四个`▶ 1:13:00`。

### 状态转换及相关函数

课件给出的状态转换关系可以整理如下：

- `UNUSED → USED`：由 `allocproc` 分配并初始化 PCB
- `USED → RUNNABLE`：
  - `fork` 创建普通子进程后使其可运行
  - `userinit` 创建第一个用户进程
- `RUNNABLE → RUNNING`：由 `schedule` 选择进程并投入运行
- `RUNNING → RUNNABLE`：由 `yield` 主动让出 CPU
- `RUNNING → SLEEPING`：由 `sleep` 使进程进入等待状态
- `SLEEPING → RUNNABLE`：由 `wakeup` 唤醒等待中的进程
- `RUNNING → ZOMBIE`：由 `exit` 终止进程，等待父进程回收
- `ZOMBIE → UNUSED`：父进程回收退出进程后，由 `freeproc` 释放 PCB

## 7. 进程控制块PCB的概念与主要内容

> 课件 第 18–25 页 · 讲解从 `1:16:03` 开始

### 进程控制块 PCB 的基本概念

==PCB（Process Control Block，进程控制块）==又称**进程描述符、进程属性**，是操作系统中表示进程的数据结构。"block"本义指内存中的一块区域，PCB 就是内存中专门存放进程控制相关数据的区域，用于记录进程的各种属性、描述进程的动态变化过程（如状态、优先级、PID、名称等所有相关信息）`▶ 1:16:03`。

- 操作系统通过 PCB 来控制和管理进程。
- **进程与 PCB 一一对应**；PCB 是系统感知进程存在的唯一标志，进程失去 PCB 就无法被系统正常管理`▶ 1:16:03`。
- 类比：PCB 类似学生在校期间跟随四年、持续更新的学籍表；正如要证明某人曾在西南联大就读必须查阅学籍档案，找不到档案就无法确认其身份`▶ 1:16:03 · 1:18:17`。

### 进程表与不同系统中的实现

**进程表**是所有进程 PCB 的集合。系统通常在内存中开辟一段连续空间存放进程表，并预先估算可支持的最大进程数、提前预留对应数量的 PCB 存储空间，而不是动态逐个分配`▶ 1:19:01`。

不同操作系统中 PCB 没有唯一的实现方案，名称各异但含义一致`▶ 1:20:20 · 1:26:55`：

| 系统 | PCB 对应的数据结构 |
|---|---|
| Linux | `task_struct` |
| Windows | `EPROCESS`、`KPROCESS`、`PEB`（内容拆分存放在三个结构中） |
| Solaris | `proc_t`（proc 结构，定义于 `<usr/src/uts/common/sys/proc.h>`） |
| Xv6 | `proc` 结构（`<kernel/proc.h>`） |

> **老师强调**：Xv6 中的 PCB（proc 结构）是后续需要重点学习的内容；但真实场景远比 Xv6 复杂——要考虑调度优先级、权限位、信号处理等问题。Solaris 的相关内容可自行课后查看`▶ 1:31:24`。

### PCB 的主要内容

PCB 记录的信息可分为三大类：==进程描述信息==、==进程控制信息==、==CPU 现场信息==。

#### 1. 进程描述信息

- **进程标识符（process ID, PID）**：唯一，通常是一个整数。
- **进程名**：通常基于可执行文件名，不唯一。
- **用户标识符（user ID, UID）**：标识进程所属用户。
- **进程组关系、父子关系标识**。

#### 2. 进程控制信息

- 当前状态
- 优先级（priority）
- 代码执行入口地址（PC，进程切换时需保存和恢复）`▶ 1:20:55`
- 可执行文件名（磁盘地址）
- 运行统计信息（执行时间、页面调度等）
- 进程间同步和通信信息；阻塞原因
- 进程的队列指针、消息队列指针
- 所拥有的资源和使用情况
- **虚拟地址空间的现状**
- **打开文件列表**

其中两类最重要的资源信息都是 PCB 内嵌的子数据结构`▶ 1:22:07`：

- **地址空间**：创建进程时必须为其分配地址空间。早期直接分配实际物理内存；采用虚拟内存技术后改为"地址承诺"的方式——类似网上预订酒店，预定后到店肯定有房，但具体房号要办理入住时才确定，即进程运行时才真正分配对应的物理内存`▶ 1:28:07`。地址空间的管理结构可用 AVL 树或链表实现：AVL 树查找效率更高，链表实现更简单；地址空间与物理内存之间的映射关系是另一项独立内容`▶ 1:29:14`。PCB 中必须包含可通过 inode 定位磁盘上可执行文件的字段，因为进程是程序执行的载体，缺失该字段就无法关联到对应可执行文件`▶ 1:26:55`。
- **打开文件表**：进程创建时即生成。以 Unix 为例，子进程会继承父进程所有已打开的文件；即使父进程没有打开任何文件，子进程也默认包含三个缺省项——标准输入、标准输出、标准错误输出，对应文件描述符 **0、1、2**`▶ 1:22:07 · 1:30:18`。

#### 3. CPU 现场信息（context，上下文）

这是 PCB 中最重要的一类信息`▶ 1:23:15`，核心是各类寄存器状态：

- 通用寄存器值
- 程序计数器 **PC**
- 程序状态字 **PSW**
- 地址寄存器，如**栈指针**
- 指向赋予该进程的段/页表的指针

当进程暂时不运行（被抢占）时，操作系统把当前寄存器状态保存到 PCB 的现场信息中；下次调度该进程时再将保存的上下文加载回寄存器，进程就能无感知地从断点继续执行。这类似影视拍摄中的**场记**工作：保存当前现场，恢复时无缝衔接`▶ 1:23:15`。

其底层依据是 CPU 的工作循环：从 PC 取地址 → 取指令 → 执行指令，不断往复。操作系统正是通过修改 PC 和寄存器的现场状态，来切换 CPU 执行的内容`▶ 1:23:15`。

### 实例：Solaris、Linux、Xv6 中的 PCB

**Solaris（`proc_t`）**：进程表中的 proc 数据结构包含大量字段，并通过指针关联各子结构，例如[@20页]：

- `p_exec`：可执行文件

- `p_cred`：认证信息

**Linux（`task_struct`，以 2.6.x 为例）**：结构庞大，可按功能分类理解，随版本迭代会有小幅变化`▶ 1:31:24`，主要包括：

- **运行统计与时间**：`utime`、`stime`、`cutime`、`cstime`、`start_time`、各类间隔定时器 `it_real_value` 等、上下文切换计数 `nvcsw/nivcsw` 等

## 8. 进程地址空间与独立虚拟地址

> 课件 第 26–32 页 · 讲解从 `1:33:18` 开始

### 进程地址空间的基本概念

地址空间是操作系统对**内存的抽象**。操作系统不再让进程直接访问物理内存，而是在创建进程时为每个进程分配一个独立的地址空间；正如进程是对 CPU 的抽象，地址空间就是对内存的抽象`▶ 1:33:18 · 1:35:42`。

地址空间是与具体物理内存相映射的抽象空间：进程在自己的地址空间中使用虚拟地址，由操作系统和硬件负责将虚拟地址映射到物理内存位置`▶ 1:35:42 · 1:39:00`。

### 现代操作系统地址空间的四个特点

1. **空间巨大**：具体大小取决于体系结构和操作系统；老师强调需重点记住 Linux x86 与 RISC-V SV6 对应的地址空间尺寸`▶ 1:36:31`。
2. **布局统一一致**：各进程地址空间的总体分段布局相同`▶ 1:36:31`。
3. **安全**：进程之间相互隔离，并通过地址空间随机化等机制提高攻击成本`▶ 1:36:31 · 1:39:00`。
4. **稀疏**：48 位虚拟地址空间中，只有很小一部分地址存放实际内容，其余地址为空；代码段、数据段、栈（通常栈大小约 8MB）占比极小，堆和栈之间有大量空闲区域，可用于放置动态链接共享库、内存映射文件等`▶ 1:36:31 · 1:45:42`。

### 实验：两个进程中的同名变量

程序示例：

```c
int myval;

int main(int argc, char *argv[])
{
    myval = atoi(argv[1]);
    while (1)
        printf("myval is %d, loc 0x%lx\n",
               myval, (long) &myval);
}
```

同时运行两个该程序的实例：

```bash
./Myval 5
./Myval 6
```

- 两个进程中 `myval` 的**值不同**（一个为 5，一个为 6），但打印出的变量**虚拟地址相同**。
- 原因：两个进程各自拥有独立的地址空间；同一程序编译后，编译器会把同一个变量安排在相同的虚拟地址偏移位置。因此两个进程中的 `myval` 虚拟地址相同，却通过各自的映射对应到不同的物理内存，互不影响`▶ 1:39:00 · 1:55:44 · 1:57:25`。

> **老师强调/类比**：同一个小区的不同楼栋都有门牌号为 208 的房间，房间号相同，但属于不同楼栋的独立空间。虚拟地址同理：地址相同，但位于不同进程的独立地址空间中，对应不同物理地址`▶ 1:57:25`。

### ASLR：地址空间布局随机化

在现代系统中重复运行同一程序，变量等对象的地址常常不一样，这是因为启用了 **ASLR（Address Space Layout Randomization，地址空间布局随机化）**：

- 作用：随机调整各段的地址位置，增加黑客预测目标地址的难度，提升攻击成本、增强安全性`▶ 1:39:00 · 1:57:25`。
- 注意：ASLR 只改变各段的具体起始地址，**整体布局顺序保持不变**`▶ 1:44:54`。
- 关闭 ASLR 后，不同进程中同一程序的同一变量会落在地址空间的相同位置`▶ 1:39:00 · 1:57:25`。

关闭命令：

```bash
sudo sysctl -w kernel.randomize_va_space=0
```

> **老师强调**：老式机器没有地址随机化时，相同程序的同一变量虚拟地址完全一致；现代机器关闭随机化后地址也会保持一致，这正体现了虚拟内存的核心思路`▶ 1:57:25`。

### 从源代码到进程地址空间

进程是“一个具有一定独立功能的程序在一个数据集合上的一次执行过程”。其生成与加载过程为：

1. 源代码文件（`.c`）经过**编译、链接**生成可执行文件。
2. 可执行文件内部包含文件头、代码段、初始化数据段等内容。
3. 创建/加载进程时，可执行文件的代码段、数据段等被映射到进程地址空间对应区域；堆、栈则在运行时动态生成`▶ 1:42:43 · 1:43:32`。

加载时的重要细节：操作系统**不会立刻把可执行文件内容真正全部读入物理内存**，而是先定位可执行文件，分别为代码段、数据段建立独立的内存区域（area）映射，按需加载`▶ 1:43:32`。

### 进程地址空间的布局

每个进程的地址空间都有统一、固定的分段布局，从低地址到高地址依次包含：

| 区域   | 说明                                     |
| ---- | -------------------------------------- |
| 代码段  | 存放程序代码，对应可执行文件的代码部分                    |
| 数据段  | 存放初始化数据/全局变量，如示例中的 `myval`（`my_value`） |
| 堆    | 运行时动态增长，用于动态内存分配                       |
| 空闲区域 | 堆、栈之间的大片稀疏地址空间，可放置共享库、内存映射文件等          |
| 栈    | 运行时动态生成，用于函数调用、局部变量等，通常约 8MB           |
| 其他内容 | 共享库、内存映射文件等                            |

整体虚拟地址空间分为两大部分：

- **用户地址空间**：位于低地址部分（从 `0x0000……` 开始），存放用户进程的代码段、数据段、堆、栈、共享库等；全局变量 `myval` 即位于用户空间的数据段`▶ 1:44:54`。
- **内核地址空间**：位于高地址部分（到 `0xFFFF……`），由操作系统占用`▶ 1:44:54`。

进程执行时，`PC` 指向代码段中的指令，`SP` 指向当前栈位置，分别支撑取指执行与函数调用栈管理。

可通过以下命令查看某个实际进程的地址空间各段映射：

```bash
cat /proc/PID/maps
```

## 9. 虚拟内存区域、maps与Linux虚拟内存组织

> 课件 第 33–35 页 · 讲解从 `1:46:30` 开始

### 从一个实验观察进程地址空间

下面的程序用于观察进程的虚拟内存布局：

```c
#include<stdio.h>
#include<stdlib.h>
int main() {
    printf("hello, world!");
    int *a = malloc(sizeof(int));
    getchar();
    return 0;
}
```

它满足三个条件：

- **用到了堆**：`malloc(sizeof(int))` 会在堆上分配内存；
- **用到了常量**：`"hello, world!"` 是字符串常量；
- **进程不会自动退出**：`getchar()` 使进程阻塞，方便查看其内存映射。

程序运行后，通过 `/proc/<pid>/maps` 可以查看该进程的虚拟内存区域`▶ 1:48:10`。

### /proc/pid/maps

`/proc/<pid>/maps` 用于显示一个进程当前==映射的内存区域及其访问权限==。

每一行描述一个虚拟内存区域（VMA, Virtual Memory Area），典型格式为：

```text
起始地址-结束地址  权限  偏移量  设备  inode  映射文件
```

以上面程序中的几行为例：

```text
00400000-00401000 r-xp 00000000 fc:01 925064  /root/tmp/hello
00600000-00601000 r--p 00000000 fc:01 925064  /root/tmp/hello
00601000-00602000 rw-p 00001000 fc:01 925064  /root/tmp/hello
00c0b000-00c2c000 rw-p 00000000 00:00 0       [heap]
...
7ffc47264000-7ffc47285000 rw-p 00000000 00:00 0  [stack]
```

各字段含义：

| 字段 | 含义 |
|---|---|
| `00400000-00401000` | 该虚拟内存区域的起始、结束地址 |
| `r-xp` | 访问权限：读、写、执行、是否共享 |
| `00000000` | 在映射文件中的偏移量 |
| `fc:01` | 文件所在设备号 |
| `925064` | 文件 inode |
| `/root/tmp/hello`、`[heap]`、`[stack]` | 映射来源或区域名称 |

权限位中：

- `r`：可读；
- `w`：可写；
- `x`：可执行；
- `p`：私有映射（private）；若为 `s` 则表示共享映射（shared）。

例如代码段权限为 `r-xp`，即可读、可执行但不可写；数据段可能是 `r--p` 或 `rw-p`，不可执行。

### 实验中观察到的地址空间布局

从 maps 的输出可以看到一个典型 Linux 进程的虚拟地址空间布局：

1. **低地址：程序自身的代码段和数据段**
   - `00400000` 附近是可执行文件 `hello` 的映射；
   - `r-xp` 区域是代码段；
   - `r--p` 区域是只读数据部分；
   - `rw-p` 区域是可写数据部分。

2. **随后是堆**
   - `[heap]` 区域权限为 `rw-p`；
   - `malloc` 分配的内存位于该区域。

3. **中间大片区域：共享库和动态映射区**
   - 可以看到 `libc-2.17.so`、`libdl-2.17.so`、`ld-2.17.so` 等共享库；
   - 每个共享库通常也分成代码段、只读段、可写数据段；
   - 这部分空白区域还可用于 `mmap`，将文件或其他对象映射进进程地址空间`▶ 1:48:10`。

4. **高地址附近：栈**
   - `[stack]` 区域权限为 `rw-p`；
   - 用于函数调用栈、局部变量等。

5. **特殊区域**
   - `[vdso]`、`[vsyscall]` 是内核提供的特殊映射区域，用于加速部分系统调用或提供相关信息。

> **老师强调**：低地址起为代码段、数据段，之后是堆；高地址附近为栈；中间大片空闲区域用于存放共享库，也可以通过 memory map 映射大文件`▶ 1:48:10`。

### 有名映射与匿名映射

==一个文件==可以映射到进程的某段虚拟内存区域中。映射时，==相关文件描述符==保存在描述该区域的结构体中，这种区域称为**有名内存区域**。

与之对应，==没有关联具体文件的映射==称为**匿名映射内存区域**。

在 maps 中可以这样大致区分：

- 行末带有文件路径，如 `/usr/lib64/libc-2.17.so`、`/root/tmp/hello`，通常是有名映射；
- 行末没有文件路径，或标记为 `[heap]`、`[stack]` 的区域，通常属于匿名映射或特殊匿名区域。

### 为什么不用大数组管理虚拟地址空间

现代体系结构下虚拟地址空间非常大，例如 48 位地址空间包含 $2^{48}$ 个地址。若为每个虚拟页都分配一个数组项，需要巨大的存储空间，甚至根本无法分配`▶ 1:46:30`。

因此 Linux 采用类似**稀疏矩阵**的管理思想：

- 不为整个地址空间连续分配表项；
- ==只为真正有内容的区域建立描述结构==，例如代码段、数据段、堆、栈、共享库映射区等；
- 每个结构==记录该区域的起始地址和结束地址==；
- 再把这些结构==组织成链表、AVL 树或其他便于查找的数据结构== `▶ 1:46:30`。

这样，稀疏的地址空间只需要描述已经使用的区间。

### vm_area_struct：虚拟内存区域描述符

在 Linux 内核中，进程的一段独立虚拟地址空间由 `vm_area_struct` 描述。它表示一个具有连续地址范围和统一属性的虚拟内存区域 `▶ 1:52:09`。

其核心信息包括：

1. **区域起始地址和结束地址**
   - 描述该 VMA (Virtual Memory Area) 在整个虚拟地址空间中的范围；
   - 例如某个代码段从 `0x400000` 到 `0x401000`。

2. **链表指针**
   - 用于将进程的多个虚拟内存区域串联起来；
   - 所有区域可保存在 `task->mm->mmap` 链表中。

3. **protection 保护权限字段**
   - 描述区域是否可读、可写、可执行；
   - 例如代码段可执行，数据段不可执行，只读段不可写`▶ 1:52:09`。

4. **flags 标志字段**
   - 描述区域的其他属性；
   - 课件中说明该部分后续再讲`▶ 1:52:09`。

5. **映射文件信息**
   - 如果是有名映射，`vm_area_struct->vm_file` 域保存所映射文件的相关信息；
   - 匿名映射则没有对应的普通文件映射。

### Linux 中进程虚拟内存的组织结构

进程的进程控制块（PCB，在 Linux 中对应 `task_struct`）中有一个内存管理指针 `mm`，即：

```text
task_struct -> mm_struct
```

`mm_struct` 是进程的地址空间管理结构，其中包含：

- 指向虚拟内存区域链表的指针，即课件中的 `task->mm->mmap`；
- 其他用于组织 VMA 的数据结构，例如树结构；
- 顶级页表指针，即多级页表中顶级页表的地址`▶ 1:53:45 · 1:54:34`。

组织关系可以概括为：

```text
PCB(task_struct)
    |
    v
mm_struct
    |--------------------------------|
    v                                v
VMA 链表 / AVL 树               顶级页表指针
    |
    v
vm_area_struct -- vm_area_struct -- vm_area_struct ...
(代码段)          (数据段)          (堆/栈/共享库...)
```

### 为什么除了链表还要使用树结构

使用链表可以顺序管理各个 VMA，但当通过 `mmap` 申请一段新的虚拟地址空间时，内核必须先查找这段地址是否已经被占用`▶ 1:53:45`。

- 链表查找需要逐个区域检查，效率较低；
- AVL 树等平衡二叉树可以按照地址范围快速检索，效率远高于链表`▶ 1:53:45`。

> **老师强调**：这部分结构与 ICS 课程内容关联，非常重要；自己实现时可以使用链表或二叉树完成`▶ 1:55:00`。

### 页表指针与进程切换

`mm_struct` 中还包含顶级页表指针，即四级页表的顶级页表地址`▶ 1:54:34`。

- 进程正在 CPU 上运行时，顶级页表基址会存放在 CPU 的专用寄存器中；
- 当进程被换出 CPU 时，该信息保存在 PCB 相关的内存管理结构中；
- 当进程再次被调度运行时，操作系统==恢复其页表基址，使地址翻译重新指向该进程自己的页表==。

### mmap：利用中间空闲区域映射文件

进程地址空间中间的大片空闲区域可==通过 `mmap` 建立新的内存映射==。使用内存映射后，大文件可以直接映射到虚拟内存区域，而不必先通过普通 `read` 把整个文件读入内存缓冲区`▶ 1:48:10 · 1:51:04`。

对于需要处理大文件的任务，例如排序：

- 传统方式需要反复进行文件读写和数据复制；
- mmap 方式可以==像访问内存一样访问文件内容==；
- 缺页时由操作系统把所需文件页加载进内存；
- 因而可以避免一次性读入整个文件，并减少数据拷贝，提高效率`▶ 1:51:04`。
