## 2. 缺页异常与地址转换回顾

> 课件 第 41 页 · 讲解从 `11:35` 开始

### 地址空间与地址转换

- CPU 执行程序时使用和获取的是**虚拟地址（Virtual Address）**，虚拟地址不能直接用于访问物理内存，必须经过**地址转换（地址翻译）**。
- **虚拟地址空间（VM, Virtual Memory）**与**物理内存空间（PM, Physical Memory）**是两个相互独立的地址空间。

### 地址转换的硬件机制

- 地址转换由 **MMU（Memory Management Unit，存储管理单元）**完成。
- CPU 将虚拟地址交给 MMU，MMU 依据存放在内存中的**页表**完成虚拟地址到物理地址的转换。
- **TLB（Translation Lookaside Buffer，转译后备缓冲器）**位于 MMU 内部，用于缓存近期使用的地址转换结果，加速地址转换过程。

### 缺页异常（Page Fault）的触发逻辑

1. CPU 发出虚拟地址给 MMU 请求转换。
2. MMU 查 TLB；TLB 未命中则查页表。
3. 若该指令（或数据）所在的虚拟地址**尚未映射到物理内存**，对应页面仍只存在于虚拟地址空间中（例如页面在外存），MMU 由硬件发现该问题并触发 **Page fault（缺页异常）**事件。
4. 触发异常后进入**内核态**，由操作系统接管并完成后续处理（如将所需页面从磁盘调入物理内存、更新页表等），处理完成后再恢复原指令的执行。

> **老师强调**：缺页异常是"硬件发现问题、陷入内核、由操作系统完成处理"的动态过程；进程执行、文件打开、I/O 等操作也都是类似的动态流程，需要重点理解这种动态性`▶ 13:39`。

## 3. Hello World程序的执行流程

> 课件 第 95–99 页 · 讲解从 `15:29` 开始

### Hello World 程序的执行流程

本章通过一个最简单的 Hello World 程序，观察操作系统在其执行全过程中扮演的角色。核心抓住三个关键点：**操作系统具备相应功能、向用户提供服务、运行过程中涉及 CPU 状态（用户态/内核态）的转换**`▶ 15:29`。

示例程序：

```c
#include <stdio.h>
int main(int argc, char *argv[])
{
    puts("hello world");
    return 0;
}
```

其中 `puts`（最终触发 write 类系统调用）和 `return`（退出进程）都属于系统调用，需要操作系统参与完成`▶ 16:03 · 38:51`。

> **老师强调**：思考"该程序执行时第一条指令是什么？是 main 函数中的代码吗？"这是一个思考题，可以使用 ICS 课程要求掌握的 `objdump`（object dump）工具反汇编可执行文件自行探究——实际上程序入口在 main 之前还有启动代码（如 `_start`）`▶ 16:44`。

---

### 完整执行步骤

#### 第一步：用户请求执行程序（用户态）

用户需要先告知操作系统要执行 Hello World 程序，常见方式有`▶ 17:55`：

- 最传统的方式：编译生成可执行文件后，在命令行（shell 提示符）下输入文件名并回车；
- 通过图形界面菜单点击；
- 在 IDE 环境中选择运行。

shell 是运行在**用户态**的操作系统交互接口。用户发起请求后，流程交由操作系统接管`▶ 18:59`。

#### 第二步：操作系统查找并解析可执行文件（内核态）

操作系统通过**文件系统**（负责磁盘抽象）根据文件名在磁盘上查找该文件，并完成以下工作`▶ 18:59`：

1. **检查文件类型**：确认它是合法的可执行文件。可执行文件有固定的格式要求，本课程以 Linux 为背景，采用 **ELF（Executable and Linkable Format）** 格式`▶ 20:26 · 20:52`。
2. **解析头部（header）**：
   - 各类数据结构开头通常设有 header，用于记录整体结构和各字段信息；
   - header 中存放的**魔数（Magic Number）**是判断文件是否为可执行文件的关键依据`▶ 21:37`。
3. **定位代码与数据**：根据 header 找到文件内的 section table / program table，从中确定代码段、各类数据段（只读数据段、普通数据段、BSS 段等）的起始位置与长度，计算出对应的运行地址，并换算出它们在可执行文件中的位置及对应的磁盘块地址，存放到指定位置`▶ 22:55`[课件]。

> 这些预先算出的磁盘位置信息，会在后面缺页异常读盘时被使用`▶ 32:25`。

#### 第三步：创建进程并建立映射（内核态）

- 程序必须依托**进程**才能运行。操作系统创建一个新进程，并将 Hello World 可执行文件**映射**到新建进程的 **PCB（进程控制块）**中，表示由该进程执行该程序`▶ 24:26`。
- 通过这个映射，运行时可以按需从磁盘把代码和数据加载到内存（涉及"可执行文件如何映射到进程"这一问题）`▶ 24:26`。

#### 隐藏的关键环节：进程调度

> **老师强调（课件重点）**：创建进程之后**并不会立刻执行**，而是统一进入**进程调度**环节。课件上标注红色箭头与问号的地方，正是要大家理解这个隐藏的调度环节`▶ 28:13`。

- 调度器若选中 Hello World 进程，就为它设置 CPU 上下文；若选中其他进程，则为其他进程设置上下文`▶ 28:13`。
- 若调度程序选中该进程，操作系统为其设置 **CPU 上下文（context）**，把程序起始地址写入 **PC（程序计数器）**，CPU 即可自动取指执行`▶ 26:20`。
- 下一个指令周期，CPU 到跳转后的目标地址取指执行，这一动作称为"跳道"；它只是描述跳转动作，并非物理实体概念`▶ 27:53`。

#### 第四步：执行第一条指令，触发缺页异常（异常处理在内核态）

- 由于此时可执行文件的虚拟地址尚未映射到物理内存，执行第一条指令**一定会触发缺页异常（page fault）**`▶ 28:13`。
- 触发异常的**瞬间进程仍处于用户态**，进入异常处理后才切换到**内核态**`▶ 30:45`。

缺页异常的处理过程：

1. 操作系统**内存管理模块**分配一页物理内存；
2. 利用第二步预先算出的代码位置（文件位置 + 相对偏移），**按页粒度**将代码从磁盘读入内存；每次读入几页由系统策略决定`▶ 32:25`。
3. 处理完成后，**回到触发异常的那条指令重新执行，而不是执行下一条指令**。因为 CPU 取指时 PC 已自动更新为下一条指令地址，所以硬件会把触发异常指令的相关上下文压栈保存，以便事后取回该地址重新执行（不同架构压栈保存机制有差异）`▶ 32:25`。

> 对 Hello World 这种极小的程序，一页物理内存就能容纳全部代码，只需一次缺页处理；大型程序则需要多次触发缺页中断，逐页把代码读入内存`▶ 32:25`。

#### 第五步：执行 puts 输出字符串（用户态发起系统调用 → 内核态处理）

程序执行 `puts`（write 系统调用）向显示器写字符串，程序本身在用户态，一旦执行系统调用就切换到内核态`▶ 35:40`。显示输出的完整链路为：

1. 操作系统确定输出目标为**标准输出**，该设备通常由一个专门的进程管理，内核将要写的字符串送给该进程`▶ 36:21`[课件]。
2. 控制设备的进程把字符串**转换成像素**，将像素（含颜色、亮度、位置、视觉效果等信息）写入设备的存储映像区——**帧缓冲区（frame buffer）**[@课件]。
3. 与显示器交互只需要两类信息：**显示命令**和**显示数据**。无论像素屏、LED、激光等何种显示设备，都有共同的显示缓冲区，只要把数据写入缓冲区即可`▶ 36:52`。
4. 视频硬件把像素转换成显示器可接收的视频信号；信号经接口传到显示器，显示器解码并控制 LED 发光，以一定刷新率动态更新[@课件]`▶ 36:52`。
5. 最终我们在屏幕上看到 "hello world"。

随后程序执行 `return` 系统调用（退出进程），同样需要切换到内核态处理后再返回`▶ 38:51`。

---

### 各步骤运行状态与参与模块

| 步骤 | 主要工作 | 运行状态 |
|---|---|---|
| 第一步 | shell 接收用户执行请求 | 用户态 |
| 第二步 | 文件系统查找、校验、解析可执行文件 | 内核态 |
| 第三步 | 创建进程、建立可执行文件到进程的映射 | 内核态 |
| （调度） | 调度器选中进程、设置 CPU 上下文 | 内核态 |
| 第四步 | 执行第一条指令触发缺页异常 | 触发瞬间用户态，异常处理在内核态 |
| 第五步 | puts/write 系统调用输出字符串 | 用户态发起，内核态处理 |

> **老师强调**：哪怕是 Hello World 这样极小的程序，操作系统的**文件管理、进程管理、内存管理**三大功能模块也全部参与；此外还涉及进程调度和 I/O。这正说明操作系统各核心模块是协同工作的`▶ 30:45 · 38:51`。

---

### 结论：两种视角看执行过程

从整个流程可以归纳出操作系统与用户程序之间的关系：

- **程序视角**：Hello World 在运行中不断地在**用户态与内核态之间切换**——执行普通指令时在用户态，发起系统调用或发生异常时进入内核态，由操作系统提供服务后再返回用户态，如此反复`▶ 38:51`。
- **操作系统视角**：操作系统通过**调度**让 Hello World 进程获得 CPU 执行；运行中分别由进程管理、内存管理、文件系统等模块提供支持并返回`▶ 38:51`。

两种视角本质一致：用户程序通过系统调用不断请求操作系统服务，操作系统在服务与调度之间完成状态切换，这就是一个程序从启动到输出的完整执行图景。

## 4. Windows操作系统体系结构

> 课件 第 100–104 页 · 讲解从 `40:31` 开始

### 典型的操作系统架构

典型的操作系统包括 Windows、Linux、Android 等，本章以 Windows 架构为例介绍操作系统的典型体系结构。Windows 的核心架构早在 1988 年就已确定，其最核心的特征是清晰划分了**用户态（user mode）**和**内核态（kernel mode）**的分界线，系统在运行过程中会反复在这两种状态之间切换`▶ 40:31`。

Windows NT 最初采用了当时流行的**微内核设计理念**：把大量非核心功能模块放在用户态实现，而不是放入内核中`▶ 40:31`。

> **老师强调**：Windows 95/97/98 时期图形界面体验出色，但底层技术口碑不足。微软为证明技术实力曾采用微内核架构，将图形界面相关功能放在内核态之外；但图形操作需要频繁进出内核，会显著降低运行性能，最终又改回原有架构（把图形与窗口相关模块放回内核态）。架构分层图中的色彩标识是有专门设计依据的`▶ 42:54`。

### Windows 体系结构的分层

Windows 操作系统的体系结构大致可分为用户态、内核态和物理硬件三部分，自下而上、自外向内的主要组成如下：

| 层次 | 组成部分 | 说明 |
|---|---|---|
| 物理硬件 | 计算机硬件 | 操作系统运行的基础平台 |
| 内核态 | 硬件抽象层（HAL） | 封装所有与硬件相关的信息 |
| 内核态 | 设备驱动程序（device and file system driver） | 对设备和文件系统的抽象，并不直接对应硬件 |
| 内核态 | 内核（kernel） | 进程调度、上下文切换等最核心机制，其中部分模块与硬件强相关 |
| 内核态 | 执行体（executive） | 提供各类操作系统功能服务 |
| 内核态 | 系统服务分发器 | 接收用户态请求，判断并分发到具体的内核功能处理 |
| 内核态 | 图形与窗口 | 管理图形界面和窗口（性能原因放入内核态） |
| 内核态 | 内核态可调用接口 | 供内核侧使用的调用接口 |
| 用户态 | 系统进程、服务进程 | 提供系统管理和后台服务 |
| 用户态 | 用户进程、环境子系统 | 运行业务应用，提供不同子系统环境 |
| 用户态 | 动态链接库（DLL） | 应用程序与操作系统之间的重要接口形式 |

### 硬件抽象与可移植性

操作系统是运行在硬件之上的**第一层软件**，必须和硬件打交道；但不能让所有功能都直接绑定硬件，否则一旦更换硬件平台（例如从 x86 切换到 RISC-V、龙芯），几乎所有功能都要修改`▶ 44:05`。

因此，操作系统设计的核心思路之一是**易移植性**。为实现跨硬件适配，Windows 专门设置了**硬件抽象层（HAL, Hardware Abstraction Layer）**，把所有和硬件相关的信息都封装在该层中。这是操作系统最基础的设计原则之一`▶ 44:05`。

需要注意，Windows 架构中与硬件相关的部分不止 HAL`▶ 45:15`：

- **设备驱动程序（device and file system driver）**：本质上是一种抽象设计，并不直接对应具体硬件；
- **内核模块（kernel）**：其中的进程调度、上下文切换模块也必然和硬件强相关；
- 除上述部分外，其余模块均与具体硬件平台无关`▶ 45:15`。

### 系统调用与请求处理路径

从抽象视角看：硬件之上包裹着操作系统，而应用程序与操作系统之间的统一接口就是**系统功能调用（系统调用）**`▶ 47:02`。

系统功能调用的具体形式包括：

- 动态链接库（DLL）；
- 系统调用等`▶ 47:02`。

其作用是连接应用程序与操作系统：应用程序按照接口规范提交请求后，请求从用户态进入内核态，由专门的**系统服务分发器**判断该请求应由内核的哪个具体功能处理；随后操作系统按照既定路径完成服务，内核侧最终通过调度实现进程切换`▶ 47:02`。

整体关系可以概括为：

```text
应用程序
   │  系统功能调用（DLL、系统调用等）
   ▼
操作系统（用户态 → 内核态：分发、执行体、内核、驱动、HAL）
   │
   ▼
计算机硬件
```

> **老师强调**：用户态与内核态的明确划分、硬件抽象层带来的可移植性，以及系统调用作为应用与内核之间的统一接口，是理解 Windows（以及一般操作系统）体系结构的三条主线`▶ 40:31 · 44:05 · 47:02`。

## 5. UNIX与Linux内核架构

> 课件 第 105–110 页 · 讲解从 `48:34` 开始

### UNIX 架构与内核结构

UNIX 是经典操作系统，其架构自诞生至今没有大的改动。早期架构图常以同心圆绘制，现在多画为分层结构：

1. **最内层：硬件**；
2. **硬件之外：操作系统内核（Kernel）**；
3. **内核外侧：系统调用接口（System Call Interface）**；
4. 系统调用接口之上是用户程序及各类库、应用等。

这种结构体现出操作系统对硬件的封装：用户程序不能直接操作硬件，而是通过统一的系统调用接口请求内核服务`▶ 48:34`。

### UNIX 操作系统内核模块

Kernel 的核心模块划分与《操作系统三本经典》中的主线一致，主要包括：

| 核心主题 | 对应内核模块 | 作用 |
|---|---|---|
| 虚拟化 | 进程管理、虚拟内存、CPU 调度 | 为进程提供独占处理器和内存的抽象 |
| 并发 | 同步、互斥、进程/线程调度等 | 管理多个执行流的并发执行 |
| 持久化 | 文件系统 | 管理磁盘等持久存储设备上的数据 |

UNIX 最初就将**进程控制与内存管理**放在紧密相关的模块中，因为内核存在的核心意义就是支撑进程运行；进程是运行实体，而运行必然依赖内存`▶ 49:15`。

进程管理通常涉及：

- 进程创建与终止；
- 进程调度；
- 进程间通信（IPC）；
- 进程状态管理等。

内存管理通常涉及：

- 物理内存管理；
- 虚拟内存；
- 地址映射；
- 内存分配与回收等。

> **老师强调**：学习时可以把进程和内存拆开讲解，例如先学进程创建，再学调度和内存管理，但不能把二者完全割裂看待。进程运行必然依赖内存，这是冯·诺依曼体系结构的基本常识`▶ 50:48`。

### 文件系统与设备管理

从系统分层看，**文件系统位于内核较上层**，是对磁盘等存储设备的抽象管理；磁盘本身属于设备层范畴`▶ 52:23`。

Linux 早期将 I/O 设备主要分为两类：

| 设备类型 | 传输单位与特点 | 例子 |
|---|---|---|
| 字符设备 | 以字符为单位，低速传输 | 老式针式打印机 |
| 块设备 | 以数据块为单位，高速传输 | 磁盘 |

不同 I/O 设备的速度差异很大。为了平衡慢速设备与上层访问需求之间的差距，操作系统引入了**软件缓存（buff/cache）**：先把从磁盘读出的大量数据暂存在内存缓存中，再按需提供给上层使用。这是操作系统中缓存思想的早期实现之一`▶ 52:23`。

课堂还提出一个可课后探究的问题：计算机组成原理中的硬件缓存（如 L1、L2 Cache）与 UNIX 系统中的软件缓存相比，究竟哪一个提出得更早？UNIX 诞生于 20 世纪 60 年代，但该问题老师未作考证，可进一步查阅资料`▶ 54:19`。

### Linux 架构

Linux 采用**紧凑的模块化内核架构**，各内核模块之间存在明确的调用关系，而不是彼此完全独立`▶ 1:04:58`。

其核心结构可概括为两层：

1. **上层：面向用户态的系统调用接口**  
   - 是所有类 UNIX 系统进入内核的统一入口；
   - 用户程序通过 `fork`、`read`、`write` 等系统调用请求内核服务。

2. **底层：硬件相关模块**  
   - 包括与具体体系结构相关的代码，例如 x86 架构支持；
   - 包括中断处理、设备访问等底层机制；
   - 系统调用最终需要经由这些底层机制完成实际执行`▶ 1:04:58`。

在系统调用接口与硬件相关层之间，Linux 内核还包含进程管理、内存管理、文件系统、设备驱动、网络协议栈等核心组件。它们共同向上提供统一服务，向下屏蔽硬件差异。

### Linux 内核组件

可按功能将 Linux 内核组件理解为：

- **系统调用接口**：用户态进入内核态的统一边界；
- **进程管理模块**：负责进程创建、调度、退出和 IPC 等；
- **内存管理模块**：负责物理内存、虚拟内存和地址空间管理；
- **文件系统模块**：负责文件、目录及持久化数据管理；
- **设备驱动模块**：负责控制字符设备、块设备及其他硬件设备；
- **网络模块**：实现网络协议和网络 I/O；
- **缓存模块**：通过 buffer/cache 缓和磁盘等设备的速度差异；
- **体系结构与中断相关代码**：处理特定硬件平台、异常和中断。

其中，进程与内存紧密耦合，文件系统建立在块设备和设备驱动之上，系统调用则为用户态提供统一入口。

### xv6 与 Linux 内核模块/分层的异同

xv6 是本课程的重点阅读对象，其与 Linux 的架构差异示意图可作为参考`▶ 1:04:58`。

| 比较方面 | xv6 | Linux |
|---|---|---|
| 设计目标 | 教学用、结构简洁、便于阅读 | 实用、通用、功能完整 |
| 系统调用接口 | 提供少量核心系统调用 | 系统调用丰富，兼容类 UNIX 接口 |
| 内核结构 | 模块少，分层和调用关系清晰 | 紧凑的模块化架构，模块多、调用关系复杂 |
| 进程与内存管理 | 实现基本的进程、调度和虚拟内存机制 | 支持复杂调度、多种内存管理机制和大量进程特性 |
| 文件系统 | 简单文件系统，适合理解基本原理 | 支持多种文件系统和复杂缓存机制 |
| 设备支持 | 仅支持少量教学所需设备 | 支持大量设备驱动和硬件平台 |
| 硬件相关层 | 范围小、易理解 | 包含复杂的体系结构相关代码和中断处理 |
| 学习价值 | 适合完整阅读内核主线代码 | 适合理解真实工业级内核的组织方式 |

二者的共同点是：都属于类 UNIX 内核，都以**系统调用接口作为用户态进入内核的统一入口**，并在内核中实现进程、内存、文件系统、设备和中断等基本机制；区别主要在于规模、复杂度和工程完备程度`▶ 1:04:58`。

### Android 操作系统架构

Android 是移动设备主流操作系统之一，采用分层架构，自底向上分为四层：Linux 内核层、系统运行库层、应用程序框架层、应用程序层。

#### 1. Linux 内核层

Android 的底层是经过裁剪和修改的 Linux 内核，并不是原封不动的标准 Linux 内核`▶ 1:07:05`。谷歌针对移动设备特点进行了专门扩展：

该层包含一个 C/C++ 库集合，供 Android 系统的各个组件使用，例如：

- 3D 图形库；
- SQLite 轻量级数据库；
- 媒体库等。

老师特别指出，**Runtime 运行时系统是 Android 的核心**。谷歌搭建好运行时之后，再向上提供应用程序框架，使应用开发者不必直接处理底层细节`▶ 1:08:35`。

#### 3. 应用程序框架层

开发者可以完全使用核心应用程序所使用的框架 APIs。该层提供：

- 内容提供者（Content Provider）；
- 资源管理器（Resource Manager）；
- 以及 Activity 管理、通知管理等通用开发组件。

应用框架降低了 APP 开发门槛：开发者按照框架规范开发，即可将应用发布到应用商店供用户下载`▶ 1:08:35`。

> **老师强调**：Android 凭借更低的应用开发门槛建立了完善的开发生态。2010 年代，Android 与苹果 iOS 是移动端两大主流系统，较低的开发门槛吸引了大量开发者参与应用开发`▶ 1:08:35`。

#### 4. 应用程序层

该层面向最终用户，包含系统自带应用和第三方应用，例如电子邮件、短信、日历、地图、浏览器和联系人管理等。

OpenHarmony 是鸿蒙系统的开源版本。鸿蒙系统可以分为开源的 OpenHarmony 和商用版本，整体同样采用分层架构`▶ 1:10:07`。

- **分布式任务调度**；
- 文件、网络、安全等系统基础能力。

> **老师强调**：分布式软总线是鸿蒙最具特色的架构之一，是 OpenHarmony 分布式能力的重要基础，感兴趣可以自行查阅相关资料`▶ 1:10:07`。

应用层包括：

## 7. 操作系统的地位、名称演化与主要工作

> 课件 第 120–128 页 · 讲解从 `1:15:08` 开始

### 操作系统的地位

从计算机系统的层次结构来看，操作系统位于硬件之上、应用程序之下，是软硬件之间的关键中间层：

| 层次 | 相关角色 |
|---|---|
| 应用程序 | 应用软件设计者 |
| 系统功能调用（接口） | ↓↑ |
| 操作系统 | 操作系统设计者 |
| 计算机硬件 | —— |
| 终端用户 | 通过应用程序使用计算机 |

终端用户通常不直接接触操作系统，而是使用应用软件；应用软件设计者通过操作系统提供的**系统功能调用**来使用硬件资源；操作系统设计者则负责管理硬件、对上提供服务。

### 名称的演化

“操作系统”这一名称并非一开始就存在，历史上经历了多次演变：

- 监控（督）程序（系统）Monitor
- 执行系统（程序）Executive System (program)
- 控制系统（程序）Control System (program)
- 管理程序 Supervisor / Supervisory System
- 核心程序 Kernel
- 操作系统 Operating System

其中从 **Supervisor 到 Operating** 的称呼变化，体现了人们对这层软件认识的发展。RISC-V 架构的特权级中至今保留了 **Supervisor（监管级）**，这一特权级高于普通用户态，正对应操作系统管理和控制计算机的地位`▶ 1:15:08`。

关于 **Operating** 的含义：该词源自医学手术场景——复杂手术需要多位医生协同，必须有一位主刀医生（Operating surgery）统一决策、发号施令，因此 Operating 带有“决策、主管、最高权力”的意味。可参考电影《OP Center》：片中白宫的 OP 小组作为决策智囊团处理核弹头被盗的紧急事件，体现了 Operating“核心、主管”的属性`▶ 1:16:28`。

### 操作系统的主要工作

可以从以下几个方面理解操作系统的核心工作（这并非严格划分，而是帮助理解）：

- **程序的执行**：负责程序的启动、执行以及程序结束的完整流程`▶ 1:19:44`。
- **完成个性的工作（与硬件有关）**：直接与硬件交互的控制工作，是操作系统中难度最高的部分；虽然不需要设计硬件，但必须控制硬件，因此必须掌握硬件知识`▶ 1:19:44`。
- **完成共性的工作**：任何程序都需要的基本服务，如 `fork()`、`open()` 等系统调用的实现，相对容易理解`▶ 1:19:44`。目标是易于使用、提供基本服务、保持统一性。
- **性能、安全、健壮性等问题**。

### 个性：硬件相关

#### 没有操作系统会怎样

层次关系上，操作系统对上提供**虚拟机器界面**，对下通过**物理机器界面**操作硬件：

```
应用程序
-----------------------  虚拟机器界面
操作系统
-----------------------  物理机器界面
硬件
```

如果没有操作系统，就要面对这样的问题：怎样把目标代码送给硬件？怎样输出打印结果？——人们只能直接对二进制程序进行操作，从二极管等发光器件上读取答案。在无操作系统的时代，需要手工背记二进制 `0101` 这样的指令，逐条按键输入，再从指示灯读出结果，过程极其繁琐，这种方式早已被淘汰`▶ 1:21:05`。

#### 硬件相关工作的特点

典型的硬件相关工作包括：实现代码中的存储器物理地址，对设备接口寄存器和设备接口缓冲区进行读写等。这类工作有以下特点：

- 实现过程的代码与硬件因素密切相关，需要设置、测试和使用物理地址、设备接口寄存器等。
- 必然**复杂繁琐、代码量大**：对接硬件的接口、寄存器等内容会大幅增加代码复杂度，代码量随支持的硬件种类增多而膨胀`▶ 1:21:51`。
- 实现代码**不通用**。

可以通过 Linux 源码直观验证：只保留单一硬件架构、单一设备的代码，删除其余硬件适配代码，就能看出硬件相关代码占比极高。这正是操作系统设计 **HAL（硬件抽象层）** 的原因——尽可能把硬件相关差异屏蔽在该层，使上层代码保持通用`▶ 1:21:51`。

#### 软盘 I/O 的例子

为了体会硬件操作的复杂程度，可以比较两个要求：

- “从文件读数据块”——只需给定文件名、起始位置、读取长度，逻辑简单；
- “移动磁头、等待（旋转到位）、放下磁头”——底层磁盘读取必须依次完成这些具体硬件操作，流程繁琐`▶ 1:23:30`。

以软盘控制芯片 **NEC PD765** 为例：

- 共有 **16 条命令**；
- 每条命令都要向一个设备寄存器装入长度 **1～9 字节**的特定数据，用于读写数据、移动磁头臂、格式化磁道，以及初始化、检测状态、复位、校准控制器及设备等；
- 以 **READ** 命令为例，需要 **13 个参数**，包括：
  - 要读取的磁盘块地址
  - 磁道的扇区数
  - 物理介质的记录格式
  - 扇区间隙
  - 对已删除数据地址标识的处理方法
- 操作结束时，控制器芯片在 **7 个字节**中返回 **23 个状态及出错字段**；
- 程序员还要时刻注意步进电机的开关状态。

操作系统通过这类控制器芯片与硬件交互，指令长短不一、参数众多，驱动编写难度很大。课程不要求大家自己编写驱动，只需了解其复杂性并掌握规避方法`▶ 1:24:36`。

> **老师强调**：硬件相关内容是课程重点，只需理解其设计逻辑，重点在于如何屏蔽硬件差异，不要求自行编写驱动`▶ 1:21:51 · 1:24:36`。

这种对底层硬件细节的处理，就是**硬件相关操作的屏蔽和统一**。早期操作系统厂商需要为新硬件编写驱动来适配硬件；而现在操作系统生态成熟，反过来由硬件厂商主动适配操作系统接口`▶ 1:26:48`。

### 共性工作

共性是指**任何一个程序都需要的、最基本的工作**。它们具有以下特征：

- 具有共性，工作过程相同；
- 与具体应用无直接关系，即与用户关心的应用目标无直接关系。

操作系统通过共性服务为上层带来：

- **简化、方便**：把复杂操作封装成简单接口；
- **抽象**：隐藏底层实现细节；
- **标准化**：提供统一的使用方式。

### 作为应用软件与现实硬件之间的软件

操作系统对下封装参差不齐的硬件，对上提供统一接口，类似对毛坯墙面进行美化处理`▶ 1:27:27`。其作用可概括为：

- **硬件抽象，可移植性**：通过抽象层屏蔽硬件差异，使上层软件更易于移植；
- **有限变为“无限”（接近）**：把有限的物理资源扩展为更易用、近乎“无限”的可用资源；
- **提供保护**：对资源和程序进行隔离与保护。

因此，操作系统本质上构造了**一台等价的扩展机器（虚拟机）**：它比底层硬件更容易编程。

### 1. 处理器侧：关注寄存器

处理器侧核心关注以下内容：

- **通用寄存器**：保存函数调用和运算中的临时数据
- **控制状态寄存器**：支持处理器状态控制、异常和陷入等机制
- **程序计数器 PC**：记录当前指令地址，指示处理器下一条要执行的指令

> **老师强调**：通用寄存器、控制状态寄存器和程序计数器 PC 等前期知识在后续课程中都会用到，需要回顾并掌握`▶ 1:34:37`。

### 2. 内存侧：掌握进程地址空间布局

进程地址空间通常包含代码段、数据段、堆和栈等区域：

| 区域 | 来源与作用 |
|---|---|
| 代码段 | 来自可执行文件，存放程序指令 |
| 数据段 | 来自可执行文件，存放全局变量、静态数据等 |
| 堆 | 运行时由 `malloc` 等函数动态申请 |
| 栈 | 运行时为函数调用动态生成，用于保存栈帧、返回地址、局部变量等 |

关于栈，需要特别理解：

- `main` 函数对应栈中的第一个栈帧
- 每次进行函数调用，都会生成新的栈帧
- 函数返回时，对应栈帧被销毁
- 栈是程序**运行时动态生成**的
- 磁盘上的可执行文件中不存在程序运行后的原始栈内容

> **老师强调**：进程地址空间中代码段、数据段来自可执行文件，堆由 `malloc` 动态申请，栈随函数调用动态创建和销毁；这些 ICS 基础不能遗忘，否则会影响后续对操作系统机制的理解`▶ 1:34:37`。

## 9. 操作系统引导与RISC-V启动流程

> 课件 第 129–137 页 · 讲解从 `1:38:13` 开始

### 操作系统引导的核心概念

操作系统引导描述的是从按下电源键到出现 Shell 提示符的完整长链路，涉及以下关键概念：

- **Bootloader（引导加载程序）**：负责把内核从磁盘加载到内存并跳转执行的程序，是系统启动的“敲门砖”。Bootloader 是通用概念，在 RISC-V 架构下需要结合具体固件具体分析`▶ 1:38:13`。
- **特权级（M/S/U mode）**：RISC-V 共有三级特权模型，开机后特权级会动态切换，从最高权限逐层下放至用户态`▶ 1:38:13 · 1:45:30`。
- **BIOS/UEFI 与 SBI**：
  - BIOS/UEFI 是 x86 等平台上的固件接口标准；
  - **SBI（Supervisor Binary Interface，监管者二进制接口）**是运行在 Supervisor 层的接口规范，定义了 **S mode 与 Machine mode 之间的调用约定与标准函数集合**`▶ 1:38:13 · 1:40:48`。可以类比已学的 ABI（应用程序二进制接口，规定函数调用规则、caller/callee 保存哪些寄存器等调用规范），只不过 ABI 面向应用程序，而 SBI 面向内核所在的监管层`▶ 1:38:13`。
- **内核镜像加载**：操作系统内核会被制作成内核镜像（如 kernel.bin）存放在磁盘上，由 bootloader 加载到内存后才能运行`▶ 1:41:35`。

### 系统启动的典型流程

整体引导链路为：

```text
上电 → ROM 代码/固件 → Bootloader → 加载内核镜像到内存
     → 内核初始化 → 启动 init 进程 → 启动 shell
```

以 xv6 为例，可划分为四个阶段：

| 阶段 | 主要工作 |
|------|----------|
| **01 引导加载** | 计算机加电后，BIOS/UEFI 加载引导程序（如 boot.S）。引导程序负责初始化硬件、设置页表，并把 xv6 内核从磁盘加载到内存。 |
| **02 内核初始化** | 内核执行 main 函数，依次初始化关键子系统：`kinit` 初始化物理内存分配器，`pinit` 建立进程表，`trapinit` 配置中断处理，并初始化控制台等核心设备驱动。 |
| **03 创建 init 进程** | 调用 `userinit` 创建第一个用户进程，执行 `/init` 程序，完成文件系统的挂载与初始化，并启动 Shell 终端。 |
| **04 启动调度器** | 内核调用 `scheduler` 进入无限循环，在就绪队列中选择并调度进程执行，标志系统正式进入多任务并发运行状态。 |

其内在逻辑是“**硬件引导 → 内核自举 → 环境初始化 → 进程调度**”的四步闭环，完成从裸机硬件到可交互操作系统的完整启动。

关于 init 进程的补充：

- 第一个用户进程 **init（1 号进程）不是通过 fork 创建的**，而是由 `userinit` 直接生成；它是所有用户进程（包括 shell）的祖先`▶ 1:42:32`。
- 在它之前还有 Unix 体系下的 **0 号进程**`▶ 1:42:32`。
- 初始化完成后系统进入调度器循环，进程在用户态与内核态之间来回切换`▶ 1:42:32`。

### 引导要解决的两个核心问题

1. **内核文件怎么运行？** —— 内核镜像（kernel.bin）平时存放在磁盘上，必须先被加载到内存中才能执行。
2. **如何找到内核文件并从起始点开始运行？** —— 由 BIOS 与 bootloader 协作完成定位、加载，并跳转到内核入口地址。

### XV6-RISCV 启动流程详解

实验环境运行在 **QEMU 模拟机**上，通过缺省 BIOS 完成引导，具体过程如下`▶ 1:45:30`：

1. **BIOS 加载 OpenSBI 固件**：BIOS 将 OpenSBI 固件加载到地址 **`0x8000`**（M mode 地址，可在 LD 链接脚本中查看）。
2. **OpenSBI 初始化硬件并跳转内核**：OpenSBI 完成硬件初始化后，跳转到内核入口地址 **`0x80200000`**。
3. **建立启动栈**：之后为每个 CPU 核心建立 **16K 大小**的启动栈（作为对比，Linux 内核栈大小为 8MB）。
4. **串行初始化各核心**：调用 `main` 完成各 CPU 核心的串行初始化。
5. **进入调度器**：最终每个核心都进入自身**永不返回**的调度器死循环。

整个流程从最高权限的 **M mode** 开始，逐层完成硬件初始化，最终把权限下放到用户态的 shell。相关地址都可以在 `kernel.ld` 中查看`▶ 1:45:30`。

结合代码文件，分三步理解：

#### （1）入口点 `_entry` 与多核栈布局

- `kernel.ld`（链接脚本）中指明程序的入口点为 **`_entry`**，对应 `entry.S` 中的代码。
- 思考题：**多核情况下，CPU 各核心的栈是怎么排列的？** 课件会提供多核环境下各核心栈的排列示意图，作为代码阅读参考`▶ 1:47:31`。每个核心拥有独立的启动栈（各 16K），需结合 `entry.S` 与 `kernel.ld` 理解其排布。

#### （2）entry → start：特权级切换

- `entry.S` 执行后进入 `start`（位于 `start.c`）。
- 思考题：**`start` 函数运行在什么特权模式里？**
  - 提示：**`mret` 指令会从 `mepc` 寄存器中加载地址并开始执行**。借助 `mret`，系统可以从 Machine mode 切换到更低特权级（S mode），并跳转到预先写入 `mepc` 的地址（即后续的 main），这正是特权级下放的关键机制。

#### （3）start → main：初始化与多核启动

- `start` 完成 Machine mode 下的必要配置后，切换到 S mode 进入 `main`。
- 需要参考 `main.c` 总结 XV6-RISCV 的**多核启动流程**：各核心被串行初始化，依次初始化各子系统，之后每个核心进入自己的调度器循环。

### 拓展：真实 Linux 的启动

真实 Linux 启动同样从上电自检、加载 bootloader 开始，是一个接力式的过程，涉及以下概念：

| 概念 | 说明 |
|------|------|
| **固件（Firmware）** | 存放在 ROM 上，负责自检（POST）并加载 bootloader。 |
| **BIOS** | 较旧的固件标准，依次初始化硬件，支持 **MBR**（主引导记录）分区表的磁盘分区。 |
| **UEFI** | 较新的标准，功能类似 BIOS，支持 **GPT**（全局唯一标识分区表）磁盘分区；启动方式正从传统 BIOS 转向 UEFI。 |
| **MBR** | 主引导记录，大小 **512 字节**，位于可启动磁盘的 **0 号扇区**，其中包含用于加载、启动内核的引导程序。 |
| **Bootloader** | 被 BIOS 加载，负责把内核文件加载到内存并运行。 |
| **GRUB** | 常用的 bootloader，支持多种操作系统的启动，可在开机时选择要启动的目标系统。 |

接力关系为：

```text
固件/BIOS(UEFI) 自检 → 加载 bootloader（如 GRUB）
                    → bootloader 加载内核镜像到内存 → 运行内核
```

老师提到，嵌入式或 flash 版本的引导过程相对简单；目前机器普遍支持多操作系统引导（如 GRUB），由用户选择启动目标系统`▶ 1:48:48`。
