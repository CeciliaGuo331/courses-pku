## 1. 中断与异常的概念和分类

> 课件 第 21 页 · 讲解从 `04:35` 开始

### 事件的总体分类：中断与异常

系统运行过程中会发生各种需要处理的事件，按来源可以分为两大类：中断（外中断）和异常（内中断、例外）。统一术语有助于课程内部以及不同课程之间的讨论`▶ 04:35`。

- **中断（Interrupt，外中断）**：来自 CPU 外部的异步事件，由 I/O 设备或其他硬件部件发出，例如网卡、硬盘、时钟、打印机、键盘、鼠标等`▶ 05:07`。
- **异常（Exception，内中断/例外）**：在 CPU 执行指令的过程中由指令本身引发的内部同步事件，例如系统调用、页错误（缺页，Page Fault）、断点、算术溢出等`▶ 05:07`。

> **术语说明**：ICS 课程把所有事件统称为"异常"，再把来自 I/O 设备等硬件的事件明确称为"中断"；本课程则直接把事件分为中断和异常两大类。两种划分没有本质矛盾，只是总体称呼不同`▶ 07:11`。

常见事件的归类如下：

| 大类 | 典型事件 |
|---|---|
| 中断（外中断） | I/O 中断、时钟中断、硬件故障 |
| 异常（内中断、例外） | 系统调用、页错误/页故障、保护性异常、断点指令、其他程序性异常（如算术溢出等） |

### 按同步性与产生原因进一步划分

事件还可以按照"是异步发生还是同步发生"以及"是意外事件还是有意安排"两个角度细分：

- **Exceptions（同步，sync）**：fault（故障）、syscall/trap（系统调用/陷入）
- **Interrupts（异步，async）**：interrupt（硬件中断）、software interrupt（软件中断）
- 从事件性质看，有些事件是 **Deliberate（有意识安排的）**，如系统调用；有些是 **Unexpected（意外的）**，如可恢复或不可恢复的错误`▶ 09:37`。

中断是**异步**事件，可以延后处理；异常是**同步**事件，必须立即处理`▶ 07:47`。

> **老师的类比**：微信消息是异步通知，可以稍后再看；来电是同步事件，不接就无法通话。中断类似前者，异常类似后者`▶ 08:46`。

### 四类事件的原因、同步性与返回行为

异常可以进一步细分为陷入、故障、终止三类，加上中断共四类，核心区别如下表：

| 类别 | 原因 | 异步/同步 | 返回行为 |
|---|---|---|---|
| 中断 Interrupt | 来自 I/O 设备、其他硬件部件 | 异步 | 总是返回到下一条指令 |
| 陷入 Trap | 有意识安排的（如系统调用） | 同步 | 返回到下一条指令 |
| 故障 Fault | 可恢复的错误（如缺页） | 同步 | 返回到当前指令（重新执行） |
| 终止 Abort | 不可恢复的错误 | 同步 | 不会返回 |

要点说明：

- **中断**处理完成后，总是回到被打断指令的**下一条指令**继续执行`▶ 08:46`。
- **陷入（Trap）**是程序有意识安排的事件，典型例子是系统调用；处理完成后返回**下一条指令**`▶ 07:47 · 08:46`。
- **故障（Fault）**是出现后可以修复的错误，典型例子是缺页异常；操作系统把缺失的页面准备好后，需要**重新执行触发异常的那条指令**，所以返回地址是**当前指令**`▶ 07:47 · 08:46`。
- **终止（Abort）**对应不可恢复的错误，处理程序**不会返回**原程序`▶ 07:47`。

> **老师强调**：中断与异常的概念和分类比较重要，且与其他课程相关联，需要扎实掌握；尤其要记住不同类别在"同步/异步"和"返回地址"上的区别`▶ 04:35 · 08:46`。

## 2. 中断异常机制中的软硬件分工

> 课件 第 22–24 页 · 讲解从 `10:16` 开始

### 中断/异常机制中的软硬件分工

中断/异常机制是现代计算机系统的核心机制之一，依靠**硬件与软件相互配合**，使计算机系统的能力得以充分发挥。整个处理过程分为上下两段：**上半段由硬件完成，下半段由软件完成**`▶ 10:16`。

| 分工 | 任务名称 | 主要职责 |
|---|---|---|
| 硬件 | 中断/异常**响应** | 捕获中断源发出的中断/异常请求，以一定方式响应，并将处理器控制权交给特定的处理程序 |
| 软件 | 中断/异常**处理程序** | 识别中断/异常类型，并完成相应的处理 |

- **硬件该做什么**：发现、接收中断/异常请求，并把控制权转交到对应的处理程序。
- **软件要做什么**：操作系统针对不同的中断/异常原因，执行对应的处理代码；不同中断原因对应不同处理流程，因此教材对具体处理逻辑做了简化`▶ 12:25`。

> **老师强调**：考试中常有同学无法理清软硬件交接的流程，必须重点掌握"硬件先捕获、再转交操作系统处理"这一过程`▶ 12:25`。

### 硬件——中断响应过程

中断响应是指**发现中断、接收中断的过程，由中断硬件部件完成**。CPU 的工作周期可分为取指周期、执行周期和中断周期，其基本流程如下：

1. CPU 按周期不断地**取下一条指令 → 执行指令**。
2. 在**每条指令执行周期的最后时刻**，若中断处于允许（开启）状态，硬件扫描中断寄存器，查看是否有中断信号。
   - 中断是**异步事件**，检查点固定安排在一条指令执行结束之后`▶ 14:24`。
   - 若无中断信号，继续进入下一条指令的取指—执行周期。
3. 若有中断，硬件将该中断触发器的内容按规定编码送入 **PSW（程序状态字）** 的相应位，该编码称为**中断码**。
4. 通过**交换中断向量**（新旧 PSW 交换）引出中断处理程序，此时才正式把处理器控制权转交给操作系统`▶ 16:06`。
5. 处理完毕后返回，继续取下一条指令。

关于请求的捕获与记录：

- 硬件首先通过**中断寄存器**捕获中断源发来的请求，并记录对应的中断类型；若不及时记录，请求就会丢失`▶ 11:11`。
- 这与进程的 signal 机制类似：signal 用 vector 记录所有收到的信号，但**同类信号不排队**——第一个信号尚未处理时，第二个同类型信号会直接丢失`▶ 12:02`。

### 软硬协同的核心接口——中断向量表

硬件在得到中断码后，需要据此把控制权转移给正确的处理程序，承担这一桥梁作用的数据结构就是**中断向量表**。

- **中断向量**：一个内存单元（表中的一个条目），存放对应中断处理程序的**入口地址**以及程序运行所需的**处理机状态字（PSW）**。
- **中断向量表**：由若干中断向量组成的表，每个条目对应一类中断/异常。硬件按中断码查询该表，即可跳转到对应的中断处理程序。

整个转移过程为：

```text
中断源发出请求
   → 硬件捕获并生成中断码，保存到 PSW 相应位
   → 用中断码查询中断向量表
   → 交换新旧 PSW（中断向量）
   → 跳转到表项中记录的处理程序入口地址
   → 控制权转交操作系统的中断处理程序
```

中断向量表的关键性质：

- 它在**操作系统引导初始化时就已构建完成**，是操作系统初始化与中断/异常机制的重要关联；中断处理程序代码固定存放在内存对应位置`▶ 17:25`。
- 表项内容（入口地址 + PSW）由软件预先填写，查表跳转动作由硬件完成，因此中断向量表是**软硬件协同的核心接口**`▶ 17:25`。
- 表的具体结构与硬件架构相关；本课程以常用的 **X86 架构**为例，其中断向量表共有 **256 行（个表项）**，硬件依据中断号/异常类型的不同选择对应表项转移控制权`▶ 19:32`。

## 3. x86/Linux中断向量表与响应流程

> 课件 第 25–30 页 · 讲解从 `19:50` 开始

### x86/Linux 中断向量表

x86 硬件预定义了一部分基础、通用的异常表项，Linux 在此基础上进行扩展，形成自己的中断向量表。表的前半部分是硬件默认异常，如除零、调试、溢出、缺页等，操作系统通常直接复用而不修改；其余位置可由操作系统自行定义，例如 Linux 使用 `0x80` 号向量实现系统调用`▶ 20:10 · 21:23`。

> **老师强调**：操作系统引导初始化的核心工作之一，就是完成中断向量表的设置；只有表初始化完成，中断响应流程才能正常运行`▶ 21:53 · 28:33`。

中断描述表规模较大，目前约 250 万项即可满足使用需求`▶ 19:50`。

#### Linux（x86）中断向量划分

| 向量范围 | 用途 |
|---|---|
| 0～19 | 不可屏蔽中断和异常 |
| 20～31 | Intel 保留 |
| 32～127 | 外部中断（IRQ） |
| 128（`0x80`） | 用于系统调用的可编程异常 |
| 129～238 | 外部中断 |
| 239 | 本地 APIC 时钟中断 |
| 240 | 本地 APIC 高温中断 |
| 241～250 | Linux 保留 |
| 251～253 | 处理器间中断 |
| 254 | 本地 APIC 错误中断 |
| 255 | 本地 APIC 伪中断 |

其中，`0x80` 是 Linux 专门选择的系统调用入口位置，属于操作系统自定义表项，而不是 x86 硬件强制规定的异常`▶ 21:23`。

#### 常见不可屏蔽中断与异常

| 向量号 | 异常/中断 |
|---|---|
| 0 | 除零 |
| 1 | 单步调试 |
| 4 | 算术溢出 |
| 6 | 非法操作数 |
| 12 | 栈异常 |
| 13 | 保护性错误 |
| 14 | 缺页异常 |

课件还要求了解向量号 5～12、16～17 对应的异常。

> 老师建议：若要了解中断表的完整细节，应查阅 Intel 手册`▶ 21:53`。

### 中断响应的基本流程

课件将中断响应概括为以下步骤：

1. 设备发出中断信号；
2. 硬件保存现场；
3. 根据中断码查中断向量表；
4. 将中断处理程序入口地址等送入相应寄存器；
5. 执行中断处理程序。

以外设（如磁盘、光盘或打印机）发出中断为例，完整过程可分为硬件准备和软件处理两部分。

#### 1. 设备发出中断并被中断装置记录

外设完成 I/O 或发生异常时，向 CPU 发出中断信号。该中断首先由中断装置记录。正常情况下中断不会丢失；但如果前一个同类中断尚未处理完，后续中断有可能被丢弃`▶ 22:31`。

#### 2. CPU 检测并响应中断

CPU 在处理完当前指令后检测中断信号，判断中断来源，并向相关设备发送中断确认信号。

硬件随后完成进入内核处理所必需的操作：

- 将处理器状态从用户态切换到内核态；
- 在系统栈中保存被中断程序的关键上下文，主要包括：
  - 程序计数器 PC；
  - 程序状态字 PSW；
- 老师还特别提到栈指针也属于硬件压栈保存的关键寄存器之一`▶ 22:31`。

> **老师强调**：硬件只保存少量最关键的寄存器，如 PC、栈指针等；其余通用寄存器和额外上下文由中断处理程序在软件阶段保存`▶ 22:31 · 28:33`。

#### 3. 根据中断码查询中断向量表

硬件根据中断码查询已经初始化好的中断向量表，找到对应中断处理程序的入口地址，并把 PC 设置为该地址。

从此，CPU 的控制流由被中断程序转移到操作系统的中断处理程序，完成硬件与软件之间的交接`▶ 22:31`。

#### 4. 软件执行中断处理程序

中断处理程序获得控制权后，主要完成：

1. 在系统栈中继续保存其余现场信息；
2. 分析中断或异常的具体原因；
3. 执行对应的处理功能，例如：
   - 检查 I/O 设备状态；
   - 操纵 I/O 设备；
   - 在设备和内存之间传送数据；
4. 处理结束后执行中断返回指令。

以打印机为例，中断原因可能是正常完成，也可能是缺纸、缺墨、卡纸等异常结束，处理程序需要根据设备状态分别处理`▶ 27:28`。

#### 5. 恢复现场并返回

中断返回指令触发退栈操作：

- 从系统栈恢复被中断程序的上下文；
- 恢复 PC、PSW 等关键寄存器；
- CPU 状态恢复到中断发生前的状态；
- 从原来的位置继续执行被中断程序。

### 上半部与下半部

为了平衡中断处理的实时性和处理复杂度，Linux 将中断处理程序分为上半部和下半部。

| 部分 | 处理内容 | 中断状态 | 目标 |
|---|---|---|---|
| 上半部 | 紧急、必须立即响应的任务 | 关中断 | 快速完成，保证中断及时响应 |
| 下半部 | 不紧急、可延后的任务 | 开中断 | 在后续适当时机继续处理 |

老师用战地医院作类比：上半部相当于在前线对伤员进行紧急处理，要求快；下半部相当于将伤员转运到后方医院后再进行复杂手术`▶ 25:59 · 27:28`。

> **课件思考题**：理解 Linux 的中断处理流程，并解释为什么引入上半部和下半部处理。

引入上、下半部的根本原因是：中断处理期间如果长时间关中断，会导致其他中断无法及时响应，甚至造成中断丢失。因此，把必须立即完成的紧急操作放在上半部快速执行，把耗时、非紧急的数据处理等工作推迟到下半部，在开中断状态下完成，从而兼顾系统响应速度和处理能力。

### 中断/异常机制中的软硬件分工

整个中断机制由硬件和软件协同完成：

| 阶段 | 主要承担者 | 工作内容 |
|---|---|---|
| 中断发出与记录 | 设备、中断硬件 | 外设发出中断信号，中断装置记录请求 |
| 中断检测与确认 | CPU 硬件 | 当前指令结束后检测中断，确认中断来源 |
| 状态切换 | CPU 硬件 | 从用户态切换到内核态 |
| 关键现场保存 | CPU 硬件 | 将 PC、PSW、栈指针等关键上下文压入系统栈 |
| 查表与跳转 | CPU 硬件 | 根据中断码查中断向量表，设置 PC 为处理程序入口 |
| 完整现场保存 | 软件 | 保存其余寄存器和上下文 |
| 中断原因分析 | 软件 | 读取设备状态或异常信息，判断具体原因 |
| 具体处理 | 软件 | 执行 I/O、异常处理、数据传送等功能 |
| 恢复现场与返回 | 软件指令配合硬件 | 执行中断返回指令，恢复上下文并返回原程序 |

因此，中断向量表是硬件和软件交接的桥梁：硬件负责自动切换状态、保存最少现场并按表跳转；软件负责保存完整上下文、识别原因并完成具体处理。

## 4. x86中断描述符表与门描述符寻址

> 课件 第 31–37 页 · 讲解从 `32:08` 开始

### 中断、异常与系统调用

在 x86（IA32）体系结构中，中断/异常相关概念可作如下区分：

| 类别 | 引发方式 | 说明 |
|---|---|---|
| 中断 | 硬件信号引发 | 分为**可屏蔽中断**和**不可屏蔽中断** |
| 异常 | 指令执行引发 | 例如除零异常；80x86 处理器约有 20 种不同异常 |
| 系统调用 | 异常的一种 | 是用户态进入系统态（内核态）的唯一入口 |

> **老师强调**：x86 架构的中断与异常概念不要求深入掌握，仅作了解即可`▶ 32:08`。

关于异常还有一点细节：对于某些异常，CPU 在执行异常处理程序之前会产生一个**硬件出错码**，并将其压入内核态堆栈。

### 中断控制器与两种模式下的入口表

**中断控制器（PIC 或 APIC）**：负责把硬件发来的中断信号转换为中断向量，从而引发 CPU 中断。

x86 在不同处理器模式下使用不同的表来存放中断处理入口：

- **实模式：中断向量表（IVT）**
  - 存放中断服务程序的入口地址；
  - 入口地址 = **段地址左移 4 位 + 偏移地址**；
  - 不支持 CPU 运行状态（特权级）的切换，中断处理与一般的过程调用相似。
  - 老师补充：实模式表项内容较简单，仅包含程序入口地址、程序状态字（PSW）和程序计数器（PC）`▶ 34:08`。

- **保护模式：中断描述符表（IDT）**
  - 采用**门（gate）描述符**这种数据结构来描述中断向量；
  - 表的内容比实模式更丰富`▶ 34:08`。

> 老师指出：实模式的中断向量表与保护模式的中断描述符表，本质上都是存储中断处理入口的**数组**，每个元素是对应的结构`▶ 34:08`。

### 四种门描述符

中断向量表/中断描述符表的表项可以是以下四种类型的门描述符，操作系统可按需选用`▶ 35:11`：

| 门类型 | 主要内容 / 特点 |
|---|---|
| **任务门（Task Gate）** | 其中存放一个 TSS 选择符，对应中断发生时必须取代当前进程的那个进程。**Linux 没有使用任务门** |
| **中断门（Interrupt Gate）** | 给出段选择符（Segment Selector）和中断/异常处理程序的段内偏移量（Offset）；**通过中断门后系统会自动禁止中断（清 IF 位）** |
| **陷阱门（Trap Gate）** | 与中断门类似，但**通过陷阱门后系统不会自动关中断** |
| **调用门（Call Gate）** | （课件列出，未展开） |

> **老师强调**：Linux、Windows 常用的是**中断门和陷阱门**。二者核心区别在于：中断门在处理过程中会自动关闭中断、不响应新中断；陷阱门则不会自动关中断、处理过程中可接收新中断。操作系统根据"处理当前中断时是否需要接收新中断"来选择，没有强制规则`▶ 35:51`。

### 寻址涉及的数据结构与寄存器

中断寻址过程中会串联起两张表和两个系统寄存器：

- **IDTR**：存放中断描述符表（IDT）的基地址；
- **GDTR**：存放全局描述符表（GDT，Global Descriptor Table）的基地址；
- **IDT**：一个大数组，每一行是一个门（中断）描述符；
- **GDT/LDT**：每个元素是一个**段描述符**，包含**段基地址、界限（段长）和权限属性**`▶ 37:38`。

**段选择符格式**由三部分组成：

- **索引**：用来在 GDT/LDT 中定位段描述符；
- **特权级**；
- **GDT/LDT 指示位**：选择到 GDT 还是 LDT 中查找。

最终的中断服务程序入口地址计算方式为：

```
中断服务程序入口地址 = 段基址 + 偏移
```

其中**段基址**来自 GDT 中的段描述符，**偏移（段内偏移量）**来自 IDT 中的门描述符。

### 中断/异常的硬件处理（寻址）过程

完整流程如下`▶ 37:38`：

1. **确定向量 i**：确定与本次中断或异常关联的中断向量号 i。
2. **查 IDT**：通过 **IDTR** 寄存器找到 IDT 表，以 i 为索引取出第 i 项——中断描述符（门描述符）。
3. **查 GDT 取段基址**：通过 **GDTR** 寄存器获得 GDT 地址；用门描述符中的**段选择符**在 GDT 中找到对应的段描述符，从中取出处理程序所在段的**段基址**。
4. **特权级检查**。
5. **堆栈切换**：检查是否发生特权级变化；若是，则切换到与新特权级相对应的栈（必须使用与新特权级相关的栈）。
6. **硬件压栈**：保存上下文环境；如果该异常产生了硬件出错码，也一并压入栈中。
7. **清 IF 位**：如果是（通过中断门进入的）中断，则清除 IF 位以关闭中断。
8. **跳转执行**：用门描述符中的**段内偏移量**加上段描述符中的**段基地址**，得到处理程序入口地址，执行其第一条指令。

对应的结构关系可概括为：

```
中断向量号 i
   │（索引）
   ▼
 IDTR ──► IDT ──► 中断描述符（门描述符）
                    │            │
              段选择符            偏移量
                    │（索引）
                    ▼
 GDTR ──► GDT/LDT ──► 段描述符 ──► 段基址
                                         │
              入口地址 = 段基址 + 偏移量 ◄┘
                    │
                    ▼
              中断处理程序（内存）
```

> **老师强调**：上述全部查表操作都由**硬件自动完成**，操作系统只需在系统初始化时提前把 IDT、GDT 等表建好即可；教材的文字描述与示意图内容一致，看懂其中一个即可`▶ 37:38`。

老师还用动画说明了内存布局：系统初始化完成后，IDT 与 GDT 均已就绪，所有中断处理程序连续存放在内存的一块固定区域中，通过**统一的段基地址搭配不同的段偏移**，即可定位每一个中断处理程序的入口`▶ 41:42`。

## 5. 系统调用的概念及与库函数、API的关系

> 课件 第 38–43 页 · 讲解从 `43:32` 开始

### 系统调用的基本作用

系统调用（System call）是用户程序进入操作系统内核的常见途径之一。程序进入内核的路径主要包括中断、异常等，而系统调用属于异常类进入方式。`▶ 43:40`

从操作系统运行机制来看，用户程序通常运行在**用户态**，不能直接访问内核管理的硬件和关键资源；当程序需要操作系统提供服务时，需要通过系统调用进入**内核态**。因此，系统调用的核心作用是：

- 作为用户程序请求操作系统服务的入口；
- 使 CPU 状态从用户态陷入内核态；
- 由内核完成特定服务后，再返回用户态继续执行。

> **老师强调**：系统调用是操作系统层的重要接口，需要重点掌握。`▶ 43:40`

### 系统调用的概念

系统调用是指用户在编程时可以调用的操作系统功能，是操作系统提供给编程人员的接口。`▶ 44:12`

常见系统调用包括：

- 进程控制，如 `fork`；
- 文件使用，如 `open`、`write`；
- 进程通信；
- 目录操作；
- 设备管理；
- 信息维护等。

每个操作系统通常都会提供几百种系统调用，用来支持应用程序使用操作系统提供的各类服务。课件中还提出了两个延伸问题：

1. Linux 操作系统提供多少个系统调用？
2. 如何在 Linux 中增加一个新的系统调用？

其中，新增系统调用的实现方法属于课后自学内容。`▶ 45:02`

> **注意**：在命令行中输入一个命令并不等同于系统调用。系统调用是程序在编程层面调用操作系统功能的接口，例如程序代码中调用 `fork`、`open` 等。`▶ 44:12`

### 系统调用、库函数、API 与内核函数的关系

系统调用位于应用程序和操作系统内核之间，可以从三个层次理解：

| 层次 | 说明 | 示例 |
|---|---|---|
| 应用程序 | 用户编写的程序，运行在用户态 | `hello` 程序 |
| C 函数库 / API 接口 | 对系统调用或通用功能进行封装，方便程序员使用 | `printf`、`fopen` |
| 操作系统内核 | 真正实现系统服务，运行在内核态 | `write` 的内核实现、`open` 的内核实现 |

它们之间的关系如下：

1. **系统调用与内核函数的关系**  
   每个系统调用都对应内核中的一段函数实现。系统调用本身是内核对外提供的接口，而真正完成服务的是内核中的实现代码。`▶ 45:02`

2. **系统调用与 C 库函数 / API 函数的关系**  
   有些库函数本身就直接对应系统调用，应用程序可以直接调用，例如 `fork`、`open`、`write`；有些库函数则是在系统调用外又做了一层封装，例如：
   - `fopen` 是对系统调用 `open` 的封装；
   - `printf` 是标准 I/O 库函数，底层最终会调用 `write` 系统调用。`▶ 45:02`

因此，库函数不一定都会触发系统调用，但需要操作系统完成输入输出、文件访问、进程创建等操作时，最终通常要通过系统调用进入内核。

### 示例：`printf` 如何进入内核

以如下程序为例：

```c
#include <stdio.h>

int main() {
    printf("Hello\n");
    return 0;
}
```

应用程序调用的是标准 C 库中的 `printf()`。`printf()` 负责格式化输出等库层面的处理，当需要把内容真正写到终端或文件时，会进一步调用系统调用接口 `write()`，随后进入内核态，由内核中的 `write` 系统调用实现完成输出操作，最后再返回用户态。`▶ 45:02 · 47:23`

调用路径可以概括为：

```text
应用程序
   ↓ 调用
printf()
   ↓ 标准 C 库内部调用
write() 系统调用接口
   ↓ 从用户态陷入内核态
内核中的 write() 实现
   ↓
返回用户态
```

课件中另一个例子也说明了同样的过程：

```c
#include <stdio.h>

int main() {
    printf("greetings");
    return 0;
}
```

当应用程序调用 `printf()` 时，会触发系统调用 `write()`。

### 系统调用与普通 C 函数调用的区别

“系统调用与 C 函数调用的区别”是经典问题，也是常见面试题。`▶ 47:23`

二者的关键区别在于执行状态和调用成本：

| 对比项 | 普通 C 函数调用 | 系统调用 |
|---|---|---|
| 运行状态 | 通常全程在用户态执行 | 需要从用户态进入内核态 |
| 功能 | 调用程序或函数库中的普通函数 | 请求操作系统内核提供服务 |
| 调用开销 | 主要是普通过程调用开销 | 包含陷入内核、状态切换、内核处理和返回等开销 |
| 示例 | 普通数学计算函数、字符串处理函数 | `fork`、`open`、`write` |
| 资源访问 | 不能直接访问受保护的内核资源 | 可在内核权限下访问文件、设备、进程等资源 |

需要注意的是，像 `printf` 这样的 C 库函数从程序写法上看是普通函数调用，但它在执行过程中可能进一步触发系统调用。因此，“调用库函数”和“发生系统调用”并不是完全相同的概念。

### 动手实践：用 `strace` 跟踪系统调用

在 Linux 系统上，可以使用 `strace` 工具跟踪程序执行过程中发生的系统调用。

先编写 `hello.c`：

```c
#include <stdio.h>

int main() {
    printf("Hello\n");
    return 0;
}
```

编译为二进制程序 `hello` 后，执行：

```bash
strace -e trace=write ./hello
```

该命令只跟踪 `write` 系统调用，可以观察到 `printf("Hello\n")` 在底层触发 `write` 系统调用的过程。课件建议课后实际运行并理解其执行路径。`▶ 47:23`

## 6. 系统调用机制设计与参数传递

> 课件 第 44–49 页 · 讲解从 `48:51` 开始

### 系统调用机制的设计

系统调用的实现可以分为**静态实现**与**动态执行**两部分。从静态角度看，操作系统需要预先规定陷入指令、系统调用号、参数传递方式和系统调用表；从动态角度看，用户程序执行陷入指令后，借助硬件的中断/异常机制从用户态进入内核态，再由内核根据系统调用号执行相应服务例程`▶ 48:51`。

系统调用不需要重新设计一套硬件机制，而是直接建立在硬件已提供的**中断/异常机制**之上`▶ 48:51`。其设计主要包括以下内容：

1. **选择一条特殊指令：陷入指令（访管指令）**
   - 该指令用于主动引发异常，从而完成从用户态到内核态的切换。
   - 陷入指令又称**访管指令**，“访管”即访问内核态（supervisor）管理程序的意思`▶ 48:51`。
   - 不同体系结构使用的指令不同：
     - x86 架构下，Linux 传统上使用 `int $0x80` 作为系统调用入口。
     - x86 还提供了 `sysenter` / `sysexit`、`syscall` / `sysret` 等专门用于系统调用进入和返回的指令`▶ 48:51`。
   - 奔腾 3 之后的 CPU 增加了新的系统调用指令，但旧程序仍可使用 `int` 指令；最终编译成哪类指令由编译器决定`▶ 51:21`。

2. **规定系统调用号和参数**
   - 每个系统调用都事先分配一个唯一编号，也叫**功能号**。
   - 操作系统需要定义自身支持哪些系统调用及对应编号；系统调用编号通常遵循 POSIX 等标准规范`▶ 51:40`。
   - 操作系统也可以自定义系统调用，但如果不在标准范围内，就不符合相应标准，不过一般不影响程序在该系统上运行`▶ 51:40`。
   - 系统调用在用户程序中往往以函数形式出现，并可能携带参数`▶ 52:28`。

3. **建立系统调用表**
   - 系统调用表用于存放各个系统调用服务例程的入口地址。
   - 它本质上是一张跳转表：进入内核后，根据系统调用号查询该表，即可找到对应的处理代码`▶ 52:56`。
   - 系统调用表在操作系统初始化时建立即可`▶ 1:04:14`。

> **老师强调**：系统调用表和中断向量表是**两张不同的表**。中断向量表中只有系统调用入口所对应的那一项；通过陷入指令进入内核后，还需要根据系统调用号查询系统调用表，才能找到具体的服务例程。往年考试中有 30%–40% 的学生误以为二者是同一张表`▶ 52:56`。

4. **体现机制与策略分离**
   - 系统调用是“机制与策略分离”的典型例子。
   - “机制”是固定的：用户程序通过陷入指令进入内核的通路一致。
   - “策略”是可选择的：进入内核后，根据不同的系统调用号选择不同的服务例程和实现方式`▶ 1:04:57`。

### 系统调用的参数传递

系统调用执行时，需要解决一个关键问题：**怎样把用户程序中的参数传递给内核？**

常用方法有三种：

| 传递方法 | 做法 | 特点或限制 |
|---|---|---|
| 陷入指令自带参数 | 把参数直接编码在陷入指令中 | 指令长度有限，还要携带系统调用功能号，只能携带少量参数；指令结构复杂，目前基本不使用`▶ 1:05:22` |
| 通过通用寄存器传递 | 执行陷入指令前，把系统调用号和参数放入约定的寄存器 | 操作系统和用户程序都可访问寄存器，简单直接；但寄存器数量会限制参数个数。32 位架构下较受限，64 位架构通用寄存器较多，压力较小`▶ 1:05:22` |
| 通过内存专用堆栈区传递 | 把参数打包放到内存栈中，再把栈指针传给内核 | 适合参数过多、寄存器放不下的情况`▶ 1:05:22` |

目前主流方式是**通过寄存器传递参数**，寄存器的选择和参数装入工作通常由编译器自动完成`▶ 1:05:22`。

### 系统调用执行过程举例

以高级语言中的 `write()` 系统调用为例：

- 程序员在高级语言中调用 `write()`。
- 编译后，编译器生成相应汇编代码：
  - 把系统调用号送入指定寄存器；
  - 把参数依次放入约定寄存器；
  - 执行 `int $0x80` 触发系统调用，陷入内核`▶ 1:07:03`。

整体编译关系可概括为：

```text
write()  ──编译──►  movl $4, %eax
                    ……
                    int $0x80
```

### 高级语言视角

示例程序：

```c
#include <unistd.h>

int main() {
    char string[7] = {'H', 'e', 'l', 'l', 'o', '!', '\n'};
    write(1, string, 7);
    return 0;
}
```

输出结果：

```text
Hello!
```

其中：

- `write(1, string, 7)` 表示向文件描述符 `1`（标准输出）写入从 `string` 开始的 7 个字节。
- `return 0` 在程序结束阶段也会涉及相应的系统调用，用于进程退出等处理`▶ 1:07:03`。

### 汇编语言视角

对应的 x86 Linux 汇编代码如下：

```asm
.section .data
output:
    .ascii "Hello!\n"
output_end:
    .equ len, output_end - output

.section .text
.globl _start
_start:
    movl $4, %eax          # eax 存放系统调用号
    movl $1, %ebx          # 文件描述符：标准输出
    movl $output, %ecx     # 输出字符串的首地址
    movl $len, %edx        # 输出长度
    int $0x80              # 引发一次系统调用

end:
    movl $1, %eax          # 1 号系统调用：退出进程
    movl $0, %ebx          # 退出状态码为 0
    int $0x80
```

执行 `write` 系统调用时，各寄存器的作用为：

| 寄存器 | 存放内容 | 本例值 |
|---|---|---|
| `%eax` | 系统调用号 | `4`，表示 `write` |
| `%ebx` | 第 1 个参数：文件描述符 | `1`，标准输出 |
| `%ecx` | 第 2 个参数：缓冲区地址 | `output` |
| `%edx` | 第 3 个参数：写入字节数 | `len` |

`int $0x80` 执行后，CPU 从用户态切换到内核态；内核根据 `%eax` 中的系统调用号 `4` 查询系统调用表，执行 `write` 对应的服务例程。

程序末尾：

- `movl $1, %eax`：将系统调用号设为 `1`；
- `movl $0, %ebx`：将退出码设为 `0`；
- `int $0x80`：触发系统调用。

`1` 号系统调用的作用是**退出当前进程**，其中 `%ebx` 中的 `0` 表示程序正常退出。

## 7. 系统调用执行过程与Linux x86实现

> 课件 第 50–65 页 · 讲解从 `1:09:14` 开始

### 系统调用的总体执行过程

系统调用属于异常类中断，进程执行到特殊陷入指令时触发，整体执行流程与普通中断一致，区别仅在于触发场景不同`▶ 1:09:14`。整个过程分为四个阶段：

1. **中断/异常机制（硬件完成）**：硬件自动保护现场，通过查中断向量表（IDT）把控制权转给系统调用总入口程序。
2. **系统调用总入口程序（软件完成）**：进一步保存现场，将参数保存在内核堆栈中，通过查系统调用表把控制权转给相应的处理例程或内核函数。
3. **执行系统调用例程**：完成具体的内核功能。
4. **恢复现场，返回用户程序**。

> **老师强调**：硬件只保存少量现场，入口程序首先要进一步保存现场，剩余部分由软件补全并存入内核堆栈`▶ 1:11:12`。

### Linux 在 x86 上的系统调用实现基础

Linux 基于 x86 处理器时，选择 `int $0x80`（中断向量号 128）作为陷入指令。

#### 门描述符的初始化

系统初始化时在 `sched_init()` 中调用：

```c
set_system_gate(0x80, &system_call);
```

对 IDT 表中的第 128 号门进行初始化，门描述符中包含：

- **第 2、3 字节**：内核代码段选择符（`__KERNEL_CS`）
- **第 0、1、6、7 字节**：偏移量，即 `system_call()` 可执行代码的第一条指令地址

定位入口地址时，用代码段描述符中的基地址加上陷阱门描述符中的偏移量`▶ 1:13:01`。

#### 门类型与特权级

| 属性 | 设置 | 含义 |
|---|---|---|
| 门类型 | 15（陷阱门） | 触发后 IF 位保持不变，仍可响应中断 |
| DPL | 3 | 与用户级特权相同，允许用户进程使用该门 |

> 之所以使用陷阱门，是因为系统调用进入内核后仍允许响应中断`▶ 1:14:45`。

#### 相关头文件

- `include/linux/syscalls.h`
- `include/asm-i386/unistd.h`：定义系统调用号

#### 系统调用号示例

```c
#define __NR_exit      1
#define __NR_fork      2
#define __NR_read      3
#define __NR_write     4
#define __NR_open      5
#define __NR_close     6
#define __NR_waitpid   7
#define __NR_creat     8
#define __NR_link      9
#define __NR_unlink   10
#define __NR_execve   11
#define __NR_chdir    12
#define __NR_time     13
```

> **老师强调**：系统调用号有标准映射，但 x86 架构的实际编号可能与标准定义不同，要以架构对应的 `unistd.h` 为准`▶ 1:14:45`。

### 执行 `int $0x80` 时的硬件行为

#### 1. 特权级切换与栈切换

由于特权级从用户态（3）切换到内核态（0），必须切换栈：

- 用户栈 → 内核栈
- CPU 从**任务状态段 TSS** 中装入新的栈指针 `SS:ESP`，指向内核栈
- TSS 中存有对应 0～3 四个特权级的栈指针（32 位下为 `SS0/ESP0`、`SS1/ESP1` 等，64 位下对应 `RSP`）

此步骤由硬件自动完成`▶ 1:18:39`。

#### 2. 硬件自动保存现场

硬件按顺序把以下内容压入内核栈：

1. 用户栈信息 `SS:ESP`
2. `EFLAGS`
3. 用户态 `CS`
4. 用户态 `EIP`

这些信息用于最终返回用户程序。压入 EFLAGS 后：

- **TF 位复位**
- **IF 位保持不变**（陷阱门的特点）

#### 3. 定位系统调用入口

- 用向量号 128 在 IDT 中找到门描述符
- 取出段选择符装入 CS
- 由代码段描述符基地址 + 陷阱门偏移量，定位到 `system_call()` 入口

#### 4. 特权级检查

规则：代码只能访问相同或较低特权级的数据。由于门描述符 DPL=3，用户态代码有权通过该门进入内核。

#### 内核栈布局（硬件 + 软件）

栈上的压栈顺序为`▶ 1:23:06`：

```
硬件压入：SS、ESP、EFLAGS、CS、EIP
软件压入：系统调用号（EAX）
SAVE_ALL：其余全部寄存器
```

### 参数传递

系统调用使用寄存器传递参数，最多传递 **6 个**：

| 寄存器 | 用途 |
|---|---|
| `eax` | 保存系统调用号；返回时保存返回值 |
| `ebx` | 第 1 个参数 |
| `ecx` | 第 2 个参数 |
| `edx` | 第 3 个参数 |
| `esi` | 第 4 个参数 |
| `edi` | 第 5 个参数 |

进入内核态后，`system_call` 再把这些寄存器值保存到内核堆栈中。

#### 参数传递示例

假设 C 库中系统调用号为 3 的函数原型为：

```c
int sys_func(int para1, int para2);
```

C 编译器产生的汇编伪码：

```asm
movl 0x8(%esp), %ecx   # 将用户态堆栈中的 para2 放入 ecx
movl 0x4(%esp), %ebx   # 将用户态堆栈中的 para1 放入 ebx
movl $0x3, %eax        # 系统调用号 3 保存在 eax 中
int  $0x80             # 引发系统调用
...
movl %eax, errno       # 将结果存入全局变量 errno
movl $-1, %eax         # eax 置为 -1，表示出错
```

### Linux 系统调用完整执行流程

以用户程序调用 `write()` 为例：

```text
用户态
  ┌─────────────────────┐
  │ 应用程序 main()      │  write(...);
  └─────────┬───────────┘
            ▼
  ┌─────────────────────┐
  │ C 库封装例程 write() │  准备参数 → int $0x80
  └─────────┬───────────┘
─────────── 陷入（用户态 → 内核态）───────────
            ▼
内核态
  ┌─────────────────────┐
  │ entry(system_call)  │  push %eax; SAVE_ALL
  └─────────┬───────────┘
            ▼
  ┌─────────────────────┐
  │ 查 sys_call_table    │  call sys_write
  └─────────┬───────────┘
            ▼
  ┌─────────────────────┐
  │ sys_write() 内核函数 │  执行具体功能并返回
  └─────────┬───────────┘
            ▼
  ┌──────────────────────┐
  │ ret_from_sys_call    │  调度/信号检查 → RESTORE_ALL
  └──────────┬───────────┘
─────────── 返回（内核态 → 用户态）───────────
             ▼
  继续执行陷入指令之后的用户代码
```

具体步骤为：

1. 用户态调用 C 库函数 `write()`；
2. 封装例程准备参数，执行 `int $0x80` 产生异常；
3. CPU 在 IDT 中通过 0x80 找到 `system_call()`；
4. `system_call()` 把参数保存在内核栈，根据系统调用号索引系统调用表，找到 `sys_write()`；
5. `sys_write()` 执行完后，经 `ret_from_sys_call()` 返回用户程序`▶ 1:21:15`。

### SAVE_ALL：保存全部寄存器

`system_call` 入口处先压入系统调用号，再执行 `SAVE_ALL`：

```asm
#define SAVE_ALL \
cld; \
pushl %es; \
pushl %ds; \
pushl %eax; \
pushl %ebp; \
pushl %edi; \
pushl %esi; \
pushl %edx; \
pushl %ecx; \
pushl %ebx; \
movl $(__KERNEL_DS), %edx; \
movl %edx, %ds; \
movl %edx, %es;
```

注意：

- 压栈顺序为 `es、ds、eax、ebp、edi、esi、edx、ecx、ebx`；
- 保存完段寄存器后，把 `ds`、`es` 切换为内核数据段 `__KERNEL_DS`。

### 系统调用表 sys_call_table

`sys_call_table` 位于 `entry.S` 中，描述系统调用号与内核处理函数之间的对应关系：

```asm
.data
ENTRY(sys_call_table)
    .long SYMBOL_NAME(sys_exit)
    .long SYMBOL_NAME(sys_fork)
    .long SYMBOL_NAME(sys_read)
    .long SYMBOL_NAME(sys_write)
    ...
```

其功能相当于跳转表：每项占 4 字节，存放对应内核函数的地址；以系统调用号为索引，即可找到处理函数入口`▶ 1:23:59`。

### system_call 关键代码分析

#### 保存现场并检查系统调用号

```asm
system_call:
    pushl %eax                  # 将系统调用号压栈
    SAVE_ALL
    ...
    cmpl $(NR_syscalls), %eax   # 检查是否是合法的系统调用号
    jb   nobadsys
    movl $(-ENOSYS), 24(%esp)   # 非法：把栈中 eax 设为 -ENOSYS
    jmp  ret_from_sys_call
```

> **老师强调**：系统调用表条目数量有限（如只有约 200 个），若调用号越界（如第 208 个），直接返回 `-ENOSYS` 错误，不再执行后续处理`▶ 1:24:37`。

#### 调用具体内核函数

```asm
nobadsys:
    call *SYMBOL_NAME(sys_call_table)(,%eax,4)  # sys_call_table[eax]
    movl %eax, EAX(%esp)    # 将返回值存入栈中保存 eax 的位置
    jmp  ret_from_sys_call
```

`call *sys_call_table(,%eax,4)` 表示以 `eax × 4` 为偏移进行间接跳转，调用对应处理函数，例如 `sys_write`、`sys_read`、`sys_fork``▶ 1:26:39`。

### ret_from_sys_call：返回前的处理

```asm
ret_from_sys_call:
    cli                            # 关中断
    cmpl $0, need_resched(%ebx)
    jne  reschedule                # 需要重新调度
    cmpl $0, sigpending(%ebx)
    jne  signal_return             # 有未处理信号
restore_all:
    RESTORE_ALL                    # 弹栈恢复，返回用户态
```

#### 1. 关中断

由于通过陷阱门进入内核时 IF 保持不变、中断处于开启状态，返回阶段需要先关中断，保证返回过程不被打断`▶ 1:28:02`。

#### 2. 检查 need_resched

- `need_resched` 是进程描述符中的一位；
- 若不为 0，跳转到调度模块选择新进程运行，且跳转后不返回；
- 若为 0，原进程继续执行。

这体现了：内核处理完请求后，由调度器决定接下来哪个进程占用 CPU`▶ 1:28:02`。

#### 3. 检查 sigpending 并处理信号

- 信号标志存放在一个**向量（位图）**中，而不是队列；不同信号对应向量中的某一位`▶ 1:32:28`。
- 若向量为 0，说明没有待处理信号，直接执行 `RESTORE_ALL` 返回用户态。
- 若向量不为 0，说明有未处理信号，进入 `signal_return` 处理。

> **老师强调（结合 ICS 第八章）**：所有信号都在内核态返回用户态的最后时刻统一处理。此时目标进程已经被调度选中，内核会一次性把发给该进程的信号全部处理完，有多少处理多少；处理完毕后才能返回用户态继续运行`▶ 1:31:06 · 1:33:18`。

#### 4. RESTORE_ALL

将 `SAVE_ALL` 保存的寄存器以及硬件保存的上下文依次恢复，最终回到用户态，从陷入指令之后继续执行。

### 阻塞型 I/O 系统调用的两个阶段

`read`、`write` 等慢速 I/O 系统调用属于阻塞型系统调用：

1. 进程执行系统调用后主动阻塞，放弃 CPU，不再占用处理器；I/O 实际由 DMA 或 I/O 控制器完成。
2. I/O 结束后设备发出中断，内核唤醒等待该事件的进程，使其恢复执行。

> **老师强调**：`read/write` 系统调用的完整执行必须分为上述两个阶段。往年考试常考此细节，只写一个阶段会丢分，必须吃透全流程，不能只掌握大致逻辑`▶ 1:17:04`。

## 8. 系统调用小结与内核低层工作步骤

> 课件 第 66–68 页 · 讲解从 `1:34:04` 开始

### 系统调用小结

- **定义**：系统调用是用户在程序中调用操作系统所提供子功能的手段；它最初的完整名称是「操作系统功能调用」，因名称过长而简称为「系统调用」`▶ 1:34:04`。
- **本质**：一种特殊的过程调用。形式上与普通过程调用相近，但实现方式不同：它由专用的特殊机器指令——**访管指令（陷入指令）**触发，每种机器的指令集都支持该指令`▶ 1:34:04`。
- **地位**：系统调用是操作系统提供给编程人员的**唯一接口**，也是用户态切换到内核态（旧称**目态→管态**）的唯一接口`▶ 1:34:04`。
- **作用**：借助系统调用，用户程序可以动态请求和释放系统资源，完成与硬件相关的工作，以及控制程序的执行等。
- **数量与标准**：每个操作系统通常提供几百种系统调用，并遵循 **POSIX 标准**。

### 系统调用与 C 函数调用的区别

二者在源代码形式上看起来都是一次函数调用，但关键区别在于：

| 对比项 | C 函数调用 | 系统调用 |
|--------|-----------|----------|
| 执行状态 | 全程在用户态执行 | 通过陷入/访管指令由目态转入管态 |
| 实现指令 | 普通的过程调用指令（如 call） | 特殊的陷入（访管）指令 |
| 调用对象 | 用户程序内或函数库中的普通函数 | 操作系统内核提供的服务例程 |
| 开销 | 较小 | 涉及状态切换、现场保存与分派，开销较大 |

> **老师强调**：系统调用由专用的陷入指令触发，是用户态切换到内核态（旧称目态到管态）的唯一接口`▶ 1:34:04`。

### 完成系统调用机制所需的条件（准备工作）

#### 静态准备

1. **封装内核函数 → 库函数（API）**：把内核提供的功能封装成对外的接口，放入函数库供用户程序调用。
2. **访管指令与陷入机制**：硬件/体系结构必须提供陷入（访管）指令及相应的陷入机制。
3. **编译器支持**：编译器能够把用户编写的系统调用代码转换为符合规范的指令`▶ 1:35:06`。
4. **操作系统初始化工作**：初始化相关数据表，确定系统调用编号和参数传递方式，并建立**系统调用表**`▶ 1:35:06`。

#### 动态执行流程

系统调用的运行过程与中断类似，依次为`▶ 1:35:06`：

1. 执行陷入（访管）指令，陷入内核；
2. 进入总入口程序；
3. 压栈保存现场；
4. 通过系统调用表（分派表）查表分派，找到对应的系统调用服务例程；
5. 执行该服务例程；
6. 执行完成后退出并返回用户态。

### 中断发生后 OS 低层工作步骤

1. **硬件压栈**：保存程序计数器等重要寄存器。
2. **硬件装入新的程序计数器**：从中断向量装入新的 PC 等，将执行权移交给中断/陷入处理程序。
3. **汇编语言过程保存寄存器值**：完成现场保存（save all）。
4. **汇编语言过程设置新的堆栈**。
5. **C 语言中断服务程序运行**：例如读取并缓冲输入；信号处理、系统调用服务例程也由 C 等高级语言编写。
6. **进程调度程序决定下一个将运行的进程**。
7. **C 语言过程返回至汇编代码**。
8. **汇编语言过程开始运行新的当前进程**：完成最终的上下文切换，切换到目标进程执行。

### 全流程的职责划分

- **硬件**：压栈保存重要寄存器，把执行权移交给中断/陷入处理程序。
- **汇编代码**：完成现场保存（save all）以及上下文切换的底层操作。
- **C 等高级语言**：编写中断处理程序、信号处理和系统调用服务例程。
- **调度程序**：处理完成后不能直接返回用户态，必须先进入调度逻辑，由调度程序决定下一个要运行的进程，再返回汇编层完成最终的上下文切换`▶ 1:36:46`。

> **老师强调**：该低层工作流程已通过示意图、文字说明、X86 架构实现、保护模式流程、系统调用实现等多个场景反复讲解（重复六七次），必须牢记各步骤的先后顺序，不能出错`▶ 1:36:46`。

## 9. 机制与策略分离原则

> 课件 第 69–70 页 · 讲解从 `1:39:19` 开始

### 机制与策略分离原则

操作系统设计的核心原则之一是**机制与策略分离**（separation of mechanism and policy）。这一原则在整个软件开发中普遍存在，可以从"固定不变的底层实现"与"灵活可调的上层决策"两个角度来理解。

- **机制（Mechanism）**：固定不变的底层实现逻辑，负责保障基础性能与功能。例如一个加法函数，其机制就是"接收两个参数、返回两数之和"，这套实现规则本身不会改变`▶ 1:39:19`。
- **策略（Policy）**：灵活可调的上层决策。例如调用加法函数时传入什么具体参数值、选择何种执行策略，都可以根据需求调整`▶ 1:39:19`。

> **老师强调**：机制与策略分离是操作系统中广泛应用的重要设计。机制负责保障基础性能，本身固定不变；策略负责实现灵活性，可以灵活调整`▶ 1:41:35`。

### 原则在操作系统中的体现

| 层次 | 属于机制（固定） | 属于策略（可调） |
|------|------------------|------------------|
| 中断/异常处理 | 中断异常的进入、响应与分发机制 | 中断向量表、系统调用表中的表项地址及对应处理代码 |
| 硬件中断 | 硬件预设的中断优先级及响应顺序 | 通过屏蔽高优先级中断、开放低优先级中断来微调实际响应顺序`▶ 1:40:30` |
| 进程调度 | "按优先级高低选择进程上 CPU"的调度规则 | 各进程的优先级取值（修改优先级即可让某进程立即获得 CPU）`▶ 1:43:02` |

以中断为例：中断异常的处理流程是固定的底层机制；而**中断向量表、系统调用表属于可调整的策略**——只需修改对应的处理代码、调整表中表项的地址，就可以改变具体的处理逻辑，而无需改动底层机制本身`▶ 1:41:35`。

硬件层面也体现这一原则：硬件为中断预设了固定的优先级，响应时优先处理高优先级中断；但这个顺序可以通过"屏蔽高优先级中断、开放低优先级中断"的方式进行微调，从而改变实际响应顺序`▶ 1:40:30`。

后续进程调度部分会进一步用到该原则：在基于优先级的调度中，"按优先级高低选择进程上 CPU"是固定的调度机制，而修改某个进程的优先级、使其立即获得 CPU 执行权限，则属于可调整的策略`▶ 1:43:02`。

### 内核的进入与退出（整体结构）

课件第 70 页的图示展示了应用程序与内核、外部设备之间的交互路径，可以帮助理解机制与策略所处的位置：

- **应用程序 → 函数库 → 系统调用接口 → 内核**：应用程序通过函数库发出系统调用，经系统调用接口进入内核。
- **内核内部**：包含系统调用实现、异常服务例程、设备驱动等；并通过**系统调用表**和**中断向量表**完成分发——这两张表正是"可调整策略"的载体。
- **异常（代码执行出错）**：CPU 执行出错时陷入内核，由异常服务例程处理。
- **外部设备 → 中断 → 内核 → 设备访问/数据流**：外部设备通过中断通知内核，内核借助设备驱动完成设备访问与数据流动。

在这套结构中，进入/退出内核的陷入与分发流程是固定机制，而向量表、系统调用表中的具体表项以及调度优先级等则是可灵活配置的策略。

## 术语

| 术语 | 解释 |
| --- | --- |
| 异常控制流（ECF） | 由事件发生而改变处理器正常取指执行顺序的控制流，是理解中断、异常和系统调用的核心线索。 |
| 中断 | 来自 CPU 外部 I/O 设备或其他硬件部件的异步事件，处理完成后通常返回下一条指令。 |
| 异常 | CPU 执行指令过程中产生的同步事件，包括陷入、故障和终止等类型。 |
| 陷入（Trap） | 程序有意识安排的同步异常，系统调用是其典型例子，处理后返回下一条指令。 |
| 故障（Fault） | 可恢复的同步错误，例如缺页异常，修复后通常重新执行触发故障的指令。 |
| 终止（Abort） | 不可恢复的严重错误，发生后通常不会返回原程序继续执行。 |
| 中断响应 | 由硬件完成的捕获中断、保存必要现场、查找中断向量并转交处理程序的过程。 |
| 中断向量表 | 按中断号索引的表，表项保存中断处理程序入口地址及相应处理机状态。 |
| 中断描述符表（IDT） | x86 保护模式下按中断号索引门描述符的数据结构，用于定位中断或异常处理程序。 |
| 门描述符 | IDT 中的表项结构，常见类型包括中断门、陷阱门、任务门和调用门。 |
| 中断门 | 进入处理程序时硬件自动清除 IF 位、关闭中断的一类门描述符。 |
| 陷阱门 | 进入处理程序时不会自动关闭中断的一类门描述符，Linux 的 0x80 系统调用门使用陷阱门。 |
| 全局描述符表（GDT） | 存放段描述符的表，硬件结合段选择符从中取得段基址以定位处理程序。 |
| 上半部与下半部 | Linux 将紧急且需要关中断快速执行的处理放在上半部，将可延迟的非紧急处理放在下半部。 |
| 系统调用 | 操作系统提供给用户程序调用内核功能的接口，通过陷入指令使用户态进入内核态。 |
| 陷入指令/访管指令 | 主动引发异常并从用户态进入内核态的特殊指令，如 int 0x80、syscall、ecall 等。 |
| 系统调用号 | 为每个系统调用预先分配的功能编号，用于索引系统调用表。 |
| 系统调用表 | 保存系统调用号与对应内核服务例程入口地址映射关系的跳转表。 |
| int 0x80 | 32 位 x86/Linux 常用的系统调用陷入指令，对应 IDT 的 128 号表项。 |
| SAVE_ALL | 系统调用入口中的汇编例程，用于把通用寄存器等剩余现场保存到内核栈。 |
| ret_from_sys_call | Linux 系统调用返回前的公共路径，在其中处理重新调度和待处理信号等事项。 |
| 任务状态段（TSS） | x86 中保存不同特权级栈指针等处理器状态信息的数据结构，特权级切换时硬件可从中取得内核栈。 |
| 机制与策略分离 | 固定的底层实现机制与可变的上层决策策略相分离，以同时保证系统基础能力和灵活性。 |
