## 1. 回顾：中断异常、调度三问题与调度基本要素

> 课件 第 8–25 页 · 讲解从 `04:26` 开始

### 调度要解决的三个核心问题

CPU 调度围绕三个问题展开，三者的关系是：调度时机决定"何时进入调度"，调度算法决定"选谁"，上下文切换决定"如何完成换人"。

| 问题 | 含义 | 对应内容 |
|---|---|---|
| **What（选谁）** | 依据什么原则挑选进程/线程分配处理器 | 调度算法 |
| **When（何时选）** | 何时分配处理器 | 调度时机 |
| **How（怎么换）** | 如何分配 CPU，即进程的上下文切换 | 调度过程 |

老师强调：**调度时机是理解整个调度逻辑的关键**——它承接前面的中断异常机制，又引出后面的调度算法；机制与策略相分离，而进程切换的上下文是重点，对应的切换代码很短、多为汇编写就，需要结合代码深入理解`▶ 06:55`。

---

### 前置回顾：中断/异常是进入内核的唯一通路

中断异常机制是用户态进程进入内核的**唯一通路**，系统设计必须保证这条通路及其触发事件是确定的。触发进入内核的三类来源：

- **外部硬件中断**：以 CPU 为中心的外部硬件发来中断信号；
- **异常**：CPU 执行指令时发生异常；
- **Trap（系统调用）**：用户程序执行刻意安排的 trap 指令。

内核处理完对应服务后，统一从调度出口返回用户态`▶ 04:26`。

典型的进入内核、进而可能引发调度的事件包括：

- 创建、唤醒、退出等进程控制操作；
- 进程等待 I/O、I/O 中断；
- 时钟中断（如时间片用完、计时器到时）；
- 进程执行过程中出现 abort 异常；
- 执行 `yield` 主动放弃 CPU。

> **老师强调**：`fork()` 是系统调用，会触发 trap 指令进入内核，在内核中完成新进程创建——这就是先讲中断异常机制的原因`▶ 11:24`。

---

### CPU 调度的时机

需要进行调度的典型情形：

- 进程执行完毕并退出；
- 进程由于某种错误或异常而终止；
- 新进程被创建；
- 运行进程要等待 I/O 操作或其他资源，进入阻塞态；
- 被唤醒的阻塞进程重新回到就绪态；
- 进程用完所分配的时间片，回到就绪队列；
- 进程主动放弃 CPU。

**调度发生的完整链路**：

```
事件发生
 → 当前运行的进程暂停运行
 → 硬件机制响应，进入操作系统
 → 处理相应事件（处理过程中某些进程状态变化，也可能出现新进程）
 → 就绪队列需要调整
 → 进程调度按预设算法从就绪队列选一个进程
```

调度发生的精确时刻是：**内核对中断/异常/系统调用处理后、返回到用户态前的最后时刻**`▶ 06:55`。

在这个调度节点上：换人就触发调度算法选择新进程，不换人就直接返回原进程继续运行`▶ 06:55`。

#### 两类最常见的抢占触发场景

> **老师强调（会考）**：以下两类事件是最常见的抢占触发场景`▶ 12:29`。

1. **`fork()` 创建更高优先级的新进程**：`fork()` 新建进程放入就绪队列，从内核返回调度程序时，比较新进程与当前进程的优先级，若新进程优先级更高则发生抢占`▶ 12:29`。
2. **等待事件的旧进程被唤醒**：原本等待磁盘读结果的进程从等待态转为就绪态时，若其优先级高于当前运行进程，也会触发抢占`▶ 12:29`。

抢占式调度的核心实现逻辑，就是在内核处理完事件、返回调度节点时比较进程优先级，始终让最高优先级的进程先上 CPU，无需额外复杂实现`▶ 12:29`。

---

### 调度过程：进程切换与上下文切换

进程调度程序从就绪队列选出要运行的进程（可能是刚被暂停的进程，也可能是另一个新进程）后，需要完成**进程切换**：一个进程让出处理器，由另一个进程占用处理器的过程。

#### 什么是上下文

进程运行时，其硬件状态保存在 CPU 的寄存器中，包括：

- 程序计数器（PC）；
- 程序状态寄存器（PSW）；
- 栈指针；
- 通用寄存器；
- 其他控制寄存器。

进程不运行时，这些寄存器的值保存在 **PCB** 中。将 CPU 硬件状态从一个进程换到另一个进程，就称为**上下文切换（context switch）**。

上下文切换主要包括两部分工作：

1. **切换全局页目录**，加载新的地址空间；
2. **切换内核栈和硬件上下文**，硬件上下文包含内核执行新进程所需的全部信息（如 CPU 相关寄存器）。

整个过程 = 保存原进程的各种状态 + 恢复新进程的各种状态。

#### 上下文切换具体步骤（A 下、B 上）

1. 保存进程 A 的上下文环境（PC、PSW、其他寄存器……）；
2. 用新状态和其他相关信息更新进程 A 的 PCB；
3. 把进程 A 移至合适的队列（就绪、阻塞……）；
4. 将进程 B 的状态设置为运行态；
5. 从进程 B 的 PCB 中恢复上下文（PC、PSW、其他寄存器……）。

#### XV6 中的上下文切换

在 `<kernel/swtch.S>` 中：

- `a0` 寄存器存放第一个参数：指向 **old 进程上下文**的指针；
- `a1` 寄存器存放第二个参数：指向 **new 进程上下文**的指针。

#### 上下文切换的开销（cost）

- **直接开销**：内核完成切换所用的 CPU 时间
  - 保存和恢复寄存器；
  - 切换地址空间（相关指令比较昂贵）。
- **间接开销**：
  - 高速缓存（Cache）、缓冲区缓存（Buffer Cache）、TLB（Translation Look-aside Buffer）失效。

### 调度算法的设计背景

#### 三类进程及其关注的目标

| 类型                    | 特征                                        | 典型程序             | 关注指标             |
| --------------------- | ----------------------------------------- | ---------------- | ---------------- |
| **交互式进程** interactive | 经常与用户交互，大量时间等待用户输入；响应要快，平均延迟应低于 50~150 ms | shell、文本编辑器、图形应用 | 响应时间、均衡性         |
| **批处理进程** batch       | 不必交互，通常后台运行，不必很快响应                        | 营业额计算、利息计算、索赔处理  | 吞吐量、周转时间、CPU 利用率 |
| **实时进程** real-time    | 有实时需求，不应被低优先级进程阻塞，响应时间要短                  | 视频/音频、机械控制       | 最后期限、可预测性        |

应用场景在不断演进：批处理系统 → 多道程序设计系统 → 批处理与分时混合系统 → 个人计算机 → 网络服务器 → 人-机-物协同。老师补充：服务器、个人计算机、物联网、大模型等不同场景适用的调度算法各不相同 `▶ 09:22`。

#### 调度算法的设计考虑（多维度）

- **用户角度**：周转时间、响应时间、最后期限；
- **系统角度**：吞吐量、CPU 利用率、公平性、强制优先级、平衡资源；
- 此外还有均衡性、可预测性等。

#### 调度算法衡量指标

**性能指标：**

- **吞吐量（Throughput）**：每单位时间完成的进程数目；
- **周转时间 TT（Turnaround Time）**：每个进程从提出请求到运行完成的时间；
- **响应时间 RT（Response Time）**：从提出请求到第一次回应的时间。

**非性能指标：**

- **公平性（Fairness）**；
- **资源利用率**，如 CPU 利用率（CPU Utilization，即 CPU 做有效工作的时间比例）。

**特定场景指标：**

- 实时性、能耗。

各指标之间需要**折衷权衡**：它们是可供决策的依据，且相互依赖。

### 设计调度算法要讨论的五个要点

> PCB 是非常重要的数据结构，所有调度决策都要参考 PCB 中记录的、与 CPU 调度相关的信息`▶ 09:22`。

#### 1. 进程优先级（数）

- **静态优先级**：进程创建时指定，运行过程中不再改变；
- **动态优先级**：创建时指定一个初值，运行过程中可动态变化，例如等待时间较长的进程可提升优先级。

（老师提示：要区分"优先级"与"优先数"，以及动态/静态优先级`▶ 09:22`。）

#### 2. 进程就绪队列的组织

- **按优先级排队（多级就绪队列）**：设置就绪队列 1、就绪队列 2、……、就绪队列 n，进程因创建进入队列，等待的事件发生后从等待队列回到相应就绪队列，被调度上 CPU；可发生抢占，等待事件时再进入等待队列。
- **另一种排队方式**：不同队列各自挂接 CPU，按各自的创建、调度、结束流程组织。

老师补充：Windows 和 FreeBSD 采用不同的队列调度结构`▶ 09:22`。

#### 3. 抢占式与非抢占式调度

指进程占用 CPU 的方式：

- **可抢占式（Preemptive，可剥夺式）**：当有比正在运行进程优先级更高的进程就绪时，系统可强行剥夺当前进程的 CPU，交给更高优先级进程。
- **不可抢占式（Non-preemptive，不可剥夺式）**：进程一旦被调度运行，除非由于自身原因不能运行，否则一直运行下去。

老师补充：不可抢占方式下，进程只有在自身触发阻塞（如主动等待磁盘 I/O）、时间片到、主动结束时才会让出 CPU；抢占与不可抢占的差异仅靠现有中断/调度机制即可实现，无需额外改动`▶ 13:54`。

#### 4. I/O 密集型与 CPU 密集型进程

按进程执行过程中的行为划分：

- **I/O 密集型（I/O-bound）**：频繁进行 I/O，通常花费大量时间等待 I/O 完成（如打印、读写等），CPU 占用占比低；表现为"短 CPU 区间 + I/O 等待"交替`▶ 14:36`。
- **CPU 密集型（CPU-bound，计算密集型）**：需要大量 CPU 时间进行计算，表现为长 CPU 区间。

调度算法通常会**偏好 I/O 密集型进程**：这类进程频繁让出 CPU，有利于提升系统整体资源利用率；未来对 I/O 密集型进程的调度处理更重要`▶ 14:36`。

#### 5. 时间片（Time slice / quantum）

时间片是一个时间段，分配给调度上 CPU 的进程，确定允许该进程连续运行的时间长度。

- **固定与可变**：可设为固定大小，也可为不同就绪队列配置不同大小的时间片；老师指出时间片是 PCB 中的重要调度参数，具体取值适配后续展开`▶ 16:08`。
- **选择时间片需考虑的因素：**
  - 进程切换的开销；
  - 对响应时间的要求；
  - 就绪进程个数；
  - CPU 能力；
  - 进程的行为。

## 2. 批处理系统调度算法：FCFS、SJF/SRTN与HRRN

> 课件 第 26–36 页 · 讲解从 `16:39` 开始

### 批处理系统调度算法概述

批处理系统的核心优化目标包括：

- **CPU 利用率**
- **吞吐量**（单位时间完成的作业数）
- **周转时间**（从作业提交到完成的总时间）
- 同时兼顾公平性与资源平衡

批处理系统中常见的调度算法有：

- 先来先服务（FCFS, First Come First Serve）
- 最短作业优先（SJF, Shortest Job First）
- 最短剩余时间优先（SRTN/SRT, Shortest Remaining Time Next）
- 最高响应比优先（HRRN, Highest Response Ratio Next）

> 参考教材：OSTEP 第 7 章 Scheduling。

---

### 先来先服务 FCFS

#### 基本思想

FCFS 按照进程进入就绪队列的先后顺序分配 CPU：

- 先就绪的进程先执行；
- 属于**非抢占式调度**；
- 一个进程获得 CPU 后，会一直运行，直到结束或因 I/O 等事件阻塞。

#### 优点

- 实现简单；
- 从等待顺序的角度看较为公平。

#### 缺点

- 长进程会使排在它后面的短进程等待很久，==交互式体验差==；
- CPU 和 I/O 资源的==整体利用率可能较低==；
- 实际系统中很少单独使用 FCFS。

#### 周转时间

周转时间定义为：

$$
T_{\text{turnaround}}=T_{\text{completion}}-T_{\text{arrival}}
$$

即进程从到达至完成所经历的总时间。

平均周转时间为所有进程周转时间之和除以进程数。

#### FCFS 示例

三个进程按顺序就绪：P1、P2、P3。

| 进程 | 运行时间 |
|---|---:|
| P1 | 24s |
| P2 | 3s |
| P3 | 3s |

按 FCFS 顺序执行为：

```text
P1                     P2   P3
|----------------------|----|----|
0                      24   27   30
```

完成时刻分别为：

- P1：24
- P2：27
- P3：30

若三个进程都在时刻 0 到达，则周转时间为：

- P1：24s
- P2：27s
- P3：30s

平均周转时间：

$$
\frac{24+27+30}{3}=27\text{s}
$$

吞吐量：

$$
\frac{3\text{ jobs}}{30\text{s}}=0.1\text{ jobs/s}
$$

#### 改变调度顺序

若改为先执行两个短作业，再执行长作业，即顺序为 P2、P3、P1：

```text
P2    P3    P1
|----|----|----------------------|
0    3    6                      30
```

周转时间为：

- P2：3s
- P3：6s
- P1：30s

平均周转时间：

$$
\frac{3+6+30}{3}=13\text{ s}
$$

吞吐量仍为：

$$
\frac{3}{30}=0.1\text{ jobs/s}
$$

这说明：

- 调度顺序不会改变该例中所有作业全部完成的总时间；
- 但会显著影响==平均周转时间==；
- 先执行短作业可以明显降低平均周转时间。

---

### 最短作业优先 SJF

#### 基本思想

SJF 总是优先选择**预计运行时间最短**的进程执行，核心思路是：

> 先完成短作业，以改善短作业的周转时间，并降低平均周转时间。

SJF 分为两种版本：

1. **非抢占式 SJF**
   - 当前进程一旦开始运行，就一直执行到结束或被 I/O 阻塞；
   - 即使之后到达更短的作业，也不会抢占当前进程。

2. **抢占式 SJF：最短剩余时间优先 SRTN**
   - 当新进程就绪时，比较当前进程和新进程的剩余运行时间；
   - 如果新进程的剩余时间更短，则立即抢占当前进程；
   - 系统始终选择剩余运行时间最短的进程执行。

---

### SJF 与 SRTN 示例

四个进程的到达时刻和总运行时间如下：

| 进程 | 到达时刻 | 运行时间 |
|---|---:|---:|
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |
| P4 | 5 | 4 |

#### 非抢占式 SJF

时刻 0 只有 P1 到达，因此 P1 开始执行。由于非抢占式 SJF 不允许新到达的短进程抢占 P1，所以 P1 一直运行到时刻 7。

时刻 7 时，P2、P3、P4 均已就绪：

- P2 剩余 4；
- P3 剩余 1；
- P4 剩余 4。

选择最短的 P3 执行。随后在 P2 和 P4 中选择，二者运行时间均为 4。执行顺序可表示为：

```text
P1                     P3   P2        P4
|----------------------|----|---------|---------|
0                      7    8        12        16
```

完成时刻：

- P1：7
- P3：8
- P2：12
- P4：16

#### 抢占式 SRTN

每次有新进程到达时，都要重新比较所有就绪进程以及当前进程的剩余运行时间。

执行过程如下：

1. **时刻 0**：只有 P1 到达，P1 开始运行。
2. **时刻 2**：P2 到达。
   - P1 剩余 5；
   - P2 剩余 4；
   - P2 更短，P2 抢占 P1。
3. **时刻 4**：P3 到达。
   - P1 剩余 5；
   - P2 剩余 2；
   - P3 剩余 1；
   - P3 最短，P3 抢占 P2。
4. **时刻 5**：P3 运行 1 个时间单位后结束，同时 P4 到达。
   - P1 剩余 5；
   - P2 剩余 2；
   - P4 剩余 4；
   - P2 最短，恢复 P2。
5. P2 从时刻 5 运行到时刻 7，执行完剩余的 2 个时间单位。
6. 时刻 7 时，P4 剩余 4，P1 剩余 5，选择 P4。
7. P4 从时刻 7 运行到时刻 11。
8. 最后恢复 P1，从时刻 11 运行到时刻 16。

甘特图为：

```text
P1      P2    P3 P2      P4             P1
|-------|-----|--|-------|--------------|------------------|
0       2     4  5       7             11                 16
```

#### 时刻 7 之前各任务剩余运行时间

课件要求列出抢占式情形下时刻 7 之前各任务的剩余运行时间：

| 时刻/事件 | P1 剩余 | P2 剩余 | P3 剩余 | P4 剩余 | 当前运行 |
|---:|---:|---:|---:|---:|---|
| 0，P1 到达 | 7 | — | — | — | P1 |
| 2，P2 到达 | 5 | 4 | — | — | P2 抢占 P1 |
| 4，P3 到达 | 5 | 2 | 1 | — | P3 抢占 P2 |
| 5，P3 完成、P4 到达 | 5 | 2 | 0 | 4 | P2 恢复 |
| 7，P2 完成 | 5 | 0 | 0 | 4 | 接下来运行 P4 |

---

### SJF 的性质

#### 优点

- 可以获得最短的平均周转时间；
- 尤其在所有进程同时可运行时，SJF 的平均周转时间最优；
- 短作业能够快速完成，系统平均等待时间较短。

> **老师强调**：当所有进程同时到达时，SJF 可以得到最短的平均周转时间。该结论可以通过交换任意两个相邻进程的调度顺序，比较平均周转时间的变化来证明。

#### 缺点

1. **不公平，可能产生饥饿**

   如果系统中不断有短作业到达，长作业可能一直得不到 CPU，从而产生饥饿现象。

2. **需要预测未来**

   SJF 必须预先知道每个作业的预计运行时间，但实际运行时长在执行前往往无法精确知道。

批处理系统中通常要求作业提交时给出预估运行时间。若用户故意虚报运行时间，系统也会在作业运行过程中记录实际耗时并进行记账结算，因此虚报并不能带来额外收益。

对于运行模式固定的批处理作业，运行时间可能较容易估计。例如，全球连锁餐饮企业每天固定时间统计各门店销售数据的批处理任务，其数据规模和处理流程相对稳定，运行时长也较稳定可控。

---

### 最高响应比优先 HRRN

HRRN（Highest Response Ratio Next）是一种综合考虑**等待时间**和**作业处理时间**的调度算法。

#### 响应比公式

每个进程计算一个响应比 $R$：

$$
R=\frac{\text{作业周转时间}}{\text{作业处理时间}}
$$

其中，在调度决策时刻：

$$
\text{作业周转时间}
=
\text{作业处理时间}
+
\text{作业等待时间}
$$

所以：

$$
R=
\frac{\text{作业处理时间}+\text{作业等待时间}}
{\text{作业处理时间}}
$$

化简为：

$$
R=1+\frac{\text{作业等待时间}}{\text{作业处理时间}}
$$

调度时，系统选择响应比最高的进程运行。

#### 直观含义

响应比同时受到两方面影响：

- **处理时间越短，响应比越高**：短作业更容易被优先调度，效果类似 SJF；
- **等待时间越长，响应比越高**：等待很久的长作业响应比会逐渐增大，最终有机会被调度。

因此，HRRN 是 FCFS 与 SJF 之间的折中：

| 算法 | 主要依据 | 特点 |
|---|---|---|
| FCFS | 到达顺序、等待时间 | 简单公平，但短作业可能被长作业阻塞 |
| SJF | 作业处理时间 | 平均周转时间短，但长作业可能饥饿 |
| HRRN | 等待时间与处理时间的比值 | 同时照顾短作业和等待时间长的作业 |

#### 为什么 HRRN 能避免长作业饥饿

- 对短作业而言，处理时间小，即分母小，因此在相同等待时间下响应比更高，容易被优先执行；
- 对长作业而言，随着等待时间不断增加，响应比也不断上升；
- 当长作业等待足够久后，其响应比可以超过后来到达的短作业，从而获得执行机会。

#### 开销与适用问题

HRRN 每次调度时都要为各个就绪进程重新计算响应比并进行比较、选择，因此会产生额外开销。系统还需要为每个进程维护与等待时间、处理时间和响应比相关的信息。

> **老师强调**：HRRN 的重要意义不只是算法本身，而是体现调度设计中的折衷权衡：不能只考虑平均周转时间，还要兼顾公平性、饥饿问题和调度开销。

若采用抢占式 HRRN，还需要频繁重新计算所有进程的响应比并重新排序，系统开销更大，因此是否值得抢占需要根据具体场景权衡。课件中也特别提出了“抢占 or 不可抢占”的 tradeoff 问题。

## 3. 交互式系统调度：时间片轮转与虚拟轮转

> 课件 第 37–48 页 · 讲解从 `32:16` 开始

### 交互式系统常用调度算法

交互式系统的调度目标与批处理系统不同，更关注：

- **响应时间**：用户发出请求后，系统要尽快响应。
- **公平性、平衡性**：各进程应较公平地共享 CPU，避免某些进程长期得不到运行。
- **抢占与优先级反转**：交互式系统常使用抢占式调度，同时要处理优先级反转等问题。

常见算法包括：

| 调度算法                              | 说明                                |
| --------------------------------- | --------------------------------- |
| 时间片轮转 RR（Round Robin）             | 每个就绪进程轮流运行一个固定时间片                 |
| 优先级调度 HPF（Highest Priority First） | 优先调度优先级最高的进程                      |
| 多级队列调度                            | 将进程放入不同队列，分别调度                    |
| 多级反馈队列调度                          | 进程可在不同队列间移动，兼顾 CPU 密集型和 I/O 密集型进程 |
| 最短进程优先 SPN                        | 思想类似批处理系统中的短作业优先，只是对象变为交互式进程      |

> **老师强调**：最短进程优先与批处理系统的短作业优先本质思想一致，不再重复；各类调度算法都可以设计成抢占式或非抢占式版本 `▶ 32:16`。

---
 
### 时间片轮转调度 RR

#### 基本思想

时间片轮转的核心是**周期性任务切换**：

1. 系统维护一个可运行进程列表，即就绪队列。
2. 每个进程被调度到 CPU 后，只能运行一个固定长度的时间片。
3. 时间片用完后，无论进程是否结束，都被强制换下 CPU。
4. 该进程重新回到就绪队列队尾，等待下一轮调度。
5. 时钟中断是实现时间片的基础。

其运行过程可概括为：

```text
P1 → P2 → P3 → P4 → P1 → P3 → …
```

如果某个进程的时间片用完，就排到就绪队列末尾；如果进程提前结束，则直接退出。

#### 时间片的硬件与系统实现

进程被调度运行时，操作系统会把时间片换算成定时器值，并加入系统定时器队列。定时器依赖时钟中断定期计数：

- 计算机晶体振荡器发出稳定脉冲；
- 脉冲触发时钟中断；
- 每次时钟中断使当前进程的定时器值减一；
- 减到 0 时，表示时间片到期，触发进程切换和调度。

多个进程同时存在时，每个进程都有自己的定时器信息，当前运行进程的时间片到期后发生轮转`▶ 33:39 · 35:44 · 36:03`。

#### 设计目标

RR 的目标是改善短任务的平均响应时间：

- 短进程通常轮转一到两次即可完成；
- 长进程不会一直独占 CPU；
- 所有就绪进程都能较公平地获得 CPU 时间`▶ 36:37`。

---

### RR 调度示例：时间片 q = 20

四个进程的执行时间如下：

| 进程 | 总执行时间 |
|---|---:|
| P1 | 53 |
| P2 | 8 |
| P3 | 68 |
| P4 | 24 |

假设四个进程按 P1、P2、P3、P4 的顺序在时刻 0 到达，时间片为 20。

调度片段如下：

```text
0    20   28   48   68   88  108  112  125  145  153
| P1 | P2 | P3 | P4 | P1 | P3 | P4 | P1 | P3 | P3 |
```

执行过程：

- P1 先运行 20，剩余 33；
- P2 只需要 8，在 28 时刻完成；
- P3 运行 20，剩余 48；
- P4 运行 20，剩余 4；
- P1 再运行 20，剩余 13；
- P3 再运行 20，剩余 28；
- P4 运行最后 4，完成；
- P1 运行最后 13，完成；
- P3 依次运行 20 和 8，完成。

#### 等待时间计算

| 进程 | 等待时间计算 | 等待时间 |
|---|---|---:|
| P1 | $(68-20)+(112-88)$ | 72 |
| P2 | $20-0$ | 20 |
| P3 | $(28-0)+(88-48)+(125-108)$ | 85 |
| P4 | $(48-0)+(108-68)$ | 88 |

因此：

$$
\text{平均等待时间}
=\frac{72+20+85+88}{4}
=66.25
$$

---

### 时间片大小的选择

时间片 $q$ 的大小直接影响 RR 的性能。

#### 时间片过长

如果时间片大于典型的交互请求所需处理时间：

- 短进程可能在一个时间片内就结束；
- 但排在前面的长进程会长期占用 CPU；
- RR 会逐渐退化为 FCFS；
- 短进程响应时间变长。

因此，时间片过长会失去轮转调度的意义`▶ 38:48`。

#### 时间片过短

如果时间片过短：

- 进程会频繁被抢占；
- 上下文切换次数大幅增加；
- CPU 时间被大量用于切换而非实际计算；
- 还会带来 TLB 刷新等间接开销。

> **老师强调**：上下文切换不仅有直接的寄存器保存、恢复开销，还可能带来 TLB 刷新等空间局部性方面的间接开销`▶ 39:11`。

#### 响应时间与时间片的关系

设就绪队列中有 $n$ 个进程，时间片长度为 $q$。一个进程通常要等待其他进程各自运行一个时间片后才能再次得到 CPU，因此粗略响应时间与：

$$
n \times q
$$

有关。

==时间片过大，短任务等待时间增加；时间片过小，切换开销增加。==实际系统中通常采用经验值，并参考 Linux、Windows 等成熟操作系统的设置，再结合具体应用场景测试调整`▶ 38:09 · 39:59`。

---

### RR 的开销

假设：

- 时间片为 10 ms；
- 一次进程切换花费 0.1 ms。

则每经过约 10 ms 的有效运行，需要 0.1 ms 的切换开销：

$$
\frac{0.1}{10}=1\%
$$

即 CPU 约有 1% 的时间用于调度切换。

课件给出的不同运行长度对应切换次数如下：

| 进程运行时间 | 时间片 | 上下文切换次数 |
|---:|---:|---:|
| 12 | 10 | 0 |
| 10 | 10 | 1 |
| 6 | 10 | 1 |
| 1 | 10 | 9 |

这里反映的是不同时间片设置和进程运行长度下，进程被切分及调度的次数差异。时间片越小，长进程经历的切换通常越多。

---

### RR 的优缺点

#### 优点

- **公平**：每个就绪进程按顺序轮流获得 CPU。
- **响应快**：有利于交互式计算，短进程等待时间较短。
- **避免长进程长期独占 CPU**。
- 适合需要快速响应的通用分时系统。

#### 缺点

- 进程切换带来较高开销；
- 时间片过小时上下文切换过于频繁；
- 对长度相近的进程，RR 未必比 FCFS 更好；
- 时间片大小需要根据系统目标仔细权衡。

> **老师强调**：经验上时间片取 10 ms、切换开销为 0.1 ms 时，CPU 开销约占 1%，通常较为合适`▶ 40:12`。

---

### RR 与 FCFS 的进一步比较

#### 两个相同长度进程的例子

设有两个进程 A、B：

- A 运行时间：100 ms；
- B 运行时间：100 ms；
- 时间片：1 ms；
- 假设上下文切换不耗时间；
- A、B 按 A 在前、B 在后的顺序到达。

使用 RR 时：

```text
A B A B A B … A B
```

每次各运行 1 ms：

- A 在第 199 ms 完成；
- B 在第 200 ms 完成。

也就是说：

- A 的等待时间为 99 ms；
- B 的等待时间为 100 ms；
- 两个进程合计等待时间为 199 ms。

使用 FCFS 时：

- A 从 0 运行到 100；
- B 从 100 运行到 200；
- A 等待 0 ms；
- B 等待 100 ms；
- 合计等待时间为 100 ms。

> **老师强调**：当进程长度相近时，RR 不断交替执行反而会使两个进程都较晚完成；FCFS 让一个先完成、另一个后完成，整体周转表现更好。因此 ==RR 并不是在所有情况下都优于 FCFS== `▶ 41:35 · 43:38`。

#### 四个进程在不同算法下的平均等待时间

仍使用四个进程：

| 进程 | 执行时间 |
|---|---:|
| P1 | 53 |
| P2 | 8 |
| P3 | 68 |
| P4 | 24 |

不同时间片和 FCFS 情况下的等待时间如下：

| 调度方式 | P1 | P2 | P3 | P4 | 平均等待时间 |
|---|---:|---:|---:|---:|---:|
| RR(q=1) | 84 | 22 | 145 | 121 | 61.25 |
| RR(q=5) | 82 | 20 | 85 | 57 | 61.25 |
| RR(q=8) | 80 | 8 | 85 | 58 | 57.25 |
| RR(q=10) | 82 | 10 | 85 | 56 | 61.25 |
| RR(q=20) | 72 | 20 | 85 | 68 | 66.25 |
| Best FCFS | 32 | 0 | 85 | 88 | 31.25 |
| Worst FCFS | 68 | 85 | 0 | 8 | 83.5 |

可以看出：

- RR 的结果明显受时间片影响；
- FCFS 的结果高度依赖进程到达或排列顺序；
- 最优 FCFS（短进程优先排列）平均等待时间很低；
- 最差 FCFS 下平均等待时间很差；
- RR 通过轮转避免了最差情况下短进程被长进程完全阻塞，但也付出切换和整体周转时间方面的代价。

---

### 经典五状态模型中的 RR 队列规则

在标准五状态模型中：

1. 系统通常设置一个就绪队列；
2. 进程被调度到 CPU 运行；
3. 若运行完成，则退出系统；
4. 若时间片用完但进程未完成，则回到就绪队列队尾；
5. 若进程在时间片未用完时发起 I/O 或等待某事件，则进入相应等待队列；
6. 等待事件完成后，进程再回到就绪队列。

问题在于：一个进程因为 I/O 阻塞而离开 CPU，I/O 完成后却必须排到就绪队列末尾，无法很快再次获得 CPU。

---

### 虚拟轮转法 Virtual RR

虚拟轮转法是对经典 RR 队列规则的改进。

#### 为什么偏好 I/O 密集型进程

I/O 密集型进程通常：

- 只使用很短的一段 CPU 时间；
- 很快发起 I/O 请求；
- 主动放弃 CPU，让其他进程使用；
- I/O 操作由磁盘、网卡、打印机或 DMA 等部件并行执行。

==操作系统偏好这类进程，是因为让它们尽快发出 I/O 请求，可以同时保持 CPU 和 I/O 设备忙碌，提高系统整体资源利用率== `▶ 46:32 · 48:06`。

#### 虚拟轮转法的队列结构

在普通就绪队列之外，增加一个辅助队列：

- 普通时间片用完的进程进入普通就绪队列；
- 因 I/O 等待而阻塞、等待事件完成后返回的进程进入辅助队列；
- 调度时优先从辅助队列中选择进程；
- 辅助队列为空时，再从普通就绪队列调度。

可概括为：

```text
I/O 完成 ──→ 辅助队列（优先）
时间片用完 ──→ 普通就绪队列（队尾）
```

这样，I/O 密集型进程从等待状态返回后，不必和所有计算密集型进程一起排在就绪队列末尾，而能较快再次获得 CPU，继续发起下一次 I/O。

> **老师强调**：虚拟轮转法的关键修改是新增一个优先的辅助队列，用来接纳从等待状态返回的进程，使 I/O 密集型进程得到更好的响应 `▶ 44:26 · 46:32`。
 
---

### CPU 密集型与 I/O 密集型混合示例

系统中有三个进程：

| 进程 | 行为 |
|---|---|
| A | 需要计算 1000 ms，CPU 密集型 |
| B | 需要计算 1000 ms，CPU 密集型 |
| C | 循环执行：使用 CPU 1 ms，然后使用磁盘 I/O 10 ms |

进程 C 的每个周期为：

```text
CPU 1 ms → 磁盘 I/O 10 ms → CPU 1 ms → 磁盘 I/O 10 ms → …
```

C 大约 91% 的时间处于磁盘 I/O 阶段。单独运行时：

- C 可以使磁盘利用率达到约 91%；
- A 或 B 单独运行时，可以使用接近 100% 的处理器。

混合运行时的目标是：

> **同时保持 CPU 和磁盘忙碌**，既不能让 CPU 长时间空闲，也不能让磁盘长期空闲`▶ 48:06 · 49:53`。

#### 使用 FCFS

如果 A 或 B 先于 C 运行：

- A、B 都是 CPU 密集型进程；
- C 可能等待多达 2000 ms 才能获得第一次 CPU；
- C 只有先运行 1 ms，才能发起磁盘 I/O 请求；
- 在 C 被阻塞期间，磁盘没有来自 C 的新任务，长时间空闲。

因此 FCFS 会导致磁盘利用率极低。

#### 使用 RR，q = 100 ms

调度形式近似为：

```text
C → A → B → C → A → B → …
```

C 先运行 1 ms 并发起 10 ms I/O，然后 A、B 分别运行较长时间。等到 C 再次获得 CPU 时，它的磁盘 I/O 早已完成，但由于不能及时发出下一次 I/O 请求，磁盘大多数时间空闲。

在大约每 200 ms 的周期中，只有约 10 ms 有磁盘操作，磁盘利用率很低`▶ 51:01`。

#### 使用 RR，q = 1 ms

调度顺序近似为：

```text
C A B A B A B … C A B A B A B … C …
```

由于时间片很短，C 可以频繁获得 CPU：

- 每次 C 的 10 ms I/O 完成后，它很快又能运行 1 ms；
- 随后立即发起下一次磁盘请求；
- 磁盘利用率接近 90%；
- A、B 只是损失少量 CPU 时间，性能受到的影响很小。

但问题是：

- 所有进程被频繁切换；
- 上下文切换次数大量增加；
- 切换开销可能显著降低系统效率。

因此，小时间片可以提高磁盘利用率，但要用较高切换开销换取`▶ 51:46`。

#### 使用 SRTN

SRTN（Shortest Remaining Time Next，最短剩余时间优先）是短作业优先的抢占式版本。

在本例中：

1. C 先运行 1 ms，然后进入 10 ms I/O 等待；
2. A 开始运行；
3. C 的 I/O 完成后回到就绪队列；
4. 比较剩余 CPU 时间，C 下一次只需要 1 ms，比 A、B 都短；
5. C 抢占 CPU，再运行 1 ms 并发起 I/O；
6. C 阻塞后 A 继续运行；
7. 该过程不断重复。

调度形式近似为：

```text
C → A → C → A → C → A → …
```

SRTN 能让 C 的 I/O 一结束就尽快运行，因此有利于保持磁盘忙碌；但由于 C 每次都拥有最短的下一次 CPU 突发，B 可能长时间得不到调度，产生公平性问题`▶ 53:08`。

---

### 本章小结

- RR 通过固定时间片和时钟中断实现周期性抢占，公平且响应快。
- 时间片过大使 RR 退化为 FCFS；时间片过小导致频繁上下文切换。
- RR 对短进程友好，但当所有进程长度相近时，FCFS 可能获得更好的整体周转时间。
- I/O 密集型进程虽然 CPU 使用时间短，但及时运行它们可以提高磁盘等外设利用率。
- 虚拟轮转法通过增加辅助队列，让 I/O 完成返回的进程优先得到调度，是对经典 RR 的改进。

## 4. 优先级调度与优先级反转

> 课件 第 49–52 页 · 讲解从 `1:04:30` 开始

### 最高优先级调度算法

核心思路：从就绪队列中选择优先级最高的进程投入运行`▶ 1:04:30`。

#### 优先级的表示与设定

- 若系统用**优先数**表示优先级，必须先明确约定：是优先数越大优先级越高，还是越小优先级越高`▶ 1:04:30`。
- 通用的优先级设定原则：
  - 系统进程优先级 **高于** 用户进程；
  - 前台进程优先级 **高于** 后台进程；
  - 操作系统通常更偏好 **I/O 型进程**`▶ 1:04:30`。

#### 静态优先级与动态优先级

- 优先级可以在整个生命周期内保持不变，即**静态优先级**；
- 也可以在运行过程中动态调整，即**动态优先级**；
- 若支持动态调整，PCB 中需要保存相应的优先级字段`▶ 1:04:30`。

#### 就绪队列组织

就绪队列可以按照优先级组织：

- **单就绪队列**：新的高优先级进程进入时，按优先级插入到队列中的对应位置；
- **多就绪队列**：将进程插入到与其优先级相匹配的队列中`▶ 1:06:23`。

#### 算法评价

- 优点：实现思路简单；
- 缺点：调度不公平，低优先级进程可能长期得不到执行，从而产生**饥饿（starvation）**`▶ 1:06:23`。

> **老师强调**：后续评价调度算法时，需要结合公平性、是否支持抢占等指标进行分析`▶ 1:06:23`。

---

### 优先级反转问题

优先级反转又称**优先级反置、优先级翻转、优先级倒挂**（Priority Inversion）。

它是指在基于优先级的调度中，==一个低优先级进程持有高优先级进程所需的资源==，导致高优先级进程不得不等待低优先级进程释放资源，违背了“高优先级进程应优先运行”的设计原则`▶ 1:07:31 · 1:08:03`。

> **老师强调**：优先级反转只发生在**基于优先级的抢占式调度**场景中；非抢占式调度不会发生该问题`▶ 1:08:03`。

#### 典型场景

设三个进程访问同一个临界资源：

- **H**：高优先级进程；
- **M**：中优先级进程，CPU 型；
- **L**：低优先级进程。

执行过程如下：

1. **L 先进入临界区**，持有共享资源；
2. L 尚未退出临界区时，**H 就绪并抢占 CPU**；
3. H 也想进入同一临界区，但资源已被 L 占用，因此 H 阻塞；
4. CPU 交还给 L，但在 L 继续执行前，**CPU 型的 M 就绪**；
5. M 优先级高于 L，因此 M 抢占 CPU 并长时间运行；
6. L 无法继续执行，也就无法释放资源；
7. H 虽然优先级最高，却被 L 和 M 间接阻塞，长期无法运行`▶ 1:09:21`。

表面上看，高优先级进程 H 被低优先级进程 L 阻塞；更严重的是，==中优先级进程 M 也能通过拖延 L 来间接拖延 H==，因此形成“优先级反转”。

#### 真实案例：火星探测器

美国火星探测器搭载的实时操作系统 VxWorks 采用基于优先级的抢占式调度，曾出现优先级反转问题。系统中主要有三类任务：

- 高优先级：数据传输任务；
- 中优先级：通信任务；
- 低优先级：火星环境测量任务。

事件过程：

1. 低优先级测量任务占用总线；
2. 高优先级数据传输任务抢占 CPU，但因无法获取总线而阻塞；
3. 中优先级通信任务占用 CPU 长时间运行；
4. 低优先级任务无法继续执行并释放总线；
5. 高优先级数据传输任务长时间停滞，最终导致探测器反复重启`▶ 1:11:42`。

> **老师补充**：火星探测器系统本身带有优先级反转解决方案，但相关开关被人为关闭，导致问题无法被处理，最终系统触发重启`▶ 1:17:58`。

---

### 优先级反转的影响

- 高优先级进程停滞不前；
- 系统整体性能降低；
- 在实时操作系统中可能造成严重后果，属于系统错误；
- 因此实时系统中出现优先级反转时，必须主动干预`▶ 1:11:23 · 1:14:03`。

---

### 优先级反转的解决方案

#### 1. 设置优先级上限

优先级上限协议（Priority Ceiling Protocol）的基本思想是：

- ==当低优先级进程占用临界资源并阻塞了高优先级进程时，将该低优先级进程的优先级提升到系统规定的最高优先级==；
- 使它能够快速执行完临界区代码并释放资源；
- 当它退出临界区后，再将其优先级恢复为原来的值`▶ 1:16:31`。

这样可以防止中优先级进程在低优先级进程持有资源期间抢占 CPU。

#### 2. 优先级继承

优先级继承（Priority Inheritance）的基本思想是：

- 当低优先级进程阻塞了某个高优先级进程时，让低优先级进程==暂时**继承被阻塞的高优先级进程的优先级**==；
- 低优先级进程以高优先级继续执行，尽快退出临界区并释放资源；
- 释放资源后，再恢复到原来的优先级`▶ 1:16:31`。

优先级继承与优先级上限的目标相同，都是==暂时提高资源持有者的优先级==，使其尽快释放资源；区别主要在于提升后的优先级==取值不同==：

| 方案       | 临时优先级               |
| -------- | ------------------- |
| 优先级天花板协议 | 提升到系统规定的优先级上限/最高优先级 |
| 优先级继承    | 继承被它阻塞的高优先级进程的优先级   |

> **老师说明**：前两种解决方案本质上都是调整进程优先级，算法都比较简单 `▶ 1:16:31`。

#### 3. 使用中断禁止

基本思想：

- 低优先级进程进入[^1]临界区后禁止中断；
- 在临界区执行期间，进程不会被其他进程或中断打断；
- 等其完整执行完临界区代码并释放共享资源后，再退出“禁止中断”状态；
- 一旦退出临界区，就可以正常被抢占，高优先级进程随后进入临界区`▶ 1:14:03 · 1:16:01`。

该方法通过保证临界区执行的原子性，从根源上避免低优先级进程在持有资源期间被抢占。但禁止中断只应限制在临界区范围内，不能长时间禁用。

## 5. 多级队列、多级反馈队列及其他交互调度算法

> 课件 第 53–58 页 · 讲解从 `1:18:40` 开始

### 多级队列调度算法（Multilevel Queue Scheduling）

多级队列调度算法将就绪进程划分到多个队列中，理解该算法需要关注四个核心问题`▶ 1:18:40`：

- **根据什么分队列**：一般按进程的类型或优先级分类，例如前台交互进程、后台批处理进程分别进入不同队列。
- **排队方式**：常见有两种——纯按优先级排队；以及进程从最高级队列开始，逐级降级调度`▶ 1:18:40`。
- **哪些进程优先级高**：不同队列被赋予不同优先级，通常队列级别越高，其中进程的优先级越高。
- **每一级队列调度策略是否相同**：各级队列可以采用不同的调度策略，例如高优先级前台队列用时间片轮转，低优先级后台队列用 FCFS。

调度时通常优先服务高优先级队列：只有高优先级队列为空时，才调度低优先级队列中的进程。

---

### 多级反馈队列调度算法（Multilevel Feedback Queues，MFQ）

#### 算法背景与定位

- 1962 年由 **Corbato** 提出，最初应用于 **CTSS（Compatible Time-Sharing System，兼容分时系统）**。
- UNIX 的分支 BSD（由加州大学伯克利分校开发发布）的 **5.3 版**采用了该算法；课堂上也提到其最早被 FreeBSD 采用`▶ 1:19:45`。
- 它是一个**综合调度算法**，在多种调度目标之间进行折衷权衡（tradeoff）。

#### 机制与策略分离

多级反馈队列体现了"机制与策略分离"的设计思想`▶ 1:20:46`：

- **机制**：固定不变的调度流程。例如：按优先级选择进程、多级队列的组织方式、队列间的调度顺序等。
- **策略**：可以调整的规则。例如：通过优先级继承等方式调整进程优先级，从而改变调度顺序。

#### 基本规则（固定机制）

1. 设置多个就绪队列，**第一级队列优先级最高**。
2. 给不同队列中的进程分配**长度不同的时间片**：第一级队列时间片最小；随着队列优先级降低，时间片增大。
3. 当第一级队列为空时，才在第二级队列调度，以此类推。
4. 各级队列内部按照**时间片轮转（RR）** 方式调度。
5. 新创建的进程就绪后，进入**第一级队列**。
6. 进程用完时间片而放弃 CPU 后，进入**下一级**就绪队列；到达最底层后不再降级，仍按轮转方式调度`▶ 1:23:50`。

> **老师强调**：低优先级进程被调度的机会少，但一旦获得调度，时间片更长——这是一种平衡设计；但该设计仍可能导致低优先级进程**饥饿** `▶ 1:22:09`。

#### 进程的去向：用完时间片 vs. 阻塞

| 放弃 CPU 的原因 | 进程去向 | 队列级别变化 |
|---|---|---|
| 用完时间片 | 进入下一级就绪队列 | 降一级（到底层后不再降） |
| 因阻塞（如 I/O）放弃 CPU | 进入相应等待队列；事件发生后返回**原来一级**就绪队列 | **不降级** |

- 进程因阻塞（如执行 I/O）放弃 CPU 时，从 Running 态进入 Blocked 态；当等待事件发生（如磁盘中断）后转为就绪态。`read` 是阻塞式系统调用`▶ 1:24:47`。
- 阻塞解除后返回**原来的优先级队列**而不降级，这本身就是对 **I/O 密集型进程的偏好设计**：I/O 型进程常因等待事件而主动放弃 CPU，用不完时间片，因而能长期停留在高优先级队列`▶ 1:24:47 · 1:29:46`。
- 与之相对，**CPU 密集型进程**会反复用完时间片，逐渐"沉降"到低优先级队列，可能产生饥饿问题；操作系统后续会设计相应策略（如老化机制）来缓解饥饿`▶ 1:29:46`。

#### 两个可选策略（考点讨论）

> **老师强调**：课件中打问号的两处是考点，具体选择属于"策略"层面，没有唯一标准答案`▶ 1:25:56`。

**讨论一：解除阻塞的进程回到原就绪队列的队首还是队尾？**

- 回队首或队尾都是可选策略，一般不会插入队列中间，因为没有明确的插队原则`▶ 1:25:56`。

**讨论二：被 I/O 阻塞、未用完时间片的进程再次被调度时，如何处理时间片？**

可以有多种选择`▶ 1:27:07`：

- 沿用之前的**剩余时间片**；
- 重新分配一个**完整的新时间片**；
- 给予**时间片奖赏**（例如因频繁让出 CPU 而奖励更长时间片）。

#### 允许抢占时的规则

若系统允许抢占，当有更高优先级进程就绪时，可以抢占当前进程的 CPU：

- 被抢占的进程回到**原来一级**就绪队列（不降级）。
- 回到**队首还是队尾**存在讨论：课堂观点认为通常回到**队首**更符合公平原则，**Windows 系统采用此策略**`▶ 1:28:02`。
- 也有观点认为可将被抢占进程升级，但这种做法合理性不足`▶ 1:28:02`。

#### 队列模型示意

```
        创建
          │
          ▼
     ┌─────────┐  调度   ┌─────┐ 用完时间片降级
     │就绪队列1 │────────▶│ CPU │──────────┐
     └─────────┘         └─────┘          │
          ▲  ▲ 空时调度下一级             ▼
     ┌─────────┐                      ┌─────────┐
     │就绪队列2 │◀─────────────────────│  …降级…  │
     └─────────┘                      └─────────┘
          ▲  ▲ 空时调度下一级
          │  └──────────────────────────────┐
     ┌─────────┐  调度   ┌─────┐             │
```

### 交互式系统中的其他调度算法

课件要求学习并总结以下三种算法的**原理、优缺点、策略和适用场景**：

#### 公平共享调度（Fair-share Scheduling）

- 以"公平共享"为目标进行调度。
- 课堂指出：该算法即 **Linux 最终采用的完全公平调度算法（CFS）** 的思路`▶ 1:31:17`。

#### 保证调度（Guaranteed Scheduling）

- 向进程做出某种性能保证（例如保证 n 个进程时每个进程获得约 1/n 的 CPU 时间），并跟踪实际获得的 CPU 份额，优先调度偏离保证最多的进程，以兑现承诺。

#### 彩票调度（Lottery Scheduling）

- 一种**概率式调度算法**：为每个进程分配一定数量的彩票，调度时随机抽取一张彩票，持有该彩票的进程获得 CPU `▶ 1:30:41`。
- 进程持有的彩票越多，被调度的概率越高。
- 若想让某进程优先运行，可以把其他进程的彩票都分配给它，从而提高它被选中的概率`▶ 1:31:17`。

### 各种调度算法的比较

| 调度算法                 | 选择函数                | 决策模式       | 吞吐量       | 响应时间                | 开销   | 对进程的影响               | 饥饿问题 |
| -------------------- | ------------------- | ---------- | --------- | ------------------- | ---- | -------------------- | ---- |
| **FCFS**             | max[w]（等待时间最长）      | 非抢占        | 不强调       | 可能很高，特别是进程执行时间差别很大时 | 最小   | 对短进程不利；对 I/O 密集型进程不利 | 无    |
| **Round Robin**      | 常数                  | 抢占（时间片用完时） | 时间片小则吞吐量低 | 为短进程提供好的响应时间        | 最小   | 公平对待                 | 无    |
| **SJF**              | min[s]（总服务时间最短）     | 非抢占        | 高         | 为短进程提供好的响应时间        | 可能较高 | 对长进程不利               | 可能   |
| **SRTN**             | min[s−e]（剩余时间最短）    | 抢占（新进程到达时） | 高         | 提供好的响应时间            | 可能较高 | 对长进程不利               | 可能   |
| **HRRN**             | max((w+s)/s)（响应比最高） | 非抢占        | 高         | 提供好的响应时间            | 可能较高 | 很好的平衡                | 无    |
| **Feedback（多级反馈队列）** | 见算法思想               | 抢占（时间片用完时） | 不强调       | 不强调                 | 可能较高 | 可能对 I/O 密集型进程有利      | 可能   |

符号说明：

- **w**：进程已经花费的等待时间；
- **e**：到目前为止进程已经花费的执行时间；
- **s**：进程所需要的总服务时间（包含 e）。

> **老师强调**：复习对比表时重点把握四个维度——**是否存在饥饿、对哪类进程友好（I/O 型/CPU 型、长进程/短进程）、调度开销高低、响应时间与吞吐量表现**`▶ 1:31:46`。

## 6. 机制策略分离与线程调度引入

> 课件 第 59–60 页 · 讲解从 `1:32:36` 开始

### 机制与策略分离

调度框架的设计遵循一个长期确立的原则——**机制（mechanism）与策略（policy）分离**。

- **调度机制**：指"如何完成调度"的固定框架，即从就绪队列中选取实体投入 CPU 运行的基础流程，调度算法本身属于机制的一部分`▶ 1:32:36`。
- **调度策略**：指"按什么规则调度"的可调整部分，例如通过动态调整优先级来优化调度效果`▶ 1:32:36`。

**为什么要分离？**
把通用、稳定的调度执行机制与具体、可能变化的调度决策规则分开，可以在不改动底层框架的情况下替换或优化调度策略，提高系统的灵活性和可维护性。

**怎么做？**
将调度算法组织为独立的策略模块，由调度机制在恰当的时机调用；机制负责上下文切换、队列维护等通用操作，策略负责决定"下一个运行谁"（如优先数如何计算、是否抢占等）。

> **老师强调**：调度算法本身是机制，而动态调整优先级等属于策略；二者分离是调度框架中再次强调的核心原则`▶ 1:32:36`。

### 线程调度

线程调度与进程调度在本质上是一致的，核心都是**从就绪队列中选择一个实体投入 CPU 运行**，区别只在于被选择的实体类型，而这由操作系统的设计决定`▶ 1:33:16`：

- 若线程是 CPU 调度的基本单位、进程仅作为资源的容器，则所有进程调度算法都可以直接应用于线程调度。
- 若系统中只有线程这一概念，则其调度逻辑与进程调度完全相同。

课件用两张图分别展示两类线程的调度路径`▶ 1:33:16`：

| 线程类型 | 调度单位 | 调度行为 |
|---|---|---|
| 用户级线程 | 进程 | 按进程进行调度；同一进程内的线程依次运行，内核看不到线程，不会出现跨进程的线程交替调度 |
| 内核级线程 | 线程 | 线程作为独立调度单位，内核可在任意线程之间切换，支持不同进程的线程交替调度 |

> **老师强调**：用户级线程对内核对表现为进程，故同进程内线程只能依次执行；内核级线程才支持任意线程间的交替调度，这是两类线程在调度上的关键差异`▶ 1:33:16`。

### 典型系统采用的调度算法

不同操作系统在统一的调度机制之上采用了各自的调度策略`▶ 1:35:09`：

| 系统 | 调度算法 |
|---|---|
| UNIX（早期） | 动态优先数法 |
| 5.3 BSD | 多级反馈队列法 |
| Windows | 基于优先级的抢占式多任务调度 |
| Linux | 抢占式调度 |
| Solaris | 综合调度算法 |

> **老师强调**：本部分后续重点讲解 **Windows 和 Linux** 两个系统的调度实现，其余系统了解其所用算法名称即可`▶ 1:35:09`。

## 7. Windows线程调度：优先级、时间配额与调度数据结构

> 课件 第 61–65 页 · 讲解从 `1:35:45` 开始

### Windows 线程调度概述

Windows 的调度单位是**线程**，整体采用**基于动态优先级的抢占式调度**，并结合**时间配额（quantum）调整**。其核心规则包括：

- 就绪线程按优先级进入相应的就绪队列，即系统维护**多个就绪队列**；
- 系统总是选择**优先级最高的就绪线程**运行；
- 同一优先级的多个线程按时间配额进行轮转调度；
- 在多处理机系统中，多个线程可以在不同处理器上并行运行。

Windows 使用“时间配额”而不是传统意义上的纯时间长度时间片：时间配额是一个与线程运行时长相对应的整数值 `▶ 1:35:45`。线程按优先级从高到低选择队列运行，同一队列内按时间配额轮转；Windows 中不存在“线程用完时间片就自动降到低优先级队列”的多级反馈队列式降级规则 `▶ 1:35:45`。

### 引发线程调度的条件

当下列情况发生时，Windows 可能触发重新调度：

- 一个线程的**优先级发生改变**；
- 一个线程改变了它的**亲和处理机集合（Affinity）**；
- 线程正常终止，或由于某种错误异常终止；
- 新线程被创建，或一个等待线程变为就绪态；
- 线程从运行态进入阻塞态，例如主动等待或睡眠；
- 线程从运行态变为就绪态，例如被抢占或时间配额用完。

其中，==优先级变化是抢占式调度的重要触发条件==：一旦线程优先级改变，系统会立即重新选择当前优先级最高的就绪线程运行`▶ 1:37:27`。

处理器亲和集合的变化在对称多处理器（SMP）系统中尤其重要。==Windows 倾向于避免线程频繁在不同处理器之间迁移==，因此会为线程维护亲和处理器集合；当该集合改变，或有新处理器加入时，需要重新进行调度`▶ 1:37:27 · 1:38:58`。

> **老师强调**：通用调度时机包括进程或线程结束、新线程创建、等待转就绪、主动进入睡眠、运行转就绪、时间片用完等；Windows 还特别增加了“优先级改变”和“处理器亲和集合改变”两类调度时机`▶ 1:37:27 · 1:39:32`。

### 线程优先级

Windows 使用 **32 个线程优先级**，编号为 `0 ~ 31`，分为三类：

| 优先级范围 | 类别 | 说明 |
|---|---|---|
| `0` | 系统线程 / 零页线程 | 空闲线程，用于对空闲物理页面清零，也可理解为系统空闲时执行内存清扫工作 |
| `1 ~ 15` | 可变优先级 | 普通用户线程所在范围，当前优先级可在一定范围内动态升高或降低 |
| `16 ~ 31` | 实时优先级 | 优先级由系统固定，线程优先级不会被动态调整 |

- **实时优先级线程**：不改变其优先级，通常由操作系统固定分配，供高实时性要求的系统线程使用。
- **可变优先级线程**：其当前优先级可以在一定范围内升高或降低，但调整通常以基本优先级为基础。
- **零页线程（0号）**：系统中没有可运行线程时运行，负责将空闲物理页面清零。

> **老师强调**：0 号是系统空闲线程，负责清扫内存；1~15 是普通用户线程使用的可变优先级；16~31 是实时优先级，全部为系统线程，优先级不可由用户随意调整 `▶ 1:40:02`。

#### 基本优先级与当前优先级

可变优先级线程在其控制结构中维护两个优先级字段：

- **基本优先级（Base Priority）**：线程创建时确定的初始优先级；
- **当前优先级（Current Priority）**：线程当前实际参与调度的优先级，可由系统动态调整。

线程的当前优先级可以根据 I/O 完成、从等待状态唤醒、前台进程响应等情况临时升高，也可以在使用完时间配额后降低或恢复。动态调整必须处于系统允许的优先级范围内`▶ 1:42:46`。

### 线程的时间配额

#### 时间配额的含义

时间配额不是一个直接的时间长度，而是一个整数，称为**配额单位（quantum unit）**。它用来表示线程在一次调度中最多可以消耗多少运行额度。

在线程控制结构 `KTHREAD` 中，与时间配额相关的字段包括：

- `Quantum`：线程当前剩余的时间配额；
- `QuantumReset`：线程配额用完后重新设置的配额值。

相关常量包括：

```c
#define CLOCK_QUANTUM_DECREMENT 3
#define WAIT_QUANTUM_DECREMENT  1
```

这些递减值反映了不同事件对线程剩余配额的消耗方式。时钟中断会按固定配额单位扣减当前线程的时间配额；线程进入等待等情况也可能影响配额。

当一个线程用完自己的时间配额时：

- 如果存在其他相同优先级的就绪线程，则发生轮转，选择另一个同优先级线程运行；
- 如果没有其他相同优先级线程，Windows 会重新给该线程分配一个新的时间配额，并让它继续运行。

#### 时间配额与优先级调整的区别

时间配额的一个重要作用是调节线程获得 CPU 时间的多少，但**不会像提高优先级那样使低优先级线程几乎得不到执行机会**。

课件中的对比如下：

1. 用户先启动一个运行时间很长的电子表格计算程序；
2. 然后切换到一个游戏程序，游戏需要复杂图形计算和显示，属于 CPU 密集型任务；
3. 如果提高前台游戏线程的优先级，后台电子表格可能长时间得不到 CPU；
4. 如果只是增加游戏线程的时间配额，电子表格仍能继续执行，只是游戏在同等调度机会下获得更多 CPU 时间。

> **老师强调**：时间配额有两个作用：一是控制线程一次上 CPU 运行的时长；二是在不改变优先级的情况下调节线程实际获得的 CPU 时间比例。例如前台游戏和后台电子表格优先级相同时，给游戏更大的时间配额，可以让游戏运行更流畅，但不会完全饿死电子表格`▶ 1:43:15`。

### 调度器数据结构

Windows 支持多处理器和多个按优先级组织的就绪队列，其调度器主要使用以下数据结构快速定位可运行线程和空闲处理器。

#### 线程调度器就绪队列

系统为每个调度优先级维护一个就绪队列：

- 优先级 `0 ~ 31` 各有一个队列；
- 就绪线程按照其当前优先级进入对应队列；
- 调度时先寻找最高的非空优先级队列，再从该队列中选择线程。

#### 就绪位图（Ready Bitmap）

Windows 维护一个**就绪位图**，其中每一位对应一个调度优先级：

- 某位为 `1`：表示该优先级的就绪队列中至少有一个线程等待运行；
- 某位为 `0`：表示该优先级的就绪队列为空。

借助位图扫描指令或掩码运算，调度器可以快速找到最高的非空就绪队列，而不必从高到低逐个检查全部队列`▶ 1:44:42`。

#### 空闲位图（Idle Bitmap）

Windows 还维护一个**空闲位图**，其中每一位对应一个处理机：

- 某位为 `1`：表示对应处理器当前处于空闲状态；
- 某位为 `0`：表示对应处理器当前不空闲。

在多处理器调度时，系统结合线程的处理器偏好和空闲位图，为线程选择合适的处理器。

#### 进程与线程中的调度相关信息

| 层级 | 字段 | 含义 |
|---|---|---|
| 进程 | 缺省基本优先级 | 进程内线程默认继承或参考的基本优先级 |
| 进程 | 缺省处理机偏好 | 进程内线程默认的亲和处理器集合 |
| 进程 | 缺省时间配额 | 进程内线程默认使用的时间配额 |
| 线程 | 基本优先级 | 线程创建时的基础优先级 |
| 线程 | 当前优先级 | 线程当前实际参与调度的优先级 |
| 线程 | 处理机偏好 | 允许线程运行的处理器集合 |
| 线程 | 时间配额 | 线程当前剩余或重置后可使用的配额值 |

### 本章总结

- Windows 以**线程**为调度单位。
- 调度策略是**动态优先级、抢占式、同优先级时间配额轮转**。
- 优先级范围为 `0 ~ 31`：0 号为零页线程，1~15 为可变优先级，16~31 为实时优先级。
- 可变优先级线程具有**基本优先级**和**当前优先级**。
- 时间配额是整数配额单位，不是直接时间长度；它可以控制线程连续运行时长，并调节线程获得 CPU 的比例。
- 优先级变化和处理器亲和集合变化都会触发重新调度。
- 调度器通过**多级就绪队列、就绪位图和空闲位图**，在多处理器环境下快速选择最高优先级就绪线程和合适的空闲处理器。

## 8. Windows调度策略、优先级提升与空闲线程机制

> 课件 第 66–76 页 · 讲解从 `1:45:12` 开始

### 调度触发场景

Windows线程调度的触发场景分为三类，与多级反馈队列调度逻辑一致 `▶ 1:45:12`：

- 主动切换
- 抢占
- 时间配额用完

---

### 1. 主动切换

线程从**运行态转到阻塞态**，主动让出CPU，例如等待I/O、等待事件或信号量等。此时系统从当前最高优先级的非空就绪队列中选择一个线程运行。

**示例**：优先级为20的线程因阻塞主动切换，若21、20、19级就绪队列均为空，则从18级队列选取线程运行`▶ 1:45:42`。

---

### 2. 抢占

当一个**此前阻塞的高优先级线程被唤醒**、进入就绪态时，它会抢占当前正在运行的低优先级线程。

**示例**：优先级20的线程从阻塞态返回就绪，会抢占正在运行的优先级18的线程`▶ 1:46:29`。

被抢占线程的处理规则：

- 被抢占线程回到**对应优先级就绪队列的队首**`▶ 1:46:29`
- **实时优先级线程**（16–31）：时间配额重置为一个完整的时间配额，以尽快完成系统服务`▶ 1:47:04`
- **可变优先级线程**（1–15）：时间配额不变，重新获得CPU后运行剩余的时间配额`▶ 1:47:04`

---

### 3. 时间配额用完

假设线程A的时间配额用完，分两种情况：

**情况一：A的优先级没有降低**
- 若队列中有其他就绪线程：选择下一个线程执行，A回到所在就绪队列的**队尾**`▶ 1:48:25`
- 若队列中没有其他就绪线程（也无更高优先级线程）：系统给A分配一个新的时间配额，让它继续运行`▶ 1:48:25`

**情况二：A的优先级降低了**
- 这类线程通常是原本从低优先级被临时提升上来的，用完时间片后需降回原低优先级`▶ 1:49:30`
- A移入低优先级队列等待，Windows选择更高优先级的线程运行`▶ 1:49:30`

---

### 线程优先级提升与时间配额调整

#### 为什么需要动态调整

通用调度策略并非完美，无法让所有应用都受益，需要解决以下问题：

- 如何体现对某类线程的倾向性？
- 如何解决调度策略潜在不公平导致的**饥饿现象**？
- 如何改善系统吞吐量、响应时间等整体特征？

**解决方案**：
- 提升线程的优先级
- 给线程分配更大的时间配额

> **老师强调**：动态调整仅针对1～15级的可变优先级线程；系统线程（实时优先级16～31）优先级固定，不参与动态调整`▶ 1:50:05`。

#### 触发优先级提升的5种情况

| 编号  | 触发情况                      |
| --- | ------------------------- |
| 1   | I/O操作完成                   |
| 2   | 信号量或事件等待结束                |
| 3   | 前台进程中的线程完成一个等待操作          |
| 4   | 由于窗口活动而唤醒窗口线程             |
| 5   | 线程处于就绪态超过一定时间仍未运行（"饥饿"现象） |

以上提升均针对可变优先级范围（1～15）的线程。

---

#### I/O操作完成后的优先级提升

- I/O操作完成后，Windows**临时提升**等待该操作的线程的优先级，使其能更快上CPU处理数据`▶ 1:51:53`
- 实际提升值由**设备驱动程序决定**，建议值定义在 `Wdm.h` 或 `Ntddk.h` 中
- 驱动程序通过内核函数 `IoCompleteRequest` 指定提升幅度
- 提升幅度与I/O请求的**响应时间要求一致**：响应要求越高，提升幅度越大，最高不超过15级`▶ 1:51:53`
- 为避免不公平，唤醒等待线程时将其**时间配额减1**，以平衡优先级提升带来的调度倾斜`▶ 1:51:53`

#### 等待事件和信号量后的优先级提升

- 等待事件对象或信号量对象的线程完成等待后，优先级**提升1级**
- 原因：阻塞于事件或信号量的线程获得的处理器时间比CPU型线程少，提升可减少这种不平衡
- 相关函数：`SetEvent`、`PulseEvent`、`ReleaseSemaphore` 等可导致等待结束
- 提升以线程的**基本优先级为基准**，提升后不超过15
- 时间配额与衰减规则：
  1. 等待结束时，时间配额减1
  2. 在提升后的优先级上运行完剩余时间配额
  3. 随后降低1个优先级，运行一个新的时间配额
  4. 逐次衰减，直到回到基本优先级

---

#### "饥饿"线程的优先级提升

由系统线程**平衡集管理器（Balance Set Manager）** 负责：

- **每秒扫描一次**就绪队列`▶ 1:53:06`
- 发现排队超过**300个时钟中断间隔**仍未运行的线程，即认定为饥饿`▶ 1:53:06`
- 将该线程优先级**提升到15**，并分配**正常值4倍长度**的时间配额，让其快速运行以弥补饥饿损失`▶ 1:53:06`
- 线程用完该时间配额后，优先级**立即衰减回原来的基本优先级**`▶ 1:53:06`

---

### 空闲线程

当一个处理机上**没有任何可运行线程**时，Windows会调度该处理机对应的空闲线程。

- 多处理机系统中可能多个CPU同时空闲，因此**每个处理机各有一个空闲线程**
- 空闲线程优先级为**0**，只在没有其他线程可运行时才运行
- 空闲线程在一个循环中不断检测是否有要进行的工作

#### 空闲线程的执行流程

空闲线程在循环中依次执行以下工作：

1. **处理所有待处理的中断请求**
2. **检查是否有待处理的DPC (Deferred Procedure Call) 请求**：若有，清除相应软中断并执行DPC
3. **检查是否有就绪线程可进入运行态**：若有，调度相应线程运行
4. **调用硬件抽象层（HAL）的处理机空闲例程**：执行相应的电源管理功能

| ----------- | ----------------------------------------------------------- |
| 调度时机        | 内核处理完中断、异常或系统调用并准备返回用户态前，根据进程状态变化决定是否重新选择进程运行。              |
| 上下文切换       | 保存当前进程的寄存器、内核栈和地址空间等硬件现场，并恢复另一进程现场，使CPU转去执行新进程。             |
| 抢占式调度       | 当更高优先级或更符合策略的进程就绪时，系统可以强行剥夺当前运行进程的CPU。                      |
| I/O密集型进程    | 进程频繁等待I/O完成，CPU突发较短，操作系统通常偏好调度这类进程以保持I/O设备忙碌。               |
| CPU密集型进程    | 进程主要消耗大量CPU时间进行计算，通常会长时间连续占用处理器。                            |
| 时间片         | 分配给进程一次连续运行的时间段，耗尽后通常触发轮转或重新调度。                             |
| FCFS        | 先来先服务算法按进程进入就绪队列的顺序非抢占地分配CPU，简单公平但对短进程和I/O密集型进程不利。          |
| SJF         | 短作业优先选择预计运行时间最短的进程执行，可降低平均周转时间但可能导致长进程饥饿。                   |
| SRTN        | 最短剩余时间优先是SJF的抢占版本，在新就绪进程剩余时间更短时抢占当前进程。                      |
| HRRN        | 最高响应比优先选择“1+等待时间/处理时间”最大的进程，以折中短作业优先和等待公平性。                 |
| 时间片轮转RR     | 就绪进程依次运行固定时间片，时间片用完后轮换，公平且响应较快，但切换开销随时间片缩短而增大。              |
| 虚拟轮转法       | 在普通轮转基础上为因I/O阻塞后返回的进程设置辅助队列并优先调度，以改善I/O密集型进程的响应。            |
| 优先级反转       | 低优先级进程持有高优先级进程所需资源，又被中优先级进程长期抢占CPU，导致高优先级进程无法继续执行。          |
| 优先级继承       | 让持有资源的低优先级进程临时继承被阻塞高优先级进程的优先级，使其尽快释放资源。                     |
| 优先级天花板协议    | 为临界资源设置优先级上限，进入临界区的进程可被提升到该上限以避免优先级反转。                      |
| 多级反馈队列      | 设置多个优先级和时间片长度不同的队列，进程用完时间片后降级，阻塞唤醒后通常返回原队列，以兼顾短任务、交互任务和长任务。 |
| 彩票调度        | 通过给进程分配彩票并随机抽取的方式按概率分配CPU，持有彩票越多的进程被选中的概率越高。                |
| Windows时间配额 | Windows中控制线程一次运行时长的配额单位，不是直接的时间长度，可配合动态优先级调整调度倾向。           |
| 基本优先级与当前优先级 | Windows可变优先级线程保存创建时的基本优先级，以及运行过程中可临时升高或衰减的当前优先级。            |
| 处理器亲和性      | 线程倾向于在指定处理器集合上运行，以减少跨CPU迁移造成的缓存和TLB失效。                      |
| 平衡集管理器      | Windows系统线程周期性扫描就绪队列，对长期未运行的饥饿线程提升优先级并给予较大时间配额。             |
