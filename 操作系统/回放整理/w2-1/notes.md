本次课属于“操作系统概述”的开篇部分，主要回答三个问题：

1. 操作系统是什么；

### 一、操作系统是什么

操作系统是计算机系统中的一个**系统软件**，位于计算机硬件之上，是一系列程序模块的集合。它主要完成以下工作：

- 以尽量**有效、合理**的方式组织和管理计算机的软硬件资源；
- 合理组织计算机的工作流程，控制程序执行；
- 向用户和应用程序提供各种服务功能；
- 使用户能够灵活、方便地使用计算机；
- 使整个计算机系统能够高效运行。

从层次上看，操作系统是最靠近硬件的、最底层的系统软件`▶ 06:02`。它向下管理处理器、内存、磁盘、键盘、显示器等硬件资源，向上为应用程序提供统一的运行环境和服务接口。

可以从三个角色理解操作系统：

| 角色 | 核心含义 | 关键词 |
|---|---|---|
| 资源的管理者 | 管理 CPU、内存、设备、文件等资源，并负责调度与分配 | 有效、合理 |
| 服务的提供者 | 通过系统调用等接口为程序提供运行所需服务 | 方便使用 |
| 机器能力的扩展 | 把物理硬件扩展成更通用、更强大、更易用的虚拟形式 | 易于扩展、虚拟机 |

> **老师强调**：操作系统的核心职能，是以尽量有效、合理的方式组织和管理计算机的软硬件资源，这一定位必须牢记`▶ 06:47`。

#### “有效”和“合理”的关系

“有效”与“合理”并不总是完全一致，二者经常存在权衡：

- 追求资源利用效率时，可能难以同时保证公平；
- 过度追求公平均衡时，又可能降低整体资源利用率；
- 除了效率和公平，还要考虑安全、可靠性、能耗等指标。

因此，并不存在绝对的“有效”和绝对的“合理”。老师用综合素质测评中奖项名额有限作类比：评价和分配只能尽量合理，无法做到绝对合理`▶ 07:58`。学习操作系统时，需要始终关注资源利用率、性能效率、安全等目标之间的平衡`▶ 06:47`。

### 二、操作系统的三个核心作用

课件将操作系统的作用重点概括为三个方面：**硬件抽象、提供服务、应用隔离**。

#### 1. 硬件抽象

硬件抽象是指操作系统屏蔽底层硬件的物理差异和复杂操作细节，为上层应用提供统一、标准化的访问接口。

例如：

- 不同磁盘、键盘、显示器等设备的物理操作方式不同；
- 应用程序通常不需要直接操作设备寄存器或理解硬件控制细节；
- 操作系统把这些异构设备包装成相对统一的接口，例如文件操作接口。

这样，应用程序可以用相似的方式读写设备和文件，从而降低开发复杂度。

#### 2. 提供服务

操作系统通过**系统调用**为应用程序提供核心基础设施服务，典型服务包括：

- 进程创建与调度；
- 内存分配与管理；
- 文件系统管理；
- 设备访问；
- 网络通信；
- 进程间通信等。

例如，应用程序可以通过 `open` 等系统调用请求操作系统打开文件`▶ 08:39`。应用程序不直接操作硬件，而是通过操作系统提供的 API 获得服务。

从这个角度看，操作系统构建了应用程序运行的基础环境，是软件正常执行的保障。

#### 3. 应用隔离

操作系统利用独立进程、虚拟地址空间等机制，为不同应用构造相互隔离的运行环境。

应用隔离的作用包括：

- 防止一个应用的错误随意扩散到其他应用；
- 避免单个程序崩溃破坏整个系统；
- 防止应用随意访问其他应用的数据；
- 提高系统稳定性和数据安全性。

课件将这种相互隔离的运行环境称为“运行沙箱”。

> 老师在讲解系统结构时也指出，硬件抽象和应用隔离是操作系统结构图体现出的两个核心特性；此外还包括支持虚拟机、提供 API、资源管理等作用`▶ 09:56`。

### 三、从不同角度认识操作系统

### 1. 操作系统是虚拟机

操作系统可以把一个物理资源转换为更通用、更强大、更易用的虚拟形式。

例如：

- 把一个物理 CPU 虚拟成多个可并发执行的 CPU；
- 把物理内存抽象为每个进程独立的虚拟地址空间；
- 把磁盘抽象为文件和目录；
- 把复杂设备抽象为统一的 I/O 接口。

因此，从用户或应用程序的角度看，操作系统提供了一台比裸机更容易使用的“虚拟机”。老师也指出，虚拟机、容器等技术思想都与操作系统扩展机器能力的定位有关`▶ 09:14`。

### 2. 操作系统是 API 和系统服务的提供者

为了让用户程序使用虚拟机的能力，操作系统提供了一组可调用的接口，即 API 或系统调用接口。

应用程序可以通过这些接口请求操作系统完成：

- 运行和创建程序；
- 分配和释放内存；
- 访问文件；
- 进行输入输出；
- 建立网络连接；
- 进程同步与通信等。

课件将其概括为：操作系统为应用程序提供标准库式的基础接口。

### 3. 操作系统是资源管理器

虚拟化使得多个程序能够共享同一套物理资源：

- 多个程序共享 CPU，形成并发或并行执行；
- 多个程序拥有各自的虚拟地址空间，共享物理内存；
- 多个程序通过文件系统访问磁盘；
- 多个程序共享打印机、网卡等设备。

操作系统必须决定资源在多个程序之间如何分配、何时分配、分配多少，以及如何防止资源冲突。因此，它本质上也是计算机系统的资源管理器。

### 五、操作系统的设计与实现目标

设计和实现操作系统时，需要同时考虑多个目标。这些目标之间有时相互促进，有时也会产生矛盾。

#### 1. 抽象

通过抽象隐藏硬件复杂性，为上层提供简洁、统一的接口。抽象可以减少应用程序与具体硬件之间的耦合。

#### 2. 模块化

将操作系统划分为相对独立的模块，例如进程管理、内存管理、文件系统、设备管理等。模块化有助于：

- 控制系统复杂度；
- 便于理解和维护；
- 便于替换和扩展；
- 减少模块之间的错误影响。

#### 3. 使用高级语言

课件提出应使用 C 等高级语言而非完全使用汇编语言实现操作系统。高级语言具有更好的可读性、可移植性和维护性，而汇编通常只用于与硬件密切相关、对性能极其敏感的少量部分。

#### 4. 性能与最小化开销

操作系统本身会消耗处理器时间、内存和磁盘空间，因此应尽量降低管理开销：

- 最小化额外执行的指令和时间；
- 最小化额外占用的内存和磁盘空间；
- 避免因为管理机制过重而显著降低应用程序性能。

这与操作系统“高效运行”的目标相联系。

#### 5. 保护与隔离

系统需要在多个层次上提供保护：

- 应用程序之间相互隔离；
- 操作系统与应用程序之间相互保护；
- 防止应用程序直接执行特权操作；
- 防止非法访问其他进程或系统数据。

隔离进程是实现保护的重要手段。

#### 6. 可靠性

操作系统应当能够稳定运行，即使个别应用程序发生错误，也不应轻易导致整个系统崩溃。可靠性要求系统能够发现、限制并从错误中恢复。

#### 7. 节能

在现代计算机，尤其是移动设备和数据中心中，操作系统需要通过调度和资源管理降低能耗，例如合理控制 CPU 状态、设备运行状态和任务执行时机。

#### 8. 安全性

安全可以看作保护目标的扩展。操作系统需要防止恶意应用入侵、破坏系统或窃取数据。在高度网络化的环境中，程序之间通过网络频繁交互，安全性变得更加重要。

#### 9. 移动性

移动性指操作系统应能够运行在越来越小、资源越来越受限的设备上，例如手机、嵌入式设备、传感器和物联网设备。

> **老师提示**：移动性、可靠性、节能、安全等目标不需要死记硬背，但在后续分析操作系统问题时，需要把这些因素纳入考虑`▶ 11:04`。

---

### 六、本章小结

本章从定义、角色、核心作用和设计目标四个方面建立对操作系统的基本认识：

1. 操作系统是位于硬件之上的最底层系统软件；
2. 它管理 CPU、内存、设备和文件等软硬件资源；
3. 它通过系统调用为应用程序提供服务；
4. 它通过硬件抽象把复杂裸机扩展成易用的虚拟机；
5. 它通过进程和虚拟内存等机制实现应用隔离与保护；
6. 操作系统设计需要在性能、开销、可靠性、安全、节能、移动性等目标之间权衡。

其中最核心的定义是：**操作系统是资源的管理者、服务的提供者和机器能力的扩展者**。

## 2. 从不同角度认知操作系统

> 课件 1-2026-秋季-操作系统概述-发布版.pdf 第 9–13 页 · 讲解从 `11:49` 开始

### 从三种不同角度认知操作系统

可以从多种角色视角理解操作系统：服务提供者、魔幻制造者、历史教员、家长、政府、仲裁者等。

- **历史教员**：操作系统中的设计思想和技术可以迁移到后续的应用开发中`▶ 11:49`。
- **家长/管理者**：负责统筹安排系统中的各项任务`▶ 11:49`。
- **仲裁者**：在多个资源申请方之间进行裁决和分配`▶ 11:49`。

本课程重点讲解三个核心视角：

1. 资源管理的观点
2. 进程的观点
3. 虚机器观点

> **老师强调**：基本的常用设计观点有三个，即资源管理观点、进程观点和虚机器观点`▶ 21:41`。

---

### 1、资源管理的观点

资源管理观点采用**自底向上**的方式看待操作系统：操作系统位于硬件之上，是系统资源的管理者。

#### 管理的资源

| 资源类型 | 具体内容 |
|---|---|
| 硬件资源 | CPU、内存、I/O 设备、磁盘、时钟、网络接口等 |
| 软件资源 | 磁盘上的文件、信息等 |

从资源抽象的角度看，操作系统对各类硬件资源进行了抽象和管理`▶ 13:24`：

- **处理器**抽象为**进程**，管理进程就是在管理 CPU；
- **内存**对应**虚存/地址空间**；
- **I/O 设备、磁盘、网卡等**统一抽象为**文件**，由文件系统管理。

此外，单个物理 CPU 还可以通过抽象转化为多个虚拟 CPU，这属于 CPU 虚拟化的内容，后续可进一步了解`▶ 13:03`。

#### 资源管理的目的

资源管理的核心目的有两个`▶ 14:59`：

1. **实现资源共享**：让多个进程能够共同使用系统资源；
2. **提高资源利用率**：实际工作中经常需要围绕性能问题进行优化。

资源复用（共享）通过两种基本方式实现：

- **时间复用**：例如多个进程分时占用 CPU；
- **空间复用**：例如多个进程共同占用内存或存储体系中的空间。

时间和空间两类资源可以相互转换，即常说的**“时间换空间、空间换时间”**`▶ 14:59`。

> **老师强调**：资源管理并不是简单的管控，其核心目标是实现多进程共享资源并提高资源利用率`▶ 14:59`。

#### 怎样管理资源

操作系统管理资源主要包括以下工作：

##### （1）跟踪记录资源使用状况

需要记录资源的状态，例如：

- 哪些资源空闲；
- 资源好坏与否；
- 资源被谁使用；
- 已经使用多长时间等。

学习操作系统的核心抓手是**数据结构**，相比之下算法通常较简单；数据结构的作用就是跟踪和记录各类资源的使用状态`▶ 16:39`。例如：

- 管理进程依赖每个进程对应的**进程控制块（PCB）**；
- 管理文件依赖**文件描述符表、打开文件表、inode/vnode 表**等表结构。

这些管理工作本质上都是通过维护相应的数据结构来实现对资源的管控`▶ 16:39`。

##### （2）分配和回收资源

操作系统需要依据一定的资源分配策略与算法，在进程请求资源时进行分配，并在进程使用完后回收资源。

| 分配策略 | 做法 | 特点 |
|---|---|---|
| 静态分配策略 | 进程创建时一次性分配其运行所需的全部资源，运行过程中不再申请新资源 | 实现简单，但资源利用率极低，已过时 |
| 动态分配策略 | 进程运行过程中按需申请资源，用完立即归还 | 当前主流，资源利用率高，但会引入死锁等新问题 |

静态分配的一个典型问题是：如果某进程分配到了打印机但暂时闲置，其他进程也无法使用该打印机，造成资源浪费`▶ 18:12`。

动态分配提高了资源利用率，但进程在运行中不断申请、释放资源，也会带来**死锁**以及部分软件缺陷等新问题`▶ 18:12`。

#### 资源管理的目标

资源管理除了提高资源利用率，还包括：

- 资源使用时的保护；
- 协调多个进程对资源请求的冲突；
- 其他与资源分配、回收和监控相关的目标。

这些目标最终都要通过相应的**数据结构与算法**来实现。

### 2、进程的观点

进程观点是从操作系统运行的角度，**动态地观察操作系统**。

按照这一观点，操作系统由以下两部分组成：

- 一些可以**同时、独立运行的进程**；
- 一个对这些进程进行协调的**核心（内核）**。

因此，在系统运行的任意时刻拍一张“快照”，都可以看到一个内核以及若干正在运行的进程`▶ 20:21`。

#### 什么是进程

进程是：

- 完成某一特定功能的程序；
- 程序的一次执行过程。

进程具有以下特征：

- **动态性**：进程是程序的一次执行，而不是静态的程序本身；
- **生命期**：进程会诞生、运行，最终消亡。

在进程运行过程中，可能会出现资源申请冲突，例如多个进程竞争 CPU。此时需要由内核进行协调和解决`▶ 20:21`。

---

### 3、虚机器观点

虚机器观点是从操作系统内部结构出发，采用**分层结构**认识操作系统。

其基本思想是：

1. 把操作系统分成若干层；
2. 每一层完成特定功能，从而构成一个虚机器；
3. 每一层都对上一层提供支持；
4. 通过逐层功能扩充，最终形成整个操作系统虚机器；
5. 操作系统虚机器向用户提供各种功能，完成用户请求。

#### 分层结构的含义

在分层结构中，每一层对它的上一层而言都是一个独立的机器。上一层通过预先约定好的接口与下一层交互，不需要了解下层的具体实现细节`▶ 21:41`。

分层结构具有以下特点：

- **封装底层细节**：下层会隐藏更底层的实现，上层只能感知直接相邻的下层；
- **逐层提供服务**：每一层都为其上层提供服务，同时屏蔽上层对自身底层的直接操作；
- **接口清晰**：例如操作系统之上的 API 也是一层封装，用户调用 API 后会进入内核并触发系统调用。

#### 分层思想的意义

分层是解决复杂问题的有效手段，其作用包括`▶ 21:41`：

- 实现任务分解，降低系统复杂度；
- 各层通过明确接口交互，便于理解和实现；
- 出现问题时可以较快定位到具体层级。

分层结构在各类操作系统中普遍存在，但不同系统的分层清晰程度不同。例如，Linux 内部分层就相对模糊，并不是所有层次都有非常清晰的边界`▶ 21:41`。

## 3. 发展历史的启示：从Multics到UNIX与云计算

### 为什么要学习操作系统发展历史

操作系统的发展会随着**计算机硬件技术、应用需求、软件新技术**三方面共同演进，根本目标始终是：充分利用硬件资源，并为用户提供更好的服务`▶ 23:54 · 29:40`。

学习历史的重要启示在于**概念的重用与回归**：

- 技术变化会使某些思想过时并迅速消失；
- 但技术的另一种变化，又可能使这些思想以新的形态“复活”；
- 很多新技术并非凭空产生，而是旧有技术经过重新封装后的升级，核心思想往往没有本质变化`▶ 23:54`。

操作系统中的典型例子包括：

| 历史思想/技术 | 演变与回归 |
|---|---|
| 磁盘文件连续分配 | 早期机械磁盘曾采用连续分配，后因文件增长不便发展为非连续分配；CD-ROM 等只读顺序存储介质又适合连续文件分配`▶ 24:56` |
| 硬件保护 | 早期硬件具备保护机制，后来一度不再配置，现在又重新引入硬件保护`▶ 24:56` |
| 动态链接 | 最早由 Multics 提出，Unix 流行后曾不被重视，近年来又重新得到使用`▶ 26:09 · 28:47` |
| 集中计算服务 | Multics 早期希望由一台大型计算机集中服务一个地区；如今以大量相对简单的用户机器接入集中式 Internet 服务器的形式回归，即云计算`▶ 30:20` |

> **老师强调**：技术思想可能“消失—回归”，判断一种技术是否适用，要结合当时的硬件介质、应用需求和技术发展阶段，而不能只看技术本身新旧`▶ 23:54 · 24:56`。

### 从 Multics 到 Unix、云计算的历史线索

#### Multics 的背景与设计目标

Multics 项目早期由美国波士顿地区的三家单位合作开发：

- **GE 公司**：负责硬件；
- **贝尔实验室**：负责设计 PRY 语言；
- **MIT**：负责开发操作系统。

由于项目开发周期过长，GE 和贝尔实验室先后退出，最终由 MIT 完成开发并在多地推广使用`▶ 27:10`。

Multics 的目标非常宏大：希望用一台计算机服务整个波士顿地区，并且要求机器长期不能关机。为了能在**不中断系统运行**的情况下更新和维护软件，Multics 提出了**动态链接**思想`▶ 28:47`。

#### 动态链接为什么会出现

如果系统必须长期运行，就不能因为替换或更新某个软件模块而频繁停机。动态链接允许程序在运行时关联所需模块，从而支持在系统持续运行的过程中维护软件。这一需求来自 Multics 的集中式、长期运行场景`▶ 28:47`。

后来 Unix 成为主流系统，动态链接一度不再受到重视；但随着软件复用、库更新等需求发展，动态链接技术又重新回归并广泛使用`▶ 28:47`。

#### Unix 的出现及其设计哲学

从 Multics 项目退出后，贝尔实验室开发了 **C 语言和 Unix**。他们认为 Multics 过于庞大复杂，因此 Unix 主张“**短小即美好**”：

- 系统和命令设计尽量简洁；
- 命令名称通常很短，例如 `ls`、`cat`；
- 甚至早期创建文件命令中末尾的字母 `e` 都被省略，以追求简短`▶ 29:40`。

关于名称，一种合理解释是：Unix 相对于 Multics 命名，`Multi-` 表示“多”，`Uni-` 表示“单一”，二者语义相对、发音相近；Unix 末尾使用 `x`，也是为了与 Multics 的尾音保持一致`▶ 26:09`。也有说法认为 Multics 因系统过于庞杂而夭折，其名称后来被刻意简化，体现了对复杂设计的反思`▶ 30:20`。

#### 从 Multics 集中计算到云计算

Multics 最初设想由中心大型计算机向波士顿地区提供集中计算服务，用户通过开关接入中心主机即可使用计算能力。今天的云计算在结构上回归了这一思想：

- 数据中心集中部署大量服务器；
- 用户侧使用相对简单的终端或机器；
- 通过 Internet 接入集中式计算与存储服务。

因此，云计算并不是完全陌生的概念，而是 Multics 集中计算服务模式在网络、硬件和分布式系统条件成熟后的回归`▶ 30:20`。

> **老师强调**：Multics → Unix → 云计算体现了操作系统思想的继承、批判与回归。Unix 继承并简化了 Multics 的许多经验，而云计算又在新的技术条件下重现了 Multics 的集中服务思路`▶ 29:40 · 30:20`。

### 操作系统的总体发展阶段

操作系统随着硬件、应用需求和软件技术发展，大致经历了以下阶段：

1. **大型机阶段**
2. **PC 机阶段**
3. **网络阶段**
4. **移动计算阶段**
5. **云计算阶段**
6. **人机物融合阶段——泛在操作系统**

后续发展还与物联网、大数据分析、人工智能等技术密切相关。课件将“泛在操作系统”作为人机物融合阶段的方向，强调计算环境从单机、网络进一步扩展到无处不在的设备与物理世界融合`▶ 29:40`。

### 第 1 阶段：1948—1970 年

这一阶段的基本特点是：**硬件昂贵，人工便宜**。因此操作系统设计的核心目标是更有效地利用昂贵的硬件资源。

#### 早期使用方式

早期计算机缺乏用户与计算机之间的直接交互，主要经历了：

- **控制台方式**：一次只能一个用户使用，用户独占整台机器；
- **批处理方式**：按“装入程序 → 运行 → 打印输出结果”的流程处理作业。

批处理阶段几乎没有完善的保护机制。由于多个作业需要依次交接和运行，操作系统必须管理所有程序的装入、执行与结果输出，因此系统管理逻辑开始变得复杂`▶ 30:20`。

#### 推动操作系统发展的关键技术

为了让昂贵的硬件尽量少空闲，这一阶段出现了多项关键技术：

| 技术 | 作用 |
|---|---|
| 数据通道、中断 | 使 I/O 操作与计算能够重叠执行，提高 CPU 和设备利用率 |
| 多道程序设计 | 让多个程序同时处于运行状态，多个用户共享系统资源 |
| 存储保护 | 多道程序共享系统时，需要防止程序之间相互干扰或非法访问 |
| SPOOLing 技术 | 支持批处理作业的输入、排队、处理和输出流程 |

其中，**多道程序设计**是操作系统从简单作业管理走向资源共享和并发管理的重要标志；一旦多个程序共享内存和处理器，就必须引入**存储保护**等硬件与操作系统协同机制`▶ 30:20`。

> **老师强调**：第一阶段的主要矛盾是硬件太贵，所以操作系统围绕“提高硬件利用率”发展；中断、通道、多道程序设计和 SPOOLing 都是为了减少机器空闲、让 I/O 与计算尽可能重叠`▶ 30:20`。

## 4. 批处理与多道程序设计

> 课件 1-2026-秋季-操作系统概述-发布版.pdf 第 35–40 页 · 讲解从 `31:25` 开始

### 批处理操作系统的工作方式

批处理操作系统是早期操作系统的主要形态，用户不能直接操作计算机，而是以"作业"为单位把任务交给系统，由系统成批自动处理。其工作流程如下：

1. 用户将作业交给系统操作员；
2. 操作员把许多用户的作业组成一批，输入到计算机系统中，形成一个自动转接的连续作业流；
3. 操作员启动操作系统；
4. 系统自动、依次执行每一个作业；
5. 操作员把作业结果交还给用户。

老师补充，早期操作员收集作业后会先把整批作业输入并存放在磁鼓上，再启动系统依次执行；在美国，作业结果曾放在类似快递柜的格子中，用户凭编号领取`▶ 32:01`。作业的载体先后经历了穿孔卡片、纸带、磁带等形式`▶ 34:14`。

> **老师强调**：操作系统历史上的多种分类如今已经相互融合，不再单独区分；但最早的多道批处理系统仍值得讲解，因为其设计思想对后世影响深远。这种工作方式到 1991 年仍在使用，如今已很少见到`▶ 31:25`。

### 批与批作业处理

- **批（batch）**：供一次加载的磁带或磁盘，通常由若干作业组装而成，处理时使用一组相同的系统软件（称为"系统带"）。
- **批作业处理**：对批中的每个作业进行相同的处理——从磁带读入用户作业和编译链接程序，编译链接用户作业生成可执行程序，启动执行，并将执行结果输出。

### 作业的组成

批处理系统中的一个作业由三部分组成：

- 用户程序
- 数据
- 作业说明书（用作业控制语言 JCL 书写）

课件以典型的 **FMS JOB** 为例：一个作业由一张张卡片组成，卡片上记录命令和程序，例如：

```text
$JOB, 10,429754
$FORTRAN
Fortran program
$LOAD
$RUN
Data for program
$END
```

这些控制卡片依次说明作业标识、调用 Fortran 编译器、装入程序、运行以及程序数据等。

### 单道批处理与多道批处理

批处理操作系统分为两类：

| 类型 | 英文 | 特点 |
|---|---|---|
| 单道批处理系统 | simple batch processing / uni-programming | 内存中一次只有一个作业，作业依次执行 |
| 多道批处理系统 | multiprogramming system | 多个程序同时进入内存，由操作系统调度切换 |

**单道批处理**一次仅执行一个作业，后续作业必须等当前作业执行完毕；该模式下 CPU 和 I/O 设备无法同时工作，资源利用率极低`▶ 34:42`。

**多道程序设计（multiprogramming）** 的核心思想是：让多个程序同时进入内存，由操作系统调度周转，让不同作业分别使用 CPU 或 I/O 设备，从而充分协调各类资源`▶ 35:33`。这一思想直接催生了调度相关技术——在单道作业模式下不存在复杂的调度需求`▶ 35:33`。

系统中的作业通常可分为两类`▶ 36:59`：

- **Heavy compute（计算密集型）**：长时间占用 CPU 计算，例如天气预报；
- **Heavy I/O（I/O 密集型）**：频繁进行输入输出。

不同作业对内存、磁盘、终端、打印机等资源的需求各不相同，当多道作业同时驻留内存时，就需要设计相应的调度算法`▶ 36:59`。

### 单道与多道的性能对比（课件实例）

设有三个作业：

| 作业 | 类型 | 运行时长 | 内存需求 | 磁盘 | 终端 | 打印机 |
|---|---|---|---|---|---|---|
| JOB1 | Heavy compute | 5 min | 50K | 否 | 否 | 否 |
| JOB2 | Heavy I/O | 15 min | 100K | 否 | 是 | 否 |
| JOB3 | Heavy I/O | 10 min | 80K | 是 | 否 | 是 |

单道程序按顺序逐道运行作业；多道程序则让 CPU、磁盘、打印机等设备交叉被不同作业使用`▶ 38:13`。两种方式的指标对比如下：

| 指标 | 单道 Uniprogramming | 多道 Multiprogramming |
|---|---|---|
| 处理器利用率 | 22% | 43% |
| 内存利用率 | 30% | 67% |
| 磁盘利用率 | 33% | 67% |
| 打印机利用率 | 33% | 67% |
| 总耗时（Elapsed time） | 30 min | 15 min |
| 吞吐率 | 6 jobs/hr | 12 jobs/hr |
| 平均响应时间 | 18 min | 10 min |

可以看出，多道程序设计显著提高了各类资源的利用率和吞吐率，并缩短了总耗时与平均响应时间，这正是引入多道程序设计的目的`▶ 38:13`。

### I/O 瓶颈与卫星机方案

**问题**：慢速的输入输出处理直接由主机完成。在进行输入输出时，CPU 处于等待状态。

多道程序设计虽然缓解了 CPU 等待 I/O 的问题，但并未根本消除矛盾：CPU 的计算速度远快于 I/O 速度，这一矛盾至今仍然存在——即使在大模型场景下，数据传输通路的速度仍远慢于 GPU 的运算速度；如果在 I/O 阶段没有其他可调度的程序，CPU 依然需要等待，因此需要把 I/O 任务专门拆分出去`▶ 39:13`。

**解决：卫星机（卫星处理机）**

- 由独立的卫星机完成面向用户的输入输出（纸带或卡片），中间结果暂存在磁带或磁盘上；
- 主计算机只负责运算。

老师举了早期的实际硬件搭配`▶ 40:55`：

- 主机 **IBM 7094**：仅负责运算；
- 卫星机 **IBM 1401**：负责把读卡机上的程序、数据转录到磁带上，并把磁带上的运算结果输出到打印机。

这样便实现了 I/O 与主运算的分离。课件最后一页展示了美国西雅图计算机历史博物馆中的相关原型设备，包括 IBM 7094、IBM 1401、磁带机、卡片输入机和针式打印机等`▶ 40:55`。

## 5. SPOOLing假脱机技术

> 课件 1-2026-秋季-操作系统概述-发布版.pdf 第 41–45 页 · 讲解从 `43:13` 开始

### SPOOLing 假脱机技术概述

SPOOLing（Simultaneous Peripheral Operation On-Line，同时的外围设备联机操作，又称假脱机技术）于 1961 年在英国曼彻斯特大学的 Atlas 机上诞生。

- **核心思想**：利用磁盘（或磁带）作为缓冲，在高速设备中形成**输入井**和**输出井**来传递数据，将输入、计算、输出分别组织成独立的任务流，使 I/O 与计算真正并行。
- **目的**：提高 I/O 效率和设备利用率，缓解 CPU 与低速 I/O 设备之间速度不匹配的矛盾。

> **老师强调**：假脱机不再依赖多台硬件"卫星机"，而是用纯软件技术实现：外在表现类似脱机 I/O 处理，实际由主机统一联机管理外部设备。它也是最早批处理操作系统的原型，该技术思想沿用至今`▶ 43:13`。

### 多道批处理系统中的进程组织

在单台计算机上，SPOOLing 系统拆分为多个进程协同工作：

| 组成部分 | 职责 |
|---|---|
| **输入进程** | 从卡片机等输入设备读取数据、源程序、作业说明书，写入磁盘上的输入井 |
| **作业调度进程** | 按调度策略从输入井选择搭配得当的作业调入内存（就绪） |
| **作业控制进程** | 控制作业在内存中运行（运行、等待、就绪状态转换），结果送入输出井 |
| **输出进程** | 从输出井取出结果，送往打印机等输出设备 |

作业的完整流向为：

```
输入设备 → 输入井(磁盘) → 作业调度 → 内存运行 → 输出井(磁盘) → 输出设备
```

**生产者-消费者关系**：各进程以数据缓冲区（输入井/输出井）为中介两两协作——

- 输入进程生产数据写入输入井，调度进程从中读取消费；
- 调度进程分发作业给作业控制进程执行；
- 作业控制进程生产结果写入输出井，输出进程读取并打印。

> **老师强调**：这是操作系统课程中**生产者-消费者模型的早期原型**。多道批处理系统用软件统一管控整个作业流程，各道程序分段独立运行，中间通过生产者-消费者模式实现同步协同`▶ 45:26 · 46:39`。

### SPOOLing 系统工作原理

硬件上，主机通过通道连接卡片机、打印机和磁盘（磁盘上划分输入井与输出井），工作分四步：

1. 作业进入磁盘上的**输入井**；
2. 按某种调度策略选择几个搭配得当的作业，调入内存；
3. 作业运行的结果输出到磁盘上的**输出井**；
4. 结果从输出井送到打印机输出。

### SPOOLing 技术的主要特点

1. **提高 I/O 速度**：把对低速外设的 I/O 操作转变为对输入井/输出井（高速磁盘）的操作，缓和了 CPU 与低速 I/O 设备速度不匹配的矛盾。
2. **将独占设备改造为共享设备**：系统实际上并没有为任何进程真正分配物理设备，而是在输入井/输出井中为进程分配一个存储区、并建立一张 I/O 请求表，从而使独占设备在逻辑上可被共享。
3. **实现虚拟设备功能**：多个进程可同时使用一台独享设备，而每个进程都认为自己在独占该设备，即实现了设备的**虚拟分配**。

### 应用实例：以 SPOOLing 方式使用打印机

打印流程：

- 用户提交打印任务后，系统将待打印文档暂存到磁盘上的**打印请求队列**（含要打印的文件）；
- 专门的**打印守护进程（daemon）**从队列中依次取出任务，直接控制打印机输出；
- 由此实现多个任务"同时"打印，提高了打印效率。

> **老师强调**：打印守护进程清空队列后进入睡眠状态，收到新任务时被唤醒，其工作原理完全基于多道批处理的原型——这一 1960 年代的技术至今仍在使用`▶ 47:24`。

## 8. 保护、处理器模式与特权级别

> 课件 2-2026-秋季-操作系统运行环境和运行机制-发布版.pdf 第 10–15 页 · 讲解从 `1:18:09` 开始

### 处理器的组成与寄存器

处理器由运算器、控制器、一系列寄存器以及高速缓存构成。寄存器可分为两大类：

**1. 用户可见寄存器**
- 包括数据寄存器、地址寄存器以及条件码寄存器；
- 机器语言可以直接引用这些寄存器；
- **数据寄存器**（data register）：又称通用寄存器；
- **地址寄存器**（address register）：用于存放地址；
- **条件码寄存器**：保存 CPU 操作结果的各种标记位。

**2. 控制和状态寄存器**
- 用于控制处理器的操作；
- 在某种特权级别下才可以访问、修改；
- 典型寄存器包括：
  - **程序计数器（PC，Program Counter）**；
  - **指令寄存器（IR，Instruction Register）**；
  - **程序状态字（PSW，Program Status Word）**。

### 操作系统的保护需求

操作系统具有并发、共享等特征，这就要求系统必须实现保护与控制。硬件机制可以将操作系统与用户程序隔离开，从而为保护提供基础。

隔离是实现保护的手段，需要实现两层保护`▶ 1:18:09`：

1. **操作系统与进程之间的隔离**：防止用户进程干扰操作系统；
2. **进程与进程之间的互相保护**：防止一个进程影响或破坏其他进程。

保护功能主要由硬件机制实现。硬件提供不同的处理器运行模式（mode），不同模式下可以执行的指令集合不同`▶ 1:18:43`：

- 用户进程只能执行最小的、非特权的指令集合；
- 操作系统具有最高权限，可以执行所有指令。

> **老师强调**：硬件可以提供多种运行模式，但软件可以根据需要选择是否启用全部模式，并不一定把硬件支持的所有模式都用上`▶ 1:18:43`。

### 处理器状态（模式）

现代处理器通常将 CPU 状态划分为两种、三种或四种。处理器会在程序状态字寄存器 PSW 中专门设置一位或若干位，用来表示当前程序对资源和指令的使用权限，从而确定 CPU 当前所处的状态。

需要注意：PSW 是抽象的通用名称，不同指令集架构中的具体寄存器名称不同`▶ 1:20:23`：

| 架构 | 状态/控制相关寄存器 |
|---|---|
| 通用抽象 | PSW（程序状态字） |
| x86 | EFLAGS 寄存器 |
| RISC-V | 对应特权状态相关寄存器 |

在 x86 架构中，EFLAGS 寄存器包含与系统控制、状态标志等相关的字段，描述符中也设置了权限级别。课件提示可进一步参考 Intel 手册，并对比 ARM、RISC-V 等其他 ISA 的状态控制寄存器。

> **老师强调**：操作系统设计者必须理解这些标志位和特权字段的含义，才能正确设置处理器状态`▶ 1:20:23`。

### 特权指令与非特权指令

根据指令使用权限，可以将指令分为：

- **特权指令（privileged instruction）**：只能由操作系统使用，用户程序不能使用；
- **非特权指令**：用户程序可以正常使用的指令。

为了支持这种权限区分，操作系统至少需要两种 CPU 状态：

| CPU 状态 | 运行对象 | 指令权限 |
|---|---|---|
| 内核态（Kernel Mode） | 操作系统程序 | 可以执行所有指令，包括特权指令 |
| 用户态（User Mode） | 用户程序 | 只能执行非特权指令，不能执行特权指令 |

当前多数操作系统主要只使用内核态和用户态两种状态`▶ 1:22:20`。

### x86 的特权级别

x86 支持四个处理器特权级别，也称为特权环：

- **R0**
- **R1**
- **R2**
- **R3**

从 R0 到 R3，特权能力由高到低：

| 特权级 | 权限 | 典型用途 |
|---|---|---|
| R0 | 最高，可执行所有指令 | 内核态，运行操作系统 |
| R1、R2 | 介于 R0 与 R3 之间 | 大多数系统中使用较少 |
| R3 | 最低，只能执行最小指令集 | 用户态，运行用户进程 |

因此，从抽象角度看：

- **R0 相当于内核态**；
- **R3 相当于用户态**；
- R1、R2 介于两者之间。

目前大多数基于 x86 处理器的操作系统只使用 R0 和 R3 两个特权级别。

x86 的 EFLAGS 中 I/O 特权级字段为 2 位，因此最多可以表示 4 种模式，也可以只使用其中部分模式`▶ 1:20:23`。

此外，x86 为四个特权级分别配置了独立的栈指针，例如 `SS0/ESP0`、`SS1/ESP1` 等，共四套栈。硬件保证在模式切换时同步切换栈指针，从而避免操作系统栈与用户进程栈发生冲突`▶ 1:22:20`。

### RISC-V 的三种特权模式

RISC-V 架构提供三种特权模式：

| 模式 | 名称 | 作用/特点 |
|---|---|---|
| U 模式 | 用户模式（User Mode） | 运行用户程序 |
| S 模式 | 监管模式（Supervisor Mode） | 即操作系统运行状态 |
| M 模式 | 机器模式（Machine Mode） | 位于操作系统之下，权限更高 |

其中，机器态位于操作系统之下，操作系统不能直接控制机器态，只能向其发送请求；这种关系类似用户态进程向操作系统发出请求`▶ 1:25:20`。课堂中提到，目前机器态暂未使用`▶ 1:25:20`。

### 本章小结

- 处理器包含用户可见寄存器和控制/状态寄存器，PSW 用于记录处理器状态；
- 并发和共享要求操作系统提供保护，而保护依赖硬件的隔离机制；
- 硬件通过不同处理器模式区分可执行指令集合；
- 特权指令只能在内核态执行，非特权指令可在用户态执行；
- 操作系统最基本需要内核态和用户态两种状态；
- x86 提供 R0–R3 四个特权环，但主流操作系统通常只用 R0 和 R3；
- RISC-V 提供 U、S、M 三种特权模式，其中 S 模式用于运行操作系统。

### 特权指令的判断标准

题目给出的是**指令功能名称**，而不是具体指令格式，因为不同架构（x86、RISC-V）的具体指令各不相同`▶ 1:27:54`。

判断依据：
- **特权指令**：该功能关键到若普通用户可以随意调用，就会导致系统混乱，只能由内核态执行。
- **非特权指令**：用户程序可以直接调用，不会影响整个系统的运行`▶ 1:27:54`。

### 各指令分类

| 指令功能 | 类别 | 说明 |
|---|---|---|
| 启动 I/O | 特权指令 | 直接操作外设，用户不能随意使用`▶ 1:33:57` |
| 内存清零 | 特权指令 | 可能清掉系统或其他程序的内存，影响全局`▶ 1:33:57` |
| 修改程序状态字 | 特权指令 | 程序状态字包含处理器状态等关键信息，不能让用户随意改`▶ 1:33:57` |
| 设置时钟 | 特权指令 | 普通用户无法直接修改系统时钟，需通过系统接口完成`▶ 1:33:57` |
| 允许/禁止中断 | 特权指令 | 中断开关属于系统级控制 |
| 停机 | 特权指令 | 会使整个系统停止运行 |
| 控制转移 | 非特权指令 | 用户程序内部正常的流程跳转 |
| 算术运算 | 非特权指令 | 普通计算指令，不影响系统运行 |
| 取数指令 | 非特权指令 | 在用户自己的地址空间内访问数据 |
| 访管指令 | 非特权指令 | 见下方特别说明 |

> **老师强调（易错题）**：访管指令从名称上很难判断，但它是**非特权指令**。它是用户态进入内核态（在 RISC-V 中为管理态）的入口，是用户态**主动**调用内核功能的入口，因此必须允许用户态执行`▶ 1:32:18`。

> **老师强调**：设置时钟是特权指令，普通用户不能直接修改系统时钟，只能通过系统提供的接口间接完成`▶ 1:33:57`。

## 10. CPU状态转换与陷入入口

> 课件 2-2026-秋季-操作系统运行环境和运行机制-发布版.pdf 第 17 页 · 讲解从 `1:34:24` 开始

### CPU 状态之间的转换

用户态与内核态之间会发生频繁的双向切换，但两个方向的转换途径并不对称：

| 转换方向 | 转换途径 |
|---|---|
| 用户态 → 内核态 | 唯一途径：中断/异常/陷入机制 |
| 内核态 → 用户态 | 设置程序状态字 PSW |

- 用户态运行的程序不能直接执行特权指令或访问操作系统资源，必须通过中断、异常或陷入进入内核态。异常、陷入在不同课程和操作系统中命名可能不同，但都属于广义中断的范畴`▶ 1:34:24`。
- 内核态完成处理后，通过修改程序状态字（PSW）中的状态位返回用户态，从而形成完整的态转换路径`▶ 1:34:24`。

> **老师强调**：必须区分特权指令与非特权指令，因为系统运行过程中会频繁发生用户态与内核态的双向转换`▶ 1:34:24`。

### 陷入指令（访管指令）

陷入指令又称**访管指令**，是硬件提供给用户程序的接口，用于主动调用操作系统的功能（服务）。用户程序执行该指令后，会通过陷入机制从用户态进入内核态，由操作系统完成相应服务。

需要注意：在 RISC-V 中，`ecall` 本身属于**非特权指令**，它的作用是触发陷入，使 CPU 进入内核态，而不是说用户程序可以直接执行特权操作`▶ 1:35:56`。

常见的陷入/系统调用入口指令包括：

- `int`
- `trap`
- `syscall`
- `sysenter` / `sysexit`
- `ecall`

### 不同体系结构中的入口指令

| 指令 | 体系结构 / 环境 | 说明 |
|---|---|---|
| `ecall` | RISC-V | 用户程序主动发起陷入、调用操作系统服务的入口指令，属于非特权指令`▶ 1:35:56` |
| `int 0x80` | x86 / Linux | Linux 选择的系统调用中断入口；x86 共提供 256 个中断向量入口，0x80 是 Linux 选用的一个，不同操作系统可以选择不同中断号`▶ 1:37:04` |
| `sysenter` / `sysexit` | 后续 x86 型号 | 为快速进入/退出内核态提供硬件支持；早期奔腾之前的 x86 没有这对指令，只能直接操作中断向量表完成陷入`▶ 1:37:51` |
| `syscall` | 部分体系结构/体系结构演进后的系统调用指令 | 硬件提供的快速系统调用入口之一 |
| `trap` | 部分体系结构中的陷入指令命名 | 用于触发异常/陷入并进入内核态 |

内核态在不同资料中也称为 **supervisor mode（管态）**。

### 软硬件协作关系

陷入机制体现了操作系统与硬件之间的协作：

- 硬件负责提供陷入指令、中断向量、状态切换等机制；
- 操作系统决定使用哪个入口，例如 Linux 选择 `int 0x80` 作为传统系统调用入口；
- 硬件新增 `sysenter/sysexit` 等指令后，操作系统可以根据需要选择使用，也可以继续使用原有的陷入方式`▶ 1:37:51`。

> **老师总结**：硬件提供支持，软件按需选用，这正体现了软硬件之间的协作关系`▶ 1:37:51`。

## 11. 中断/异常机制的作用与基本概念

> 课件 2-2026-秋季-操作系统运行环境和运行机制-发布版.pdf 第 18–22 页 · 讲解从 `1:39:03` 开始

### 中断/异常机制的重要性

中断（也可与异常统称为"事件"）是计算机设计人员提供给操作系统的**核心底层机制**，其重要性如同汽车发动机、飞机引擎，是系统运行的核心驱动支撑。操作系统是由"中断驱动"或"事件驱动"的：

- 无事件发生时，操作系统处于空闲状态；
- 有事件触发时，操作系统才执行对应的工作，例如用户点击鼠标图标、时钟定时器到时等`▶ 1:39:17`。

中断机制的主要作用有三点：

1. **及时处理设备发来的中断请求**：例如磁盘 DMA 控制器完成读写任务后，通过中断告知 CPU 执行结果；键盘、鼠标、打印机等外设的请求也属于此类`▶ 1:42:11`。
2. **捕获用户程序提出的服务请求**：即捕获用户程序发起的系统调用（如 `fopen`、`fork` 等），由操作系统完成对应的核心操作`▶ 1:42:11`。
3. **防止用户程序执行过程中的破坏性活动**：例如硬件通过页表项的权限位发现用户对只读内存执行写操作时，会主动报错并终止该非法操作，保护系统安全`▶ 1:42:11`。

> **老师强调**：中断机制极其重要，类似飞机的引擎，是操作系统运行的核心驱动支撑；中断与异常的协同必须配合得当，否则系统无法正常运作`▶ 1:39:03 · 1:39:17`。

### 中断/异常的概念

中断/异常是 **CPU 对系统发生的某个事件作出的一种反应**。其执行过程为：

1. CPU 暂停正在执行的程序；
2. 保留现场（保存寄存器/上下文）；
3. 自动转去执行内核中相应事件的处理程序；
4. 处理完成后返回断点，继续执行被打断的程序。

这一过程的核心是：**事件的发生改变了处理器的控制流**。不同的事件对应不同的处理程序，既包括来自外部设备的中断，也包括系统调用等改变控制流的操作`▶ 1:44:42 · 1:47:21`。

需要注意的是，事件处理完成后并非立刻返回原程序，而是**统一进入调度程序**，由调度程序决定后续是返回断点继续执行，还是切换到其他进程；调度规则是预先规定好的。除非出现严重错误，被打断的程序最终都能够恢复执行，整个流程形成闭环`▶ 1:48:02`。

中断/异常具有三个特点：

| 特点 | 含义 |
|------|------|
| 随机发生 | 何时、何处发生不可预知 |
| 自动处理 | 响应与控制权转交由硬件自动完成 |
| 可以恢复 | 在以后某个时刻能够回到断点继续执行 |

> **老师强调**：其中自动转去处理程序的操作由硬件完成，这是硬件将处理器控制权交给软件的关键步骤`▶ 1:44:42`。

### 中断与异常的引入原因

两类事件术语的演化有其历史背景：

- **中断的引入**：为了支持 CPU 和设备之间的并行操作，解决 I/O 速度远慢于 CPU 的矛盾。CPU 启动设备进行输入/输出后，设备由控制器独立工作，CPU 转去处理与此 I/O 不相关的事情；当设备完成 I/O 后，通过向 CPU 发中断报告此次 I/O 的结果，让 CPU 决定后续处理`▶ 1:50:38`。
- **异常的引入**：表示 CPU 执行指令时本身出现的问题，这类情况不属于中断，因此后来新增了异常概念。例如算术溢出、除零、取数时的奇偶错、访存地址越界，或执行了"陷入指令"等；此时硬件改变 CPU 当前的执行流程，转到相应的错误处理程序、异常处理程序，或执行系统调用`▶ 1:50:38`。

### 事件的分类

事件可分为中断（外中断）和异常（内中断、例外）两大类，其下包含多种具体类型：

- **中断（外中断，异步）**：I/O 中断、时钟中断、硬件故障等；
- **异常（内中断/例外，同步）**：系统调用、页错误/页故障、保护性异常、断点指令、其他程序性异常（如算术溢出等）。

从触发性质上看：
- 异步事件（Interrupts）：包括 interrupt（中断）、software interrupt（软件中断），属于非预期（Unexpected）事件；
- 同步事件（Exceptions）：包括 fault（故障）、syscall/trap（系统调用/陷入），属于有意识安排的（Deliberate）或指令执行自身产生的事件`▶ 1:50:38`。

进一步可细分为中断、陷入、故障、终止四类，对比如下：

| 类别 | 原因 | 异步/同步 | 返回行为 |
|------|------|-----------|----------|
| 中断 Interrupt | 来自 I/O 设备、其他硬件部件 | 异步 | 总是返回到下一条指令 |
| 陷入 Trap | 有意识安排的（如系统调用） | 同步 | 返回到下一条指令 |
| 故障 Fault | 可恢复的错误（如页故障） | 同步 | 返回到当前指令（重新执行） |
| 终止 Abort | 不可恢复的错误 | 同步 | 不会返回 |

### 中断/异常机制的工作原理

中断/异常机制是现代计算机系统的核心机制之一，通过**硬件和软件相互配合**使计算机系统得以充分发挥能力。二者分工如下：

- **硬件：中断/异常响应**
  捕获中断源发出的中断/异常请求，以一定方式响应，将处理器控制权交给特定的处理程序。
- **软件：中断/异常处理程序**
  识别中断/异常类型并完成相应的处理。

即硬件负责"发现事件、保存现场、转交控制权"，软件（操作系统中的处理程序）负责"识别事件、具体处理"，二者协同完成整个中断/异常处理流程。
