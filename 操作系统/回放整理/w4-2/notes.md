## 1. 课程引入：调度问题与资源池化

> 课件 第 2–8 页 · 讲解从 `04:36` 开始

### 为什么需要处理器调度

处理器调度的核心作用是**控制、协调进程对 CPU 的竞争**：按照一定的调度算法从就绪队列中选择一个进程，把 CPU 的使用权交给它。它与此前学习的进程、中断与异常紧密关联——内核在处理完任何中断或异常事件后，出口流程一定会转向调度模块，由调度模块决定是否重新选择进程投入运行，确定哪个进程获得 CPU、能运行多长时间`▶ 04:36`。

系统中的典型场景是：

- N 个进程就绪、等待上 CPU 运行；
- M 个 CPU（M ≥ 1）；
- 调度需要决策：**给哪一个进程分配哪一个 CPU**。

在只有一个 CPU 时，通过调度让进程轮流使用 CPU，宏观上多个进程"同时"运行，这就是**并发**：同一时间段内多个进程都已启动且尚未结束，但任一时刻只有一个进程在 CPU 上执行。在多处理器环境下则可以实现真正的**并行**。并发与并行的实现都依赖调度`▶ 16:17`。

> **老师强调**：调度的核心价值在当下仍有很强的现实意义。以 DeepSeek、ChatGPT 为代表的大模型推理服务，本质上也是不同层面的调度：操作系统中调度对象是进程/线程，对应 CPU 核心；推理引擎中调度对象是用户请求、token 生成任务，对应 GPU、显存、KV Cache 三类资源`▶ 06:48`。

### 调度的底层思想：资源池化

调度的核心底层概念是**资源池化**：调度模块位于资源使用者和后端资源池之间，统一决策资源的分配`▶ 10:56`。

- **资源池化**是把多个（可能跨节点的）物理资源整合、抽象为可以统一调配、共享使用的逻辑资源，它是调度的前置条件，为调度器提供可管理的资源范围`▶ 12:37`。
- 大模型推理调度与进程调度逻辑高度相似，可做如下概念映射`▶ 10:56`：

| 操作系统进程调度 | 大模型推理调度 |
|---|---|
| 进程 | 推理请求 |
| 进程的时间片运行 | 推理中的 KV Task 块 |
| 就绪队列、调度决策 | 请求队列、调度决策模块 |
| 哪个进程获得 CPU | 哪个推理任务获得 GPU |
| 虚拟内存管理 | KV Cache 管理 |

推理引擎（如 ALL 推理引擎库）的调度器同样支持资源不足时的**优先级抢占**策略；注意力机制中 KV Cache 的管理则类似操作系统的虚拟内存管理`▶ 10:56`。

资源抽象有不同层次，本质上都是调度问题`▶ 14:16`：

1. **无虚拟化**：单 CPU 单内存，进程/线程直接运行；
2. **虚拟化**：多 CPU，按时间片调度分配；
3. **集群**：如 Kubernetes，多节点统一资源，配合容器调度；
4. **GPU 池化**（大模型场景）：整合多块 GPU 的算力、显存统一分配。

单机资源管理较简单；跨节点场景需要整合多节点的 CPU、内存等资源统一调度，本质仍是调度问题。调度还需要根据资源粒度（细粒度/粗粒度）权衡调度代价，解决任务该在哪个 CPU 上运行、如何匹配空闲 CPU 的问题`▶ 12:37`。

### 调度的目标

调度系统的通用目标是`▶ 09:01 · 15:18`：

- **高吞吐**
- **低延迟**（对具身智能、智能驾驶等实时性要求极高的应用尤为关键`▶ 09:01`）
- **保证公平**
- **不饥饿**
- 统一管理资源，**提高资源利用率**
- **灵活性、可扩展性**：资源不足时可以直接扩容
- 降低统一管理的成本

> **老师强调**：调度并不是"越快越好"，也不是随便选一个进程就行。不同系统（实时系统、云服务器、台式机、手机）的调度目标不同，因此适用的调度算法也不同，算法必须适配具体场景的限制`▶ 23:58`。选择进程时也不能只看单一因素，而要兼顾多维度指标，就像规划出行、买房买车需要多因素权衡一样`▶ 24:47`。

### 调度要解决的三个问题

处理器调度围绕 **What / When / How** 三个问题展开`▶ 15:55`：

| 问题 | 含义 | 对应内容 |
|---|---|---|
| **What**（依据什么） | 依据何种原则挑选进程/线程分配处理器 | 调度算法 |
| **When**（何时） | 何时分配处理器 | 调度时机 |
| **How**（如何） | 如何分配 CPU，即进程的上下文切换 | 调度过程 |

**调度时机（When）** 的核心是触发调度的事件：事件发生并处理完成后，才决定是否需要调度、是否重新选择运行进程`▶ 18:07`。

**特殊情况——没有就绪进程**：如果就绪队列为空、没有可调度的进程，操作系统会专门安排一个**系统空闲进程（idle 进程）** 占用 CPU，等待新的可调度进程出现`▶ 19:02`。

### 调度的三个层次

调度与进程状态转换密切相关，按照调度发生的层次可分为三类：

**1. 长程调度（作业调度 / 宏观调度）**
- 在**创建新进程时**进行；
- 决定一个新进程是否能进入当前活跃进程集合。

**2. 中程调度**
- 负责进程在**内存与外存之间的交换**；
- 从存储资源管理的角度：把进程的部分或全部换出到外存，可以为当前运行进程腾出所需内存空间；需要时再把进程所需部分换入内存（即**交换技术**）。

**3. 短程调度（微观调度）**
- 从处理机资源分配的角度，**选择就绪进程或线程进入运行状态**；
- 时间尺度通常是**毫秒级**；
- 由于短程调度算法被频繁使用，实现上要求**高效**。

### 调度过程与上下文切换（How）

选中新进程后，调度过程需要：妥善保存旧进程的状态以便日后恢复执行，再把新进程送入 CPU 运行，其核心操作就是**上下文切换（Context Switch）**；在代码中可以通过切换模块定位实际的进程切换逻辑`▶ 20:12`。

根本问题在于：多个进程竞争的是**有限、可被抢占**的 CPU 资源，因此必须明确 CPU 的分配规则、进程切换时机，同时关注切换带来的额外代价`▶ 09:48`。

- 老师用 **4×100 米接力的交接棒**作类比：上下文切换既要保证交接顺畅、不能失误，又不能降速过多、影响整体效率`▶ 09:48`。
- **切换开销的折中**：切换过于频繁会导致开销过高；长时间不切换又对用户进程不友好（响应变差），因此需要在两者之间权衡`▶ 21:30`。

### 调度算法的分类与核心概念

不存在能适配所有场景的通用调度算法，因此需要针对不同场景分类讨论`▶ 21:52`。按操作系统类型，调度算法可分为：

- 适用于**批处理系统**的调度算法；
- 适用于**交互式系统**的调度算法；
- 适用于**实时系统**的调度算法。

有些算法只适用于特定类别，有些则可以适配多类场景`▶ 25:50`。

> **老师强调**：
> - **抢占式调度与非抢占式调度是核心概念**。"抢占式"是调度算法的一种前缀属性，可以与优先级等其他调度规则组合，形成新的调度算法`▶ 26:30`。
> - 学习调度算法**不是死记硬背优缺点**，而要像工作中提交方案一样，全面分析不同方案的优劣，把各个考虑点覆盖到位`▶ 22:38`。

此外还有一条系统设计的通用原则——**机制与策略分离**，它在调度算法设计中同样适用`▶ 27:43`。后续课程会结合 Windows、Linux 等实际操作系统的调度实例来帮助理解理论；本节先建立调度时机（when）与调度过程（how）的整体框架`▶ 28:02`。

## 2. 处理器调度的三个层次与空闲进程

> 课件 第 5–7 页 · 讲解从 `28:41` 开始

### 处理器调度的三个层次

依据七状态进程模型，调度可划分为长程调度、中程调度和短程调度三个层次。

| 调度层次 | 别称 | 主要职责 |
| --- | --- | --- |
| 长程调度 | 作业调度、宏观调度 | 创建新进程时，决定其是否进入当前活跃进程集合 |
| 中程调度 | 交换调度 | 负责进程在内存与外存之间的交换 |
| 短程调度 | 微观调度、处理器调度、进程调度 | 从就绪进程或线程中选择一个进入运行状态 |

#### 长程调度（作业调度 / 宏观调度）

长程调度作用于新进程创建阶段：决定处于 new 态的进程能否进入就绪队列或就绪挂起队列，从而控制当前系统中的活跃进程数量，即控制系统负载。当负载过重时，新进程会被放入缓冲地带暂存；待负载降低后再将其激活`▶ 28:41`。

#### 中程调度

中程调度负责进程在内外存之间的交换，对应状态转换包括：

- 阻塞 ↔ 阻塞挂起
- 就绪 ↔ 就绪挂起`▶ 28:41`

从存储资源管理的角度，中程调度采用交换（swap）技术：把进程的部分或全部内容换出到外存，为当前运行进程腾出所需内存空间；随后再把当前进程所需的部分换入内存。

#### 短程调度（微观调度 / 处理器调度）

短程调度从处理机资源分配的角度出发，负责把就绪态进程调度到运行态，即选择哪个就绪进程或线程获得 CPU`▶ 28:41`。这是本课程重点讲解的调度层次。

短程调度具有以下特点：

- 时间尺度通常为毫秒级，实际中也可能达到微秒级`▶ 31:21`。
- 由于调度算法被频繁调用，实现时必须高效，要求能够实时完成选择。

> **老师强调**：短程调度的核心要求是"快"，调度算法必须高效实时`▶ 31:21`。

需要注意的是，调度并不只发生在"就绪 → 运行"这一个环节，其他进程状态之间的选择与切换同样属于调度问题`▶ 31:21`。

### 处理器调度的基本含义

处理器调度的本质是**控制、协调进程对 CPU 的竞争**：按照一定的调度算法，从就绪队列中选择一个进程，并把 CPU 的使用权交给被选中的进程。

- 调度程序（scheduler）：负责挑选就绪进程的内核函数。
- 一般系统场景：
  - 有 N 个进程处于就绪状态，等待上 CPU 运行；
  - 系统中有 M 个 CPU，且 M ≥ 1；
  - 需要决策的问题是：给哪一个进程分配哪一个 CPU？`▶ 32:10`

因此，调度不仅是单处理机上"选一个进程"的问题，在多 CPU 环境下还包括把指定进程分配到指定 CPU 的决策。

### 空闲进程（idle 进程）

如果就绪队列中没有任何就绪进程，而处于阻塞态的进程又无法使用 CPU，操作系统会安排一个**系统空闲进程**占用处理器。

- 空闲进程也称 **idle 进程**或**闲逛进程**`▶ 33:31`。
- 其核心特性是：**可以被任何事件打断**。一旦有就绪进程出现或某个事件发生，空闲进程会立即让出 CPU`▶ 33:31`。

> 老师在课上举了一个历史例子：北大曾研制的 6912 计算机搭载四道操作系统，当系统没有任务可运行时，会播放《东方红》作为空闲提示——听到这首曲子就表示操作系统正处于空闲状态。这可以看作早期"空闲进程"行为的一种形象体现`▶ 35:59`。

## 3. 调度要解决的 What、When、How

> 课件 第 8 页 · 讲解从 `41:07` 开始

进程调度需要解决三个核心问题：**What（按什么原则选）、When（什么时候选）、How（怎么完成切换）**，分别对应调度算法、调度时机和调度过程（上下文切换）。

### What：调度算法

- 解决"**依据什么原则挑选进程/线程来分配处理器**"的问题。
- 具体体现为**调度算法**：按照一定的选择标准（如优先级、等待时间、运行时长等），从就绪队列中选出一个进程/线程获得 CPU。

### When：调度时机

- 解决"**何时分配处理器**"的问题，即调度程序在什么时刻被触发、重新选择进程。
- 典型的调度时机包括进程终止、进程阻塞、时间片用完、有更高优先级进程到来等（课件只列出"调度时机"这一要点）。

### How：调度过程（上下文切换）

- 解决"**如何分配 CPU**"的问题。
- 本质是**进程的上下文切换**：把 CPU 从旧进程切换到新进程的过程，即保存旧进程的上下文（如寄存器、程序计数器等状态），并恢复新进程的上下文，使其得以继续执行。

> **老师强调**：进程调度的三个核心问题为——What 对应调度算法（选择进程的依据与原则）；When 对应调度时机（何时分配处理器）；How 对应进程上下文切换（将 CPU 从旧进程切换到新进程的过程）`▶ 41:07`。

三者的关系可以概括为：**When 决定调度在什么时刻发生，What 决定此刻选谁，How 决定如何把 CPU 实际交到被选中的进程手中。**

## 4. CPU调度时机与中断异常出口

> 课件 第 9–10 页 · 讲解从 `41:54` 开始

### CPU 调度的时机：何时需要选择新进程

调度时机要回答的问题是：**什么时候操作系统需要开始选择一个新进程来运行**`▶ 41:54`。

> **老师强调**：调度时机这部分内容待会要提问，需要认真记忆`▶ 41:54`。这两页是课程核心关键；如果以后忘记，说明学习不到位。按照“二八原则”，这部分内容加上虚拟存储，覆盖了核心的 20%；掌握核心后，其余 80% 的高层内容可以由此推导`▶ 49:44`。

#### 从进程状态变化看调度时机

常见需要调度的情况包括：

- 进程执行完毕并退出；
- 进程由于某种错误或异常而终止；
- 创建新进程；
- 运行进程等待 I/O 操作或其他资源，进入阻塞态，此时 CPU 空闲；
- 被唤醒的阻塞进程重新回到就绪态；
- 进程用完分配给它的时间片，回到就绪队列；
- 进程主动放弃 CPU。

这些场景都可以结合进程三状态模型推导：只要当前进程离开运行态，或者有新进程进入就绪队列，就绪队列发生变化，就可能需要重新调度`▶ 41:54`。例如，运行态进程时间片到后回到就绪态，自然需要调度程序重新选择；阻塞态进程被唤醒回到就绪态，也可能导致重新选择`▶ 44:34`。

进程主动放弃 CPU 的典型操作是执行 `yield`。在线程相关场景中，主动让出 CPU 的操作也属于这一类`▶ 44:34`。

#### 从中断/异常事件看调度时机

典型事件可以归纳为：

| 事件类型 | 例子 | 对应操作或机制 |
|---|---|---|
| 进程控制操作 | 创建、唤醒、退出 | 创建对应 `fork()` 系统调用；阻塞对应 `block`；唤醒对应 `wakeup()` 或 `signal()`；退出对应 `exit()` 触发的异常事件`▶ 45:37 · 46:59` |
| I/O 相关事件 | 进程等待 I/O、I/O 中断 | 等待 I/O 会进入阻塞；I/O 完成后通过中断唤醒 |
| 时钟事件 | 时间片用完、计时器到时 | 由时钟中断驱动时间片计时器`▶ 46:59` |
| 异常事件 | 进程执行中出现 abort 异常 | 可能导致进程终止 |
| 主动让出 | 执行 `yield` | 进程主动放弃 CPU |

课件中的调度时机与这些确定事件是一一对应的：操作系统处理的事件都是确定的，不存在未知事件；每个确定事件都能对应到进程状态模型中的某个状态变化节点`▶ 45:37`。

#### 时钟中断与时间片的区别

时钟中断和时间片不是同一个概念`▶ 46:59`：

- **时钟中断**：由硬件定时装置（如晶体振荡器）按固定频率发出的中断信号；
- **时间片计时器**：存放在内存中的一个整数计数器。

每次时钟中断到来时，内核会将相关计时器的值减 1；当计数器减到 0 时，表示时间片用完或某个计时器到时，于是触发相应的调度或唤醒操作`▶ 46:59`。

### 事件发生后的完整处理流程

调度并不是在事件发生的一瞬间任意进行的，而是遵循固定的硬件、软件处理顺序：

1. 发生中断、异常或系统调用事件；
2. 当前运行进程暂停运行；
3. **硬件机制响应事件**，使 CPU 进入操作系统内核态；
4. **内核软件处理相应事件**；
5. 处理后，某些进程状态可能发生变化，也可能出现新进程，或者 CPU 变为空闲；
6. 操作系统调整就绪队列；
7. 进程调度程序根据预设调度算法，从就绪队列中选择一个进程；
8. 处理完成后**返回用户态**运行被选中的进程。

> **老师强调**：流程顺序一定是**先由硬件完成响应，再由软件处理事件，处理完后返回用户态**，不存在硬件处理和软件处理交错的流程；以往考试中很少有同学能完全答对这个顺序`▶ 51:21`。

#### 统一的调度点：返回用户态前的最后时刻

无论是中断、异常，还是系统调用，内核处理结束后，在**返回用户态前的最后时刻**，都会统一进入调度流程`▶ 53:30`。

因此，CPU 调度时机可以从两个等价视角理解：

- 从进程模型看：进程状态或就绪队列发生变化，可能需要重新选人；
- 从底层机制看：中断/异常/系统调用处理完毕、即将返回用户态前，是统一的调度点。

中断异常机制是处理各类事件的通用机制，不同事件对应不同的处理策略，体现了操作系统中**机制与策略分离**的设计原则`▶ 51:21`。以上内容已经覆盖全部 CPU 调度时机`▶ 53:30`。

## 5. 进程切换与上下文切换过程

> 课件 第 11–14 页 · 讲解从 `1:04:30` 开始

### 进程调度与进程切换的发生

进程调度程序首先从就绪队列中选择一个准备运行的进程。被选中的进程有两种可能：

- 刚刚被暂停执行的当前进程；
- 另一个处于就绪态的新进程。

在内核判断需要重新调度时，会先根据重调度标志判断是否真的需要切换进程：

- **不需要切换**：让刚被暂停的当前进程继续执行；此时原来的上下文仍保存在系统栈中，直接弹栈即可恢复执行，不需要进行进程切换`▶ 1:04:30 · 1:06:41`。
- **需要切换**：调用调度算法选择一个新的就绪进程，并执行进程切换`▶ 1:04:30`。

进程切换是指一个进程让出处理器，由另一个进程占用处理器的过程。

> **老师强调**：调度过程本质上就是上下文切换，它与具体体系结构相关；相关汇编代码篇幅不长，但执行顺序非常重要，后续会结合代码详细讲解`▶ 1:04:30`。

### 上下文与上下文切换

进程运行时，其硬件状态保存在 CPU 的寄存器中。这些寄存器主要包括：

- 程序计数器（PC）；
- 程序状态寄存器（程序状态字，PSW）；
- 栈指针；
- 通用寄存器；
- 其他控制寄存器。

当进程不运行时，这些寄存器的值需要保存在该进程的 PCB 中。这里的“不运行”并不是指进程终止，而是指进程由于中断、时间片到、阻塞等原因暂时暂停，以后仍可能被调度执行`▶ 1:08:12`。

上下文切换，就是把 CPU 硬件状态从一个进程切换到另一个进程的过程。它包括：

1. 保存原来运行进程的各种状态；
2. 恢复新进程的各种状态。

上下文切换主要包含两部分工作：

- **切换全局页目录**，加载新进程的地址空间；
- **切换内核栈和硬件上下文**，其中硬件上下文包括内核执行新进程所需的全部信息，如 CPU 相关寄存器。

> **老师强调**：寄存器切换中需要重点更新页表起始地址寄存器，因为不同进程对应不同页表；如果页表不切换，新进程将仍在旧进程的地址空间中执行`▶ 1:08:12`。

### 上下文切换的具体步骤

以“进程 A 下 CPU、进程 B 上 CPU”为例，切换过程如下：

1. **保存进程 A 的上下文环境**  
   包括程序计数器、程序状态字、通用寄存器等。

2. **更新进程 A 的 PCB**  
   用新的状态和其他相关信息更新其 PCB。

3. **把进程 A 移至合适的队列**  
   根据暂停原因，将其放入就绪队列、阻塞队列等。

4. **将进程 B 的状态设置为运行态**。

5. **从进程 B 的 PCB 中恢复上下文**  
   恢复程序计数器、程序状态字、其他寄存器等，使 CPU 从进程 B 上次暂停的位置继续执行。

从内核实现角度看，若确定要切换到新进程，需要先把原进程的寄存器组（register file）保存到它的 PCB 中，再把新进程 PCB 中保存的状态恢复到寄存器，最后由内核把控制权交给新进程`▶ 1:06:41`。新进程的上下文就存放在它的 PCB 中，恢复到对应寄存器后即可继续运行`▶ 1:08:12`。

### XV6 中的上下文切换

在 XV6 的 `<kernel/swtch.S>` 中，上下文切换通过汇编实现，并使用两个参数：

- `a0` 寄存器：存放第一个参数，指向 **old 进程上下文**的指针；
- `a1` 寄存器：存放第二个参数，指向 **new 进程上下文**的指针。

其基本含义是：把当前旧进程的硬件上下文保存到 `a0` 所指向的位置，再从 `a1` 所指向的位置恢复新进程的硬件上下文。

## 6. 上下文切换的直接与间接开销

> 课件 第 15 页 · 讲解从 `1:10:54` 开始

### 上下文切换开销的基本概念

上下文切换虽然是提高系统资源利用率所必需的机制，但它本身会带来开销（overhead/cost）。操作系统中的开销通常指三类资源消耗：

- **CPU 消耗**：切换过程占用 CPU 执行内核代码
- **时间消耗**：切换期间无法执行用户有用工作
- **空间消耗**：为保存上下文、维护相关数据结构占用内存

> **老师强调**：为了提升系统资源利用率，进程上下文切换不可避免，因而其开销也必然存在`▶ 1:11:11`。

上下文切换开销可以分为**直接开销**和**间接开销**两类。

### 直接开销

直接开销是指**内核完成切换本身所消耗的 CPU 时间**，主要包括：

- **保存和恢复寄存器**：把当前进程的寄存器状态保存到其进程控制块（PCB/进程描述符）中，并把即将运行进程的寄存器现场恢复出来`▶ 1:12:53`。
- **切换地址空间**：执行与地址空间切换相关的指令，例如修改页表基址寄存器等。这类指令的代价通常比较昂贵`▶ 1:12:53`。

也就是说，从一个进程的上下文切出、再切入另一个进程的上下文中，内核执行的全部指令耗时都属于直接开销。

### 间接开销

间接开销主要来自切换引起的**缓存局部性被破坏**，表现为高速缓存、缓冲区缓存和 TLB 等失效后重新预热所付出的代价：

- **高速缓存（Cache）失效**
- **缓冲区缓存（Buffer Cache）失效**
- **TLB（Translation Look-aside Buffer，转译旁视缓冲区/快表）失效**

频繁切换时，原有进程在 Cache/TLB 中积累的有用条目可能被清空或被其他进程的内容挤掉；进程重新获得 CPU 后，需要经历大量 cache miss，逐步把缓存重新填充、预热起来，这段 miss 处理时间就是间接开销`▶ 1:12:53`。

### 降低间接开销的技术

新的处理器技术可以在 Cache/TLB 的条目中加入**进程标识（如地址空间标识符 ASID）**。这样在切换进程时，缓存不必整体清空：硬件可以根据条目中的进程标识区分条目属于哪个进程。被切走的进程再次回到 CPU 上运行时，它此前留在 Cache/TLB 中的内容仍然可以命中，从而减少缓存失效和重新预热的代价，降低上下文切换的间接开销`▶ 1:14:41`。

### 小结

| 开销类型 | 含义 | 主要来源 |
|---|---|---|
| 直接开销 | 内核执行切换操作本身占用的 CPU 时间 | 保存/恢复寄存器、切换地址空间等指令 |
| 间接开销 | 切换后缓存性能下降造成的额外执行代价 | Cache、Buffer Cache、TLB 失效及重新预热 |

利用带进程标识的 Cache/TLB 技术，可以避免切换时一律清空缓存，使进程恢复运行后仍能命中原有缓存，从而缓解间接开销。

## 7. 不同系统类型的调度目标与衡量指标

> 课件 第 17–19 页 · 讲解从 `1:15:13` 开始

### 三类系统的调度目标

不同类型的操作系统中，进程的特征不同，调度算法追求的目标也不同。系统中的进程主要分为交互式进程、批处理进程和实时进程三类。

#### 交互式进程（interactive process）

- 需要经常与用户交互，因此会花费大量时间等待用户的输入操作。
- 对响应时间要求高，平均延迟应低于 **50～150 ms**。
- 典型程序包括：shell、文本编辑程序、图形应用程序等。
- 调度目标主要是：**响应时间快、均衡性好**。

老师指出，交互式系统追求的是较低的响应时间`▶ 1:16:35`。

#### 批处理进程（batch process）

- 不必与用户交互，通常在后台运行。
- 不要求很快得到响应。
- 典型程序包括：营业额计算、利息计算、索赔处理等。
- 调度目标主要是：**吞吐量高、周转时间短、CPU利用率高**。

老师举例说明：麦当劳总部每天对各门店的营业额和销售数据进行汇总统计，就属于典型的批处理场景`▶ 1:16:35`。

#### 实时进程（real-time process）

- 具有实时需求，不应被低优先级进程阻塞。
- 要求响应时间短，并强调在规定时限内完成任务。
- 典型场景包括：视频/音频播放、机械控制、智能驾驶、股票交易等。
- 调度目标主要是：**满足最后期限、具有可预测性**。

老师强调，实时系统的核心是不能出现数据延迟或卡顿`▶ 1:15:13`。实时调度的核心目标是满足任务的截止时间（DDL）；当系统资源无法满足所有进程时，可以丢弃低优先级任务，优先保证高优先级任务的截止期限，即实现“期限可调度”`▶ 1:17:47`。

### 调度算法设计的发展背景与考虑角度

调度算法的设计需要结合具体应用场景。操作系统及其应用场景经历了以下发展过程：

批处理系统 → 多道程序设计系统 → 批处理与分时的混合系统 → 个人计算机 → 网络服务器 → 人-机-物协同系统。

老师说明，调度算法设计是后续课程的重点，需要按不同系统类型和场景分别讨论`▶ 1:15:13`。随着系统从早期批处理发展到现代个人计算机、网络服务器和物联网等人机协同场景，不同角色关注的指标也不同`▶ 1:18:48`。

调度算法的设计考虑可以从两个角度理解：

| 考虑角度 | 具体指标                      |
| ---- | ------------------------- |
| 用户角度 | 周转时间、响应时间、最后期限、公平性、强制优先级等 |
| 系统角度 | 吞吐量、CPU利用率、平衡资源、均衡性、可预测性等 |

这些指标又可以进一步划分为性能因素和其他因素：

- **性能方面**：吞吐量、周转时间、响应时间、最后期限、CPU利用率等。
- **其他方面**：公平性、强制优先级、资源平衡、均衡性、可预测性等。

> **老师强调**：不同角色关注的指标之间必然存在矛盾，并不存在只优化单一目标的完美方案，需要通过协调、折中与权衡，形成普遍可接受的调度方案`▶ 1:18:48`。

### 调度算法的衡量指标

#### 性能指标

1. **吞吐量（Throughput）**  
   指单位时间内完成的进程数目。吞吐量越大，说明系统在相同时间内完成的任务越多。批处理系统通常非常关注吞吐量。

2. **周转时间（Turnaround Time, TT）**  
   指一个进程从提出请求到运行完成所经历的总时间。它是批处理系统的典型衡量指标`▶ 1:19:48`。

3. **响应时间（Response Time, RT）**  
   指从用户提出请求到系统第一次作出回应所经历的时间。它是交互式系统的典型衡量指标`▶ 1:19:48`。

   老师特别说明，第一次回应不一定是最终运行结果，也可以是进度提示。及时给出反馈可以让用户知道任务正在推进，避免用户因为长时间无感知而随意中断任务`▶ 1:19:48`。

#### 非性能指标

1. **公平性（Fairness）**  
   调度时应避免某些进程长期得不到服务，要尽量让进程合理共享CPU资源。

2. **资源利用率**  
   例如 **CPU利用率（CPU Utilization）**，表示CPU用于执行有效工作的时间比例。调度算法应尽量减少CPU空闲，提高系统资源使用效率。

#### 特定场景下考虑的指标

- **实时性**：主要用于实时系统，要求任务在截止期限之前完成。
- **能耗**：在移动设备、嵌入式设备或物联网场景中，调度算法还可能需要考虑降低能量消耗。

### 本章小结

三类系统的核心调度目标可以概括为：

| 系统类型 | 典型进程/场景 | 核心调度目标 |
|---|---|---|
| 交互式系统 | shell、文本编辑器、图形应用 | 响应时间短、交互均衡 |
| 批处理系统 | 营业额计算、利息计算、索赔处理 | 吞吐量高、周转时间短、CPU利用率高 |
| 实时系统 | 音视频、机械控制、智驾、股票交易 | 满足最后期限、响应可预测 |

调度算法设计本质上是一个在多种相互依赖的指标之间进行折衷权衡的过程，需要根据系统目标决定优先保证哪些指标。

## 8. 调度算法设计要点：PCB、优先级与就绪队列

> 课件 第 20–22 页 · 讲解从 `1:23:47` 开始

### 调度算法设计的核心考虑因素

设计 CPU 调度算法时，需要围绕以下几个共性基础问题展开，不同操作系统会选择不同的实现方案`▶ 1:25:51`：

- PCB 中需要记录哪些与 CPU 调度有关的信息
- 进程优先级及就绪队列的组织方式
- 抢占式调度与非抢占式调度
- I/O 密集型与 CPU 密集型进程的区分
- 时间片大小的选择

其中 I/O 密集型/CPU 密集型、优先级与优先数、就绪队列组织、抢占与非抢占模式是本次讨论的调度属性`▶ 1:27:12`。

### PCB 中的调度相关信息

设计调度算法时，**所有参考因素都必须有对应的 PCB 数据支撑，没有记录的数据无法作为调度依据**。因此，需要根据所采用的调度策略，在 PCB 中记录相应的调度相关信息；PCB 中记录的信息与调度算法设计直接相关`▶ 1:23:47`。

> **老师强调**：调度依据必须落到 PCB 的具体字段上，无记录则无法参与调度决策`▶ 1:23:47`。

举例来说，Windows 的 PCB 中为优先级设置了两个字段`▶ 1:23:47`：

| 字段 | 含义 |
|---|---|
| 基本优先级 | 进程创建时确定 |
| 可变优先级 | 运行过程中可动态调整 |

两个字段配合，可以为调度器提供更丰富的决策依据`▶ 1:23:47`。

### 进程优先级（数）

#### 优先级与优先数的区分

- **优先级**：反映进程真实的轻重缓急、重要程度的高低，认知上与日常生活中的"优先级"一致`▶ 1:27:23`。
- **优先数**：优先级在计算机系统中通常用数字来表达，这个量化的数字就称为优先数`▶ 1:27:23`。

> **老师强调**：优先级和优先数不是同一概念，要注意区分——优先级是重要程度本身，优先数只是它的量化指标`▶ 1:27:23 · 1:28:39`。

#### 静态优先级与动态优先级

优先数（优先级）按其在进程运行期间是否可变，分为两类：

| 类型 | 特点 |
|---|---|
| 静态优先级 | 进程创建时指定，运行过程中不再改变 |
| 动态优先级 | 进程创建时指定一个初始优先级，运行过程中可以动态变化 |

动态优先级的一个典型调整策略是：**等待时间较长的进程可提升其优先级**，以避免长期得不到调度。实际系统中静态和动态两种方式都可以实现`▶ 1:28:39`。前面提到的 Windows"基本优先级 + 可变优先级"两个字段，正是为支持动态优先级而设计的`▶ 1:23:47`。

### 进程就绪队列的组织

就绪队列如何组织，是调度算法设计必须明确的问题，包括采用单队列还是多队列、多队列按什么规则组织等`▶ 1:25:51`。课件给出了两种典型的多队列排队方式。

#### 方式一：按优先级排队

- 系统按优先级设置多个就绪队列（就绪队列 1、就绪队列 2、……、就绪队列 n）。
- 进程创建时，根据其优先级进入对应的就绪队列；等待的事件发生后，进程从等待队列回到它所属的就绪队列。
- 调度规则：**优先级最高的队列优先调度；只有当高优先级队列为空时，才会调度低优先级队列中的进程**。
- 进程在 CPU 上运行时可能被抢占，也可能因等待某事件而进入等待队列，运行结束则终止。

**饥饿问题**：在这种方式下，如果高优先级队列持续有新进程创建，低优先级就绪队列中的进程会长期得不到调度，从而产生饥饿`▶ 1:29:36`。

#### 方式二：按运行行为逐级降级

另一种排队方式中，多个队列不再固定对应进程的固有优先级，而是构成一条"降级路径"`▶ 1:31:02`：

1. 所有新创建的进程都首先进入**最高优先级队列**。
2. 进程每运行完一个时间片，就向下一级（优先级更低的）队列降级。
3. 各级队列中的进程被依次调度上 CPU 运行，结束则终止。

这种模式同样可能出现饥饿问题；但它的一个重要作用是：**可以通过进程在优先级降级路径上的表现，区分出进程的行为类型**（例如频繁因 I/O 阻塞而用不完时间片的进程，会停留在较高层级，表现为 I/O 密集型；持续用满时间片、一路降级的进程，则表现为 CPU 密集型）`▶ 1:31:02`。

> **老师强调**：这两种就绪队列对应的调度框架是本节重点，需要掌握`▶ 1:31:02`。

两种方式的核心区别在于：方式一中队列对应进程**固定的优先级**；方式二中队列反映进程**运行过程中的动态行为**，所有进程都从最高队列开始、按时间片使用情况逐级下降。

## 9. 抢占式与非抢占式调度及课堂练习

> 课件 第 23 页 · 讲解从 `1:32:31` 开始

### 3. 抢占与非抢占

抢占式与非抢占式描述的是**进程占用 CPU 的方式**，即当前正在运行的进程能否被系统强行夺走 CPU。

#### 可抢占式（Preemptive，可剥夺式）

当有比当前正在运行进程**优先级更高的进程进入就绪态**时，系统可以强行剥夺当前运行进程的 CPU，将其分配给更高优先级的进程使用`▶ 1:32:31`。

**高优先级进程就绪的常见触发条件（课堂练习①）**：

- **`fork` 创建高优先级子进程**：当前进程通过 fork 创建了一个优先级高于自己的子进程，子进程进入就绪态`▶ 1:51:49`。
- **阻塞的高优先级进程因中断返回就绪态**：例如一个高优先级进程此前因等待磁盘 I/O 而阻塞，磁盘中断发生后，该进程被唤醒并回到就绪态`▶ 1:51:49`。

**可抢占调度的通用机制**：由"**事件触发 → 内核处理 → 调度决策**"的流程保证`▶ 1:51:49`。

1. 发生事件（如 fork、磁盘中断）；
2. 内核处理该事件；
3. 检查到就绪队列中存在比当前运行进程优先级更高的进程；
4. 设置 `reschedule` 标志，触发调度程序，切换当前进程`▶ 1:51:49`。

#### 不可抢占式（Non-preemptive，不可剥夺式）

某一进程被调度运行后，**除非由于它自身的原因不能运行，否则一直运行下去**（通常直到执行完毕）`▶ 1:32:31`。

**进程因自身原因无法继续运行的具体情况（课堂练习②）**：

- 进程**执行完毕**，正常终止；
- 进程发起 I/O 请求等操作而**主动进入阻塞态**（如等待磁盘、键盘输入）；
- 进程等待某事件（如等待信号量、等待子进程）而阻塞。

> **老师强调**：以上两种模式的触发条件——「存在比当前运行进程优先级更高的进程就绪」与「当前进程因自身原因无法继续运行」——是课堂随堂练习的内容，要求在 2 分钟内写出`▶ 1:35:59`。理解可抢占调度的关键是抓住"事件触发—内核处理—调度决策"这一通用流程，而不要把无关的机制误认为与抢占有关`▶ 1:51:49`。

#### 两种模式对比

| 对比项 | 可抢占式 Preemptive | 不可抢占式 Non-preemptive |
|---|---|---|
| CPU 能否被强行剥夺 | 能，高优先级进程就绪时可被强行切换 | 不能，只能由运行进程主动让出 |
| 调度时机 | 有更高优先级进程进入就绪态即可触发 | 进程运行完毕或因自身原因阻塞时才调度 |
| 响应性 | 高优先级任务能及时得到响应 | 高优先级任务可能需等待当前进程主动放弃 CPU |
| 触发示例 | fork 出高优先级子进程；磁盘中断唤醒高优先级进程`▶ 1:51:49` | 进程终止；进程请求 I/O 进入阻塞 |

## 10. 进程行为与时间片设计

> 课件 第 24–25 页 · 讲解从 `1:40:31` 开始

### 进程行为分类：I/O密集型与CPU密集型

按照进程在执行过程中的行为特征，可以将进程划分为两类：

| 类型 | 别称 | 行为特征 |
| --- | --- | --- |
| **I/O密集型（I/O-bound，I/O型）** | I/O型 | 频繁进行I/O操作，通常花费大量时间等待I/O操作完成；每次只占用CPU很短时间（短CPU区间）就会发起I/O请求并主动让出CPU |
| **CPU密集型（CPU-bound，CPU型/计算密集型）** | 计算密集型 | 需要大量CPU时间进行计算，呈现长CPU区间，较少进行I/O等待 |

从进程执行的时间分布上看，两类进程的差异体现为"长CPU区间、短CPU区间与I/O等待时间"的组合方式不同。

> **老师强调**：未来对I/O密集型进程的调度处理更加重要。

**为什么调度算法普遍倾向于优先选择I/O密集型进程？** 所有调度算法都存在倾向性，都会在两类进程中优先选择I/O密集型进程，原因有二`▶ 1:41:11`：

1. **提升系统所有资源的整体利用率**：计算机系统的资源不止CPU一种。I/O型进程在CPU上运行很短时间就发起I/O请求、主动让出CPU，这既保障了CPU的利用率，也能让磁盘等外设资源同步投入工作，避免其他资源闲置`▶ 1:41:11`。
2. **补偿其执行时间损失**：I/O型进程通常只用了很短的时间片就发起I/O，剩余的时间片配额没有用完。优先调度它能让它尽快用完剩余配额，补偿它因等待I/O而损失的执行时间`▶ 1:41:11`。

> 调度算法的首要设计目标是**公平**，保证所有进程获得均等的机会。例如上一版Linux调度算法CFS（完全公平调度算法），其核心目标就是公平`▶ 1:40:31`。

### 时间片（Time Slice / Quantum）

**定义**：时间片是一个时间段，是调度程序分配给被调度上CPU运行的进程的单次最长CPU运行时长，确定了允许该进程一次运行的时间长度`▶ 1:45:00`。

#### 时间片设计需要考虑的因素

- 进程切换的开销
- 对响应时间的要求
- 就绪进程的个数
- CPU能力
- 进程的行为

#### 时间片的两个核心设计问题

**1. 时间片取长一点还是短一点？**

时间片长度需要在切换开销与响应灵活性之间折中：

- **时间片过长**：进程切换频率过低，系统灵活性差、响应不及时。老师类比为"四年不换宿舍"`▶ 1:45:00`。
- **时间片过短**：进程切换过于频繁，进程切换开销在总时间中的占比过高。老师类比为"频繁换宿舍带来的高额成本"`▶ 1:45:00`。

因此时间片的取值通常依赖系统经验值来调整参数，在两者之间取得平衡`▶ 1:45:00`。

**2. 固定还是可变（是否对所有进程统一设置）？**

即时间片是对所有进程统一设置同一个长度，还是针对不同进程分配不同长度的时间片。具体规则依不同操作系统的设计而定`▶ 1:45:00`。

**问题 3：Ctrl+C 与 kill 终止进程的异同**

有学生提问：按 Ctrl+C 终止进程与调用 `kill` 杀进程这两种方式有什么异同？`▶ 1:50:35`

老师解答：两种方式最终都是由内核向目标进程发送终止信号，区别只在于进入内核的路径不同：

| 方式 | 触发途径 | 后续过程 |
|------|----------|----------|
| Ctrl+C | 中断触发内核处理程序 | 内核处理程序向目标进程发送信号 |
| `kill` | 系统调用触发内核 | 内核向目标进程发送信号 |

两种方式殊途同归，最终都由内核完成信号发送；更具体的细节可以查阅内核源码确认`▶ 1:50:35`。

## 术语

| 术语 | 解释 |
| --- | --- |
| 处理器调度 | 处理器调度是按一定调度算法从就绪队列中选择进程或线程，并把 CPU 使用权交给它的过程。 |
| 长程调度 | 长程调度决定新创建的进程是否进入当前活跃进程集合，用于控制系统负载。 |
| 中程调度 | 中程调度负责进程在内存和外存之间，或不同挂起状态与活跃状态之间的交换。 |
| 短程调度 | 短程调度从就绪进程或线程中选择一个进入运行态，时间尺度通常为毫秒级，要求实现高效。 |
| 空闲进程 | 当系统中没有就绪进程时，操作系统让 idle 进程占用 CPU，它可在新的可运行进程出现时立即让出处理器。 |
| 调度时机 | 调度时机是指因进程退出、创建、阻塞、唤醒、时间片用完或主动放弃 CPU 等事件而需要重新选择进程的时刻。 |
| 上下文切换 | 上下文切换是保存当前进程硬件状态并恢复另一个进程硬件状态，使 CPU 从一个进程转到另一个进程执行的过程。 |
| PCB | PCB 保存进程运行状态及调度所需信息，是进程被暂停后能够恢复执行和参与调度决策的重要依据。 |
| 直接切换开销 | 直接切换开销指内核保存和恢复寄存器、切换地址空间等指令本身消耗的 CPU 时间。 |
| 间接切换开销 | 间接切换开销指进程切换后 Cache、Buffer Cache 和 TLB 等失效并重新预热所带来的性能损失。 |
| 吞吐量 | 吞吐量表示单位时间内系统完成的进程或任务数量，是批处理系统重点关注的指标。 |
| 周转时间 | 周转时间是进程从提出请求到运行完成所经历的总时间。 |
| 响应时间 | 响应时间是从用户提出请求到系统第一次作出回应所经历的时间，是交互式系统的重要指标。 |
| 优先级与优先数 | 优先级表示进程的重要程度，优先数是用于表示优先级的量化数值，二者概念并不完全等同。 |
| 静态优先级与动态优先级 | 静态优先级在进程创建后保持不变，动态优先级则可在运行过程中根据等待时间、I/O 行为等因素调整。 |
| 可抢占式调度 | 可抢占式调度是指更高优先级进程就绪时，系统可以强行剥夺当前运行进程的 CPU。 |
| 非抢占式调度 | 非抢占式调度是指进程一旦获得 CPU，除非自身阻塞、出错或结束，否则会一直运行下去。 |
| I/O密集型进程 | I/O密集型进程频繁等待 I/O 操作完成，每次占用 CPU 的计算突发通常较短。 |
| CPU密集型进程 | CPU密集型进程需要大量连续计算时间，主要瓶颈在于处理器资源。 |
| 时间片 | 时间片是调度程序分配给进程一次连续占用 CPU 的最长时间长度，其大小需要在响应时间和切换开销之间权衡。 |
