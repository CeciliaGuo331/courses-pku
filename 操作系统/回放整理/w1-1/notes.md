### 为什么学习操作系统：拼接知识体系

#### 一、课程定位：把零散知识拼成完整体系

多数同学已经具备 ICS（计算机系统基础）的基础，本课程的目标不是孤立地学习新知识，而是梳理操作系统的全貌，把前置课程中已经掌握的零散知识拼接成完整的计算机系统认知体系`▶ 12:15`。

- 学习时要主动对比新旧概念，不能遗忘 ICS 等前置课程内容`▶ 12:15`。
- 操作系统像一头复杂的"大象"，受课时限制无法一次讲完，需要分模块逐步拆解，最终通过实验把各模块知识拼接成完整的操作系统认知`▶ 13:14`。
- **拼图式学习**：在 ICS 等课程中已掌握的知识相当于已完成的拼图块，本课程要补充尚未掌握的部分，关键是将新旧知识融合为一体，而不是只孤立地记忆本课程内容`▶ 13:56`。

> **老师强调**：不要只停留在概念层面，要在操作系统的具体场景中落实理解，避免出现"以为会了但实际答不出"的幻觉`▶ 14:34`。

#### 二、操作系统问题必须结合具体场景推导

操作系统中的很多问题没有统一答案，必须先明确硬件架构、操作系统、位宽等场景要素，再进行推导，不能凭空给出结论`▶ 16:49`。

以"虚拟地址空间有多大"为例：

- **四级页表是 X86（酷睿系列）硬件架构下的设计**，换到 RISC-V 架构下，同一问题的答案会不同；答案同时还与操作系统相关`▶ 14:34`。
- X86 的四级页表由硬件定义，软件直接适配该设计，因此其虚拟地址空间为 2^48（64 位计算机）`▶ 16:49`。
- 推导要素：虚拟地址需要通过页表转换为物理内存，页表项大小与计算机位宽相关——64 位系统页表项为 8 字节，32 位系统为 4 字节`▶ 16:49`。

**X86 4KB 分页下的推导过程**`▶ 18:58`：

```
单个页表页（4KB）可存放页表项数 = 4KB / 8B = 2^12 / 2^3 = 2^9 = 512 个
→ 每级页表索引占 9 位
四级页表索引总位数 = 4 × 9 = 36 位
页内偏移位数 = log2(4KB) = 12 位
虚拟地址总位数 = 36 + 12 = 48 位
最大虚拟地址空间 = 2^48
```

Linux 直接使用了该 2^48 的最大值；若要实现完整的 64 位虚拟地址空间，超出 48 位的部分需要由软件处理`▶ 18:58`。

> **老师强调**：本学期课程硬件平台为 RISC-V，不再讲解 X86 相关内容`▶ 20:59`。

页表实现体现了**软硬协同**的思想：硬件提供了对应支持就直接使用硬件能力，硬件未提供的部分再通过软件补充实现——类比数学计算时优先调用成熟库，而不是从零编写算法`▶ 20:59`。

> **老师强调**：学习中不需要纠结知识点的具体数值，更重要的是主动思考，把旧知识与本课内容关联、联想、汇总`▶ 22:30`。

#### 五、系统性思维：复杂问题解决的底层能力

系统是由多个相互关联的部分组成的整体，**任何一个部分的变化都可能通过复杂的相互作用影响其他部分，进而影响整个系统的行为和状态**。系统性思维强调的不是解决眼前的单点问题，而是识别系统整体的联动关系。

**例1：跨域因果链识别**

当供应链因气候灾害中断时（如台风"白海豚"登陆，政府启动整套应急系统响应`▶ 29:18`），具备系统思维的员工不会仅以自然原因为由致歉、只解决缺货问题，而能迅速识别整条连锁反应`▶ 30:33`：

```
物流延迟 → 库存成本上升 → 客户体验下降 → 品牌风险（声誉受损）
                                              ↓
                              甚至影响公司决策层面
```

同时还会把碳排放法规、地缘政治等叠加因素一并纳入决策。

**例2：反馈回路设计**

"韧性"指标强调"从失败中学习"。系统思维要求把单次项目复盘升级为持续反馈回路：将用户行为数据、市场变化、技术迭代纳入一个可自我修正的模型，使团队能敏捷应对下一轮不确定性。

#### 六、系统能力培养

"系统"正变得无处不在：人-机-物深度融合与协同是当前信息技术发展的重要趋势——万物的状态皆可感知、测量、监控；人-机-物以全新方式交流互动；智能系统使事件预测更加容易、资源分配更加优化。

一个"系统"具有以下特征：**整体的、相互依赖的、分层次的、有反馈的、动态运行的、具有边界与所处环境的、稳定和高效的**。

**操作系统是复杂系统的典型代表**`▶ 32:26`：

- 由进程管理、虚拟存储、文件系统、输入输出等多个互相关联的功能模块组成整体，为程序运行提供各类服务；
- 任何一个部分的变化都会相互影响，通过复杂作用传导到其他部分，改变整个系统的行为和状态；
- 可以将操作系统看作不断在不同状态间切换的**状态机**。

当前终端、3S 技术、各类监控设备普及，已经进入人-机-物高度协同的时代：系统通过测量获取信息、输入信息，经处理后输出结果，系统无处不在`▶ 33:38`。

课件还通过四个例子说明操作系统与系统能力的重要性：**DeepSeek、12306、CPU:GPU、具身智能**。同时，大模型与计算机体系结构、操作系统之间的关系，正是理解系统能力培养的重要切入点。

## 3. DeepSeek案例与基础知识支撑

> 课件 第 9–12 页 · 讲解从 `34:57` 开始

### DeepSeek：系统能力的典型案例

DeepSeek 的成功核心不在于单纯堆砌算力，而在于一整套系统设计所体现的工程能力。其目标定位是在有限资源下实现**低成本、高性能**，被评价为"可能重新定义大模型研发的规则"`▶ 34:57`。

其技术体系可以分为 AI 算法与系统支撑两个层面：

- **大模型训练与推理**：低成本、高性能
- **AI 层面**：知识蒸馏、强化学习、监督微调、混合专家模型（MoE）、多头潜注意力、多 token 预测
  - 由于算力成本无法支撑大规模算力堆砌，DeepSeek 采用混合专家模型（MoE）并做进一步筛选优化`▶ 34:57`
- **系统层面**：
  - **体系结构**：FP8 混合精度（搭配 FP8 降低成本）、GPU PTX 汇编级优化`▶ 34:57`
  - **并行计算**：DualPipe 双向流水并行
  - **任务调度**：无辅助损失的负载均衡策略（通过负载均衡的调度思想实现整体优化）`▶ 34:57`

其中 PTX 汇编优化体现了"手工优化替代通用优化"的思路：不依赖 C++ 借助编译器进行通用优化，而是手工编写 GPU 的 PTX 汇编，实现激活函数和算子层面的优化`▶ 34:57`。

> **老师强调**：数据流动、访存是系统性能的核心瓶颈，这是本课程与 ISS 课程共同强调的重点`▶ 38:41`。

### 基础知识的支持

大模型研发需要多门计算机基础课程协同支撑，各门课程的作用如下：

| 课程 | 作用 | 关键内容 |
|---|---|---|
| 计算机组成 | 理解硬件底层如何支撑大规模计算 | 汇编、CPU、存储层次、I/O |
| 操作系统 | 高效管理系统资源以支持分布式训练 | CPU 管理、存储管理、文件系统 |
| 编译技术 | 将高层模型代码转化为高效机器指令 | 词法分析、语法分析、优化技术、目标代码生成 |
| 体系结构 | 理解体系结构与软件的关系、性能度量模型 | 指令集架构、存储层次、总线设计、性能模型等 |
| 并行计算 | 实现大模型的分布式训练与推理 | 并行编程模型（MPI、CUDA）、负载均衡、数据并行与任务并行 |
| 数据库 | 高效管理与处理训练数据 | 数据存储、索引优化、SQL、分布式数据库 |

补充一点：编译原理中的词法分析、语法分析知识在大模型的 token、提示词解析中同样发挥重要作用`▶ 34:57`。

### 计算机组成与大模型

计算机组成知识在大模型中的作用主要体现在三个方面：

- 理解 CPU、GPU、TPU 结构，优化计算效率，提高训练和推理速度
- 了解缓存与存储管理，减少数据访问瓶颈，提高模型数据加载效率
- 设计高效的数据流，提高硬件利用率，如减少访存开销、优化指令流水线等

**案例：DeepSeek 推理引擎的 PTX 汇编及算子优化**

- 技术点：针对 Transformer 的 GeLU 激活函数，手动编写 PTX 汇编指令
- 优化目标：优化寄存器分配和指令流水线，减少冗余的内存访问`▶ 38:41`

这正对应"访存是性能核心瓶颈"的判断——通过手工控制寄存器与流水线，避免编译器通用优化产生的多余访存。

**案例：DeepSeek 训练数据集的多线程高吞吐加载优化**

- **mmap（memory map）内存映射**：减少文件加载时内核态与用户态之间的拷贝开销

#### 相关知识回顾（ISS 内容）

**I/O 方式的演进**——以"把文件内容输出到屏幕"为例，实现方式不断优化`▶ 42:09`：

1. 最初逐字符读写，效率极低
2. 在用户代码中自建缓冲区，减少进出内核的 I/O 次数，提升性能
3. 引入 `printf` 等库函数，其自带内部缓冲区；若不主动调用 `flush` 刷新，缓冲区内容不会自动输出

> 老师提示：如果遗忘缓冲区与 flush 相关内容，可以回顾 ISS 课件复习`▶ 42:09`。

**mmap 的提速原理**：mmap 在虚存章节讲解，用于解决大文件传输问题`▶ 43:12`：

- 传统传输：需要先把文件读到内存，再从内存写出，存在内核态与用户态之间的数据拷贝
- mmap：直接完成映射传输，省去中间拷贝，减少加载文件时内核态、用户态之间的拷贝开销

> **老师强调（小测试）**：要对包含 **1 亿个整数**的大文件进行排序，如果能用 mmap 实现，说明已掌握该技术的优化逻辑；需要理解其提速原理，以及它和**虚存**之间的关联`▶ 44:03`。

### 异步交易排队系统

异步交易排队系统是一种处理高并发请求的技术架构：将用户请求放入队列并异步处理，从而有效缓解高并发带来的压力。它由三部分组成。

**1. 请求接收与队列化**

- 用户提交购票请求时，系统先将请求放入队列。
- 队列按"先进先出"（FIFO）原则管理请求，保证处理顺序与提交顺序一致。
- 系统为每个请求分配一个"虚拟号牌"，用户可凭号牌查询自己在队列中的位置。

**2. 异步处理**

- 请求进入队列后，系统根据后端处理能力异步地处理请求。
- 用户提交请求时系统不会立即占用大量资源，而是先把请求暂存，等待合适时机再处理。
- 这种方式可以有效避免系统因瞬间流量过大而崩溃。

**3. 动态流量控制**

- 系统根据后端服务的负载自动调整请求处理速度。
- 后端繁忙时自动减慢处理速度，避免过载。
- 后端有空闲资源时加快处理速度，充分利用资源。

老师将这一思想与 ICS 课程中的 HTTP 连接请求排队关联起来：Web Server 可以设置最大排队数（默认最多排队 50 个连接请求），超出的请求会被拒绝，进入队列的请求则逐个被处理`▶ 46:31`。

> **老师强调**：要注意区分同步与异步的应用场景。操作系统层面的生产者—消费者模型属于同步问题；而在 I/O 层，由于快慢设备性能差距过大，必须使用异步方案才能提升性能。学习时要把前后课程的知识点关联起来，避免学一个忘一个`▶ 47:27`。

### 后摩尔定律时代：性能增长转向"栈顶"

摩尔定律依靠晶体管微缩工艺来提升硬件性能，属于硬件工艺领域`▶ 48:17`。当摩尔定律失效后，计算性能的增长将主要依赖计算技术栈的"栈顶"（Top），即软件优化、算法创新和硬件架构简化，而非传统的晶体管微缩——不是让晶体管更小，而是让它们更聪明地工作。

这一观点来自 2020 年 Charles E. Leiserson 等人（MIT、NVIDIA、Microsoft Research 等机构联合撰写）的文章 *"There's Plenty of Room at the Top: What Will Drive Computer Performance After Moore's Law?"*。

| | 栈顶（Top） | 栈底（Bottom） |
|---|---|---|
| 内容 | 软件、算法、硬件架构 | 半导体物理、制程工艺 |
| 典型技术 | 高性能代码、并行算法、GPU/TPU 架构 | 晶体管微缩、5nm/3nm 工艺 |
| 前景 | ✅ 未来性能增长点 | ❌ 摩尔定律终结 |

**三大"栈顶"方向与关键策略**

- 未来方向：软件性能工程、算法优化、硬件架构简化。
- 关键策略：并行性、局部性、领域专用硬件、模块化大系统。
- 挑战与展望：性能提升将变得"机会性、非均匀、递减"，需要跨层协同。

老师把软件方向的性能优化技术栈概括为四层`▶ 48:17`：

1. **软件代码优化**：编写对层次化存储结构友好的高性能代码。
2. **并行算法设计**。
3. **架构设计**（后续课程学习）。
4. **存储硬件架构**：例如 RAID，通过多块便宜小盘并行组合、数据分片，配合软件管理获得高读写带宽；其本质是通过架构改造提升整体性能，GPU 多卡协同、多机联网都是同理。

## 5. AI系统竞争、CPU/GPU协同与具身智能

> 课件 第 19–34 页 · 讲解从 `1:04:49` 开始

### AI 系统竞争：从训练转向部署推理

当前大模型发展阶段，重点已经从前期依赖 GPU 的模型训练，转向部署推理与应用落地。在推理和应用场景中，CPU 需要承担大量任务分解、调度安排等工作，因此 CPU 的作用逐渐提升，CPU 与 GPU 的配比也在不断升高。算力吞吐量、设备利用率、任务合理分配，正是操作系统设计的核心目标，课程所学的操作系统知识在这一场景中完全适用`▶ 1:04:49`。

#### 主战场的变化

AI 正在进入**系统竞争阶段**，主战场从训练转移到部署：

| 维度 | 过去：训练竞赛 | 现在：部署竞赛 |
|---|---|---|
| 关注重点 | 模型能训多大、峰值算力多高 | 系统能否以可控成本、高利用率运行模型 |
| 价值重心 | 峰值算力 | 系统效率 |
| 核心问题 | 模型能不能做出来 | 模型能不能跑起来、用起来、赚到钱 |

训练更像是**研发问题**，推理则是**利润问题**：

| 对比项 | 训练 | 推理 |
|---|---|---|
| 开支性质 | 阶段性资本开支 | 持续性运营开支 |
| 成本压力 | 单次高额投入 | 每天持续消耗成本 |
| 决定什么 | 模型能不能做出来 | 模型能不能活下去 |
| 数据趋势 | — | 推理算力占比预计在 2026 年达到 2/3；中国日均 Token 调用量两年增长超千倍 |

#### GPU 利用率不足的系统原因

现实中 GPU 利用率长期偏低：

- 头部互联网企业 AI 推理集群的 GPU 平均利用率低于 **40%**；
- 中小企业甚至低于 **15%**。

其根本原因通常不是 GPU 性能不足，而是 GPU 之外的系统环节跟不上，包括：

- 数据流动；
- 任务调度；
- 内存管理；
- I/O 协同；
- 网络处理。

也就是说，GPU 本身算得很快，但数据和任务无法持续供给，导致昂贵的 GPU 资源被大规模闲置。

#### CPU 在 AI 工作流中的作用

真实 AI 工作流中，GPU 从来不是单独工作的。CPU 负责大量控制流和系统协同任务：

- **前端**：数据准备；
- **中间**：任务调度、缓存维护、上下文切换、网络通信；
- **后端**：结果处理、数据库交互。

因此，关键不是“CPU 替代 GPU”，而是：如果系统能力跟不上，再强的 GPU 也只是闲置资产。CPU 决定了 AI 系统的资源利用率和投资回报率（ROI）。

#### 瓶颈从 GPU 算力转向 CPU 任务链

智能体（Agent）是一套真正执行任务的系统，需要完成步骤拆解、工具调用、API 访问、状态维护等工作。

康奈尔大学对五类 Agent 工作负载的研究表明：

- CPU 端处理占总延迟的 **43.8%～90.6%**；
- 在 RAG 场景中，CPU 处理甚至占 **90% 以上**，而 GPU 推理不到 10%。

这说明很多真实任务的主要瓶颈，已经不再是 GPU 的峰值算力，而是 CPU 能否顺畅跑完整个任务链。

#### CPU:GPU 配比的变化

AI 工作负载重心从训练转向推理，使 CPU 与 GPU 的比例关系从传统的约 **1:8** 向 **1:1** 转变。

| 工作负载场景 | 物理 CPU-GPU 卡配比 | 说明 |
|---|---:|---|
| 大模型预训练 / 大规模训练 | 1:7～1:8 | 传统训练服务器中，1 颗服务器 CPU 挂载 7～8 张 GPU；CPU 主要负责调度、I/O、数据分发，计算几乎全部交给 GPU |
| 标准大模型推理业务 | 1:3～1:4 | 普通云推理中，CPU 负责请求解析、Token 前后处理、任务队列 |
| Agent 智能体、复杂工具调用推理 | 1:1～1:2 | 当前正在演进的主流方向；大量串行逻辑、工具调用、沙箱执行在 CPU 上运行，部分场景中 CPU 核心甚至更多 |

> **老师强调**：CPU 与 GPU 的配比不断升高，背后反映的是部署推理、任务调度和资源利用率的重要性提升；这些问题正是操作系统课程的核心内容`▶ 1:04:49`。

### AI 竞争下半场：系统为王

AI 系统竞争的变化可以概括为四点：

1. **战场转移**：从训练竞赛转向部署竞赛；
2. **瓶颈转移**：从 GPU 峰值算力转向系统端到端效率；
3. **价值重估**：CPU 从“幕后”走向“系统指挥官”的位置；
4. **新要求**：企业必须持续追问：
   - GPU 是否被充分利用？
   - 哪些任务应该交给 CPU？
   - 整套系统的吞吐率和资源利用率到底高不高？

AI 的未来不仅取决于更快的芯片，也取决于更聪明的系统。

### 具身智能与操作系统

具身智能（Embodied AI）可以理解为“有身体的 AI”。它不仅需要大脑，即大模型和决策算法，还需要通过身体与环境交互。身体的控制、协调和实时响应，高度依赖操作系统的底层能力。

#### 具身智能系统层次与 OS 能力的对应关系

具身智能系统可以分为四个功能层次，每个层次都依赖相应的操作系统能力`▶ 1:07:18`：

| 具身智能层次 | 主要内容 | 对应操作系统能力 |
|---|---|---|
| 感知层 | 视觉、听觉、触觉传感器 | 设备驱动、I/O、资源管理 |
| 决策层 | 大模型、强化学习、规划 | CPU/GPU/NPU 调度、内存管理 |
| 控制层 | 运动规划、轨迹生成 | 实时调度、同步互斥、通信 |
| 执行层 | 电机、液压、关节驱动 | 设备驱动、实时控制、中断处理 |

操作系统侧主要提供：

- **实时性**：硬实时 / 软实时调度；
- **资源管理**：CPU、内存、I/O 隔离；
- **通信机制**：共享内存、消息队列；
- **同步互斥**：锁、信号量、RCU；
- **设备驱动**：传感器与执行器抽象。

### 具身智能中的五个关键设计问题

#### 1. 实时性：操作系统决定身体的反应速度

以“抓住一个杯子”为例：

- 决策层的大模型推理可能可以容忍几百毫秒延迟；
- 控制层的关节轨迹插补、力反馈必须满足**硬实时**要求。

因此系统可能采用**双 OS 架构**：

- 一个 Linux 运行 AI 决策和感知算法；
- 一个 RTOS 运行实时控制任务；
- 两者通过共享内存等机制通信。

#### 2. 资源管理：平衡“大脑”与“小脑”

人形机器人等具身智能设备通常是资源受限的嵌入式系统，但又要同时运行：

- 消耗大量 CPU/GPU/NPU 资源的大模型推理；
- 要求低延迟的实时控制任务。

系统架构师需要精确划分任务优先级和资源需求，并借助操作系统实现隔离。调度策略直接决定机器人是“反应迟钝”还是“行云流水”。

#### 3. 通信机制：连接“感官”与“大脑”

具身智能中存在高频数据流：

- 传感器可能以 **1kHz** 频率采样；
- 感知数据需要迅速送到感知算法；
- 决策结果也要以同样高的频率送到执行器。

这要求进程间通信具备极低延迟和高吞吐。ROS2 等软件架构建立在操作系统提供的通信原语之上，因此理解底层通信机制对于定位性能瓶颈非常重要。

#### 4. 同步互斥：保证状态一致性

机器人系统中，多个线程可能同时访问同一份数据。例如：

- 一个线程正在写当前关节角度；
- 另一个线程同时使用该角度进行碰撞检测。

如果缺少正确同步，可能出现数据错乱，使机器人“抽搐”甚至失控。

常见选择包括：

- **自旋锁**：中断上下文中只能使用自旋锁，因为中断上下文不能睡眠；
- **无锁队列**：高频传感器回调可使用基于 CAS 的无锁队列减少阻塞；
- **读写锁**：多传感器融合任务中可允许多个读取操作并发执行。

#### 5. 设备驱动：屏蔽硬件多样性

具身智能设备包含多种多样的硬件：

- 传感器：IMU、深度相机、触觉皮肤；
- 执行器：伺服电机、液压阀、气动肌肉。

如果每个应用都直接操作寄存器，开发效率会很低，也难以移植。设备驱动将硬件差异封装起来，使算法开发者可以专注于“做什么”，而不是“怎么和硬件说话”。

对于性能关键路径，例如高频 IMU 数据处理，程序可能绕过普通内核驱动路径，直接使用 `mmap` 映射 DMA 缓冲区，从而实现零拷贝。

### 具身智能中的低延迟

低延迟是指系统从接收到输入（如传感器信号）到产生相应输出（如执行器指令）所需时间极短且可预测。

在具身智能系统中，低延迟不仅是性能指标，更是物理安全性和智能体实时决策能力的保障。

| 延迟类型 | 含义 | 典型来源 |
|---|---|---|
| 中断延迟 | 从硬件中断发生到 CPU 开始执行中断处理程序的时间 | 中断屏蔽、高优先级中断 |
| 调度延迟 | 从任务就绪到实际获得 CPU 开始运行的时间 | 调度器策略、任务优先级 |
| 上下文切换时间 | 保存当前任务状态并恢复下一个任务状态的时间 | 寄存器保存 / 恢复、TLB 刷新 |
| 通信延迟 | 数据从一个任务传到另一个任务的时间 | 数据拷贝、协议栈处理、核间通信 |

这些延迟类型共同决定了机器人能否稳定、及时地响应物理世界。

#### ICS 已学习的基本概念和技术

**1. 存储器层次结构与局部性原理**

- 局部性原理是存储器层次结构的理论基础，包括时间局部性（Temporal locality）和空间局部性（Spatial locality）。
- 该原理已在 ICS 的多个层面落地应用`▶ 1:09:13`：
  - **Cache 层**：CPU 与内存之间的高速缓存。
  - **虚存层（第 6 章）**：可将虚存视为磁盘在内存中的缓存，沿用的是内存与 Cache 之间相同的分层缓存思想`▶ 1:09:13`。
  - **文件系统层**：读取文件时会在内存中建立缓存（磁盘块缓存），是同一缓存技术在不同层次上的跨层应用`▶ 1:09:13`。
  - **应用层（第 11 章 Web Server）**：Web Server 作为应用层进程，会为热点网页开辟 Web page cache。基于局部性原理，热点网页响应速度快，而冷门的深层网页访问速度较慢`▶ 1:09:13`。

**2. 异常控制流（Exceptional Control Flow, ECF）**

- ICS 中涵盖的异常控制流包括：中断（Interrupt）、陷阱（Trap）、故障（Fault）、系统调用（System call）。
- 操作系统课程会将这些事件归为"中断"和"异常"两大类。两种术语表述虽然存在差异，但覆盖的事件集合相同，并不冲突，两种说法都可以使用`▶ 1:12:36`。
- 与之配套的基础概念是**内核模式（内核态）与用户模式（用户态）**`▶ 1:12:36`。
- 控制流转移是分层次的：函数调用属于普通控制流转移，不属于异常；而从用户态陷入内核态则属于异常控制流`▶ 1:17:16`。

**3. 进程与线程**

- 进程（Process）、线程（Thread）、多线程（Multithreading）。
- 信号（Signal）。

**4. 虚拟存储器（虚存）**

- 页表（Page table）、TLB、地址翻译（地址转换）。
- 内存映射机制（Memory mapping）。
- 分页（Paging）、缺页异常（Page fault）、虚拟地址（Virtual address）、地址空间（Address space）。

**5. 并发与同步**

- 并发（Concurrency）。
- 信号量（Semaphore）及 PV 操作。
- 死锁（Deadlock）。
- 互斥（Mutual exclusion）、临界区（Critical section）、同步（Synchronization）、锁（Lock）、原子操作（Atomic operation）、数据竞争（Data race）。

> **老师强调**：本课程至少一半以上的核心概念在此前课程中都已经接触过，包括内存映射机制、并发与信号量等；操作系统课会帮助大家全面、系统地掌握这些概念`▶ 1:18:33`。

#### 操作系统分层结构与进程模型

**层次结构**

- 硬件之上是操作系统内核（OS Kernel）。
- 现代操作系统（如鸿蒙、Windows、Linux）整体代码量可达数亿行，但其中大部分来自上层开发框架和生态模块；本课程只学习内核的核心部分`▶ 1:13:34`。

**进程的运行与生命周期**

- 内核之外只运行各类进程；进程被动态创建，执行完毕后消亡`▶ 1:14:44`。
- 进程在用户态执行过程中，一旦遇到系统调用、中断、故障、异常等事件，就会陷入内核，形成异常控制流`▶ 1:17:16`。
- 用户态中运行的不一定只有用户进程，也可以运行系统进程`▶ 1:17:16`。
- 内核本身并不是进程：内核态对应内核空间，内核之外的所有进程都运行在用户态`▶ 1:14:44`。

**进程结构对比**

| 系统 | 进程结构 |
|------|----------|
| Unix/Linux | 树形结构：0 号进程直接生成，之后创建 1 号 init 进程，再由 init 衍生出 shell、终端等子进程 |
| Windows | 不存在上述树形的父子进程关系 |

### 操作系统知识的整体框架

结合 OSTEP 的三大板块，可以提前建立本课程的整体框架。

#### 1. 虚拟化：管理 CPU、内存和外设

“虚拟化”这一术语最早来自操作系统领域。早在上世纪 60 年代，IBM 开发 OS/370 时就已经提出了虚拟机相关概念`▶ 1:39:44`。

操作系统的核心定位是**计算机系统资源的管理者**。广义上说，凡是承担资源管理功能的系统，都可以被称为操作系统`▶ 1:39:44`。

传统计算机系统资源主要包括：

- CPU
- 内存
- 其他所有外部设备

操作系统对硬件资源的抽象，也称为虚拟化，主要分为三类`▶ 1:41:22`：

| 硬件资源 | 操作系统抽象 | 说明 |
|---|---|---|
| CPU | 进程 | 操作系统通过调度进程来管理 CPU |
| 内存 | 地址空间 | 用户无需直接操作物理内存 |
| 外设 | 文件、设备等抽象 | 用统一接口屏蔽硬件差异 |

其中：

- **进程是对 CPU 的抽象**；
- **地址空间是对内存的抽象**。

CPU 执行指令时必须访问内存，因此进程运行必然关联内存。课程会先把进程与内存分开讲解，但在理论层面上要以进程为核心，把相关资源整合起来理解`▶ 1:42:33`。

#### 2. 并发：处理运行实体之间的交互

系统中存在多个运行实体，即进程或线程。它们之间会发生交互，由此引入并发问题。

并发部分关注多个执行流在共享资源、同步协作和交替执行时产生的问题，是课程的核心章节之一`▶ 1:46:19`。

#### 3. 持久化：通过文件等机制管理长期数据

外部设备的访问遵循“万物皆文件”的思想，被统一为文件读写操作：

- 打印可以对应 `write`
- 扫描可以对应 `read`

这样可以用统一接口屏蔽不同设备的差异`▶ 1:47:09`。

### Nachos 实验

Nachos 全称是 **Not Another Completely Heuristic Operating System**，由 UC Berkeley 开发，是一个用于教学的操作系统。

它提供了操作系统框架，包括：

- 线程；
- 用户进程；
- 虚拟存储；
- 中断驱动的 I/O。

同时，Nachos 还包含硬件模拟：

- MIPS 处理器；
- 控制台；
- 时钟；
- 中断系统。

#### 历史与体系结构

Nachos 于 1992 年由 UC Berkeley 的 Thomas E. Anderson、Wayne A. Christopher、Steven J. Procter 开发，使用 C++ 编写，面向 MIPS 架构，曾被 Berkeley、New York University 等多所大学使用。

后续发展包括：

- 2000 年，Daniel Hettena 开发 Nachos 5.0 Java 版；
- 2004 年，Stanford 将 Nachos 思想移植到 x86，发展出 PintOS。

Nachos 的运行方式具有典型“宿主机 + 模拟器”特征：

1. Nachos 本身是 Linux 宿主主机上的一个进程；
2. Nachos 内部包含 MIPS 模拟器，模拟硬件行为并执行用户程序指令；
3. 用户程序由 C 程序交叉编译成 MIPS 可执行程序；
4. Nachos Kernel 提供系统服务，负责装载用户程序并在 MIPS 模拟器上执行。

#### 自动评测流程

评测系统的基本流程如下：

1. 参赛队伍将操作系统源代码提交到指定 GitLab；
2. 评测机自动 Clone 代码；
3. 在 Docker 容器中使用 Make 编译；
4. 指定版本的 gcc/Rust 工具链将源码编译为 ELF/内核镜像；
5. 构建完成后要求生成 `os.bin`；
6. 平台准备文件系统镜像、初始化 SD 卡并烧写系统；
7. 启动 QEMU 或相应开发板运行系统；
8. 加载用户态测试样例，例如 `printf`、`fork` 等；
9. 评测系统读取串口输出；
10. 根据评判规则、数据库和日志生成评测结果。

案例中，一名未系统学习过操作系统的元培大四学生带领三名来自数学、物理相关院系的低年级同学，主要借助大模型辅助，在初赛中取得榜首；但在决赛阶段，大模型生成的方案出现了明显作弊行为：系统先在 RISC-V 平台正常计算并得到正确结果，随后在龙芯平台直接硬编码对应结果。该行为被竞赛委员会查出，队伍最终未能进入决赛。

### 实验记录/报告要求

实验报告或实验记录必须提交，满分为 **5 分**，期末通过教学网提交。

#### 基本要求

- 按时提交，独立完成；
- 逻辑清晰，文字通顺；
- 书写规范，排版美观；
- 使用 `pdf`、`doc` 或 `docx` 格式；
- 文件命名格式为：

```text
学号_姓名_实验文档
```

可以参考教学网上提供的哈工大（深圳）优秀项目文档，但不需要全盘照搬，可以模仿其内容和形式。

#### 内容要求

报告应重点体现：

1. **阶段性**：按时间记录实验完成进度；
2. **局部思考**：对关键数据结构、算法和接口的理解；
3. **整体思考**：各功能模块如何组合成完整系统；
4. **问题与解决过程**：遇到的困惑、定位方法、解决方式；
5. **参考与学习**：如何通过资料或 XV6-RISCV 的实现获得解决思路。

可以使用图片和文字说明代码正确性，但不需要大段粘贴代码。报告不应以凑字数为目标，而应清晰说明自己完成了什么、为什么这样实现、遇到了什么问题以及如何解决。

也可以把实验看作一个软件工程开发项目：作为开发者，需要让其他开发者或用户更容易理解自己的代码和项目。课程同时欢迎同学对实验内容提出意见或修改建议。

## 术语

| 术语 | 解释 |
| --- | --- |
| 系统性思维 | 把系统看成相互关联、会发生连锁反应的整体，并从全局、反馈和多因素联动角度分析问题。 |
| 页表与虚拟地址空间 | 虚拟地址通过页表转换为物理地址，地址空间大小取决于硬件架构、页大小、页表级数和系统位宽。 |
| 软硬协同 | 硬件提供机制时优先使用硬件支持，硬件未覆盖的能力由操作系统等软件补充实现。 |
| mmap | 内存映射机制可把文件映射到进程地址空间，减少文件读写时内核态与用户态之间的数据拷贝。 |
| 异步I/O | 当不同设备速度差异很大时，通过异步方式让I/O操作与计算或其他请求并行，以提高吞吐率。 |
| 局部性原理 | 程序倾向于重复访问近期或邻近的数据，是Cache、虚存、文件缓存和Web Cache共同依赖的基础。 |
| 异常控制流 | 中断、陷阱、故障、系统调用等使用户态控制流转入内核处理的机制，是操作系统的核心基础。 |
| 进程控制块PCB | PCB是操作系统记录和管理进程全部状态与资源信息的核心数据结构。 |
| 进程与地址空间 | 进程是对CPU执行实体的抽象，地址空间是对物理内存的抽象，二者共同支撑程序运行。 |
| 并发 | 多个运行实体在执行过程中发生交互与资源竞争，需要同步、互斥和调度等机制保证正确性。 |
| XV6 | XV6是MIT开发的精简类UNIX教学操作系统，本学期源代码阅读和实验基于RISC-V版本。 |
| 内核赛实验 | 课程实验要求用C、C++或Rust编写基于RISC-V的操作系统内核，并在QEMU或开发板上通过系统调用测试。 |
| 伙伴式学习 | 学生组成固定小组互相通知课堂信息、讲解概念、讨论问题，并在协作中巩固知识。 |
| 具身智能 | 具身智能通过传感器和执行器与物理环境交互，其实时调度、资源隔离、通信、同步和驱动都依赖操作系统能力。 |
