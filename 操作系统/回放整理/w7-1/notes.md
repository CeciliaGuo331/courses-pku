### 主题引入：内存管理与进程的关系

本部分开启操作系统的新主题——**内存管理**。内存管理与前面学习的进程管理紧密关联：

- 推荐教材《Three Easy Pieces》的第一部分为"虚拟化"：进程是对 CPU 的抽象（实现物理 CPU 到虚拟 CPU 的映射），内存与虚存也归入这一部分`▶ 05:20`。
- 进程创建的标准步骤包括分配 PID、分配 PCB、**分配地址空间**；进程运行必须依赖内存，因此内存管理与进程模型密不可分`▶ 05:20`。
- 内存管理的核心任务：进程运行时需要为其分配一块内存`▶ 05:20`。

现代内存已演化为**虚存机制**：进程创建时分配虚拟内存，运行过程中按需将磁盘内容加载到物理内存并建立映射。本课程将回溯内存管理的演化历程——先讲传统的、纯粹的内存管理解决了什么问题，再讲后续虚存管理的问题，从问题出发梳理整个演化过程`▶ 05:20`。

操作系统的本质是管理计算机资源，内存是核心资源之一。操作系统对内存做了抽象，通过抽象出**地址空间**的概念来管理内存；类似地，操作系统通过管理进程（对 CPU 的抽象）来间接管理 CPU 资源`▶ 09:55`。

## 2. 地址绑定时机与地址重定位

> 课件 第 5–11 页 · 讲解从 `17:37` 开始

### 程序执行前的准备过程

一个程序从源代码到真正在内存中运行，需要经历以下阶段：

1. **编译（Compile）**：多个源程序（.c 文件）分别由编译器编译，生成各自的目标文件（.o 文件）。
2. **链接（Linking）**：链接器将多个目标文件以及系统库、其他目标文件合并，形成磁盘中的装载模块（可执行文件）。
3. **装载（Load）**：装载器（loader）把磁盘上的装载模块装入内存。
4. **运行（Run）**：CPU 执行内存中的指令。

这条主线引出一个核心问题：**在哪个阶段把指令和数据中的地址绑定（binding）到实际的内存地址？**`▶ 17:37`

### 地址绑定的四个时机

| 绑定时机 | 能否绑定 | 说明 |
|---|---|---|
| 编译时（Compile time） | 理论可行，实际不用 | 若只有单个源文件，且预先知道程序加载到内存的起始位置（如 1000），编译器可直接把相对地址（如偏移 200）转换成物理地址（1200）。但实际通常有多个 .c 文件，链接前各目标文件的先后顺序未知，无法提前确定地址`▶ 18:50` |
| 链接时（Linking time） | 理论可行，实际不用 | 多个 .o 合并成可执行文件时，各模块的顺序和长度都已确定，理论上可以转换地址；但此时生成的仍是以 0 为首地址的相对地址形式，并未绑定真正的物理地址`▶ 20:40` |
| 装载时（Load time） | 早期采用 | 装载时程序在内存中的位置已经确定，装载器可逐条修改指令中的地址。这种方式存在明显缺陷`▶ 20:40` |
| 运行时（Run time） | 现代系统采用 | 程序加载后仍可在内存中移动，执行指令时才把逻辑地址转换为物理地址，方式最灵活`▶ 21:35` |

> **老师强调**：地址绑定可以在上述任意阶段完成，但各阶段都有约束，有些阶段实际没有操作的必要；讨论地址时必须先明确说的是逻辑地址空间还是物理地址空间`▶ 21:35 · 22:31`。

### 逻辑地址与物理地址

- **逻辑地址（相对地址、虚拟地址）**
  - 用户程序经编译、汇编后形成目标代码，目标代码通常采用相对地址形式。
  - 其首地址为 0，其余指令中的地址都相对于首地址编址。
  - 链接阶段会在这个相对地址空间内部调整地址：例如把另一个源文件中的函数 f 放在前 100 个单元处，原本地址为 20 的变量 i 就会被调整为 120，但这仍然是相对地址`▶ 24:36`。
  - **逻辑地址不能直接用来在内存中读取信息**`▶ 23:16`。

- **物理地址（绝对地址、实地址）**
  - 内存中存储单元的真实地址，可直接寻址。

- **地址重定位（地址映射、地址转换）**
  - 定义：将用户程序中的逻辑地址转换为运行时可由机器直接寻址的物理地址的过程。
  - 目的：保证 CPU 执行指令时能正确访问内存单元`▶ 23:16`。

### 静态地址重定位

**做法**：当用户程序被加载到内存时，**一次性**完成所有逻辑地址到物理地址的转换，一般由软件（装载器）完成`▶ 26:50`。

课件示例（注意磁盘上的装载模块内部地址仍为相对地址）：

| 阶段 | 变量 i / 函数 f 的地址表示 |
|---|---|
| 源程序 | `store 20`，`branch f` |
| 目标程序 | 起始为 0，如变量地址 20 |
| 磁盘装载模块（链接后） | 函数 f 在偏移 0，变量 i 在偏移 120：`store 120`、`branch 0` |
| 装入内存（起始地址 1000） | 地址被整体改写：`store 1120`、`branch 1000` |

即程序加载到内存起始位置 1000 后，原相对地址 120 被一次性改写为物理地址 1120`▶ 26:50`。

**缺点**：
- 程序一旦装入内存，位置就固定了，无法移动；若要变更位置，只能整体搬迁并重写所有地址`▶ 21:35`。
- 要求作业在运行前将整个程序全部装入内存；而现代程序体积庞大，且并不需要所有代码同时驻留内存，因此静态重定位不适应现代需求`▶ 27:32`。

### 动态地址重定位

**做法**：加载程序时**不修改**程序中的地址，地址变换推迟到进程执行过程中——即逐条指令执行时才完成逻辑地址到物理地址的映射`▶ 27:32`。

在课件示例中，装入内存后指令里保存的仍是 `store 120`、`branch 0` 这样的相对地址，真正的物理地址在执行时通过"地址映射"得到。

- 优点：程序在内存中可以移动，便于实现虚拟存储等机制。
- 因为每条指令执行时都要做一次地址转换，所以**转换性能必须得到保障**，靠软件逐条修改效率太低，必须有硬件支持`▶ 27:32 · 28:56`。

### 动态重定位的硬件实现——MMU

动态地址转换由 **MMU（内存管理单元，Memory Management Unit）** 完成：

- CPU 执行指令时拿到的是**逻辑地址**。
- MMU 负责把逻辑地址转换为**物理地址**，再送到物理内存寻址。
- 最早、最简单的 MMU 形式是一个**重定位寄存器（基址寄存器）**：其中存放进程在物理内存中的起始地址。
- 转换公式：

```text
物理地址 = 重定位寄存器内容（基址） + 逻辑地址
```

课件示例：

```text
逻辑地址 456  +  重定位寄存器 12000  =  物理地址 12456
```

后续虚拟存储体系中地址转换仍然由 MMU 完成，只是其内部实现机制更加复杂`▶ 28:56`。

### 静态与动态重定位对比

| 对比项 | 静态地址重定位 | 动态地址重定位 |
|---|---|---|
| 转换时机 | 装入内存时一次性完成 | 每条指令执行时完成 |
| 实现方式 | 软件（装载器）修改地址 | 硬件 MMU 进行映射 |
| 装入后地址形式 | 已是物理地址 | 仍保留逻辑地址 |
| 程序能否在内存中移动 | 不能，移动需重写全部地址 | 可以，修改基址寄存器即可 |
| 是否要求全部装入内存 | 要求 | 不要求，便于虚拟存储 |
| 运行时开销 | 装入时一次开销 | 每条指令都需转换，依赖硬件性能 |

## 3. 地址保护与内存管理演化

> 课件 第 12–18 页 · 讲解从 `30:53` 开始

### 地址保护与内存管理演化

#### 一、要解决的两个核心问题

**问题1：进程地址空间的隔离与保护**

系统中同时存在进程 A、B、Z 等多个进程，每个进程都有自己独立的地址空间，它们共享同一块物理内存。必须确保进程只能访问属于自己的内存区域。

**问题2：内存分配方式的转变**

随着进程体积增大，为一个完整进程分配整块连续物理内存越来越困难，由此推动了三个维度的演化：

| 传统方式 | 演化方向 | 含义 |
|---|---|---|
| 连续性 | 离散性 | 将进程拆分后分散存入内存的空闲块 |
| 驻留性 | 交换性 | 进程未运行完可先调出内存，之后再重新调入运行 |
| 一次性 | 多次性 | 进程不必一次性全部装入，可在运行过程中按需多次调入 |

这种离散存放以**页（Page）/页框（Page Frame）**为单位：地址空间的一页可以放入物理内存中任意一个空闲页框，即"全配置指一页对应一页"`▶ 37:11`。

---

#### 二、地址保护（地址越界检查）

地址保护的目标：
- 确保每个进程拥有独立的地址空间；
- 确定进程可访问的合法地址范围，使进程只访问其合法地址，防止地址越界。

**硬件实现机制：基地址寄存器 + 界限寄存器**

CPU 每次访问内存时，对进程给出的地址进行范围校验：

```
基地址 ≤ 地址 < 基地址 + 界限
```

- 若地址落在该区间内（"是"）：校验通过，再完成地址转换，得到合法物理地址；
- 若地址不满足条件（"否"）：判定为地址越界，陷入操作系统进行处理。

> **老师强调**：单靠记录起始位置的基地址寄存器无法完成保护，必须搭配界限寄存器做范围校验；逻辑地址必须同时满足"≥ 基地址"和"< 基地址 + 界限"两个条件，校验通过后才能进行地址转换`▶ 32:44`。

基地址寄存器和界限寄存器由操作系统通过**特殊的特权指令**加载，普通用户程序不能修改，从而保证保护机制本身不被破坏。

---

#### 三、已经成为常识的基础概念

1. **多道程序设计模型**：允许多个程序同时进入内存，这是内存越界等问题产生的根源。
2. **程序装载到内存才可以运行**：程序以可执行文件的形式保存在磁盘上，运行前需装载入内存。
3. **独立地址空间**：每个进程有自己独立的地址空间。
4. **隔离性**：一个进程执行时不能访问另一个进程的地址空间，也不能访问操作系统的内存空间。
5. **权限约束**：进程不能执行不适当（越权）的操作。
6. **局部性原理**。
7. **存储体系**（由快到慢、由小到大）：
   - 寄存器
   - 高速缓存 L1 → L2 → L3
   - 内存
   - 本地磁盘
   - 远程磁盘

> **老师强调（课程核心常识）**：多道程序设计模型是内存越界等问题的产生根源；程序代码初始存放在磁盘上，创建进程时为每个进程分配独立的物理地址空间，进程既不能访问其他进程的地址空间，也不能访问操作系统的内存空间；进程必须按权限执行操作，不可越权`▶ 37:40`。

---

#### 四、多道程序设计与内存管理

因为同时有多个用户程序驻留在内存中，内存管理需要做更多工作：

- **支持地址重定位**：程序中的地址不一定是最终的物理地址。在程序运行前无法计算出物理地址，因为不能确定程序会被加载到内存的什么位置，所以必须支持地址转换。
- **支持地址保护**：进程之间不能互相访问对方的内存。

> **老师强调**：多道程序设计导致内存管理复杂度提升的根本原因在于——程序内的地址并非最终物理地址，需要进行地址转换，并实施相应的内存保护`▶ 38:54`。

---

#### 五、内存管理的演化过程

| 阶段 | 内存使用方式 |
|---|---|
| ① 早期物理内存使用 | 同一时刻内存中只运行一个进程，进程结束退出后再换入新进程 |
| ② 多道程序 / 分时共享 | 内存中同时驻留操作系统和多个进程；早期进程以整体为单位连续装载，后来发展为拆分成多份、不连续装载 |
| ③ 虚拟化内存 | 每个进程拥有独立的虚拟地址空间，OS 与各进程的空间交错映射到物理内存，存在未分配区域 |

早期多道程序设计下，要求将整个进程一次性装入物理内存，占用一段连续空间；由于不同程序长短不一，系统按运行时机把它们分配到内存中的不同区域`▶ 30:53`。

现代虚存阶段，每个进程的地址空间远大于物理内存。例如 X86-64 架构下 Linux 的进程地址空间可达 2⁴⁸，远超 16G/32G 的物理内存容量，因此无法整体装入物理内存`▶ 39:14`。

**巨大虚拟地址空间的实现思路**：采用离散存放，将地址空间按固定大小的页/帧划分；不要求地址空间的所有页都对应物理内存，仅在需要时才把对应页调入内存，灵活性很高`▶ 41:11`。

> **老师强调（ICS 总结的现代虚拟地址空间三大核心特点）**：
> 1. **巨大**：每个进程的地址空间远大于物理内存；
> 2. **统一**：所有进程的地址空间遵循统一的内存布局；
> 3. **私有**：每个进程独立拥有自己的地址空间，天然解决了进程间地址越界问题，只剩下越权访问问题需要管控。
>
> 操作系统在 PCB 中通过**稀疏结构**的描述来管理进程的地址空间，兼具简洁性与管理便利性`▶ 41:45`。

#### 六、内存管理的基本功能

围绕虚拟化内存，内存管理需要完成：

1. **给进程分配内存——地址空间**
2. **往内存加载内容——映射进程地址空间到物理内存**
3. **存储保护——地址越界检查、权限控制**
4. **共享内存**
5. **最小化存储访问时间**

虚拟化内存的三个目标：
- **透明性**：地址转换与管理对用户程序透明；
- **效率**：尽量降低存储访问的时间开销；
- **保护**：保证进程间、进程与 OS 间的隔离与权限安全。

## 4. 地址空间与现代虚拟内存映射

### 地址空间的管理

现代虚拟内存的核心工作流程为：

1. 创建进程时，为其分配对应的虚拟地址空间；
2. 建立虚拟地址空间与磁盘上可执行文件的映射关系——可执行文件的代码段、数据段等 section 分别映射到虚拟地址空间的对应位置；
3. 按需将对应的代码、数据从磁盘加载进物理内存（以 Linux 为例）`▶ 43:58`。

地址空间管理需要回答三类问题：

- **地址空间里有什么内容？** 这些内容从哪里加载到地址空间？具体位于什么位置？
- **空闲空间如何组织、分配（placement，放置）、回收、分割与合并？**
- 哪些页面在内存中？涉及常驻集、活跃页面、工作集等概念。

> **老师强调**：要清楚什么是活跃页面、什么是工作集、什么是常驻集。

程序使用的地址应当与物理内存地址无关，这正是虚拟内存提供的抽象。

### 进程地址空间的内容

进程地址空间分为**用户地址空间**和**内核地址空间**两大部分，每个进程都有寄存器状态（如 SP、PC）以及多个存储区域。

典型 Linux 进程地址空间从低地址到高地址的布局大致如下：

| 地址（示例） | 区域 | 来源 / 说明 |
|---|---|---|
| `0` | （低地址，保留） | 不映射，便于捕获空指针等错误 |
| `0x08048000` | 只读的代码和数据 | 来自可执行文件的 text 等段 |
| 向上 | 读/写数据 | 来自可执行文件的 data 段等 |
| 向上 | 运行时堆 | 运行时由 `malloc` 创建，向高地址增长 |
| `0x40000000` | 共享库的存储器映射区域 | 运行时创建，映射共享库 |
| 高地址向下 | 用户栈 | 运行时创建，向低地址增长 |
| `0xc0000000` | 内核虚拟存储器 | 内核地址空间起始（32 位示意） |
| `0xffffffff` | 内核地址空间顶部 | 高地址端 |

其他内容还包括**共享库、内存映射文件**等。

> **老师强调**：必须掌握地址空间各组成部分的**来源与布局**：代码段、数据段来自可执行文件；堆、栈、共享库的来源以及它们在地址空间中的排列顺序要明确`▶ 48:26`。

### Linux 中地址空间的描述：`vm_area_struct`

在 Linux 中，进程地址空间中的一个个连续区域用 `vm_area_struct` 节点描述。每个节点包含四个核心字段：

- **start**：区域起始地址；
- **end**：区域结束地址；
- **flag**：标志；
- **protection**：访问权限。

> **老师强调**：`vm_area_struct` 的四个核心字段 start、end、flag、protection 必须掌握`▶ 45:49`。

将编译生成的二进制代码段映射到虚拟地址空间时，需要把该段的起止地址写入对应的 area 结构体，完成虚拟地址空间中的“登记”；之后再进一步建立到物理内存的映射`▶ 45:49`。

### 保护与权限

虚拟存储通过两方面提供保护：

- **地址隔离**：进程只能访问自己地址空间中已登记的区域，越界访问会被拦截；
- **访问权限**：通过 area 的 `protection` 字段配置，例如代码段可设为只读、可执行，而栈区域通过匿名文件映射，通常设置为**不可执行**`▶ 46:49`。

共享内存等机制在后续内容中专门讲解`▶ 46:49`。

### 虚拟内存的特性与性能

内存管理的另一个核心目标是**最小化内存访问时间**。常用手段是启用 Cache：命中时无需访问内存，从而缩短访存时间`▶ 46:49`。

引入虚拟内存后，系统具备三大特性：

- **透明性**：对用户进程无感知，进程不需要关心虚存的实现细节；
- **高效性**；
- **保护性**。

这些特性可以满足内存管理的基本要求`▶ 47:32`。

### 物理内存空闲空间的管理

除了组织虚拟地址空间，内存管理还需要组织**物理内存的空闲空间**，把虚拟地址空间中的内容装入物理内存`▶ 49:27`。

相关术语：

- 物理内存分配对应英文 **placement（放置）**；
- 回收对应 **replacement**；
- 需要实现分配、回收、**分割**、**合并**等逻辑。

传统多道程序设计中，需要为整个程序分配一块连续的物理内存：

- **分配**时，从空闲空间中划出一块，并把剩余空间**分割**开；

## 5. 空闲物理内存的数据结构

> 课件 第 22–24 页 · 讲解从 `52:07` 开始

### 物理内存管理的核心

物理内存管理的核心是管理**空闲空间**：已经分配出去的内存不需要管理，回收之后再重新纳入空闲空间的管理。因此这本质上是一个**数据结构与算法**的问题——用什么结构组织空闲内存，以及用什么算法从中分配`▶ 52:07`。

管理目标有两个衡量维度：

| 衡量指标 | 目标 | 相关概念 |
|---|---|---|
| 内存资源利用率 | 尽可能减少资源浪费 | 内碎片、外碎片 |
| 性能 | 尽可能降低分配延迟，节约 CPU 资源 | 分配/回收算法的效率 |

### 物理内存的两种划分方式

物理内存的划分分为两类，二者对应不同的管理数据结构`▶ 53:30`：

- **等长划分**：把内存划分成大小相同的单元（现代主流方式是把物理内存等长划分为页框，这是本课程的核心）`▶ 52:07`。
- **不等长划分**：每个空闲区的大小不同，需要专门的分配算法`▶ 1:05:18`。

### 空闲物理内存的数据结构

#### 1. 位图（Bitmap）

- 每个分配单元对应位图中的一位，`0` 表示空闲，`1` 表示占用（也可以相反约定）。
- 特别适合**等长划分**：每个页框对应 1 个 bit，分配时无论是否要求连续，只需找到值为 `0` 的空闲位即可分配，管理实现简单`▶ 53:30`。
- 不等长划分不适合用位图管理，因为单元大小不一，单个 bit 无法表达长度信息`▶ 55:00`。

#### 2. 空闲区表 / 已分配区表

- 表中每一项记录一个空闲区（或已分配区）的**起始地址、长度、标志**。
- 常用于**不等长划分**`▶ 55:00`。
- 实现上有两种形式：
  - 拆成两张表：空闲区表 + 已分配区表；
  - 或用一张表，通过标志位区分该项是空闲区还是已分配区`▶ 55:00`。

#### 3. 空闲块链表

把空闲区组织成链表，常见类型包括：

- **隐式空闲链表**
- **显式空闲链表**
- **分离空闲链表**

### 分配算法

在不等长划分中，由于空闲区大小各不相同，需要相应的分配算法在空闲区中挑选合适的一块，常见有：

- **首先适配（First Fit）**
- **最佳适配（Best Fit）**
- **最差适配（Worst Fit）**
- **下次适配（Next Fit）**`▶ 52:07`

> 老师说明：位图、空闲区表/链表以及几种适配算法内容相对简单，课堂上快速带过；课程的重点是现代主流的**等长页框划分**及其管理`▶ 52:07`。

无论采用哪种划分方式和数据结构，管理目标都是一致的：兼顾**内存资源利用率**与**分配性能**，尽量降低分配延迟`▶ 1:05:18`。

## 6. 内存分配、回收与分离适配算法

> 课件 第 25–30 页 · 讲解从 `1:06:37` 开始

### 内存分配算法

动态分区分配中，内存存在两类碎片：

- **内碎片**：分配给进程的空间大于进程实际需求，分区内部被浪费的空间。
- **外碎片**：分区之间存在大量太小、难以利用的空闲空间。

常见的内存分配算法有四种。它们的共同思路是：在空闲区表中寻找一个能够满足进程大小要求的空闲区，把其中一部分分配给进程，剩余部分形成一个新的空闲区`▶ 1:06:37`。

| 算法 | 查找/选择规则 | 特点 |
|---|---|---|
| **首次适配 First Fit** | 从空闲区表开头开始，找到第一个满足要求的空闲区 | 实现简单，查找较快，是目前常用的算法`▶ 1:06:37` |
| **下次适配 Next Fit** | 从上次找到的空闲区位置之后继续查找 | 避免每次都从表头开始搜索 |
| **最佳适配 Best Fit** | 扫描整个空闲区表，选择满足要求的最小空闲区 | 尽量减少一次分配后剩余空间的大小，但可能留下很多很小的外碎片 |
| **最差适配 Worst Fit** | 总是选择满足要求的最大空闲区 | 分割后剩余部分通常仍较大，可能还能继续使用`▶ 1:06:37` |

> **老师强调**：这几种算法的实际性能差异并不特别大；首次适配是目前常用的算法`▶ 1:06:37`。

### 空闲区表与已分配区表

系统通过表来记录内存分区情况，每个表项通常包含：

- **始址**：分区起始地址；
- **长度**：分区大小；
- **标志**：记录该分区是空闲，还是已分配给某个进程。

空闲区表只记录未分配分区，已分配区表记录已经分配给进程的分区。表会预先设计较多表项，尚未使用的条目称为**空项**`▶ 1:08:44`。

| 38K | 10K | P2 已分配 |

### 内存回收

当进程释放内存时，系统不能简单地把该分区标记为空闲，还需要检查它与前后空闲区是否相邻，并尽可能合并，以减少外碎片。

回收时共有四种情况：

1. **上相邻**：释放分区的前一个分区是空闲区，与上方空闲区合并；
2. **下相邻**：释放分区的后一个分区是空闲区，与下方空闲区合并；
3. **上下都相邻**：释放分区前后都是空闲区，将三个分区合并成一个大空闲区；
4. **上下都不相邻**：不与任何空闲区相邻，则新增一个空闲区表项。

> **老师强调**：释放内存时，如果存在相邻空闲区就要进行合并；如果上下都相邻，则把上方空闲区、被释放分区、下方空闲区三部分合并为一个空闲区`▶ 1:10:37`。

### 分离适配算法

**分离适配（Segregated Fit）**是内存管理和资源分配领域的经典算法，其核心思想是：**按照块大小分类组织空闲块，使分配时优先在对应大小类别中查找，从而减少搜索开销**`▶ 1:10:54`。

它与普通扫描整个空闲区表的方法相比，重点在于通过大小分类提高查找效率。课件列出了几种常见变体：

| 变体名称 | 特点 | 典型应用 |
|---|---|---|
| **Simple Segregated Storage** | 不合并、不分割，块大小固定 | 嵌入式实时系统，要求确定性延迟 |
| **Segregated Fit** | 允许分割大块，释放时可选合并 | dlmalloc（Doug Lea malloc） |
| **Buddy System（伙伴系统）** | 只允许 2 的幂次大小，合并时必须严格配对 | Linux 内核页分配、GPU 显存管理 |
| **Slab Allocator** | 按对象类型分离，而不是单纯按大小分离 | Linux 内核 `kmalloc`、对象缓存 |
| **PagedAttention** | 按 token 数划分 Block，动态分配 | vLLM KV Cache 管理 |

其中，大模型推理中的 **PagedAttention** 将 KV Cache 按 token 数量组织成 Block 并动态分配，体现了分离适配思想在现代系统中的应用`▶ 1:10:54`。

## 7. Linux 伙伴系统

> 课件 第 31–32 页 · 讲解从 `1:12:46` 开始

### 伙伴系统概述

伙伴系统（Buddy System）是一种经典的内存分配方案，Linux 底层内存管理采用的就是一种特殊的"分离适配"算法，GPU 显存分配中也有应用`▶ 1:12:46`。

**主要思想**：

- 将内存按 **2 的幂次**进行划分，组成若干空闲块链表，每种大小的块对应一条链表
- 分配时查找相应链表，找到能满足进程需求的最佳匹配块`▶ 1:12:46`

### 分配算法

1. 首先将整个可用空间看作一块大小为 $2^U$ 的完整块
2. 假设进程申请的空间大小为 $s$：
   - 若满足 $2^{U-1} < s \le 2^U$，则直接分配整个块
   - 否则，将块对半划分为两个大小相等的"伙伴"，每块大小为 $2^{U-1}$
3. 持续对半划分，直到产生大于或等于 $s$ 的最小块为止`▶ 1:12:46`

也就是说，无论申请多大空间，最终实际分配的都是 **2 的整数次幂大小**的块。

### 合并规则

- 释放一个块时，检查它的**伙伴**（即最初从同一块分裂出来的配对块）是否也空闲
- 若伙伴空闲，则两块合并成更大的块，并继续向上检查新块的伙伴是否空闲，形成**连锁合并**
- 若仅仅是地址相邻但并非伙伴关系，则**不能合并**

> **老师强调**：只有最初从同一块分裂出来的配对块才是"伙伴"，相邻的非伙伴块不能合并；这种连锁合并是伙伴系统的核心特点`▶ 1:12:46 · 1:14:31`。

### 1 MB 内存分配示例

以总容量 1 MB 的内存为例，演示分配与释放的完整过程：

| 操作 | 结果说明 |
| --- | --- |
| 初始状态 | 整块 1 M 空闲 |
| A 申请 100K | 1M 依次对半切分为 512K → 256K → 128K，分配一个 **128K** 块给 A |
| B 申请 240K | 在剩余空间中切分出 **256K** 块分配给 B |
| C 申请 64K | 从某个 128K 空闲块中再对半切分，分配一个 **64K** 块给 C，另 64K 保持空闲 |
| D 申请 256K | 从更大的空闲块中直接分配一个 **256K** 块给 D |
| 释放 B | B 的 256K 变为空闲，但其前后相邻块**都不是它的伙伴**，因此不发生合并，仅新增一个空闲块 |
| 释放 A | A 的 128K 释放后，与其伙伴（原 C 所在 128K 中剩余的那个 64K 尚在占用等情况）按伙伴关系逐级判断，可合并的部分向上合并为更大的空闲块 |
| E 申请 75K | 75K 大于 64K，故分配最小满足需求的 **128K** 块给 E |
| 释放 C | C 的 64K 释放，若其伙伴 64K 空闲，则合并成 128K，并继续尝试向上合并 |
| 释放 E | E 的 128K 释放后与伙伴合并成 256K，再继续连锁合并 |
| 释放 D | D 的 256K 释放，所有块逐级向上合并，最终恢复为完整的 **512K、512K，再合并成 1M** |

> **老师强调**：注意申请大小与实际分配大小的对应关系——100K、75K 都分配 128K，240K 分配 256K；分配取的是"不小于申请量的最小 2 的幂次块"`▶ 1:14:31`。

### 伙伴系统的特点

- **优点**：分配与释放速度快；通过伙伴合并能有效缓解外部碎片，逐步还原大块连续空间
- **缺点**：分配块必须是 2 的幂次大小，当请求大小接近下一个幂次边界时会产生明显的**内部碎片**（如申请 240K 实际分配 256K）

## 8. SLAB、SLUB 与 SLOB 分配器

> 课件 第 33–36 页 · 讲解从 `1:17:11` 开始

### SLAB 分配器

SLAB（Simple List of Addressable Blocks）分配器于上世纪 90 年代由 Jeff Bonwick 最先在 Solaris 2.4 操作系统内核中设计并实现，后被引入 Linux 内核，用于在运行时动态管理内核内存的分配与释放，追求**可靠性和高性能**`▶ 1:17:11`。

**为什么引入 SLAB：**
- 伙伴系统以页为单位进行分配，而内核中存在大量频繁分配的**小对象**（如进程的 PCB、文件系统的 i 节点等），若每次都向底层现申请内存会很慢`▶ 1:17:11 · 1:18:36`。
- SLAB 的核心思想是"**批发—零售**"：先向伙伴系统申请大块内存，再将其细分成固定大小的小块进行管理，类似用户空间的堆分配`▶ 1:17:11`。
- 只分配固定大小的内存块，块大小通常为 $2^n$ 字节（$3 \le n < 12$），即 8 B～2048 B。

### 实现方法

- 将可用内存按大小划分为不同的区域，每个区域维护一个**空闲对象列表**。
- 分配时：SLAB 在与请求大小相符的空闲对象列表中取出一个空闲区域。
- 释放时：将内存块添加回相应的空闲对象列表，而不是立即归还给伙伴系统。
- **Slab cache（高速缓存）**：对象释放后优先放入本地高速缓存，下次分配同类对象时可直接取用，避免重复初始化开销`▶ 1:18:36`。
- 可通过 `(sudo) cat /proc/slabinfo` 查看当前系统的 slab 缓存信息。
- SLAB 广泛应用于文件系统、网络协议栈等众多内核模块，能满足大多数内核模块的需求。

> **老师强调**：slab 的具体实现细节无需深究，理解"预先从大块内存中划分出小节点空间、需要时直接取用"的思想即可`▶ 1:18:36`。

### SLAB 的问题与两种改进分配器

| 分配器 | 出现时间/版本 | 设计目标与特点 | 适用场景 |
|---|---|---|---|
| **SLAB** | Solaris 2.4 首创，后引入 Linux | 为各类小对象维护队列；队列多、实现日趋复杂、存储开销增大 | 通用内核小对象分配 |
| **SLUB** | 2007 年由 Pekka Enberg 开发，合入 Linux 2.6.22 | 提高性能与可伸缩性；采用简单数据结构，为每个 CPU 设置独立队列，减少锁竞争；可针对多核、NUMA 做本地性优化 | 多核、多节点服务器 |
| **SLOB** | 最早出现于 Linux 2.2 | 尽可能简单紧凑，减少代码大小和内存开销 | 小型嵌入式、资源受限环境 |

**SLAB 的缺陷：**
- 维护的队列过多、实现复杂、存储开销增大。
- 高并发下多处理器同时从全局队列取对象会产生**锁竞争**，导致多核系统性能下降`▶ 1:19:40`。

**改进 1 —— SLUB：**
- 不再使用全局队列，而是为**每个 CPU 单独设置队列**，大幅减少锁竞争，提高并发性能`▶ 1:20:46`。
- 可针对体系结构做优化，例如面向 NUMA 架构的本地性设计：NUMA 下访问本节点附近内存远快于远端内存，因此应优先分配进程所在节点的内存`▶ 1:20:46 · 1:21:25`。

**改进 2 —— SLOB：**
- 简单的 Linux 内核内存分配器，以缩减代码量和内存开销为首要目标，适用于嵌入式等资源受限系统`▶ 1:21:40`。

> **老师强调**：SLAB/SLUB/SLOB 这部分内容建立概念即可，无需深入记忆细节`▶ 1:21:40`。

## 9. 连续区与分区式内存管理

> 课件 第 37–42 页 · 讲解从 `1:22:18` 开始

### 基本内存管理方案概述

早期的6种基础内存管理方案包括：单一连续区、固定分区、可变分区、分页、分段、段页式。

> **老师强调**：这6种早期方案有一个共同的核心前提——要求整个进程全部装入内存后才能运行，这与现代可分页、分段运行的机制不同`▶ 1:22:18`。

各方案的核心特征汇总如下：

| 方案 | 地址空间划分 | 内存空间划分 | 分配/加载单位 | 关键特点 |
|------|------------|------------|-------------|---------|
| 单一连续区 | —— | —— | 进程 | 每次只运行一个用户程序，独占内存，总是加载到同一内存地址 |
| 固定分区 | —— | 划分成若干连续区域（分区），大小固定 | 分区 | 每个分区大小可相同也可不同，每个分区装一个且只能装一个进程 |
| 可变分区 | —— | 按进程需求动态分割空闲空间 | 分区（进程） | 根据进程需求分配，剩余部分成为新的空闲区 |
| 页式 | 划分成大小相等的**页** | 按页大小划分为相等的**内存块**（物理页面、页框、页帧） | 页 | 逻辑上相邻的页，物理上不一定相邻 |
| 段式 | 按进程自身逻辑关系划分为若干**段** | 动态划分为若干长度不同的区域（可变分区） | 段 | 每一段在内存中占据连续空间，各段之间可以不连续 |
| 段页式 | 段式 | 页式 | 分配单位为页，加载单位为进程 | 结合段式与页式 |

---

### 1. 单一连续区（单一用户）

- **特点**：一段时间内内存中只有一个进程在运行，用户程序独占内存`▶ 1:23:13`。
- 程序总是被加载到同一个内存地址上。
- **优点**：管理简单。
- **缺点**：内存利用率低。

关于内存布局，操作系统可位于 RAM 中（低地址或高地址），设备驱动程序可位于 ROM 中；用户进程在内存中的放置位置并不固定，可以放在高地址、低地址或内存中间，不同布局均可行`▶ 1:23:13`。

---

### 2. 固定分区

- 预先把内存空间分割成若干区域，称为**分区**。
- 每个分区的大小可以相同，也可以不同；分区大小一旦确定就固定不变。
- 每个分区装一个且只能装一个进程。

**调度方式与缺陷**`▶ 1:23:34`：
- 早期做法：进程按自身大小匹配，排队进入对应分区。
- 明显缺陷：小进程会大量堆积在小分区的队列中，而大分区的空间可能闲置浪费。
- 优化做法：设置单个全局队列，当某分区空闲且满足进程需求时即可调度使用，但这种方式仅适用于特定场景。

---

### 3. 可变分区

- **核心思想**：根据进程的实际需要，从内存空闲空间中分割出一个大小合适的分区，分配给该进程；分配后剩余的部分成为新的空闲区`▶ 1:24:48`。
- **适用场景**：小型系统`▶ 1:24:48`。

**外部碎片的产生**（结合课件图示）：

初始时操作系统占用 8M，其后有 56M 空闲区。随着 P1（20M）、P2（14M）、P3（18M）依次分配，内存中进程与空闲区交错分布；当 P2 等进程运行结束被回收后，会在进程之间留下如 4M、6M 这样分散的小空闲区（"洞"）。

- 经过多次进程的分配与回收操作后，内存会逐渐形成多个分散的小空闲空间`▶ 1:24:48`。
- 这种进程之间大小不适宜利用的空闲空间称为**外部碎片（外碎片）**，它在动态分配回收内存的过程中必然出现，会导致内存利用率下降`▶ 1:26:02`。

---

### 碎片问题及解决方案

#### 碎片

- **定义**：很小的、不易利用的空闲区，会导致内存利用率下降。

#### 紧缩技术（memory compaction）

- **思想**：在内存中移动程序，将所有小的空闲区合并为较大的空闲区。
- **又称**：压缩技术、紧致技术、搬家技术`▶ 1:26:46`。

**紧缩时需要考虑的问题**`▶ 1:27:22`：

1. **系统开销**：移动进程需要付出代价，要评估这次移动是否值得。
2. **移动时机**：这与地址重定位方式密切相关。
   - **动态重定位**：支持进程移动。
   - **静态重定位**：进程移动后需要修改全部地址，开销更大。

> **老师强调**：即使采用动态重定位，**正在进行 I/O 的进程也不能移动**。原因是这类 I/O 通常由磁盘 DMA 控制器负责，DMA 会把磁盘数据直接写入进程预设的内存地址；一旦移动进程，数据就会被写入错误的位置`▶ 1:29:38`。

## 10. 分页内存管理

> 课件 第 43–46 页 · 讲解从 `1:33:22` 开始

### 设计思想

连续内存分配要求把进程整体装入内存，容易造成内存浪费：程序中往往包含大量运行时不会执行的代码，例如错误处理分支，但它们仍会占用连续空间。分页机制把进程拆分成离散的块装入内存，使程序可以不必连续存放，也为后续按需加载、只装入运行所需部分代码奠定基础`▶ 1:33:22`。

分页涉及两类地址空间：

- **逻辑/虚拟地址空间**：按固定大小划分为若干大小相等的区域，称为**页（page，虚拟页可称 virtual page）**。
- **物理内存空间**：按与页相同的大小划分为若干区域，称为**页框/页帧/物理页面/内存块（page frame）**`▶ 1:34:31 · 1:34:54`。

> **老师强调**：看到 **page** 应联想到逻辑/虚拟空间中的页；看到 **page frame** 应联想到物理内存中的页框，借此可以快速判断术语所属的地址空间`▶ 1:34:54`。

分页内存分配规则：

- 以**页**为单位进行内存分配；
- 按进程实际需要的页数分配页框；
- 逻辑地址空间中的页是连续编号的，但它们可以分散存放在任意空闲物理页框中；
- 逻辑上相邻的页，物理上不一定相邻`▶ 1:35:42 · 1:37:05`。

典型页面大小为 **4 KB 或 4 MB**`▶ 1:35:42`。

### 逻辑地址的划分

逻辑地址由硬件自动划分为两部分：

| 组成部分 | 含义 |
|---|---|
| **页号** | 逻辑地址所在的页编号，用于查页表 |
| **页内地址/页内偏移** | 地址在该页内部的偏移量 |

以 32 位逻辑地址、页面大小为 4 KB 为例：

- 4 KB = 2¹² B，因此低 **12 位**表示页内偏移，范围为 `0 ~ 4095`；
- 高 **20 位**表示页号，范围为 `0 ~ 2²⁰-1 = 0 ~ 1048575`。

```text
31                 12 11                  0
+---------------------+---------------------+
|        页号         |      页内偏移       |
+---------------------+---------------------+
```

这种划分由系统硬件自动完成，对用户程序透明`▶ 1:35:42 · 1:36:41`。由于页面大小通常取 2 的整数次幂，硬件只需按位截取地址，就能得到页号和页内偏移，实现简单高效`▶ 1:35:42`。

> **老师强调**：虚拟存储和分页地址转换必须有硬件介入，地址的拆分与转换不是由用户程序完成的`▶ 1:36:41`。

### 内存分配方式

进程的逻辑地址空间被划分为多个逻辑页，物理内存被划分为多个同样大小的页框。系统为进程分配内存时，可以把每个逻辑页放入任意一个空闲页框中。

因此：

- 进程逻辑地址空间中的页号连续；
- 物理内存中的页框可以不连续；
- 一个逻辑页占用一个物理页框；
- 即使进程的所有页都已装入内存，这些页在物理内存中也未必相邻`▶ 1:37:05`。

### 页表

由于逻辑页与物理页框之间不是简单的顺序对应关系，系统必须记录二者的映射关系。完成这一功能的核心数据结构是**页表**。

#### 页表项

页表由若干**页表项**组成。每个页表项记录：

```text
逻辑页号 → 物理页框号
```

CPU 得到逻辑地址中的页号后，用它查找页表，找到对应页表项，再从中获得物理页框号`▶ 1:38:19`。

#### 每个进程一个页表

每个进程拥有自己独立的页表，页表存放在内存中。进程切换时，页表也必须切换，因为不同进程的相同逻辑页号可以映射到不同的物理页框。

页表起始地址的保存与切换：

- 当前进程页表的起始地址由专门的硬件寄存器指向；
- 在 x86 架构中，使用 **CR3 寄存器**保存当前进程页表的起始地址；
- 进程自身的页表基地址保存在该进程的 **PCB（进程控制块）**中；
- 上下文切换时，把新进程的页表基地址装入 CR3，即可完成地址映射空间的切换`▶ 1:39:04`。

### 地址转换过程

分页机制下，从逻辑地址得到物理地址必须依靠硬件支持，主要由 **MMU（内存管理单元）**完成`▶ 1:40:28`。

基本过程如下：

1. CPU 生成逻辑地址；
2. MMU 自动把逻辑地址拆成**页号**和**页内偏移**；
3. 根据当前页表起始地址和页号查找对应页表项；
4. 从页表项中获得**物理页框号**；
5. 把物理页框号与原逻辑地址中的**页内偏移**拼接；
6. 得到最终物理地址并访问内存`▶ 1:40:28`。

可以表示为：

```text
逻辑地址 = 页号 + 页内偏移

页号 ──查页表──> 页框号

物理地址 = 页框号 + 页内偏移
```

由于逻辑页和物理页框大小相同，页内偏移在地址转换过程中保持不变，只需把逻辑页号替换成物理页框号。

当前讨论建立在以下前提上：

- 所有逻辑页都已经装入物理内存；
- 页表中的映射关系已经建立；
- 地址转换过程中暂不考虑缺页等异常`▶ 1:40:28`。

### 内碎片

分页分配以固定大小的页为单位。当进程实际需要的内存大小不是页面大小的整数倍时，最后一个页框中会有一部分空间未被使用，从而形成**内碎片**`▶ 1:41:27`。

例如页面大小为 4 KB，而进程最后一个页只需要少量字节，系统仍需分配完整的 4 KB 页框，剩余部分就属于页内浪费。

> **老师强调**：分页机制会产生内碎片；不同的内存管理方案可能产生不同类型的碎片，需要注意区分`▶ 1:41:27`。

## 11. 分段与段页式内存管理

> 课件 第 47–52 页 · 讲解从 `1:41:41` 开始

### 段式内存管理

#### 设计思想

段式内存管理的核心是**按照程序自身的逻辑关系**来划分地址空间，而不是像页式那样按固定大小等长划分。老师用了一个类比：分页像切西瓜，等分切块；分段则像按蛋糕上的花纹来切，每一块大小由内容决定`▶ 1:41:41`。

具体包括三方面：

- **用户程序地址空间**：按程序的逻辑关系划分为若干个程序段，每个程序段都有一个段名。例如主程序段 M、子程序段 X、子程序段 Y、数组 A、工作区段 B 等。
- **内存空间**：被动态地划分为若干个长度不相同的区域，称为**物理段**。每个物理段由**起始地址（段地址）和长度**确定。
- **内存分配规则**：以段为单位进行分配。每一个段在内存中占据**连续**空间，但各段之间**可以不相邻**。

段式管理中的物理内存管理方式与可变分区相同，因为段长不等，需要适配不同大小的内存区域。

> **老师强调**：段间在物理内存中不连续，需要为每个段记录起始地址和长度，管理复杂度比页式更高，还需要额外硬件支持，因此实际中使用较少`▶ 1:42:29`。

#### 逻辑地址结构

段式系统中的逻辑地址由两部分组成：

| 段号 | 段内地址 |
|------|----------|

- **段号**：标识访问的是哪一个逻辑段。
- **段内地址**：该段内部的偏移量。

#### 分段的逻辑视图

一个进程的地址空间可以由多个逻辑段组成，例如：

- 主程序段 M：段内从地址 `0` 到 `K`
- 子程序段 X：段内从地址 `0` 到 `P`，其中有入口 `E`
- 子程序段 Y：段内从地址 `0` 到 `L`，其中有入口 `F`
- 数组段 A：段内从地址 `0` 到 `N`，其中地址 `116` 处存有数据 `12345`
- 工作区段 B：段内从地址 `0` 到 `S`

按段编程时，调用语句可以直接体现段和段内地址，例如：

```text
CALL X, E    // 调用子程序段 X 中段内地址为 E 的位置
CALL Y, F    // 调用子程序段 Y 中段内地址为 F 的位置
CALL A, 116  // 访问数组段 A 中段内地址为 116 的位置
```

这体现了段式划分符合程序逻辑结构的特点。

#### 段表与内存映射

每个进程有一个**段表**，存放在内存中。段表记录：

- 逻辑段号
- 该段在内存中的起始地址（段地址）
- 该段的长度

课件示例中，进程 1 的逻辑段与内存物理段的对应关系如下：

| 逻辑段号 | 段名 | 段地址 | 长度 |
|----------|------|--------|------|
| 0 | M | K = 3200 | P = 1500 |
| 1 | X | S = 5000 | L = 6000 |
| 2 | Y | N = 8000 | — |
| 3 | A | L = 6000 | N = 8000 |
| 4 | B | P = 1000 | S = 5000 |

表中符号对应课件图示：逻辑段 M、X、Y、A、B 分别被装入内存中的不同物理区域，各物理段之间无需相邻。

段表的起始地址和段表长度等信息需要由系统保存；通常由相应的控制寄存器指向当前进程的段表。课件中提出“段表起始地址保存在何处？”，其作用是供地址转换硬件找到当前进程的段表。

#### 地址转换过程

段式地址转换由硬件完成：

1. CPU 取出逻辑地址，将其划分为**段号**和**段内地址**。
2. 根据段号查询当前进程的段表。
3. 检查段内地址是否超过该段长度，即进行越界检查。
4. 从段表中取出该段的**起始地址**。
5. 物理地址计算公式为：

```text
物理地址 = 段起始地址 + 段内地址
```

只有当：

```text
段内地址 < 段长度
```

时，访问才合法；否则发生地址越界错误。

### 段页式内存管理

#### 产生背景

段页式管理是为了**结合页式和段式的优点，克服二者缺点**而提出的混合方案：

- 段式的优点是符合用户程序的逻辑结构，便于共享、保护和按逻辑模块组织程序。
- 页式的优点是内存分配以固定大小页面为单位，避免可变分区中的外部碎片，分配和回收较简单。
- 段页式则对用户保持分段的逻辑结构，对系统在段内再采用分页机制。

老师说明，段页式就是“先分段，再在段内等长分页”的混合管理方案`▶ 1:42:29`。

#### 设计思想

- **用户程序划分**：
  - 对用户来说，仍按段的逻辑关系划分程序。
  - 对系统来说，每一段又被进一步划分为若干个固定大小的页。
- **内存划分**：按页式存储管理方案，将内存划分为固定大小的物理块（页框）。
- **内存分配**：以**页**为单位进行分配。
- 因此，同一段内的各个页面在内存中不必连续，不同段之间也不必连续。

#### 逻辑地址结构

段页式系统中的逻辑地址在形式上仍可看作：

| 段号 | 段内地址 |
|------|----------|

但段内地址又可进一步划分为：

| 页号 | 页内地址 |
|------|----------|

所以完整的逻辑地址结构为：

| 段号 | 页号 | 页内地址 |
|------|------|----------|

其中：

- **段号**：决定访问哪个段。
- **页号**：决定访问该段中的哪一页。
- **页内地址**：决定访问该页内的具体偏移位置。

#### 数据结构及有关操作

段页式管理同时需要段表和页表。

- **段表**：
  - 每个进程有一个段表。
  - 记录每一段对应的**页表始址**和**页表长度**。
- **页表**：
  - 记录该段中**逻辑页号与内存块号**的对应关系。
  - 每一段有一个页表，因此一个程序可能有多个页表。
- **空闲区管理**：同页式管理，以内存块为单位管理。
- **分配与回收**：同页式管理，以页为单位进行分配和回收。

其映射关系可以概括为：

```text
段号 → 段表项 → 该段页表始址
页号 → 页表项 → 内存块号
页内地址 → 块内地址
```

#### 地址转换过程

段页式地址转换需要依次查段表和页表：

1. 从逻辑地址中取出**段号**。
2. 用段号查**段表**，找到该段对应的**页表始址和页表长度**。
3. 检查该段内的页号是否越界。
4. 从逻辑地址中取出**页号**。
5. 用页号查该段的**页表**，得到内存块号。
6. 从逻辑地址中取出**页内地址**。
7. 将内存块号与页内地址拼接，得到物理地址：

```text
物理地址 = 内存块号 × 块长 + 页内地址
```

由于页大小与内存块大小相同，页内地址直接作为块内地址，不需要加法换算，通常由硬件拼接完成。

#### 实际应用情况

老师提到，x86 架构最初设计中确实包含段的概念，可以通过段起始地址与 IP 寄存器共同寻址来管理内存；但操作系统为了简化实现，通常为每个进程只使用一个段，因此典型的段页式方案并没有在实际系统中真正按多段方式落地`▶ 1:44:10`。

## 12. 内存“扩充”：覆盖与交换

> 课件 第 53–60 页 · 讲解从 `1:45:14` 开始

### 内存扩充的核心目标

内存扩充要解决的核心矛盾是：**在较小的物理内存空间中运行较大的程序（大进程无法装入小内存）**。当内存不足时，历史上先后出现过以下管理方案：

- **内存紧凑**：例如可变分区方式中，通过移动内存中的进程合并碎片（前面章节已讲）。
- **覆盖技术（Overlaying）**
- **交换技术（Swapping）**
- **虚存技术**：现代操作系统最终彻底解决该问题的方案（后续课程讲解）。

> **老师强调**：除紧凑外，覆盖、交换先后出现，而现代虚存最终彻底解决了大进程在小内存中运行的问题`▶ 1:45:14`。下节课开始讲虚存`▶ 1:54:55`。

---

### 覆盖技术（Overlaying）

**解决的问题**：程序大小超过物理内存总和时，如何让程序运行。

**基本思想**：

- 程序执行过程中，程序的不同部分在内存中相互替代；
- 按照程序自身的逻辑结构，把**不会同时执行的程序段共享同一块内存区域**；
- 要求程序各模块之间有明确的调用结构；
- 由**程序员声明覆盖结构**，操作系统负责完成自动覆盖。

> 老师用 Union（共用体）数据结构类比：不会同时使用的成员共享同一块存储空间，覆盖技术也是让不会同时执行的模块共享内存`▶ 1:46:18`。

该技术主要用在**早期操作系统**。

#### 覆盖示例（程序 X）

程序 X 的调用结构（总大小 54K）：

- A（8K）为主控模块，调用 B 和 C；
- B（8K）调用 D（12K）；
- C（10K）调用 E（4K）和 F（10K）。

按调用关系划分内存：

| 区域 | 大小 | 存放模块 | 说明 |
|---|---|---|---|
| 常驻区 | 8K | A | 整个运行期间一直留在内存 |
| 覆盖区 0 | 10K | B、C | B 与 C 不会同时执行，互相覆盖 |
| 覆盖区 1 | 12K | D、E、F | 三者不会同时执行，取最大模块 12K（F 为 10K、D 为 12K、E 为 4K） |

- 程序全部模块合计 **54K**；
- 采用覆盖后实际内存占用仅为 8 + 10 + 12 = **30K** 即可运行`▶ 1:46:18`。

#### 覆盖技术的不足

- **对用户不透明，增加用户负担**：需程序员手动划分功能模块、确定模块间的覆盖关系（如编写覆盖脚本），增加了编程复杂度；
- **增加执行时间**：运行过程中需要从外存反复装入覆盖模块；
- 本质是**以时间换空间**。

> **老师强调**：由于要求程序员手动编写覆盖脚本、开发成本高，覆盖技术对用户不透明，最终只是短暂使用`▶ 1:46:18`。

---

### 交换技术（Swapping）

交换技术最早用于**小型分时系统**，也称 **roll in / roll out（滚入/滚出）**。

> 老师补充背景：分时系统支持多用户同时在线，但内存容量有限。时间片一到就切换进程，把当前进程整体换出到磁盘，再把即将运行的进程换入内存独占运行；也可在内存紧张时把暂时不运行的进程换出，需要时再换入，实现进程在内存与磁盘之间的动态调度`▶ 1:48:12`。

**设计思想**：内存空间紧张时，系统把内存中某些进程**暂时移到外存**，再把外存中某些进程**换进内存**，占据前者让出的区域，即进程在内存与外存之间的动态调度。负责该工作的模块称为 **swapper**。

#### 实现交换需要解决的问题

课件围绕五个问题展开讨论：

**1. 进程的哪一部分需要换出？保存在磁盘什么位置？**

- 进程的**代码段、数据段、动态链接库**等内容原本就存放在磁盘的可执行文件中，无需重复保存；
- 只有**运行时创建或被修改的内容**需要写出，主要是**栈和堆**（以及运行时动态修改的数据）。

> 老师明确：换出的核心是堆和栈，以及运行时动态修改的数据，因为代码、原始数据、动态库在磁盘上本来就有`▶ 1:49:38`。

被换出内容存放在专门的**交换区（swap space）**：

- 交换区是系统指定的一块**特殊磁盘区域**，通常包含**连续的磁道**，操作系统可使用底层磁盘读写进行高效访问；
- 管理方式有两种：
  - 操作系统直接按磁道划分连续空间管理；
  - 通过文件系统申请一个**交换文件**存放（例如 Windows 的页文件 page file）`▶ 1:50:54`。

**2. 交换时机？**

- 一种想法是"只要进程不用就换出（很少再用）"，但操作系统**无法判断程序以后是否还会被使用**，因此不可行；
- 实际做法：在**内存空间不够、或有不够的危险时**才换出；
- 交换通常**与调度器结合使用**。

> 老师把内存动态预留类比为商家"双十一备货"：备货过多会积压货款（预留/换出太浪费），备货过少会缺货、影响体验（内存不足），需要权衡`▶ 1:51:49`。

**3. 如何选择被换出的进程？**

- 需要综合考虑进程的各种属性，通过**置换（选择）算法**决定；
- **不应换出处于等待 I/O 状态的进程**。

> 老师解释不能换出 I/O 等待进程的原因：进程换出后再换回内存时，不一定能放回原来的位置，可能导致正在进行的 I/O 寻址出错`▶ 1:53:03`。

**4. 换出后再换入是否回到原处？**

- 换出后又换入的进程**不一定回到原来的位置**；
- 这依靠**动态重定位**实现；早期 swap 机制要求换回原位置，现代操作系统借助动态重定位，换入时可放在任意空闲区域`▶ 1:53:03`。

**5. 如何处理进程空间增长？**

进程运行中，**数据段和栈段（以及堆）**都可能增长，需要为其预留空间。

#### 进程空间增长的布局演化

- **早期布局**：堆和栈相邻布置，预留空间有限，堆增长容易挤压栈，产生冲突；
- **现代相向增长布局**：
  - **栈**从高地址向低地址增长；
  - **堆**从低地址向高地址增长；
  - 两者相向而行，中间是可共享利用的空闲空间，缓解了相互挤压的问题。

> **老师强调**：当前的内存布局正是为了适配进程空间增长的需求而设计的，栈向下、堆向上的相向增长解决了空间挤压问题`▶ 1:53:58`。

### 小结对比

| 方面 | 覆盖技术 | 交换技术 |
|---|---|---|
| 处理对象 | 同一程序内不会同时执行的程序段 | 整个（或部分）进程 |
| 触发方式 | 程序员声明覆盖结构，OS 自动覆盖 | OS 在内存紧张时动态调度（结合调度器） |
| 透明性 | 对用户不透明，编程负担重 | 由系统完成，对用户透明 |
| 存放位置 | 覆盖模块仍在程序所在外存 | 专用交换区（连续磁道）或交换文件 |
| 代价 | 时间换空间，增加装入开销 | 换入换出的磁盘 I/O 开销 |
| 应用时期 | 早期操作系统，短暂使用 | 早期小型分时系统，思想延续到虚存 |

| 下次适配 | 从上次查找结束的位置继续寻找可满足请求的空闲区。 |

| 交换技术 | 在内存紧张时把进程暂时移到磁盘交换区，需要运行时再换入内存的技术。 |
