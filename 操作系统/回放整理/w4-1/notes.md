## 1. 进程虚拟地址空间与 VMA 组织

> 课件 第 26–35 页 · 讲解从 `05:10` 开始

### 进程地址空间的基本概念

操作系统给每个进程都分配了一个独立的地址空间，**地址空间是对内存的抽象**。当前系统普遍采用虚拟存储方案：进程中使用的是虚拟地址，由操作系统负责完成虚拟地址到物理内存的映射，进程无需关心二者的对应关系`▶ 05:39 · 07:24`。

每个进程都有 PCB（在 Linux 中是 `task_struct`）作为核心数据结构，其中需要描述该进程的虚拟地址空间。x86、RISC-V 等架构的虚拟地址空间非常庞大（如 $2^{48}$、$2^{39}$ 大小），但操作系统只需统一管理虚拟地址空间布局`▶ 05:39 · 13:08`。

虚拟地址空间设计的核心优势：

- **每个进程的虚拟地址空间布局完全一致**，操作系统可以统一管理`▶ 05:39`。
- **不同进程的相同虚拟地址可以映射到物理内存的不同位置**，因此进程之间互不干扰`▶ 07:24`。
- 这种"映射转换"是系统的核心机制之一，类似 C 程序在编译时会根据指令集规范、优化等级（O1/O2/O3）生成不同汇编代码，地址转换对进程是透明的`▶ 07:24`。

### 一个直观实验：相同地址、不同的值

课件程序：

```c
int myval;
int main(int argc, char *argv[])
{
    myval = atoi(argv[1]);
    while (1)
        printf("myval is %d, loc 0x%lx\n",
               myval, (long) &myval);
}
```

同时运行两个程序：`Myval 5` 和 `Myval 6`，会观察到：

- 两个进程打印出的 `myval` **值不同**（一个是 5，一个是 6）；
- 但打印出的变量**地址相同**。

原因正是每个进程拥有独立的虚拟地址空间：相同的虚拟地址在各自页表映射下指向不同的物理内存页。

> **注意（ASLR）**：在现代 Linux 上重复运行同一程序，地址可能并不一样，这是因为 **地址空间布局随机化（ASLR）**。关闭命令：
> `sudo sysctl -w kernel.randomize_va_space=0`
> 关闭后重复运行，相同变量的位置才会一致。

### 虚拟地址空间的特征与布局

虚拟地址空间的核心特征`▶ 08:34`：

1. **空间巨大**：足以容纳所有程序，也可以直接映射大文件。
2. **布局统一**：代码段从低地址向高地址放置；数据段、堆向上（高地址）增长；栈向下（低地址）增长；中间预留的巨大空间可用于内存映射、动态链接等。
3. **安全保护**：进程运行时不会超出自身地址空间范围，无需额外做地址越界检查，仅通过页表/VMA 的权限校验即可保障安全。

典型的进程地址空间（用户态部分）从低地址到高地址一般包括：

| 区域 | 说明 |
|---|---|
| 代码段（text） | 存放程序指令，通常只读、可执行 |
| 初始化数据段（data） | 存放已初始化的全局/静态变量，可读写 |
| 堆（heap） | 动态分配内存，向高地址增长 |
| 内存映射区 | 共享库、`mmap` 映射的文件、匿名映射等 |
| 栈（stack） | 函数调用栈、局部变量，向低地址增长 |

此外整个虚拟空间还划分为**用户地址空间**（从 `0x0000……` 开始）和**内核地址空间**（位于 `0xFFFF……` 高端地址）。CPU 中的 `PC` 指向代码段取指令，`SP` 指向栈顶。

### 从源代码到进程地址空间

进程是"一个具有一定独立功能的程序在一个数据集合上的一次执行过程"。地址空间的形成过程：

1. 源代码文件经过**编译链接**生成可执行文件；可执行文件内包含文件头、代码、初始化数据等，并通过**段表**描述各段。
2. 加载器根据段表把可执行文件的相应内容**加载**进进程地址空间，形成代码段、数据段等。
3. 运行过程中再建立堆、栈，并通过动态链接装入共享库。

例如课件示例中：`main` 里的局部变量 `a` 位于栈；`X(int b)` 的调用形成栈帧；全局变量进入数据段。

### 查看进程地址空间：`/proc/PID/maps`

可以通过 `cat /proc/PID/maps` 查看一个进程实际映射的内存区域及其访问权限。

课件练习程序满足"用到堆（`malloc`）、用到常量（字符串 `"hello, world!"`）、进程不自动退出（`getchar`）"三个条件，便于观察 maps：

```c
#include<stdio.h>
#include<stdlib.h>
int main() {
    printf("hello, world!");
    int *a = malloc(sizeof(int));
    getchar();
    return 0;
}
```

maps 每一行的格式为：

```
起始地址-结束地址  权限  偏移  设备  inode  映射文件/名称
```

- 权限位：`r`（读）、`w`（写）、`x`（执行）、`p`（私有）/`s`（共享）。
- 示例中可看到：
  - `00400000-... r-xp ... /root/tmp/hello`：程序自身代码段（只读可执行）；
  - `00600000-... r--p / rw-p ... /root/tmp/hello`：程序的只读数据与可读写数据段；
  - `00c0b000-... [heap]`：堆；
  - 多个 `libc-2.17.so`、`libdl-2.17.so`、`ld-2.17.so` 等：动态链接的共享库，每个库也分别有可执行段、只读段、可读写段；
  - `7ffc47264000-... [stack]`：栈；
  - `[vdso]`、`[vsyscall]`：内核提供的加速系统调用的特殊映射。

### VMA：虚拟内存区域

由于庞大的虚拟地址空间中只有少量区域真正有内容，整体呈**稀疏性**，因此内核采用基于稀疏性的数据结构来表示：每个有内容的区域被封装为一个结构体，即 **VMA（Virtual Memory Area，虚拟内存区域）**`▶ 10:00`。

`vm_area_struct` 中记录的关键信息`▶ 10:00`：

- 该区域在地址空间中的**起始、结束地址**；
- 该区域的**保护权限标志**，例如：
  - 代码段：只读 + 可执行；
  - 数据段：可读写；
  - 动态链接库的代码段：只读、可执行，数据段可读写。

VMA 按类型可分为`▶ 1:10:01`：

- **有名内存区域**：映射到某个文件，文件描述符保存在 `vm_area_struct->vm_file` 域中（如可执行文件、共享库、`mmap` 的文件）。
- **匿名映射内存区域**：没有关联文件（如堆、栈以及部分 `rw-p` 且无文件名的区域）。

### VMA 的组织

- 在 Linux 中，进程的一段地址空间用一个 `vm_area_struct` 表示，所有 VMA 存储在 `task->mm->mmap` 链表中。
- VMA 既可以串联成**链表**，也可以组织成 **AVL 树**（如 Solaris 系统采用）以加快区域查找效率`▶ 11:41`。
- Linux PCB（`task_struct`）中与虚存相关的结构是 `mm_struct`（内存管理结构体），它充当链表/树的头指针；通过这种结构，只需保存那些真正有内容的区域，即可表示 2⁴⁸、2³⁹ 大小的稀疏虚拟地址空间`▶ 13:08`。

相关操作与查找逻辑`▶ 11:41 · 13:08`：

- 使用 `mmap` 可将磁盘上的大文件直接映射到虚拟地址空间，使用时无需再手动分段 `read/write` 文件。
- 需要在地址空间分配新区域时，由操作系统查找合适的空闲区域；也可以指定某个虚拟地址段进行分配。
- 操作系统通过 AVL 树查询某个起始地址是否已被占用，从而高效完成地址区间的查找与冲突判断。

## 2. 进程表、队列与五状态模型

> 课件 第 36–38 页 · 讲解从 `14:39` 开始

### 进程表（队列）

操作系统为每一类进程建立一个或多个队列，队列中的元素是 **PCB（进程控制块）**。随着进程状态的改变，其 PCB 从一个队列进入另一个队列，以此实现进程管理。

- **实现方式**：操作系统通常在内存中分配一个大数组来存储所有 PCB；每个 PCB 带有多个指针，可分别链入就绪队列、不同的等待队列，也可通过指针关联父进程、兄弟进程等家族关系，结构灵活`▶ 14:39`。
- **就绪队列**：存放所有已具备运行条件、等待 CPU 的进程的 PCB。就绪队列也可以有多个（如按优先级划分）。
- **等待（阻塞）队列**：可有多个，分别对应不同的等待事件，例如等待 I/O、等待资源、等待信号等。课件示意中"等待 1"与"等待 2"两个队列中的 PCB 所等待的事件不同。
- **运行队列**：在单 CPU 情况下，运行态只有一个进程，因此运行队列中只有一个 PCB。

课件中的队列结构可概括为：

| 队列 | 队列中的 PCB（示意） | 说明 |
|---|---|---|
| 就绪 | PCB1、PCB2、PCB3 | 等待被调度上 CPU |
| 等待 1 | PCB4、PCB5、PCB6 | 等待某一类事件 |
| 等待 2 | PCB7、PCB8、PCB9 | 等待另一类事件 |

### 五状态进程模型的队列模型

五状态模型是与实际系统最接近的进程模型：三状态模型过于简单，而七状态模型在实际中较少使用`▶ 16:11`。该模型包含五个状态：**创建（新建）、就绪、运行、阻塞（等待）、退出（终止）**，各状态与队列的对应及转换关系如下：

1. **创建 → 就绪**：进程刚被创建，OS 为其建立 PCB 后进入就绪队列。进程状态转换的触发条件与中断、异常密切相关，例如执行 `fork()` 可触发新进程从创建态进入就绪态`▶ 16:11`。
2. **就绪 → 运行**：经进程调度（分派）选中，就绪队列队首进程的 PCB 被取出投入运行；单 CPU 下运行态只有一个进程。
3. **运行 → 退出**：进程执行完毕或被终止，PCB 被撤销、资源被回收。
4. **运行 → 就绪**：进程的时间片用完，PCB 重新回到就绪队列，等待下一次调度；被高优先级进程抢占时也会发生此转换。
5. **运行 → 阻塞**：进程在运行中需要等待某事件（如发起 I/O 请求、等待资源或信号），其 PCB 进入与该事件对应的等待队列。
6. **阻塞 → 就绪**：等待的事件发生后（如 I/O 完成中断），PCB 从相应等待队列移出，重新进入就绪队列；注意阻塞态不能直接回到运行态。

队列模型的整体流转可以表示为：

```text
新建 ──► [就绪队列] ──调度──► [运行] ──完成──► 退出
            ▲                   │
            │                   ├──时间片到──► 回到就绪队列
            │                   │
            └──事件发生── [等待队列1/2/…] ◄──等待事件──┘
```

> **老师强调**：五状态模型是与实际系统最接近、最应重点掌握的进程模型；要结合队列理解状态转换——运行态进程时间片用完回就绪队列，等待事件则进入对应的阻塞队列，事件发生后必须先回到就绪队列，而不能直接回到运行态`▶ 16:11`。

## 3. 进程控制原语与进程生命周期

> 课件 第 39–43 页 · 讲解从 `18:43` 开始

### 进程控制与原语

进程控制操作完成进程各状态之间的转换，由具有特定功能的原语完成。常见的进程控制操作包括：

- 进程创建原语
- 进程撤销原语
- 阻塞原语
- 唤醒原语
- 挂起原语
- 激活（解挂）原语
- 改变进程优先级
- ……

> **老师强调**：本章采用五状态模型，因此实际讲解的进程控制只涉及创建、撤销、阻塞、唤醒，不包含挂起、激活操作`▶ 18:43`。

**原语（primitive）** 是完成某种特定功能的一段程序，具有**不可分割性或不可中断性**，即原语的执行必须连续，执行过程中不允许被中断。原语也就是**原子操作（atomic）**。

实现原语/原子操作的核心手段是：在执行操作期间**关闭中断**，不响应任何中断请求；操作完成后再打开中断`▶ 18:43`：

```text
关中断 (disable interrupt)
执行原子操作
开中断 (enable interrupt)
```

老师补充：最初人们认为原子操作是最小的不可分割执行单位，后来才发现还存在更细粒度的原子操作`▶ 20:54`。

### 进程的创建时机与终止原因

进程拥有完整的生命周期，包括"从无到有"（创建）和"从有到无"（终止）两个阶段`▶ 21:27`。

#### 何时创建进程

- 系统初始化时（创建进程/线程）
- 操作系统提供服务时（创建提供服务的进程/线程）
- 交互用户登录系统（如登录后生成 shell 进程）
- 由现有进程派生出一个新进程（如 `fork`）
- 提交一个程序执行（例如命令行；`fork` 后通过 `exec` 替换为新程序）

#### 何时终止进程

| 类别 | 情形 |
|------|------|
| 自愿 | 正常退出 |
| 自愿 | 出错退出 |
| 非自愿 | 发生严重错误 |
| 非自愿 | 被其他进程杀死 |

可能导致进程终止的各种具体事件包括：

- 正常结束
- 给定时限到
- 缺少内存
- 存储器出界
- 保护性出错（如写只读文件）
- 算术错
- 超出时间（进程等待某事件超过最大允许时间）
- I/O 失败
- 无效指令（如试图执行数据）
- 特权指令
- 操作系统干预（如死锁发生时）
- 父进程请求中止某一子进程
- 父进程中止（子进程也随之中止）

无论由哪种渠道触发，最终结果都是进程无法继续执行`▶ 21:27`。

## 4. Unix fork/exec 与写时复制

> 课件 第 44–47 页 · 讲解从 `24:59` 开始

### UNIX 的进程控制操作

Unix/Linux 体系（包括 FreeBSD 等同类系统，区别于 Windows 体系）的进程管理围绕四个基本系统调用展开：

| 系统调用     | 作用                                      |
| -------- | --------------------------------------- |
| `fork()` | 通过复制调用进程（父进程）建立新进程（子进程），是最基本的进程建立过程     |
| `exec()` | 一系列系统调用的统称，用一段新的代码覆盖原来的内存空间，实现进程执行代码的转换 |
| `wait()` | 提供初级的进程同步措施，使一个进程等待，直到另一个进程结束为止         |
| `exit()` | 终止一个进程的运行                               |

#### fork 与 exec 的配合

在 Unix 体系下，进程创建由 `fork()` 和 `exec()` 配合完成：

1. `fork()` 克隆父进程生成子进程，除 PID 外，子进程的资源几乎与父进程完全一致；
2. 紧接着调用 `exec()`，将子进程从父进程继承来的代码、数据全部替换为目标程序的内容。`▶ 24:59`

这一设计遵循 Unix **"small is beautiful（小即是美）"** 的理念：把大操作拆分为多个短小的独立函数，可以灵活组合、好记易用。`▶ 24:59`

> **老师强调**：应阅读 OSTEP 第五章 Process API，弄清 shell、`fork()`、`exec()`、`wait()` 之间的关联，体会这样设计的好处。一个典型的 shell 执行命令的流程正是：shell 先 `fork()` 出子进程，子进程用 `exec()` 加载并运行目标程序，shell 自身则用 `wait()` 等待子进程结束。

### 传统 UNIX 的 fork() 实现

传统实现中，`fork()` 需要完成以下工作：

1. 为子进程分配一个空闲的进程描述符（proc 结构）；
2. 分配给子进程唯一标识 PID；
3. 以一次一页的方式复制父进程的地址空间；
4. 从父进程处继承共享资源，如打开的文件和当前工作目录等；
5. 将子进程状态设为就绪，插入就绪队列；
6. 对子进程返回标识符 `0`，向父进程返回子进程的 PID。

关于进程描述符在不同系统中的名称：Unix 中对应 PCB 块结构，Linux 中名为 `task_struct`，xv6 中对应 `proc` 结构。`▶ 27:39`

这种"把父进程所有内存页全部拷贝一份"的做法十分耗时，而且会占用大量内存。`▶ 27:39`

### fork() 的问题与优化动机

绝大多数场景下，`fork()` 创建子进程后会**立即调用 `exec()`** 替换进程映像。此时刚刚费力复制过来的父进程地址空间马上就会被覆盖，造成明显的时间和空间浪费。`▶ 28:42`

Linux 的解决方案是复用存储管理模块中已有的**写时复制技术 COW（Copy-On-Write）** 来优化 `fork()`。

> **老师强调（易错点）**：写时复制**并非 Linux 发明的新技术**，它本就是操作系统存储管理模块中已经存在的技术，Linux 只是复用它来优化 fork 流程。往年考试约 40%~50% 的考生误认为 COW 是 Linux 提出的，要注意区分。`▶ 28:42`

### Copy-On-Write（写时复制）

写时复制本质上是一种内存管理和数据复制策略，也是 memory map 的 `flags` 参数的典型配置。`▶ 33:28`

#### 共享映射的基本场景

当磁盘上的同一个文件对象被多个进程共享访问时，若为每个进程在物理内存中都保存一份独立副本，会造成空间浪费。优化做法是：把不同进程虚拟地址空间中的对应区域，通过各自的页表映射到**同一块物理内存**，初始赋予**只读权限**，从而以共享方式节省内存；进程后续若要修改内容，则通过 COW 机制处理，不影响其他进程。`▶ 31:05`

#### 写入时的执行逻辑

1. 通过 memory map 把该内存区域的 `flags` 标记为 copy on write；
2. 当某个进程尝试写入这块只读物理页时，触发**页错误异常**，陷入内核；
3. 内核先把该物理页的内容**拷贝到一个新的物理页框**；
4. 更新该进程对应虚拟页到新物理页框的映射；
5. 此后该进程就在自己独立的副本页上写入，其他进程不受影响。`▶ 33:28`

结果是：各进程除了被修改的页面之外，其余页面仍共享原始物理页——既节省了内存，又不破坏各进程地址空间的独立性。`▶ 33:28`

> **老师提示**：要把进程管理、存储管理的知识点关联起来理解——COW 是 memory map 的 flag 配置，而它又支撑了 fork 的优化。`▶ 33:28`

### 用 COW 重新审视 fork

虚拟内存（VM）和内存映射解释了 fork 如何为每个进程提供私有的地址空间；对于"fork() 后紧跟 exec()"这一常见情形，COW 正是完美的解决办法。`▶ 35:58`

fork 为新进程创建虚拟地址空间的步骤：

1. 创建新进程的 `mm_struct`、`vm_area_struct`、页表的**精确副本**；
2. 将父子两个进程中的每个页面都**标记为只读**；
3. 将两个进程中的每个 `vm_area_struct` 都标记为**私有 COW**；
4. 返回时，每个进程都拥有虚拟内存的精确副本（但物理页面共享）；
5. 后续若发生写入，则通过 COW 机制创建新页面。

#### 父子进程的数据结构关系

fork 生成子进程时，子进程要建立自己的一套数据结构：

- 子进程的 `task_struct` 指向自己的 `mm_struct`；
- `mm_struct` 指向自己的 `vm_area_struct` 链表；
- 这些结构从父进程复制而来，但归子进程独有；
- 此时父子进程的**页表内容相同**，且都被标记为只读，`flags` 中标记为私有 copy on write；
- 因此父子进程的数据结构彼此独立，但初始时指向相同的物理内存。`▶ 36:44`

#### 与 exec 的衔接

执行 `exec()` 时，写保护被触发、陷入内核；内核为子进程单独分配内存空间，丢弃来自父进程的原有映射，把可执行文件的代码与数据重新映射到子进程的地址空间，从而完成整个写时复制流程。`▶ 38:33`

这样一来，Linux 的 `fork` 与早期 Unix "先全量复制、随后又被 exec 全部丢弃"的 `fork` 有了显著区别：共享加按需复制使 fork 既快速又省内存，同时仍然保证每个进程拥有独立的私有地址空间。`▶ 39:26`

## 5. 线程引入的动因与应用示例

> 课件 第 48–55 页 · 讲解从 `40:23` 开始

### 线程的基本定位

线程是比进程晚出现约 20 年的运行实体。早期操作系统中，CPU 的调度实体是进程；引入线程之后，CPU 的调度实体变为线程，而进程主要成为资源分配的单位。进程内部可以包含一个或多个线程，同一个进程内的多个线程共享该进程的资源；在多核或多处理器系统中，同一进程的多个线程可以真正并行运行`▶ 40:23`。例如在 Windows 中，实际获得 CPU 运行的是进程中的线程`▶ 40:23`。

线程有多种实现方式，这与不同操作系统厂商的历史支持策略不同有关，属于历史遗留问题`▶ 41:39`。

### 引入线程的三个原因

在进程内部再派生线程，主要出于三方面考虑`▶ 42:28`：

1. **应用的需要**：许多应用本身包含多个可并发执行的任务，例如同时接收输入、刷新显示、定时保存、处理网络请求等。
2. **开销的考虑**：创建、撤销、切换进程的开销较大；线程比进程更轻量，线程相关操作所需的时间、空间和管理成本通常更低。
3. **性能的考虑**：在多核、多处理器环境下，同一进程中的多个线程可以并行执行，从而提升系统处理能力；即使在单核环境中，一个线程因 I/O 阻塞时，同进程的其他线程仍可继续运行。

### 应用示例 1：多线程字处理软件

以 Word、WPS 等字处理软件为例，整个字处理软件是一个进程，但内部通常包含多个线程。教材示例给出三个典型线程`▶ 44:13`：

| 线程 | 主要职责 |
|---|---|
| 键盘输入线程 | 接收用户的键盘输入 |
| 排版/显示线程 | 根据输入内容重新排版，并实时更新屏幕显示，实现“所见即所得” |
| 定时保存线程 | 按设定周期自动保存文件，降低异常退出造成的数据丢失风险 |

这些线程并行工作，可以提高程序的响应速度：用户输入时，界面仍能及时刷新，保存操作也不必完全打断用户操作。实际字处理软件中的线程往往不止三个；类似 Tomcat 这样的服务器软件还具有多层结构，每一层都可能包含大量线程`▶ 44:13`。

> **老师强调**：字处理软件的例子说明，应用程序内部天然存在多个可以并发处理的任务，多线程能让这些任务协作运行，使用户操作更顺畅`▶ 44:13`。

课件同时提出思考问题：如果没有线程，如何在一个进程中同时完成输入、排版和定时保存？这通常需要程序员自行拆分任务状态、设置定时器并使用复杂的事件驱动逻辑，程序结构会更复杂。

### 应用示例 2：多线程 Web 服务器

#### Web 服务器的基本工作过程

Web 服务器采用 HTTP 协议与客户端通信，基本流程为`▶ 45:52`：

1. 从客户端接收网页请求；
2. 根据请求中的 URL 找到磁盘上对应的网页文件；
3. 将网页文件从磁盘读入内存；
4. 把网页内容返回给相应客户端。

提高 Web 服务器效率的常见方法包括：

- **网页缓存（Web page cache）**：将热点网页保存在内存中，避免重复访问磁盘；
- **多线程**：使用多个线程并发处理多个客户端请求。

#### 单线程/单进程模式的问题

如果 Web 服务器只用一个服务进程顺序处理请求，读磁盘文件就是一个慢速的阻塞操作。进程执行 `read` 时可能被挂起等待 I/O 完成，在此期间既不能接收新的客户端请求，也不能处理其他任务，因此一次只能服务一个客户端`▶ 45:52`。

采用顺序编程时，必须等当前请求完成资源加载、结果返回甚至连接关闭后，才能接收下一个请求，用户等待时间长，服务器性能差`▶ 53:37`。

#### 没有线程时的两种方案

如果不使用线程，仍可构造 Web 服务，课件给出两类方案：

| 方案 | 特点 | 主要问题 |
|---|---|---|
| 一个服务进程/单线程进程 | 顺序编程，使用阻塞系统调用 | 无并行性，I/O 期间服务器不能处理其他请求，性能下降 |
| 有限状态机 / I/O 多路复用 | 使用非阻塞 I/O、事件驱动和中断机制 | 有并行性，但编程模型复杂 |

I/O 多路复用也称有限状态机，是一种基于事件驱动的技术，其典型编程接口包括 `select`，Unix 和 Windows 都提供相应实现`▶ 54:36 · 1:05:09 · 1:09:39`。它的核心思想是：把原本会阻塞进程的 `read` 等操作改造成非阻塞操作；进程发起 I/O 请求后不必等待数据返回，可以继续处理其他任务；当 I/O 完成后，再根据事件回头处理对应数据`▶ 1:05:09`。这样可以把 CPU 控制权保留在进程内部，避免进程因等待 I/O 而被整个调度挂起`▶ 1:05:09`。

但这种方式要求程序员自己维护不同请求的执行状态，并在事件发生时恢复处理，编程复杂、对程序员要求较高`▶ 1:07:28`。

#### 多线程 Web 服务器结构

多线程 Web 服务器主要由两类线程组成`▶ 45:52 · 51:56`：

- **分派线程（dispatcher / dispatch thread）**：专门负责接收客户端请求，并把请求分发给工作线程；
- **工作线程（worker threads）**：负责具体处理请求，例如查询缓存、读磁盘、组织并返回响应。

其处理过程如下：

1. dispatcher 线程接收新的网页请求；
2. dispatcher 将具体处理任务交给某个 worker 线程；
3. dispatcher 立即返回，继续接收其他客户端请求，避免新客户端长时间等待；
4. worker 线程先查询 Web 缓存：
   - 若缓存命中，直接把热点网页返回给客户端；
   - 若未命中，则访问磁盘读取网页；
5. 当某个 worker 因磁盘 `read` 阻塞时，只阻塞该 worker 线程，其他 worker 和 dispatcher 仍可继续运行；
6. I/O 完成后，该 worker 再把结果返回客户端。

worker 线程通常以**线程池**形式预先创建一批固定数量的线程。线程池体现资源池思想：线程数量有上限，不无限动态创建新线程；没有任务时 worker 睡眠，有任务时被调度处理请求`▶ 51:56`。

### 构造 Web 服务器的三种方法对比

| 模型 | 并行性 | 系统调用方式 | 特点 |
|---|---|---|---|
| 多线程 | 有并行性 | 阻塞系统调用 | 编程模型简单；一个线程阻塞时，其他线程仍可执行；适合并发请求处理 |
| 单线程进程 | 无并行性 | 阻塞系统调用 | 顺序处理请求，I/O 期间整个服务进程等待，性能差 |
| 有限状态机 | 有并行性 | 非阻塞系统调用、中断 | 基于事件驱动和 I/O 多路复用，性能潜力高，但状态管理和程序设计复杂 |

三种方案的核心区别在于**系统调用是否阻塞以及由谁承担并发控制**：

- 使用阻塞系统调用时，单线程进程一旦等待 I/O，就无法继续执行后续任务；
- 多线程方案仍可使用阻塞系统调用，但阻塞的粒度从进程缩小到线程；
- 有限状态机方案通过非阻塞 I/O 和事件分发，在单进程内部模拟并发，但需要程序员显式维护状态机`▶ 1:07:28 · 1:08:39`。

> **老师强调**：多线程方案的优点是编程模型简单。Dispatcher 只负责接收和分发请求；worker 无任务时睡眠，有任务时查缓存、读磁盘并返回结果。即使 worker 执行阻塞的 `read`，也只阻塞当前线程，不影响其他线程`▶ 1:07:28`。

### 小结

线程把“资源分配”和“CPU 调度”分离开来：进程保留地址空间、打开文件、内存等资源，线程成为实际调度和运行的实体。字处理软件体现了应用内部多任务并发的需求，Web 服务器则说明线程能有效处理阻塞 I/O 与并发请求。相比单线程阻塞模型，多线程能避免服务器因一个请求的磁盘访问而停顿；相比有限状态机，多线程又能用更简单的编程结构获得并发能力。这些内容在 ICS 中已有基础，本节从操作系统线程机制的角度重新梳理`▶ 1:09:39`。

## 6. 线程开销、概念与线程私有资源

> 课件 第 56–59 页 · 讲解从 `1:10:01` 开始

### 进程操作的开销

进程相关的操作通常时间/空间开销较大，限制了并发度的提高，主要包括：

- 创建进程
- 撤销进程
- 进程通信
- 进程切换

相比之下，线程的开销明显更小：

- 创建新线程花费时间少，撤销线程同样如此
- 两个线程之间的切换花费时间少
- 同一进程内的线程共享内存和文件，因此线程之间相互通信通常无须调用内核

> **老师强调/类比**：同一宿舍内上下铺互换床位，相当于同一进程内线程切换，速度很快；更换整个宿舍，则相当于进程切换，开销很大。同一宿舍内同学聊天无需借助外部通信方式，相当于同进程内线程通信无需内核介入；跨宿舍通知需要打电话、发消息，则相当于跨进程通信需要内核介入`▶ 1:10:01`。

这部分与 ICS 课程中的知识有关；未修过该课程的同学如有疑问，可课后提问`▶ 1:11:16`。

### 线程的基本概念

传统进程具有两个基本属性：

1. **资源的拥有者**
   - 拥有一个虚拟地址空间
   - 占有若干资源，如文件、I/O 设备
   - 提供保护机制

2. **CPU 调度单位**
   - 表示一条执行路径或执行轨迹
   - 具有状态、优先级等调度相关信息

引入线程后，将原来进程的两个属性分开处理：

- **线程**：进程中的一个运行实体，是 CPU 的调度单位
- **进程**：主要作为资源拥有者，负责持有虚拟地址空间和各类资源
- 同一进程中的多个线程共享该进程拥有的资源

线程有时也被称为**轻量级进程**。

> **老师强调**：如果系统中只有线程概念、没有进程概念，那么此时线程就等价于传统进程；只有当系统中同时存在进程和线程时，二者才有明确的职责区分，需要特别注意二者区别`▶ 1:11:32`。

### 线程的属性

线程具有以下属性：

- 线程有自己的**状态及状态转换**，因此系统需要提供相应的线程操作
- 线程不运行时，需要保存其**上下文**
  - 包括程序计数器等寄存器
- 线程有自己的**栈和栈指针**
- 线程共享所在进程的地址空间和其他资源
- 线程可以创建、撤销另一个线程
  - 程序开始运行时，通常表现为一个单线程进程

线程的栈空间是从进程地址空间中划分出来的，但这种划分**没有内存保护**。线程的私有资源主要包括：

- 线程状态
- 保存线程上下文所需的寄存器
- 私有栈
- 栈指针

> **类比**：线程的栈类似宿舍中的个人床位、书桌，名义上属于个人，但是同宿舍的人实际上可以随意使用；线程之间的栈区域划分也没有强制的内存保护`▶ 1:13:09`。

进程控制块以及进程中的其他资源由该进程内的所有线程共享。

### 单线程与多线程进程模型

#### 单线程进程模型

单线程进程中主要包含：

- 进程控制块
- 用户地址空间
- 一个用户栈
- 一个内核栈

即一个进程中只有一条执行路径。

#### 多线程进程模型

多线程进程中包含：

- 一个共享的用户地址空间
- 一个进程控制块
- 多个线程控制块
- 每个线程各自的用户栈
- 每个线程各自的内核栈

可概括为：

| 资源 | 单线程进程 | 多线程进程 |
|---|---|---|
| 进程控制块 | 1 个 | 1 个，由所有线程共享 |
| 用户地址空间 | 1 个 | 1 个，由所有线程共享 |
| 线程控制块 | 无单独线程控制块 | 每个线程 1 个 |
| 用户栈 | 1 个 | 每个线程 1 个 |
| 内核栈 | 1 个 | 每个线程 1 个 |

### 线程之间是否可以访问彼此的栈

课件问题：**线程 1 是否可以访问线程 2 的栈？**

从逻辑划分上看，同一进程内的不同线程在进程地址空间中划分了各自的栈区域；但从实际访问能力看，由于这些栈位于同一个共享的用户地址空间中，且线程栈之间没有内存保护，因此**线程 1 可以通过地址或全局指针等方式访问线程 2 栈中的数据**。

这种访问本身通常不会触发内存访问错误，但会破坏线程栈的私有性，并可能引发严重的安全问题和并发错误。

> **老师强调**：同一进程内任意线程实际上都可以访问其他线程的地址空间，这种行为不一定触发内存错误，但会带来安全问题`▶ 1:15:27`。

## 7. 用户级线程

> 课件 第 60–65 页 · 讲解从 `1:16:12` 开始

### 用户级线程（User-Level Thread, ULT）

#### 1. 基本思想

线程的实现共有三种方案（考试常考）`▶ 1:16:12`：

| 实现方式 | 实现位置 | 内核是否感知线程 |
|---|---|---|
| 用户级线程 | 用户空间 | 否，内核只管理进程 |
| 核心级线程 | 内核中 | 是，内核直接管理线程 |
| 混合方式 | 内核支持用户线程 | 用户线程与内核线程关联 |

> **老师强调**：线程实现方案的选择，本质上是操作系统对"线程管理放在哪一层"的态度选择`▶ 1:16:12`。

用户级线程的核心特征：

- **在用户空间建立线程**，由线程库提供一组管理线程的函数`▶ 1:18:06`。
- **运行时系统（runtime）** 完成线程的全部管理工作：线程创建、状态维护、调度、切换，并维护线程表，这些都发生在用户态，内核完全不参与`▶ 1:18:06`。
- **内核管理的对象仍然是进程**，不知道线程的存在；内核眼里只有进程控制块，没有线程控制块`▶ 1:16:12 · 1:18:06`。
- 线程切换**不需要内核态特权**，不用陷入内核，由线程库在用户态直接完成`▶ 1:18:06`。
- 线程库只能在**同一进程内部**切换线程，无法跨进程调度线程`▶ 1:18:06`。
- 典型例子：**POSIX Pthreads**（如 Linux 的 pthread 实现）`▶ 1:18:06 · 1:26:15`。

#### 2. 进程状态与线程状态的关系

由于内核只能看到进程，进程的状态和其内部线程的状态是两个层次的概念，二者可能不一致。以进程 B 为例：初始时进程 B 在 CPU 上运行，其内部线程 1 为就绪态，线程 2 为运行态（线程 2 代表整个进程 B 在 CPU 上执行）`▶ 1:21:05`。

课件给出三种典型场景：

**Case 1：线程执行阻塞式系统调用**

- 线程 2 执行 `read` 等阻塞式系统调用而陷入内核，内核将**整个进程 B 阻塞**`▶ 1:21:05`。
- 此时在线程库看来线程 2 仍显示为 running，但实际上它并没有运行——因为整个进程已被阻塞，CPU 已被分配给其他进程`▶ 1:21:05 · 1:43:31`。
- 更严重的是：进程内**所有线程都被连带阻塞**，即使线程 1 处于就绪态也无法运行`▶ 1:18:06 · 1:43:31`。

> **老师强调**：进程内所有线程因进程被内核阻塞而全部无法运行时，线程状态仍可能显示为 running，但实际并未占有 CPU，这一点要能区分清楚`▶ 1:43:31`。

**Case 2：进程时间片到，被切换出去**

- 进程 B 因时间片用完被调度走，CPU 切换到别的进程`▶ 1:21:05`。
- 进程 B 内部的线程状态**不发生任何变化**：线程 2 仍是运行态、线程 1 仍是就绪态，因为线程库根本不知道进程被切换了`▶ 1:21:05`。
- 当进程 B 再次被调度回来时，线程 2 继续执行。

**Case 3：线程主动阻塞（进程内切换）**

- 线程 2 主动调用 `wait`（或 `yield`）进入阻塞，运行时系统在线程表中选择同进程的线程 1，把 CPU 切换给线程 1`▶ 1:21:05`。
- 这是纯粹的用户态切换，进程 B 始终处于运行态，不涉及内核。

#### 3. 例子：POSIX 线程库 Pthreads

- Pthreads 是 **POSIX（Portable Operating System Interface）1003.4a（1003.1c 后续标准）** 定义的多线程编程接口，以线程库的形式提供给用户程序使用`▶ 1:24:04`。
- 它只规定编程接口（API），不规定线程具体由用户态还是内核实现（但课件将其作为用户级线程的例子）。

核心函数：

| 函数 | 作用 |
|---|---|
| `pthread_create` | 创建线程 |
| `pthread_exit` | 终止当前线程 |
| `pthread_join` | 等待指定线程退出 |
| `pthread_yield` | 主动让出 CPU，供同进程其他就绪线程调度 |

线程在执行完自身功能后，可以通过 `yield` 主动让运行时切换到其他线程执行`▶ 1:25:59`。

> **老师强调 / 课件提问**：为什么用户级线程要"自愿让出 CPU"？因为内核不感知线程，不会基于时间片在内核态抢占某个用户线程；线程之间能否公平使用 CPU，依赖线程库内部的调度，因此需要线程通过 `yield` 主动合作让出执行权`▶ 1:24:04 · 1:25:59`。同一进程内的线程共享地址空间，属于天然的合作关系，这与进程之间相互竞争资源的属性完全不同`▶ 1:24:04`。

#### 4. 用户级线程的优缺点

**优点**

1. **线程切换速度快**。
   - 切换在用户态完成，不需要陷入内核、不需要上下文切换到内核态、不触发内核的调度程序，只需保存/恢复少量寄存器并修改线程表中的状态，开销接近过程调用`▶ 1:26:15`。
2. **调度算法可以是应用程序特定的**。
   - 调度逻辑由线程包（线程库）在进程内部实现，应用可以根据自身需要选择合适的调度算法，无需操作系统介入`▶ 1:26:15`。
3. **可运行在任何操作系统上**。
   - 不需要修改操作系统内核，只要在用户空间实现线程库即可；若不想改动原有操作系统，基于 POSIX 标准实现用户级线程是最快的方案，Linux 就采用这种方案`▶ 1:26:15`。
4. 此外，用户级线程的规模可以很大，因为内核无需为其维护内核数据结构。

**缺点**

1. **一个线程执行阻塞式系统调用，会阻塞整个进程**。
   - 大多数系统调用是阻塞的，内核只认识进程，它一旦阻塞进程，进程中所有线程都被阻塞，哪怕其他线程处于就绪态也无法运行`▶ 1:18:06 · 1:26:15`。
2. **同一进程的多个线程不能在多个处理器上并行运行**。
   - 内核只把处理器分配给进程，一个进程在任一时刻只会被调度到一个 CPU 上，内核看不到进程内部的多个线程，因此不可能把同一进程的两个线程分别调度到两个核心上`▶ 1:26:15`。

> **老师强调**：要能够由"内核只感知进程、只能把 CPU 分配给进程"这一前提出发，推导出"同进程内多线程无法在多核上并行"这一结论`▶ 1:26:15`。

#### 5. 阻塞式系统调用问题的处理

为克服"一个线程阻塞、整组线程陪绑"的问题，有两种解决方案：

1. **把阻塞式系统调用改造成非阻塞式**
   - 采用 **Jacketing / wrapper（包装/"马甲"）技术**：在线程与真正的系统调用之间加一层封装函数，把会产生阻塞的系统调用转化为非阻塞的系统调用`▶ 1:27:38`。
   - 工作方式：当封装发现线程即将进入等待状态（例如 I/O 尚未就绪）时，不让整个进程陷入阻塞，而是代替线程主动调用 `yield` 让出执行权，让同进程的其他线程运行；之后再由线程库在合适时机回来检查 I/O 是否完成`▶ 1:27:38`。
2. **重新实现对应系统调用的 I/O 库函数**
   - 不直接使用内核提供的阻塞式 I/O 接口，而是在用户态重写一套 I/O 库函数（内部可结合非阻塞 I/O、轮询等手段），使线程级别的等待不会升级为进程级别的阻塞`▶ 1:27:38`。

两种方法的本质相同：把"内核阻塞整个进程"转化为"线程库只阻塞发起调用的那个线程"，从而让进程内其他用户线程仍然可以被调度执行。

## 8. 核心级线程与混合线程模型

> 课件 第 66–67 页 · 讲解从 `1:28:45` 开始

### 核心级线程（Kernel Level Thread，KLT）

核心级线程由**内核统一管理所有线程**，并向应用程序提供操作线程的 API 接口。其主要特点包括：

- 内核同时维护**进程和线程的上下文**；
- 线程的切换需要内核支持，在核心态完成；
- 系统以**线程为基础进行调度**，线程是 CPU 调度的基本单位；
- 典型例子：**Windows**。

在这种模型下，进程是资源的拥有者，线程是 CPU 调度单位，职责划分清晰，被认为是**最理想的进程/线程模型**。线程切换、线程调度都由内核完成，对外提供统一的 API`▶ 1:28:45`。

> **老师强调**：内核级线程模型中，进程负责拥有资源，线程负责被调度，这是最理想的进程线程模型；典型代表是 Windows，要记住`▶ 1:28:45`。

#### 补充：Windows 与线程的历史背景

Windows NT 于 1988 年启动开发，而线程概念在 1984 年左右才刚被提出。因此 Windows NT 在设计时就融入了当时的一系列新技术，包括：

- 线程；
- 面向对象；
- 微内核思想。

微软当时还从 VAX 等成熟系统团队挖来研发人员，目标之一是证明自己的技术实力`▶ 1:29:56`。

---

### 混合模型（Hybrid Thread Model）

混合模型同时结合了**用户级线程**和**内核级线程**：

- **线程创建在用户空间完成**，因此创建开销较小；
- **线程调度等管理工作在核心态完成**，可以借助内核实现真正的并行调度；
- 典型例子：**Solaris**。

#### 基本结构

在混合模型中，多个用户级线程通过**多路复用（multiplexing）**方式映射到多个内核级线程上：

```text
用户级线程 U1 ─┐
用户级线程 U2 ─┼── 多路复用 ──> 内核级线程 K1、K2、...
用户级线程 U3 ─┘
```

用户态线程库负责提供用户线程，内核则负责调度底层的内核线程。用户线程与内核线程之间**并非一一直接对应**，早期常通过**轻量级进程（Light-Weight Process，LWP）**作为中间结构连接二者，形成多路复用关系`▶ 1:31:54`。

> **老师强调**：混合模型的关键是“线程创建在用户空间、调度在核心态”，并且用户级线程与内核级线程之间通过多路复用连接；典型系统是 Solaris`▶ 1:31:54 · 1:33:56`。

#### Solaris 模型的演变

- **Solaris 8 之前**：多个用户线程通过多路复用方式与内核线程挂钩绑定；
- **Solaris 8 之后**：改为完全的**一对一模型**，即一个用户线程对应一个内核线程；
- 后来 Solaris 随 Sun 被 Oracle 收购，该系统逐渐不再活跃`▶ 1:31:54 · 1:33:56`。

---

### 两种模型对比小结

| 模型 | 线程创建/管理位置 | 调度单位 | 映射关系 | 优点 | 典型系统 |
|---|---|---|---|---|---|
| 核心级线程 | 内核管理，提供 API | 线程 | 用户线程直接由内核线程支持 | 模型清晰，能以线程为单位调度，API 统一 | Windows |
| 混合模型 | 创建在用户空间，调度在核心态 | 内核线程调度，用户线程多路复用其上 | 早期多对多/多路复用，后可演变为一对一 | 兼顾用户态创建效率与内核调度能力 | Solaris |

## 9. 协程、纤程与高并发关键词

> 课件 第 68–71 页 · 讲解从 `1:35:05` 开始

### 协程（coroutine）

#### 为什么引入协程

协程的引入主要是为了改善并发编程的性能，尤其适用于处理**异步任务**和**大量并发连接**的场景。其背后的核心驱动力是 **C10K 问题**：当单机网络连接数量提升到上万量级时，单纯依靠增加线程/进程等并发实体并不能无限提升并发能力`▶ 1:38:17`。

> **老师强调**：随着实体数量增多，会产生类似软件开发中的"沟通成本"（即调度、切换、资源竞争等开销），并不是线程越多并发能力就越强`▶ 1:38:17`。

#### 协程是什么

协程是一种由**编程语言或库**支持的并发运行实体，与操作系统本身无关。它允许在**一个线程/进程中实现多个执行流**，并在这些执行流之间进行**协作式**切换，由多个协程协同完成任务`▶ 1:35:05`。

协程的设计思路与线程类似，但**运行层次不同**：

| 对比项 | 线程 | 协程 |
|--------|------|------|
| 支持层级 | 操作系统（内核态） | 编程语言/库（用户态） |
| 调度方式 | 抢占式为主 | 协作式为主 |
| 切换开销 | 较大（涉及内核态切换） | 较小（用户态内切换） |
| 运行载体 | 进程内 | 单个线程内可运行多个协程 |

#### 协程怎么用与如何实现

协程的使用依赖于**编程语言或库的支持**，其实现更偏向语言机制的模拟——即在一个用户线程上运行多个 Task。典型代表包括：

- **Python**：`asyncio`
- **Rust**：`async_std`
- **C++20**：`coroutine`
- **Go**：`goroutine` / `coroutine`
- 其他：如 JavaScript 的异步机制等`▶ 1:35:05`

### 纤程（fiber）

纤程是 **Windows** 操作系统提供的一种比线程粒度更细的执行实体：**一个线程中可以包含多个纤程**。其概念与协程相近，同样运行在用户态层面。

> 老师说明：纤程相关细节课堂未深入展开，感兴趣可自行查阅资料`▶ 1:35:05`。

### 高并发核心关键词梳理

本章涉及的并发相关关键词及其关联如下：

| 关键词                     | 说明                                        |
| ----------------------- | ----------------------------------------- |
| **进程 / 线程 / 协程**        | 三种不同粒度、不同层次的并发执行实体                        |
| **内核态 / 用户态**           | 判断并发实体由谁支持的关键：线程靠内核，协程靠用户态语言机制`▶ 1:38:17` |
| **编程语言原生支持**            | 协程区别于线程的重要特征，依赖语言或库提供                     |
| **阻塞 / 非阻塞**            | I/O 调用是否会挂起执行流，是异步编程的基础概念`▶ 1:38:17`      |
| **异步 I/O**              | 协程主要处理的任务类型，避免等待 I/O 时浪费执行资源              |
| **I/O 密集型**             | 协程、异步 I/O 最能发挥优势的负载类型                     |
| **I/O 多路复用**            | 用少量实体监听大量连接的技术，是解决 C10K 的关键手段`▶ 1:38:17`  |
| **C10K**                | 单机万级并发连接问题，是催生协程等并发思想的核心问题`▶ 1:38:17`     |
| **线程池**                 | 预先创建并复用一组线程，避免频繁创建销毁的开销`▶ 1:40:06`        |
| **切换开销**                | 线程过多时调度切换带来的额外成本                          |
| **Golang / JavaScript** | 原生支持协程/异步并发模型的代表语言                        |

#### 线程是不是越多越好？

**不是。** 线程数量过多会带来显著的额外开销，包括：

- 线程创建与销毁的成本；
- 线程切换的开销（内核态调度、上下文保存恢复）；
- 大量线程之间的"沟通成本"与资源竞争`▶ 1:38:17`。

因此工程上通常使用**线程池**来限制并复用线程数量，从而降低这类开销`▶ 1:40:06`；而协程则从另一条路线出发——在用户态用极轻量的方式管理海量执行流，配合**异步 I/O** 与 **I/O 多路复用**来应对高并发连接场景。

## 10. 可再入程序与进程映像复习

> 课件 第 72 页 · 讲解从 `1:40:18` 开始

### 进程的特性

进程是程序的一次执行过程，具有以下五个基本特性：

- **并发性**：任何进程都可以同其他进程一起向前推进，多个进程在宏观上同时执行。
- **动态性**：进程是正在执行程序的实例。
  - 进程动态产生、动态消亡；
  - 在其生命周期内，进程在三种基本状态（就绪、运行、阻塞）之间转换；
  - 进程拥有动态的地址空间。
- **独立性**：进程是资源分配的一个独立单位，不同进程的工作不相互影响。例如，各进程的地址空间相互独立。
- **制约性**：进程在执行过程中可能与其他进程产生直接或间接的关系，因访问共享数据/资源或进程间同步而产生制约。
- **异步性**：每个进程都以其相对独立的、不可预知的速度向前推进。

### 可再入程序（可重入程序）

**可再入程序**是指可被多个进程同时调用的程序，它具有以下性质：

- 它是**纯代码**的，即在执行过程中自身代码不改变；
- 调用它的进程应该自己提供数据区。

> **老师强调**：可再入指同一段程序可被多个进程同时调用，程序自身代码为纯代码、执行过程中不改变，通过栈存储运行状态，多次递归、过程调用不会引发冲突。而随机数发生器 `rand` 函数的代码执行时会发生变化（其内部会保存并更新种子状态），属于非可再入的安全隐患。`▶ 1:40:18`

也就是说，可再入程序把"不变的代码"和"变化的数据/运行状态"分离开：代码只有一份、被所有调用者共享；数据区和栈则由每个调用进程各自提供，因此多个进程同时调用、甚至递归调用都不会相互冲突。

### 进程映像

进程在内存中的完整映像由四部分组成：

```
进程映像 = 程序（代码） + 数据 + 栈 + PCB
```

- **程序**：可被执行的代码；
- **数据**：进程使用的数据区；
- **栈**：保存过程调用、递归等运行状态；
- **PCB（进程控制块）**：记录进程的管理信息。

## 术语

| 术语 | 解释 |
| --- | --- |
| 虚拟地址空间 | 操作系统为每个进程提供的独立地址空间，由操作系统负责虚拟地址到物理地址的映射。 |
| VMA（vm_area_struct） | 表示进程地址空间中一段有实际内容的内存区域，记录起止位置、权限及映射文件等信息。 |
| mm_struct | Linux PCB 中描述进程内存管理的数据结构，是 VMA 链表或树结构的入口。 |
| 进程队列 | 操作系统以 PCB 为元素，按就绪、等待等状态组织进程的队列。 |
| 五状态进程模型 | 包括新建、就绪、运行、阻塞和终止等状态，是课程中最接近实际系统的模型。 |
| 原语 | 执行过程不可分割、不可中断的原子操作，进程控制通常通过原语完成。 |
| fork() | Unix/Linux 中通过复制父进程创建子进程的系统调用。 |
| exec() | 用新的可执行程序代码和数据替换当前进程映像的系统调用。 |
| 写时复制（COW） | 父子进程初始共享只读物理页，只有发生写入时才复制页面的优化技术。 |
| 线程 | 进程内部的运行实体和 CPU 调度单位，共享进程资源并拥有独立栈和上下文。 |
| 线程池 | 预先创建固定数量工作线程以复用线程、降低频繁创建和销毁开销的机制。 |
| 用户级线程 | 由用户态线程库管理、内核不感知其存在的线程实现方式。 |
| Pthreads | POSIX 标准定义的用户级线程编程接口，包含 create、exit、join、yield 等函数。 |
| 核心级线程 | 由内核管理线程上下文并以线程为单位调度的实现方式。 |
| 混合线程模型 | 用户级线程通过 LWP 等中间机制与内核级线程关联的线程实现方式。 |
| 协程 | 由编程语言或库支持、在一个线程内协作切换的多个用户态执行流。 |
| C10K | 单机同时处理大量网络连接时所面临的高并发问题，推动了异步 IO 和协程等技术发展。 |
| 可再入程序 | 可被多个进程或执行流同时调用而不修改自身代码的纯代码程序，调用方提供独立数据区。 |
