## 1. 回顾：有错但不丢包信道的 RDT 2.x

> 课件 第 35–37 页 · 讲解从 `05:11` 开始

### rdt 2.2 的设计思想

在 rdt 2.1 中，ACK 与 NAK 本身不携带任何序号信息，发送方只能根据收到的是 ACK 还是 NAK 判断分组是否被成功接收。

rdt 2.2 对此作了改进：

- 在 ACK 中加入**最近成功接收的分组序号 seq**。
- 发送方将返回 ACK 中的序号与自己当前发送分组的序号进行比较，从而判断最近一次发送是否成功。
- 由于带序号的 ACK 已经能够表达“期望/确认的是哪一个分组”，因此不再需要 NAK。

发送方的处理规则是：

- 如果收到正确的 ACK，且 `ACK.seq == 当前发送分组的 seq`，则认为发送成功，可以进入下一个分组的状态。
- 如果 ACK 出错，或者 `ACK.seq != 当前分组的 seq`，发送方就重传当前分组。

> **老师强调**：这里虽然本节主要回顾“有错但不丢包”的 rdt 2.x，但后续会进入更现实的信道：数据报文可能出错，也可能丢失；数据报文或 ACK 丢失都会使发送方一直收不到确认，从而无法确定此前的数据是否已经成功发送`▶ 05:11`。

---

### rdt 2.2 发送方状态机

发送方仍然是停等协议，一次只发送一个未确认分组，并通过 0、1 两个序号区分相邻分组。

| 状态 | 含义 |
|---|---|
| Wait for call 0 from above | 等待上层交给发送方序号为 0 的数据 |
| Wait for ACK or NAK 0 | 已发送序号为 0 的分组，等待对该分组的确认 |
| Wait for call 1 from above | 等待上层交给发送方序号为 1 的数据 |
| Wait for ACK or NAK 1 | 已发送序号为 1 的分组，等待对该分组的确认 |

虽然状态名中仍保留“ACK or NAK”，但 rdt 2.2 实际上只使用 ACK，不再发送 NAK。

#### 发送序号 0

在“Wait for call 0 from above”状态下，当上层调用 `rdt_send(data)` 时：

```text
sndpkt = make_pkt(0, data, checksum)
udt_send(sndpkt)
```

发送方构造序号为 0 的分组并发送，然后进入“Wait for ACK or NAK 0”状态。

在等待确认时：

```text
rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && isACK(rcvpkt,0)
```

如果收到未损坏、且确认序号为 0 的 ACK，说明序号 0 的分组已被正确接收，发送方进入“Wait for call 1 from above”状态。

如果发生以下情况：

```text
rdt_rcv(rcvpkt) &&
(corrupt(rcvpkt) || isACK(rcvpkt,1))
```

即：

- ACK 损坏；或
- 收到的是 `ACK 1`，而不是当前期望的 `ACK 0`

则发送方重传刚才的分组：

```text
udt_send(sndpkt)
```

#### 发送序号 1

在“Wait for call 1 from above”状态下，当上层调用 `rdt_send(data)` 时：

```text
sndpkt = make_pkt(1, data, checksum)
udt_send(sndpkt)
```

随后进入“Wait for ACK or NAK 1”状态。

若收到：

```text
rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && isACK(rcvpkt,1)
```

表示序号 1 的分组已被正确接收，发送方回到“Wait for call 0 from above”状态。

若收到损坏 ACK，或收到的是 `ACK 0`：

```text
rdt_rcv(rcvpkt) &&
(corrupt(rcvpkt) || isACK(rcvpkt,0))
```

则重传当前序号为 1 的分组。

---

### rdt 2.2 接收方状态机

接收方根据当前期望接收的序号，在两个状态之间切换：

| 状态 | 含义 |
|---|---|
| Wait for 0 from below | 等待来自下层的序号为 0 的数据分组 |
| Wait for 1 from below | 等待来自下层的序号为 1 的数据分组 |

#### 等待序号 0

在“Wait for 0 from below”状态下，如果收到正确且序号为 1 的分组：

```text
rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && has_seq1(rcvpkt)
```

接收方执行：

```text
extract(rcvpkt,data)
deliver_data(data)
sndpkt = make_pkt(ACK, 1, chksum)
udt_send(sndpkt)
```

即：

1. 从分组中取出数据；
2. 将数据交付上层；
3. 发送 `ACK 1`；
4. 转入等待序号 0 的下一个状态，即“Wait for 1 from below”。

如果收到损坏分组，或重复收到序号为 0 的分组：

```text
rdt_rcv(rcvpkt) &&
(corrupt(rcvpkt) || has_seq0(rcvpkt))
```

接收方不会再次向上层交付该数据，而是重发上一次的确认：

```text
udt_send(sndpkt)
```

此时 `sndpkt` 是接收方保存的、最近一次发送的 ACK，即用于确认当前已接受分组的 ACK。

#### 等待序号 1

在“Wait for 1 from below”状态下，如果收到正确且序号为 0 的分组：

```text
rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && has_seq0(rcvpkt)
```

接收方执行：

```text
extract(rcvpkt,data)
deliver_data(data)
sndpkt = make_pkt(ACK, 0, chksum)
udt_send(sndpkt)
```

即提取数据、交付上层、发送 `ACK 0`，然后转回“Wait for 0 from below”状态。

如果收到损坏分组，或重复收到序号为 1 的分组：

```text
rdt_rcv(rcvpkt) &&
(corrupt(rcmpkt) || has_seq1(rcvpkt))
```

接收方重发最近一次的 ACK，而不是重复交付数据。

---

### 为什么不需要 NAK

rdt 2.2 中，接收方对每个正确接收的新分组发送带有该分组序号的 ACK。发送方通过 ACK 序号即可判断情况：

- 收到与当前分组序号相同的 ACK：当前分组成功；
- 收到与当前分组序号不同的 ACK：当前分组没有得到正确确认；
- 收到损坏 ACK：也无法确认当前分组成功。

后两种情况都统一处理为重传当前分组。因此，NAK 所表达的“失败”信息可以由“错误 ACK、旧 ACK 或损坏 ACK 后超时/重传机制”隐含表达，不再需要单独的 NAK 分组。

---

### rdt 2.x 与丢包问题的关系

本节回顾的 rdt 2.0、2.1、2.2 都假设信道只会使比特出错，不会使分组丢失。在这种模型中，发送方最终总能收到接收方返回的反馈，只是反馈可能损坏或含义不清。

而在接下来的更现实信道中，存在两类丢失：

1. **发送方发出的数据报文丢失**：接收方根本收不到数据，因此不会返回 ACK。
2. **接收方返回的 ACK 丢失**：接收方可能已经正确收到数据，但发送方收不到确认。

这两种情况对发送方表现相同：一直收不到 ACK，因而无法判断此前的数据是否发送成功。要解决该问题，仅靠序号和确认还不够，还需要引入**超时重传机制**。

## 2. RDT 3.0：计时器与超时重传

> 课件 第 38–42 页 · 讲解从 `06:32` 开始

### 问题背景：信道不仅出错，还会丢包

RDT 3.0 面对的信道假设比 RDT 2.x 更弱：

- 信道不仅会使比特出错，还会**丢失数据包**，数据包可能永远无法到达接收方。
- 本章暂不考虑乱序问题。

在这种信道下，仅靠校验和、序号和确认已经不够：如果数据或 ACK 在网络中丢失，发送方会一直等待，协议陷入停滞。RDT 3.0 的核心改进就是在**发送方引入计时器和超时重传机制**。

---

### 核心思想：超时重传

发送方每发出一个数据包，就启动（或重置）一个计时器：

- 如果在超时时间内收到正确的确认，说明该数据包已被成功接收，停止计时器。
- 如果超时仍未收到确认，则认为数据包或 ACK 可能丢失，**重新发送该数据包**，并重启计时器。

> **老师强调**：无论丢失的是数据包本身还是 ACK，发送方超时后的处理都是重传该数据包，发送方不需要区分具体是哪一种丢失`▶ 06:32`。

如果数据包其实没有丢失，只是网络延迟过大，超时重传会使接收方收到多份相同数据。此时依靠数据包中的**序号 seq** 即可判断并丢弃重复包，而这一能力在 RDT 2.1/2.2 中已经实现，并不会增加额外负担`▶ 07:08`。

基本时序可概括为：

1. 发送方发送数据包并启动计时器。
2. 数据包丢失、出错或长时间延迟。
3. 发送方超时。
4. 发送方重发同一数据包并重启计时器。
5. 接收方根据序号处理可能重复的数据包。

---

### 两种导致重复接收的典型场景

#### Case 1：ACK 丢失

过程如下：

1. 发送方 A 发送数据包 A1。
2. 接收方 B 正确收到 A1。
3. B 生成并返回 ACK。
4. ACK 在传输过程中丢失。
5. A 因超时未收到确认，重传 A1。
6. B 再次收到 A1，发现这是重复数据包，将其丢弃，并重传对应 ACK。

#### Case 2：延时过长（long delay）

过程如下：

1. A 发送 A1。
2. 数据和 ACK 实际上都没有丢失，但端到端延迟过大。
3. A 在收到 ACK 之前计时器超时，于是重传 A1。
4. B 因此收到两份相同的 A1。

> **老师强调**：ACK 丢失和延时过长这两种场景，对接收方而言表现相同，都会重复收到同一个数据包；处理方式也一致，即记录已收到的数据包序号，发现重复包时直接丢弃`▶ 07:53`。

---

### 发送方状态机

RDT 3.0 的发送方状态机基于 RDT 2.2 修改，新增计时器相关的事件和动作。发送方共有四个状态，呈对称分布`▶ 09:43`：

| 状态 | 含义 |
|---|---|
| Wait for call 0 from above | 等待应用层请求发送序号为 0 的数据包 |
| Wait for ACK 0 | 已发送序号 0 的数据包，等待 ACK 0 |
| Wait for call 1 from above | 等待应用层请求发送序号为 1 的数据包 |
| Wait for ACK 1 | 已发送序号 1 的数据包，等待 ACK 1 |

初始状态为 **Wait for call 0 from above**。

#### 序号 0 数据包的发送流程

1. 在等待发送状态中收到 `rdt_send(data)` 事件，表示应用层要求发送数据。
2. 构造包含序号 0、数据和校验和的数据包：
   ```c
   sndpkt = make_pkt(0, data, checksum)
   ```
3. 通过不可靠信道发送：
   ```c
   udt_send(sndpkt)
   ```
4. 启动计时器：
   ```c
   start_timer
   ```
5. 进入 **Wait for ACK 0** 状态`▶ 11:16`。

在等待 ACK 0 时，可能收到：

- **损坏的 ACK**；
- **非预期序号的 ACK**，例如 ACK 1；
- **重复 ACK**；
- **正确的 ACK 0**；
- **超时事件 timeout**。

处理方式如下：

- 收到损坏的 ACK 或 ACK 1：不做额外处理，继续等待 ACK 0；等待超时机制来触发重传`▶ 11:16 · 14:02`。
- 收到重复 ACK：直接忽略，继续等待`▶ 12:30`。
- 收到未损坏且确认为 ACK 0 的分组：执行 `stop_timer`，停止计时器，然后转移到等待发送序号 1 数据包的状态`▶ 12:37`。
- 发生超时：重传之前的数据包，并重新启动计时器，继续停留在 Wait for ACK 0 状态`▶ 13:06`：
  ```c
  udt_send(sndpkt)
  start_timer
  ```

#### 序号 1 数据包的发送流程

序号 1 的流程与序号 0 完全对称：

1. 在 Wait for call 1 状态收到 `rdt_send(data)`。
2. 构造序号为 1 的数据包：
   ```c
   sndpkt = make_pkt(1, data, checksum)
   ```
3. 调用 `udt_send(sndpkt)` 发送。
4. 启动计时器。
5. 进入 Wait for ACK 1。
6. 收到正确的 ACK 1 后停止计时器，并转回 Wait for call 0。
7. 超时则重发该数据包并重启计时器`▶ 13:33`。

---

### 收到错误 ACK 时：立即重传还是等待超时？

RDT 3.0 与 RDT 2.2 的一个区别在于：收到错误或损坏的 ACK 时，发送方通常**不立即重传**，而是忽略该 ACK，继续等待，直到超时后再重传。

这样做的好处是：

- 可以避免在 ACK 只是延迟到达时进行不必要的重传；
- 能够节省带宽。

> **老师强调**：RDT 3.0 收到错误/损坏的 ACK 时一般什么都不做，等待超时重传；但如果应用对延迟要求很高，也可以设计成立即重传，这是一种性能上的取舍`▶ 14:02`。

---

### 接收方逻辑

RDT 3.0 的修改全部集中在发送方，接收方状态机与 RDT 2.2 **完全一样**`▶ 15:17`。

接收方收到数据包后：

1. 使用校验和判断数据包是否损坏。
2. 根据序号判断是否为重复数据包：
   - 若是重复包，则忽略该数据，不重复交付；
   - 若不是重复包，则将数据交付上层。
3. 转移到对应的期待状态。
4. 重传相应的 ACK。

因此，无论发送方是因为数据包丢失、ACK 丢失还是延时过长而重传，接收方都统一按“重复包”情况处理。

---

### RDT 3.0 与 RDT 2.2 的区别

| 对比项 | RDT 2.2 | RDT 3.0 |
|---|---|---|
| 信道假设 | 可能出错，但不丢包 | 可能出错，也可能丢包 |
| 发送方计时器 | 无 | 有，发送数据包后启动 |
| 超时事件 | 无 | 超时后重传数据包并重启计时器 |
| 正确收到 ACK | 直接转移状态 | 先停止计时器，再转移状态 |
| 错误/损坏 ACK | 按原协议处理 | 通常忽略，等待超时重传 |
| 接收方逻辑 | 校验、序号判重、确认 | 与 RDT 2.2 完全相同 |
| 重复包处理 | 已支持 | 继续依靠序号判重 |

> **老师强调**：RDT 3.0 与 RDT 2.2 的本质区别只在发送方增加了超时重传；接收方处理的仍然是同样的重复数据，因此接收方状态机完全相同`▶ 15:17`。

## 3. RDT 3.0 的丢包、ACK 丢失与延迟场景

> 课件 第 43–44 页 · 讲解从 `16:23` 开始

### RDT 3.0 的四类典型运行场景

RDT 3.0 在 RDT 2.2 的基础上加入了**超时重传**机制，用来处理底层信道可能出现的丢包问题。下面通过时序图分析四种典型场景。

#### (a) 无丢包（正常情况）

时序流程如下：

1. 发送方发送 `pkt0`；
2. 接收方正确收到 `pkt0`，回复 `ack0`；
3. 发送方收到 `ack0` 后，发送新的分组 `pkt1`；
4. 接收方正确收到 `pkt1`，回复 `ack1`；
5. 发送方收到 `ack1`，再发送下一个新的 `pkt0`（序号在 0、1 之间交替）。

这是无丢包、无错误的理想情况：发送方发数据包，接收方正确接收后返回对应 ACK，发送方收到 ACK 后继续发送新数据包，循环往复`▶ 16:23`。

#### (b) 数据包丢失

- `pkt0` 与 `ack0` 的传输正常；
- 发送方发出 `pkt1`，但 `pkt1` 在信道中丢失（图中标为 loss）；
- 接收方收不到 `pkt1`，自然不会回复 `ack1`；
- 发送方在超时时间内收不到确认，**定时器超时，重传 `pkt1`**；
- 重传的 `pkt1` 正确到达后，接收方回复 `ack1`；
- 发送方收到 `ack1`，继续发送新的 `pkt0`。

关键点：**发送方仅靠"超时"就能发现数据包丢失**，不需要接收方提供额外的否定确认（NAK）；超时后重传同一个序号的分组即可恢复`▶ 16:54`。

#### (c) ACK 丢失

- `pkt0`、`ack0` 正常；
- 发送方发出 `pkt1`，接收方正确收到并回复 `ack1`，但 `ack1` 在返回途中丢失；
- 发送方收不到 `ack1`，定时器超时后重传 `pkt1`；
- 接收方再次收到序号相同的 `pkt1`，**检测到这是重复分组**：忽略（不向上层交付重复数据），但**重新回复一次 `ack1`**（因为它无法知道之前的 ACK 是否到达发送方）；
- 发送方收到重发的 `ack1` 后，继续后续传输。

关键点：数据本身已经送达，只是确认丢了；接收方对重复分组"忽略数据、重发 ACK"，从而避免向上层交付重复数据，同时让发送方能够解除等待状态`▶ 17:33`。

#### (d) ACK 延迟导致过早重传

数据包和 ACK 都没有真正丢失，只是发生了**超长延迟**：

1. `pkt1` 正常到达，接收方回复 `ack1`；
2. `ack1` 延迟严重，在它到达之前发送方定时器超时；
3. 发送方误以为分组丢失，**过早重传 `pkt1`**；
4. 接收方收到重复的 `pkt1`，检测到重复后忽略数据，并重发 `ack1`；
5. 发送方收到（重发的或原先延迟的）`ack1` 后继续，发送 `pkt0`；
6. 此后旧的、迟到的 ACK（如本场景中等待 ACK0 期间到达的旧 `ack1`）可能才到达发送方；发送方**检测到 ACK 序号与当前等待的不符，直接忽略**；
7. 若 `pkt0` 的 `ack0` 也被延迟，发送方同样会超时重传 `pkt0`，接收方再次忽略重复数据并回复 `ack0`。

> **老师强调**：无论发送方还是接收方都必须做**重复检测**——接收方检测并忽略重复的数据包，发送方检测并忽略重复（或不匹配）的 ACK。发送方在等待状态下收到与自身所等序号不一致的 ACK 时，直接忽略、不执行任何操作，这与前面状态机的规则一致`▶ 19:42`。

### 四类场景对比

| 场景 | 丢失/异常对象 | 触发动作 | 接收方行为 | 是否产生重复数据交付 |
|---|---|---|---|---|
| (a) 无丢包 | 无 | 正常收 ACK 发新包 | 正常接收、回 ACK | 否 |
| (b) 数据包丢失 | `pkt1` | 发送方超时重传 `pkt1` | 收到重传包后回 `ack1` | 否 |
| (c) ACK 丢失 | `ack1` | 发送方超时重传 `pkt1` | 检测重复、忽略数据、重发 `ack1` | 否 |
| (d) ACK 超长延迟 | `ack1` 迟到 | 超时过早重传；忽略迟到/不匹配的 ACK | 检测重复、忽略数据、重发 ACK | 否 |

### RDT 3.0 的能力与假设

- 到 RDT 3.0 为止，已经覆盖了前面讨论过的全部信道不可靠情况：**数据包丢失、数据包损坏（校验和检测）、超时重传**，ACK 丢失与延迟也能通过序号和重复检测正确处理`▶ 22:02`。
- 从 RDT 1.0 到 3.0 都假设收发双方之间是一条**字节流管道，数据先进先出（FIFO）**，因此暂不考虑分组乱序到达的问题`▶ 22:02`。
- 在只考虑丢包和出错、不考虑乱序的前提下，RDT 3.0 在功能上已经可以正确、可靠地工作，能够投入实际使用（但它是停等协议，性能问题留待后续滑动窗口机制解决）`▶ 22:02`。

## 4. 停等协议的效率与信道利用率

> 课件 第 45–47 页 · 讲解从 `22:54` 开始

### 停等式协议的效率问题

从 rdt 2.0、rdt 2.1、rdt 2.2 到 rdt 3.0，都属于**停等式协议**（stop-and-wait）：发送方发出一个数据分组后必须停下来，等待接收方返回 ACK，才能发送下一个分组。这类协议在功能上可以保证可靠传输，但传输效率不高，因为在等待 ACK 的大部分时间里信道是空闲的`▶ 22:54`。

### 参数定义

| 符号 | 含义 |
|---|---|
| $F$ | 一帧（数据分组）的大小，单位 bits |
| $R$ | 信道发送速率（注入速率），单位 bits/s |
| $F/R$ | 把一帧完整注入信道所需的**发送时延** |
| $I$ | 单向传播延迟 |
| $RTT$ | 往返传播延迟，$RTT = 2I$ |

> **老师强调（简化假设）**：分析时忽略收发双方的校验和计算、序号比对等处理延迟，也忽略接收方发送 ACK 的注入延迟；只保留数据的发送时延 $F/R$ 和信号的往返传播延迟 $RTT$ 两部分`▶ 24:13 · 26:53`。

### 时间轴分析

按一个完整周期（发送一帧并等到其 ACK）梳理时间点：

- $t=0$：发送方开始发送第一个比特。
- $t=F/R$：最后一个比特发送完毕，此时信道上的"发送工作"结束。
- 第一个比特经过传播延迟 $I$ 到达接收方。
- 接收方收完最后一个比特后，校验并返回 ACK（处理与 ACK 发送延迟忽略）。
- ACK 再经过 $I$ 回到发送方。
- 发送方收到 ACK 的时刻约为：

$$t = RTT + \frac{F}{R}$$

此时才能开始发送下一个数据帧。

因此在每个周期中：

- **信道工作时间**（真正在发送数据）：$F/R$
- **发送方空闲时间**（等待 ACK）：约 $RTT$
- **一个周期总时间**：$F/R + RTT$

### 信道利用率

信道利用率（line utilization）定义为信道被有效数据占用的时间占整个周期的比例：

$$
U = \frac{\text{工作时间}}{\text{总时间}}
 = \frac{F/R}{F/R + RTT}
 = \frac{F}{F + R\cdot RTT}
$$

> **老师强调**：利用率与 RTT 直接相关——RTT 越大，等待时间占比越高，利用率越低；RTT 越小，利用率越高`▶ 26:53`。

### 例子：长肥网络（LFN, Long Fat Network）

"长肥网络"指**传播延迟长（RTT 大）且带宽大（链路"肥"）**的网络，这类网络最能暴露停等协议的缺陷。

参数：

- 帧长度 $F = 1000$ bits
- 带宽 $R = 1\text{ Mbps} = 10^6$ bits/s
- 单向传播延迟 $I = 270$ ms

计算：

- 发送时延：$F/R = 1000/10^6 = 1$ ms
- 往返延迟：$RTT = 2 \times 270 = 540$ ms
- 一个周期：$1 + 540 = 541$ ms
- 信道利用率：

$$
U = \frac{1}{1+540} = \frac{1}{541}
$$

也就是说，每花 1 ms 发送数据，就要等待 540 ms 才能发下一帧，信道在绝大多数时间里是空的，利用率极低`▶ 28:20`。

### 低利用率的根因与改进思路

**根因**：停等协议规定，任何时刻信道中**最多只能有一个未被确认的帧**。在长肥网络中，链路的"管道容量"（带宽 × 延迟）远大于一个帧，但协议不允许继续发送，因此无法用数据填满管道`▶ 30:06`。

**一种改进方法：使用更大的帧。** 增大 $F$ 可以延长发送时间 $F/R$，使利用率公式中的分子占比提高，从而略微改善利用率。但这只是治标不治本：

- 帧的最大长度受信道**比特错误率（BER, Bit Error Ratio）**限制；
- 帧越长，传输过程中出现比特错误的概率越高；
- 出错会导致整帧重传，反而增加延迟并浪费带宽。

> 因此单纯加大帧长并不是高效的解决办法，要真正填满管道，需要允许信道中同时存在多个未被确认的分组（即后续的流水线传输机制，如滑动窗口协议）`▶ 30:06`。

## 5. 流水线传输与滑动窗口机制

> 课件 第 48–55 页 · 讲解从 `31:26` 开始

### 流水线传输（Pipelining）

**基本思想**：流水线传输是对停止等待协议的性能改进，允许发送方在没有收到确认之前连续发送多个数据包，使信道中同时存在多个正在传输且未被确认的数据包`▶ 31:26`。

**与停止等待协议的对比**：停止等待协议本质上限制信道中最多只有一个分组在传输，发送一个包之后必须等待 ACK 才能发下一个；流水线协议则可以连续发送多个分组，接收方依次返回对应分组的 ACK`▶ 31:26`。

**工作过程（以最多允许 3 个未确认分组为例）**：设分组长度为 $L$，带宽为 $R$。

- $t=0$：发送第一个分组的第一个比特
- $t=L/R$：第一个分组的最后一个比特发送完毕。停止等待协议此时会停下来等待 ACK，而流水线协议继续发送第二个、第三个分组，全部发完才进入等待状态
- 第一个分组在网络中继续传输
- $t=RTT+L/R$：发送方收到第一个分组的 ACK，随后可以开始发送下一批分组

课件给出的数值例子中，3 数据包流水线的网络利用率是停等方式的 3 倍：

$$
U_{\text{sender}}=\frac{3L/R}{RTT+L/R}
$$

> **老师强调**：若允许信道中同时存在 $n$ 个未确认数据包，理论上信道利用率会比停等协议提升 $n$ 倍`▶ 34:09`。

### 实现流水线传输需要解决的三个事项

流水线传输在提升性能的同时，也带来了新的设计要求`▶ 34:39`：

**事项 1：增大序号 seq 的范围**

- 每一个等待确认的数据包都需要一个唯一的 seq
- 停等协议中只需 {0,1}（1 位序列号）即可区分新旧包，流水线中不够用
- seq 被确认之后可以循环复用，因此无需无限增长

**事项 2：发送方需保存所有未确认的数据包**

- 以便在数据包丢失、损坏或 ACK 丢失时进行重传`▶ 34:39`

**事项 3：处理多个数据包引发的异常**

- 多包传输可能出现丢失、损坏、超长延迟，尤其会引入乱序问题（停等协议不会出现乱序）
- 整体设计仍遵循自动重传请求（ARQ）的思想`▶ 34:39`

ARQ 的核心三要素：

1. **差错检测**：假设接收方能够检测传输错误，发送方可通过计时器监测 ACK 是否收到
2. **反馈**：接收方针对不同事件向发送方反馈
3. **重传**：发送方根据反馈决定重传方式

根据"反馈 + 重传"策略的不同，有两种典型方法：**回退 N 步（GBN）**和**选择重传（SR）**`▶ 37:09`。

### 窗口大小 N 的限制

理论上 $n$ 越大信道利用率越高，但数量过大会带来多方面开销`▶ 38:15`：

| 方面 | 过大的代价 |
|------|-----------|
| 发送方 | 缓存未确认包的内存开销增大，可能耗尽内存 |
| 接收方 | 缓冲区堆积未处理数据包，处理速度跟不上发送速度，可能撑爆缓冲区 |
| 网络 | 超出网络承载限制，增加带宽开销 |
| Seq | 需要更多 bit 位来表示序列号 |

因此实际中 $N$ 由多种机制共同决定，例如 TCP 的**流量控制**和**拥塞控制**，本质都是限制网络中未确认数据的总量，以保护网络与接收端`▶ 38:15`。

### 滑动窗口机制

流水线传输机制又称为**滑动窗口机制**`▶ 40:40`。

**目的**：对可以连续发出的、已发出但未确认的最多报文数作出限制。

**序号使用**：循环重复使用有限的报文序号。

**窗口概念**：

- **发送窗口**：在收到对方确认之前，可以连续发出的最多数据报文数
- **接收窗口**：可以连续接收的最多数据报文数
- 通常发送窗口大小 = 接收窗口大小（也可不同；取相同主要是为了实现方便）`▶ 40:40`

接收窗口驱动发送窗口的"滑动"。

**发送窗口的滑动规则**（以窗口大小 7、序列号 0–7 循环为例）：

- 窗口内的序列号是当前可发送的报文
- 每发出一个报文，窗口的**下限（左边界）前移一格**
- 每收到一个确认，窗口的**上限（右边界）前移一格**
- 若持续发送却收不到确认，窗口最终会缩小为 0，达到未确认报文数的上限，必须等待新的确认到达后右边界才能继续前移`▶ 41:28`

**接收窗口的滑动规则**：

- 窗口之前是已接收并确认的报文，窗口内是当前可接收的序列号范围
- 每接收一个报文，窗口的**下限前移**
- 数据交付上层并发出确认后，窗口的**上限前移**
- 若报文到达快而上层应用处理慢，窗口会被快速耗尽，接收方无法接收新数据；发送方也收不到 ACK，直到上层消耗完已接收数据，右边界前移后传输才恢复`▶ 42:50`

### 两种滑动窗口协议对比

滑动窗口协议主要有回退 N（GBN）和选择重传（SR）两种，两者都默认发送方最多可有 N 个未确认数据包，核心区别在于确认方式、计时器数量和重传范围`▶ 44:11`：

| 对比项 | 回退 N（Go-Back-N, GBN） | 选择重传（Selective Repeat, SR） |
|--------|--------------------------|----------------------------------|
| 未确认包上限 | 最多 N 个 | 最多 N 个 |
| 确认方式 | 对多个连续数据包进行**累计确认**；非连续数据包暂时不确认 | 对每个数据包进行**各自确认** |
| 计时器 | 发送方只维护 **1 个**计数器，对当前最古老的数据包计时（从该包成为最古老包开始计） | 对**每个数据包**分别维护计数器 |
| 超时重传范围 | 计数器到期时，**重传所有未确认数据包** | 计数器到期时，**只重传对应的单个未确认数据包** |

## 6. 回退 N 协议（GBN）

> 课件 第 57–61 页 · 讲解从 `45:30` 开始

### 基本思想

回退 N 协议（Go-Back-N，GBN）是流水线可靠传输协议的一种。其核心规则是：

- **接收方只按序接收**：仅确认自己期望收到的下一个报文；若收到出错报文或乱序报文（即使该报文从未收到过），直接丢弃，不缓存。
- **发送方超时后批量重传**：一旦超时，重传所有尚未被确认的报文。

老师举例：接收方已收到报文 1–5，正期望收到 6，此时却收到报文 7，接收方会固执地丢弃 7、继续等待 6——老师用《白马啸西风》台词"那些都是很好很好的，但是我偏不喜欢"形容这种行为`▶ 45:30`。

### 设计要点

**发送方：**
- 保存所有未确认的数据包，最多 N 个（N 为窗口大小），构成一个先进先出队列`▶ 48:30`。
- 由于队列中的 seq 值连续，只需维护序列号的上下界两个变量，无需为每个包维护独立状态。
- 维护两个关键变量：
  - **send_base（base）**：窗口左端，即当前第一个尚未被确认的数据包的序列号`▶ 49:56 · 1:05:39`。
  - **next_seqnum（next_seq）**：下一个待发送数据包将使用的序列号`▶ 49:56 · 1:05:39`。

发送窗口的区域划分`▶ 49:56`：

| 区域 | 含义 |
|---|---|
| 绿色（窗口左侧） | 已发送且已确认 |
| 黄色（窗口内左侧） | 已发送但未确认 |
| 蓝色（窗口内右侧） | 尚未使用的可用序列号，最左端即 next_seq |
| 白色（窗口右侧） | 当前还不能使用的序列号 |

**接收方：**
- 无需缓存数据包，只需记住一个变量：**下一个期望收到的 seq（expectedseqnum）**。

### 优缺点

- **优点**：接收方负担轻，实现简单，无需缓存乱序报文，只需维护一个期望序列号`▶ 45:30 · 49:31`。
- **缺点**：重传包数量大。一旦某个包丢失，其后已发出的包在接收方都被丢弃，发送方必须整批重传，增加了发送端与信道的负担`▶ 48:30 · 49:31`。

### 发送方：四类事件及处理

发送方状态机只有一个状态（Wait），核心就是维护 send_base 和 next_seqnum`▶ 54:57`。

**事件 1：上层有数据要发送（rdt_send）**`▶ 51:18 · 1:05:48`
- 判断 `next_seqnum < base + N` 是否成立；若不成立（窗口已耗尽），拒绝数据（refuse_data）。
- 否则用 next_seqnum 封装数据包并发送，next_seqnum 加一。
- 若发送前 `base == next_seqnum`，说明此前没有任何待确认包，本包是窗口内第一个包，需要启动计时器。

```c
rdt_send(data)
if (nextseqnum < base + N) {
    sndpkt[nextseqnum] = make_pkt(nextseqnum, data, chksum)
    udt_send(sndpkt[nextseqnum])
    if (base == nextseqnum)
        start_timer
    nextseqnum++
} else
    refuse_data(data)
```

**事件 2：收到合法 ACK(n)**（ACK 未损坏且 `n >= base`）`▶ 51:18 · 1:06:59`
- GBN 采用**累计确认**：收到 ACK n 表示序号 ≤ n 的所有数据包都已被接收方正确接收。
- 将 send_base 更新为 `n + 1`，窗口向前滑动。
- 若 `base == nextseqnum`，说明所有包都已确认，停止计时器；否则重启计时器（最旧的未确认包已改变）。

```c
rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && getacknum(rcvpkt) >= base
    base = getacknum(rcvpkt) + 1
    if (base == nextseqnum)
        stop_timer
    else
        start_timer
```

> **老师强调**：累计确认允许中间的 ACK 丢失。例如发出 6、7 号包，即使 ACK6 丢失，只要收到 ACK7，就可直接把 send_base 更新到 ACK7 之后——因为接收方在没收到 6 号包时根本不可能返回 ACK7`▶ 51:18`。

**事件 3：超时（timeout）**`▶ 51:18 · 1:08:19`
- 重启计时器。
- 重传所有未确认的数据包，即序列号从 base 到 next_seqnum − 1 的全部包。

```c
timeout
    start_timer
    udt_send(sndpkt[base])
    udt_send(sndpkt[base+1])
    …
    udt_send(sndpkt[nextseqnum-1])
```

**事件 4：收到错误/无效 ACK**`▶ 51:18 · 1:08:47`
- 包括校验差错的 ACK、重复的旧 ACK（序号落在已确认的绿色区域内，即 `< base`）。
- 直接忽略，不做任何处理，等待超时。

### 接收方处理逻辑

接收方只维护一个变量 expectedseqnum（下一个期望收到的序列号）`▶ 1:09:02`：

- **收到期望序号的数据包（正常）**：数据上交上层，发送该序号的 ACK，expectedseqnum 加一。
- **收到出错或乱序数据包**：
  - 不缓存、直接忽略该包（即使从未收到过）。
  - **重发"已收到的最大序列号"对应的 ACK**（即对 expectedseqnum − 1 的重复确认）。

```c
rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && hasseqnum(rcvpkt, expectedseqnum)
    extract(rcvpkt, data)
    deliver_data(data)
    sndpkt = make_pkt(expectedseqnum, ACK, chksum)
    udt_send(sndpkt)
    expectedseqnum++

other   // 出错或乱序
    udt_send(sndpkt)   // 重发上一个 ACK
```

例如已收到 1–5、期望 6 时收到 7，接收方忽略 7 并重发 ACK5`▶ 1:09:13`。发送方若已确认过 5，这个重复 ACK5 会作为旧 ACK 被忽略；超时后则重传 6、7`▶ 1:10:17`。

### 完整运行示例（窗口 N = 4）

初始 `base = 1`，`nextseqnum = 1`（课件示例中实际从序号 0 开始）：

1. 发送方一次性发送 **pkt0、pkt1、pkt2、pkt3**，窗口耗尽，进入等待，4 个包均待确认`▶ 1:10:46`。
2. pkt0、pkt1 正确到达，接收方返回 **ack0、ack1**；**pkt2 丢失**。
3. pkt3 到达，但接收方期望的是 2，于是**忽略 pkt3，重发 ack1**`▶ 1:11:30`。
4. 发送方收到 ack0，窗口前移一位，序号 4 可用，**发送 pkt4**；收到 ack1，窗口再前移一位，**发送 pkt5**`▶ 1:12:08`。
5. 此时 pkt2、3、4、5 共 4 个包未确认，恰满窗口。pkt4、pkt5 虽到达，但都不是接收方期望的包，继续被忽略，接收方不断重发 ack1；这些重复的 ack1 已滑出窗口（序号 < base），发送方全部忽略`▶ 1:12:33`。
6. 最旧的未确认包 **pkt2 的计时器超时**，发送方重传 **pkt2、pkt3、pkt4、pkt5** 全部四个包`▶ 1:13:22`。
7. 接收方按序收到 2、3、4、5，依次返回 **ack2、ack3、ack4、ack5**。

> **老师强调**：即使 ack2、ack3、ack4 在返回途中全部丢失也无妨——由于累计确认，只要 ack5 到达发送方，就意味着 2、3、4 都已被收到，发送方可直接推进窗口、继续发送新数据`▶ 1:14:27`。

## 7. 选择重传协议（SR）

> 课件 第 63–69 页 · 讲解从 `1:15:36` 开始

### 设计思想与要点

选择重传（Selective Retransmission / Selective Repeat，SR）与回退 N（GBN）的核心区别在于：GBN 的接收方只等待下一个按序到达的数据包，对超前到达的包直接丢弃；而 SR 对每个数据包**独立确认**——即使前面的包缺失，后续到达的包也会被接收方缓存，并单独返回该包的 ACK。对应地，发送方为**每个包单独维护计时器**，某个包超时或其 ACK 出错时，只重传这一个包，收发两侧对每个包的处理相互独立`▶ 1:15:36`。

- **接收方**：对每个到达的数据包单独确认。
- **发送方**：发出连续若干包后，若某包的 ACK 出错或该包定时器超时，只重传该出错/超时的包。
- **接收方**：缓存已收到的数据包，以便按顺序交付上层。
- 缓存无需无限大：一旦连续的按序数据包填满了"空洞"，就可以把整批数据上交上层`▶ 1:17:17`。

### 优劣

| 优点 | 缺点（代价） |
|---|---|
| 只重传真正缺失的包，相比 GBN 大幅减少重传数据量 | 接收方需要缓存乱序到达的包 |
| | 发送方需要为每个包维护独立计时器 |

### 发送窗口与接收窗口

- GBN 的发送方窗口规整：已确认的包连续排列，已发送未确认的包也连续排列；其接收方不缓存包，没有接收窗口的概念。
- SR 因为逐包确认，可能出现旧包未确认、新包已确认的**交错状态**，窗口内已确认和未确认的包交错排列。
- SR 接收方有独立的接收窗口，其中：
  - **灰色**：期望收到但尚未收到的包（包括最左端缺失的包——虽未直接收到，但根据其后连续到达的包可推断其存在；相邻紫色包即使彼此连续，因缺少前序包仍无法交付）`▶ 1:19:42`。
  - **紫色**：已收到但乱序的包，因前序包未到无法交付，只能缓存`▶ 1:19:42`。
  - **窗口最右侧（蓝色）**：窗口内剩余可用的序列号空间`▶ 1:19:42`。

### 协议事件处理

**发送方（3 类事件）**`▶ 1:20:48`

1. **发送数据**：下一个 seq 在发送窗口内（仍有可用序列号）时发送。
2. **数据包 n 超时**：只重传 n，并重置 n 的计时器。
3. **收到 ACK(n)**：
   - 若 n ∈ [sendbase, sendbase+N−1]：标记 n 为已确认；若 n == sendbase，将窗口滑动到最小的未确认包处（更新 sendbase）。
   - 若 ACK 不在窗口范围内：直接忽略。

**接收方（3 类事件）**`▶ 1:22:22`

1. **收到 n ∈ [rcvbase, rcvbase+N−1]（窗口内）**：
   - 确认 n（回复 ACK n）；
   - 若 n == rcvbase：将该包及其后所有连续已缓存的包一起交付上层，并向前推进 rcvbase；
   - 否则（乱序包）：缓存 n，不交付。
2. **收到 n ∈ [rcvbase−N, rcvbase−1]（窗口之前但不太远）**：**必须**确认 n，不能忽略。
3. **其他情形（n < rcvbase−N）**：偏离窗口过远，直接忽略。

### 为什么窗口前 [rcvbase−N, rcvbase−1] 的包仍要回 ACK？

这是理解 SR 的关键问题（课件上的 "Why?"）。

- rcvbase 推进到当前位置，意味着它之前的所有包接收方都已收到；从发送方视角看，这些包都已发出，处于"已确认"或"已发送未确认"状态。
- 发送窗口右边界必然已超过 rcvbase−1；窗口左边界推进最快时刚好到达 rcvbase，最坏情况下 rcvbase 之前的包全部处于已发送未确认状态`▶ 1:24:19`。
- 若发送窗口最左端有包未确认（比如它的 ACK 丢失），会触发超时重传，产生重复数据包。接收方对序列号落在 [rcvbase−N, rcvbase−1] 的重传包**必须回 ACK**，否则发送窗口会一直卡住无法前移；而序列号小于 rcvbase−N 的包早已超出发送窗口，无需再借助 ACK 推进窗口，故可忽略`▶ 1:26:32`。

> **老师强调**：这一设计针对的关键问题是 **ACK 丢失导致发送窗口无法推进**。

### 工作过程示例（窗口 N=4）

**场景一：数据包 2 丢失（课件 p.67）**`▶ 1:28:19`

1. 发送方连续发送 pkt0~pkt3。
2. 接收方收到 0、1，回 ACK0、ACK1；pkt2 丢失；接收方缓存 pkt3 并回 ACK3（与 GBN 不同，不依赖 pkt2）。
3. 发送方收到 ACK0、ACK1，窗口前移，发送 pkt4、pkt5；因 pkt2 未确认，窗口左边界不动，此时未确认的虽只有 2、4、5 三个包，也不能发送 pkt6。
4. pkt2 超时，单独重传 pkt2；期间接收方缓存 pkt4、pkt5 并回 ACK4、ACK5。
5. 接收方收到重传的 pkt2 后，一次性向上层交付连续的 pkt2、pkt3、pkt4、pkt5，并回 ACK2；发送方收到 ACK2 后窗口随即滑过这批已确认的包。

**场景二：ACK2 丢失（课件 p.68）**`▶ 1:31:56` `▶ 1:33:44`

1. pkt0~pkt3 全部正确接收，但 ACK2 丢失；发送方只收到 ACK0、ACK1，随后发送 pkt4、pkt5，接收方回 ACK4、ACK5。
2. 此时接收方已收到并确认 0~5，rcvbase 已推进到 **6**；发送方虽收到 ACK3、4、5，但始终收不到 ACK2，窗口卡住。
3. pkt2 超时重传。重传包的序列号 2 虽不在当前接收窗口 [6,9] 内，但落在 [rcvbase−N, rcvbase−1] = [6−4, 5] = **[2, 5]** 内，接收方必须回 ACK2（忽略数据但补发确认）。
4. 若不补发 ACK2，发送窗口将永远无法推进，整个协议卡死。

### 序列号空间与窗口大小的约束

SR 的序列号可以循环复用，无需无限增长`▶ 1:35:41`。但序列号空间过小时会产生新旧包二义性。

设序列号取值 0~3（空间大小 4），窗口大小 N=3：

- 发送方初始发送 pkt0、pkt1、pkt2；接收方全部正常接收后，接收窗口推进为 {3, 0, 1}，期望收到 3、0、1。

**(a) 正常情况**：发送方依次收到 ACK，依次发送 pkt3、新的 seq=0 数据包，无异常`▶ 1:37:15`。

**(b) ACK 全部丢失**：接收方收到 0、1、2 后回的三个 ACK 全部丢失，发送方超时重传 pkt0。此时接收方窗口正期望一个**新的** seq=0 包，无法区分到达的 seq=0 到底是重传的旧包还是新包——两个场景下接收方视角完全一致，但发送方过程完全不同，产生二义性`▶ 1:38:08`。

- 若序列号空间足够大，重传包用 seq=0、同一数据的新包用 seq=4，就不会混淆`▶ 1:41:00`。

> **老师强调（往年期末常考经典题型）**：SR 中序列号空间大小至关重要，**窗口大小不能超过序列号取值空间的一半**，即序列号空间大小至少为窗口大小的 2 倍（N ≤ 序列号空间/2）。请课后自行证明：序列号空间恰为窗口两倍时机制可正常工作，不足两倍时会出现什么异常`▶ 1:41:16`。

**课后思考**：滑动窗口协议中 GBN 的窗口大小 W 与序列号取值范围之间有什么约束、最小序列号范围是多少（与 SR 对比）`▶ 1:42:18`。

## 8. GBN 与 SR 的对比及旧报文问题

> 课件 第 70–71 页 · 讲解从 `1:42:53` 开始

### GBN 与 SR 的对比

回退 N（Go-Back-N，GBN）与选择重传（Selective Repeat，SR）的核心区别体现在四个维度：发送方的计时器、发送方的重传策略、接收方的确认方式，以及接收方对失序报文的处理方式`▶ 1:42:53`。

| 对比维度 | GBN（回退 N） | SR（选择重传） |
|---|---|---|
| 发送方：定时器 | 只维护 **1 个计时器**，只对最早未确认报文计时 | 对每个未确认报文维护**单独的计时器**，有 n 个报文就需要 n 个计时器 |
| 发送方：重传策略 | 超时后重传**所有未确认报文** | 只重传**超时或发生错误的单个报文** |
| 接收方：确认方式 | **累积确认**：发送某个确认号，代表该确认号之前的所有报文均已成功接收 | 对每个报文**独立确认** |
| 接收方：失序报文处理 | **不缓存**失序报文，依靠发送方重传所有未确认报文来补全缺失数据 | **缓存**失序报文，等收到一段连续的报文序列后，再一并交付上层 |

补充说明 GBN 的计时器行为：计时器绑定最早未被确认的报文；一旦发生超时重传或滑动窗口前移，就会重置该计时器；只要最早未确认报文的状态没有变化，计时器就保持不变`▶ 1:43:16`。

### 序列号循环复用带来的旧报文问题

#### 问题场景

假设序列号范围为 1～N：

1. 发送方发送 pkt1 后超时，于是重传 pkt1，之后依次正常发送 pkt2、pkt3、…、pktN。
2. 接收方收到了重传的 pkt1，以及随后正常到达的 pkt2～pktN，并完成了这一批报文的全部处理。
3. 但事实上，最初发送的那个 pkt1 并没有丢失，而是在网络中经过漫长时间、严重乱序后才到达接收方。
4. 此时序列号已经循环回来，接收方无法判断这个迟到的 pkt1 究竟是之前滞留的**旧报文**，还是使用相同序列号的**新 pkt1**，可能把它错误地当作新报文接收。

> **老师强调**：这是 2022 年学生提出的典型场景。在序列号范围有限、旧报文可能长期滞留网络的前提下，这种"旧报文被误认为新报文"的情况理论上确实可能发生`▶ 1:45:02`。

#### 实际网络中如何避免

实际网络通过两层机制避免上述异常：

1. **传输层：序列号空间足够大**
   - 序列号主要用于 TCP（UDP 没有序列号字段）。
   - 实际 TCP 的序列号空间 N 非常大，几乎不可能在序列号被循环复用之前，滞留的旧数据包还没到达接收方`▶ 1:46:53`。

2. **网络层：限制数据包的存活时间**
   - 每个数据包生成时带有类似"生命值"的字段，不允许数据包在网络中长时间滞留`▶ 1:46:53`。
   - 对 IP 数据包而言，这个字段就是 **TTL**：每经过一跳路由器，TTL 减 1，减到 0 就被丢弃。
   - 不同操作系统 TTL 初始值不同，常见为 64 或 128，即数据包最多经过 64 或 128 跳。
   - 路由器每一跳只需查看目的地址并转发，速度极快；即使走满 128 跳也仅需几毫秒。因此旧包不可能长期存活到序列号循环复用之后`▶ 1:48:11`。

> 综上，理论上序列号耗尽会导致旧报文混淆，但在实际中可通过"足够大的序列号空间 + 限制包存活时间（TTL）"共同避免该极端场景`▶ 1:48:11`。

## 9. 可靠传输机制在网络中的应用

> 课件 第 8 页 · 讲解从 `1:49:33` 开始

### 可靠传输机制在网络中的应用

可靠传输并非 TCP 传输层独有的问题，而是在网络体系结构的各个层次都可能需要面对和解决的问题。课件中列举了以下典型场景：

- **OSI 模型中的链路层**：链路层也可能通过差错控制、确认与重传等机制，在相邻节点之间提供可靠传输。
- **各类基于 UDP 的应用层协议**：UDP 本身不提供可靠传输，因此可靠性需要由应用自行实现，典型例子如 **TFTP**。
- **5G 通信**：无线环境下易出现丢包和误码，需要可靠传输机制保障数据传输质量。
- **时延敏感网络**：在要求低时延和确定性传输的网络中，需要结合重传策略与传输效率进行设计。
- **远程直接内存访问（RDMA）**：RDMA 需要高吞吐、低时延的远程内存访问，对底层传输机制的效率要求很高。

### 通用方法：回退 N 与选择重传

**回退 N（Go-Back-N）** 和**选择重传（Selective Repeat）** 是通用的可靠传输方法，并不只适用于 TCP 所在的传输层`▶ 1:49:33`。它们的核心区别可概括如下：

| 机制 | 接收方对乱序分组的处理 | 丢包后的重传方式 | 开销与代价 |
|---|---|---|---|
| 回退 N | 不缓存乱序到达的分组 | 发送方从丢失分组开始，重传其后的一批分组 | 协议和实现较简单，但可能重传大量已正确到达的分组，浪费带宽 |
| 选择重传 | 缓存乱序到达的正确分组 | 发送方只重传真正丢失或出错的分组 | 带宽利用率高，但接收方需要缓存和更复杂的确认机制，硬件成本更高 |

### 典型案例：AI 网络中的 GPU 高速互联

老师特别以 AI 网络中的 GPU 高速互联为例，说明了这两种机制在实际系统中的权衡：

- **早期 GPU 互联**为了简化硬件设计，采用“简单粗暴”的回退 N 算法：接收方不缓存乱序包，一旦出现丢失，发送方就直接回退并重传相关分组`▶ 1:49:33`。
- 随着大模型训练带来的网络流量不断增大，回退 N 的缺点更加明显：一次丢包可能导致大量分组被重复传输，重传开销高、浪费带宽`▶ 1:49:33`。
- **新的 GPU 互联设计**因此改用选择重传，只重传丢失的分组，以提高带宽利用率；但选择重传要求接收方缓存乱序分组并支持更复杂的控制逻辑，硬件成本也更高`▶ 1:49:33`。

> **老师强调**：选择回退 N 还是选择重传，本质上是在**实现成本/硬件复杂度**与**重传开销/带宽利用率**之间做权衡，并非选择重传在所有情况下都绝对更好`▶ 1:49:33`。

## 10. TCP 的字节序号、确认与可靠传输概览

> 课件 第 72–75 页 · 讲解从 `1:52:05` 开始

### TCP 可靠传输的定位

TCP 要在不可靠的 IP 服务之上实现可靠数据传输。IP 层可能出现：

- **报文出错**：可通过校验和发现；
- **报文丢失**；
- **报文乱序到达**。

TCP 的基本可靠传输机制是**流水线传输**：

- **发送端**：连续、流水线式地发送数据，等待确认，并在超时后重传；
- **接收端**：进行差错检测，并对正确收到的数据进行确认。

> TCP 的可靠传输机制与前面讲的 GBN、SR 有相似之处，但它不是完全等同其中某一种，而是结合了二者的一些特点。

---

### TCP 序号基于字节，而不是报文段

TCP 是面向字节流的协议，序号按照**字节编号**，而不是按照报文段编号。

- 序号表示某个字节在整个字节流中的位置；
- 一个报文段可以携带多个字节，其序号通常是该报文段中**第一个数据字节**的编号；
- 接收方返回的 ACK 值表示：**下一个期望收到的字节序号**，而不是已经收到的最后一个字节序号。

例如，收到序号为 42 的 1 个字节后，确认号应为 43，表示：

- 第 42 个字节已经收到；
- 接下来期望收到第 43 个字节。

> **老师强调**：TCP 与 GBN、SR 的一个重要区别是，TCP 基于字节流而不是报文，序号代表字节流中的字节位置，而非报文序号`▶ 1:52:05`。

### TCP 的双向传输与捎带确认

TCP 连接是双向的，通信双方同时可以是发送方和接收方。因此，确认信息通常不必单独发送，而是可以放在反向传输的正常数据包中，这称为：

- **捎带确认（piggyback）**；
- 如果一方有数据要发给对方，就可以把 ACK 放在该数据报文段中；
- 如果没有数据要发送，才发送单独的 ACK 报文段。

> **老师强调**：TCP 支持双向传输，通信双方同时为发送方和接收方，通常把 ACK 捎带在正常数据包中；无数据发送时才单独发送 ACK 报文`▶ 1:52:05`。

### 字节序号与确认号示例

主机 A 向主机 B 发送仅包含一个字符 `C` 的报文段，随后 B 将该字符回送给 A。

#### 第一步：A 向 B 发送字符 `C`

```text
Seq = 42, ACK = 79, data = ‘C’
```

含义：

- A 发送的数据字节 `C` 的序号是 42；
- ACK = 79 表示 A 期望接下来收到 B 发送的第 79 个字节；
- 这个 ACK 是对 B 此前数据的确认，与本次发送的 `C` 无关。

> **老师强调**：字符 `C` 的报文序列号为 42，表示它是字节流中第 42 个字节；携带的 ACK 为 79，表示 A 期望收到 B 发送的第 79 个字节`▶ 1:54:16`。

#### 第二步：B 向 A 回复字符 `C`

```text
Seq = 79, ACK = 43, data = ‘C’
```

含义：

- B 发送的字符 `C` 在 B 到 A 方向的字节流中序号为 79；
- ACK = 43 表示 B 已经正确收到 A 发送的序号为 42 的字节；
- B 接下来期望收到 A 的第 43 个字节。

> B 正常回复第 79 个字符时，对应的 ACK 为 43，代表第 42 个字符已经接收完成，下一个期望接收第 43 个字符`▶ 1:55:11`。

#### 第三步：A 向 B 发送单独确认

```text
Seq = 43, ACK = 80
```

含义：

- A 已经收到 B 发送的序号为 79 的字节；
- ACK = 80 表示 A 接下来期望收到 B 的第 80 个字节；
- 该报文段不携带应用数据；
- Seq = 43 是 A 到 B 方向上下一个要发送的数据字节序号，由于本报文没有数据，该序号不会因为本次确认而消耗。

> A 收到 B 的字符后，如果没有新数据需要发送，也要返回 ACK；ACK 序号为 80，表示字符 79 已接收，下一个期望接收第 80 个字节，报文不携带实际应用数据`▶ 1:55:11`。

可以用下表整理：

| 方向 | Seq | ACK | 数据 | 含义 |
|---|---:|---:|---|---|
| A → B | 42 | 79 | `C` | A 发送第 42 字节，同时期望收到 B 的第 79 字节 |
| B → A | 79 | 43 | `C` | B 发送第 79 字节，并确认已收到 A 的第 42 字节 |
| A → B | 43 | 80 | 无 | A 确认已收到 B 的第 79 字节 |

### 乱序报文段的处理

TCP 标准没有明确规定接收方应如何处理乱序到达的报文段，因此可以有不同实现方式：

| 接收方处理方式 | 优点 | 缺点 |
|---|---|---|
| **不缓存乱序报文段** | 处理简单 | 效率较低，可能导致更多数据重传 |
| **缓存乱序报文段** | 效率更高，可以等待缺失字节补齐后一次性上交 | 接收方实现更复杂 |

实际 TCP 实现中，接收端通常会缓存已经正确收到、但尚未按序到达完整字节流边界的失序报文段。

> **老师强调**：TCP 协议本身没有规定是否缓存乱序报文，但实际实现的接收端通常会进行缓存`▶ 1:52:05`。

### 高度简化的 TCP 可靠传输机制

课件给出了一个只考虑可靠传输机制的简化 TCP 模型，可以分别从发送方和接收方理解。

#### 发送方机制

- **只维护一个重传定时器**：
  - 该定时器用于最早的、尚未被确认的报文段；
  - 这一点与 GBN 类似。
- **超时后的重发策略**：
  - 只重传最早的未确认报文段；
  - 不一次性重传所有未确认报文段；
  - 这一点又与 SR 类似，因为接收方可能已经缓存了失序报文段。

#### 接收方机制

- **采用累积确认**：
  - 只有正确、按序收到报文段后，才更新确认序号；
  - 如果收到的是乱序或重复报文段，则重复发送前一次的确认序号；
  - 这一点与 GBN 类似。
- **缓存失序报文段**：
  - 对已经正确收到但缺少前序字节的报文段进行缓存；
  - 这一点与 SR 类似。

> TCP 的简化可靠传输并不是纯粹的 GBN 或 SR：发送方只给最早未确认报文段设置一个定时器，类似 GBN；但超时后只重传最早未确认报文段，并且接收方缓存失序数据，又类似 SR。

### 与一般可靠传输方案的关系

本章内容承接前面的可靠数据传输协议演进：

1. **rdt 1.0**：假设信道完美；
2. **rdt 2.0、2.1、2.2**：处理信道出错但不丢包的情况；
3. **rdt 3.0**：同时处理出错和丢包；
4. **性能优化**：
   - 流水线传输；
   - 回退 N（GBN）；
   - 选择重传（SR）；
5. **TCP 可靠传输**：
   - 在不可靠 IP 服务上实现可靠传输；
   - 使用字节序号、累积确认、超时重传、流水线发送；
   - 在机制上兼有 GBN 和 SR 的特点。

TCP 如何具体实现超时、重传、流量控制以及拥塞控制等更详细内容，将在后续课程中讲解`▶ 1:56:18`。

## 术语

| 术语 | 解释 |
| --- | --- |
| RDT 3.0 | 在可能出错和丢包的信道上，发送方通过计时器超时重传数据包，并利用序号处理重复包的可靠传输协议。 |
| 超时重传 | 发送方在发出数据包后启动计时器，若限定时间内未收到确认，则重新发送该数据包。 |
| 停等协议 | 发送方每发送一个数据包后必须等待接收方确认，才能发送下一个数据包的协议。 |
| 信道利用率 | 发送方真正用于发送数据的时间占一个完整发送周期的比例，停等协议中为 (F/R)/(F/R+RTT)。 |
| 长肥网络 | 具有高带宽和长传播延迟的网络，停等协议在其中会产生极低的信道利用率。 |
| 流水线传输 | 允许发送方在收到确认前连续发送多个数据包，使信道中同时存在多个未确认数据包。 |
| 滑动窗口机制 | 通过可循环使用的有限序号和随发送、确认向前移动的窗口，限制并管理连续发送的数据量。 |
| 回退 N（GBN） | 发送方最多保留 N 个未确认包，接收方采用累积确认且不缓存乱序包，超时后重传所有未确认包。 |
| 累积确认 | 一个确认号表示该序号之前的所有数据包都已被正确接收。 |
| 选择重传（SR） | 接收方逐个确认并缓存乱序数据包，发送方为每个包维护计时器，超时后只重传对应数据包。 |
| 接收窗口 | 接收方当前允许接收的序号范围，用于判断接收、缓存、确认或忽略到达的数据包。 |
| TCP 字节序号 | TCP 将字节流中的字节位置作为序号，而不是为报文段单独编号。 |
| 捎带确认 | TCP 在双向传输时把 ACK 信息放在携带应用数据的正常报文段中返回。 |
| TTL | IP 数据报中的生命值字段，每经过一跳递减，减到零后数据包被丢弃。 |
