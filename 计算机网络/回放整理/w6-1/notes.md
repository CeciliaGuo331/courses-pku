## 1. 传输层的位置与端到端服务

> 课件 第三讲_传输层(1)基本概念、UDP.pdf 第 3–7 页 · 讲解从 `04:38` 开始

### 传输层的位置

传输层位于应用层与网络层之间，基于网络层提供的服务，向不同主机上的应用进程提供通信服务。从层次结构看，两端主机中的传输层在逻辑上构成一条端到端的传输通道，中间路由器通常只涉及网络层及以下层次，不参与传输层处理。

### 双重屏蔽复杂性

传输层在分层体系中起到双向隔离的作用：

- **从网络的角度：屏蔽应用复杂性**
  - 因特网的设计原则是：网络本身不需要理解或适配各种应用程序。
  - 对网络层、数据链路层和物理层而言，无需考虑上层应用的多样性与复杂特性，从而大幅简化底层网络设计`▶ 05:06`。

- **从应用的角度：屏蔽底层网络复杂性**
  - 传输层向应用提供“进程之间通信”的抽象：运行在不同终端上的应用进程仿佛直接连接在一起。
  - 应用程序只需使用传输层提供的接口，就能完成跨主机通信，无需感知多跳转发、底层链路等网络细节`▶ 05:06`。

### Socket：应用层与传输层的接口

可以把应用程序和网络之间想象成存在一扇“门”：

1. 发送进程需要发送报文时，把报文推到门外；
2. 门外的运输设施（因特网）负责把报文送到接收进程的门口；
3. 接收进程需要接收报文时，打开门即可收到报文。

在 TCP/IP 网络中，这扇“门”称为 **套接字（socket）**：

- 它是应用层与传输层之间的接口；
- 也是应用程序与网络之间的 API；
- 应用程序所有收发的数据都需要通过 socket 进出`▶ 06:36`。

### 网络层与传输层的分工

| 层次 | 通信对象 | 主要职责 |
|---|---|---|
| 网络层 | 主机与主机之间 | 提供两台主机之间的通信接口，可能经过多跳链路传输数据 |
| 传输层 | 应用进程与应用进程之间 | 调用网络层接口，并在其基础上进行必要增强，提供端到端进程通信 |

网络层负责跨多跳的主机间传输；传输层则封装这些细节，为上层提供端到端的应用进程通信管道`▶ 07:07`。

### 快递类比

课件用“清华学生给北大学生寄快递”类比两类层次的关系：

- **主机** = 大学；
- **应用程序** = 学生；
- **消息** = 装在信封中的信件；
- **传输层** = 从发送者手中取走快递，并交给对应接收者；
- **网络层** = 两所学校快递站之间的运输，距离远时可能经过多跳中转。

传输层关心的是从发件人到收件人的端到端投递，不关心中间具体运输环节；网络层负责学校之间的运输和中转`▶ 07:57`。

> 老师提到，计算机网络的很多设计借鉴现实生活中简单高效的传输方式，目的是降低传输开销，而不是刻意设计得复杂晦涩`▶ 07:57`。

### Internet 网络层的尽力而为服务

Internet 的网络层基于 IP 协议，提供 **尽力而为（best-effort）** 服务：网络会尽最大努力在终端之间交付分组，但不提供任何承诺`▶ 10:07`。

具体来说，网络层：

- 不保证交付成功；
- 不保证按序交付；
- 不保证数据完整；
- 不保证延迟；
- 不保证带宽等性能指标。

### 传输层的“有所为、有所不为”

由于网络层能力较弱，传输层需要在其基础上进行功能增强，但并不能解决所有问题。

**传输层可以做到：**

- 通过差错恢复机制处理数据丢失或损坏；
- 通过重排序机制保证数据按发送顺序交付；
- 因此可以向应用提供可靠、按序的交付服务。

**传输层无法做到：**

- 无法提供确定的延迟保证；
- 无法提供确定的带宽保证。

> **老师强调**：传输层的设计遵循“有所为、有所不为”的原则；TCP 及其衍生协议通常能提供可靠、按序交付，但难以保障延迟、带宽等性能指标`▶ 10:07 · 11:47`。

### UDP 与 TCP：Internet 的两种传输层协议

传统 Internet 在传输层提供两种协议供应用层选择：UDP 和 TCP。二者的核心区别在于：在能力较弱的网络层之上，额外提供了哪些保障`▶ 12:24`。

#### UDP：最低限度的传输服务

UDP 只对网络层接口进行最简单的封装，主要功能包括：

- 将网络层的“主机到主机”数据交付扩展为“进程到进程”的数据交付；
- 发送时从多个进程收集数据并交给网络层转发；
- 接收时识别数据所属进程并分发给对应进程；
- 发送、接收数据的单位是 **数据报（datagram）**，应用层需要处理报文边界；
- 提供报文检错能力。

UDP 几乎不提供额外的可靠性保障`▶ 12:24`。

#### TCP：最低限度服务 + 增强服务

TCP 在 UDP 类似的基本进程交付能力之上，进一步提供增强服务：

- 以 **字节流** 的形式发送、接收数据，应用层感受不到报文边界；
- 提供可靠数据传输；
- 提供流量控制；
- 提供拥塞控制。

### UDP 与 TCP 对比

| 对比项 | UDP | TCP |
|---|---|---|
| 服务定位 | 最低限度传输服务 | 最低限度服务 + 增强服务 |
| 交付范围 | 进程到进程 | 进程到进程 |
| 数据单位 | 数据报 | 字节流 |
| 报文边界 | 保留，应用层需处理 | 应用层感受不到报文边界 |
| 可靠传输 | 不提供 | 提供 |
| 流量控制 | 不提供 | 提供 |
| 拥塞控制 | 不提供 | 提供 |
| 检错 | 提供报文检错 | 提供，并配合可靠性机制 |

新的传输层协议（如 QUIC）也借鉴了 UDP 和 TCP 的基本思想，但本章先围绕这两种经典协议展开`▶ 11:47`。

## 2. 套接字、端口号与端口分配

> 课件 第三讲_传输层(1)基本概念、UDP.pdf 第 8–9 页 · 讲解从 `13:47` 开始

### 套接字的标识与端口号

套接字（Socket）是应用程序对外进行网络交互的接口，需要被唯一标识。标识一个套接字的方式是 **IP 地址 + 端口号**。由于单台主机的 IP 地址通常长期不变，因此核心需要关注的是端口号`▶ 13:47`。

关于端口号：

- 每个套接字在本地都关联一个端口号。
- 端口号是一个 **16 比特** 的整数，取值范围为 **0～65535**`▶ 13:47`。
- 端口号是套接字标识的一部分。

### 端口号的分类

按照使用约定，端口号划分为不同范围，其中 **熟知端口（well-known port）** 为 **0～1023**，由公共域协议使用，例如：

| 协议 | 默认端口号 |
|------|-----------|
| HTTP | 80 |
| SSH | 22 |

访问服务时如果不填写端口号，就使用对应协议的默认端口；如果服务使用非默认端口，则需要在地址后加冒号手动指定。以 SSH 为例，不指定端口时默认使用 22，也可以通过命令行的 `-p` 参数自定义端口`▶ 13:47`。

> **老师强调**：0～1023 是熟知端口，HTTP 为 80、SSH 为 22，这些常见的对应关系需要记住。

### 报文段中的端口号字段

UDP 和 TCP 的报文段头部都携带两个端口号字段，用于识别报文的来源与目标`▶ 16:29`：

- **源端口号（source port #）**：与发送进程关联的本地端口号。
- **目的端口号（dest port #）**：与接收进程关联的本地端口号。

报文段头部的简化结构如下：

```text
┌──────────────┬──────────────┬─────────────────────┐
│ source port #│ dest port #  │ other header fields │
├──────────────┴──────────────┴─────────────────────┤
│            application data (message)              │
└────────────────────────────────────────────────────┘
              （前两个端口字段合计 32 bits）
```

### 套接字端口的分配方式

创建套接字时，端口号有两种分配方式。

#### 1. 自动分配

- 创建套接字时**不指定**端口号，由操作系统负责分配。
- **客户端通常采用这种方式**。
- 例如 TCP 套接字首次调用 `connect()` 时，如果尚未分配端口，系统会从约 **49000 多到 65535** 的范围中为该套接字分配一个端口`▶ 16:56`。

#### 2. 使用指定端口号创建套接字

- 创建套接字时**显式指定**端口号，例如创建套接字后通过 `bind` 函数绑定端口`▶ 16:56`。
- 实现公共域协议的**服务器**应当分配保留端口号（**0～1023**）。
- **服务器通常采用这种方式**，以便客户端能够通过熟知的默认端口访问到服务。

> **老师提示**：做 lab 一的同学可以熟悉 `bind` 这个接口`▶ 16:56`。

两种方式的对比如下：

| 方式 | 是否指定端口 | 典型使用者 | 说明 |
|------|-------------|-----------|------|
| 自动分配 | 否，由操作系统分配 | 客户端 | 如 `connect()` 时由系统从高端口范围分配 |
| 指定端口 | 是，通过 `bind` 等绑定 | 服务器 | 公共协议服务器应使用 0～1023 的保留端口 |

## 3. 多路复用与分用

> 课件 第三讲_传输层(1)基本概念、UDP.pdf 第 10–11 页 · 讲解从 `17:54` 开始

### 多路复用与分用的基本问题

传输层需要实现**进程到进程（process-to-process）的数据交付**。一台主机上可能同时有多个应用进程，每个进程通过套接字（socket）与传输层交互，因此传输层必须解决一个基础问题：

> **如何通过端口号，将数据对应到正确的套接字？**

无论使用 **UDP** 还是 **TCP**，都要依靠**多路复用与分用**来完成进程之间的数据交付`▶ 17:54`。

### 发送端：多路复用

**多路复用（multiplexing）**发生在发送端：

1. 多个应用进程通过各自的套接字把数据交给传输层；
2. 传输层从多个套接字收集数据；
3. 传输层在报文段中加入套接字标识等传输层首部信息；
4. 再以统一格式交给网络层发送。

可以结合下图理解：主机中的进程 P1、P2 等分别通过套接字向传输层交付数据，传输层汇总后交给网络层。

> 快递类比：复用就像快递员把一个学校里的大量信件收集起来、打包并装车，统一交给物流系统发送；传输层则是把来自多个套接字的报文收集后统一交给网络层`▶ 19:29`。

### 接收端：分用

**分用（demultiplexing）**发生在接收端：

1. 网络层把收到的数据交给传输层；
2. 传输层检查报文段中的套接字标识，尤其是端口号；
3. 根据标识判断数据属于哪个应用进程；
4. 将报文段中的数据交付给正确的套接字。

可以结合下图理解：接收端主机中可能有 P3、P4 等多个进程，传输层必须把收到的数据分别送到对应的套接字。

> 快递类比：分用就像快递员根据包裹上的地址和姓名找到对应的收件人，并把信件交付给他；接收方传输层则根据报文段中的套接字标识，将报文交给正确的套接字`▶ 19:29`。

### 为什么报文段中必须包含套接字标识

| 现实邮政系统 | 传输层 |
|---|---|
| 每个收信人应有地址和姓名，作为唯一标识 | 主机中的每个套接字都需要一个唯一标识 |
| 信封上写有收信人的地址和姓名 | 报文段首部中包含接收套接字的标识 |
| 寄件时快递员收集邮件并交给物流系统 | 发送方传输层把套接字标识放入报文段，再交给网络层 |
| 收件时根据地址和姓名交付给收信人 | 接收方传输层根据套接字标识把报文段交付给正确套接字 |

因此，端口号等套接字标识是实现复用和分用的关键：发送端依靠它标明数据来自哪个套接字、要送往哪个套接字；接收端依靠它区分不同进程的数据，从而完成端到端的进程通信。

> **老师强调**：复用和分用是传输层的核心功能术语。复用是从多个套接字收集数据并统一交给网络层；分用是从网络层收到数据后，根据端口号区分归属并交付给对应套接字`▶ 18:41`。

## 4. UDP与TCP的套接字标识

> 课件 第三讲_传输层(1)基本概念、UDP.pdf 第 12–18 页 · 讲解从 `21:20` 开始

### UDP 套接字的标识与报文交付

UDP 套接字使用 **`<IP 地址, 端口号>` 二元组**进行标识`▶ 21:20`。

接收方传输层收到一个 UDP 报文段后的处理过程：

1. 网络层先过滤掉目的 IP 不是本机的报文；到达传输层时，只需检查报文段中的**目的端口号**，将报文段交付到具有该端口号的套接字`▶ 21:20`。
2. **`<目的 IP 地址, 目的端口号>` 相同的 UDP 报文段被交付给同一个套接字，与 `<源 IP 地址, 源端口号>` 无关**——也就是说，来自不同客户的报文只要发往同一个目的端口，都会进入服务器的同一个 UDP 套接字`▶ 21:20`。
3. 报文段中的 `<源 IP 地址, 源端口号>` 并非无用：接收进程需要依据它判断发送方身份，并据此发送响应报文（回复时把对方的源 IP、源端口作为目的 IP、目的端口）`▶ 21:20`。

> **老师强调**：UDP 的核心交付逻辑是"目的 IP + 目的端口"唯一确定报文归属的套接字；源 IP、源端口不参与套接字的区分，但用于回复`▶ 21:20 · 22:54`。

#### 课件示例（第 13 页）

- 服务器 P1 创建 `DatagramSocket serverSocket = new DatagramSocket(6428);`，在端口 **6428** 上等待。
- 客户 P4 创建两个套接字：`mySocket1`（端口 **5775**）和 `mySocket2`（端口 **9157**）。
- P4 → P1：源端口 9157，目的端口 6428；P1 回复时：源端口 6428，目的端口 9157。
- P4 另一个套接字与 P1 通信：源端口 5775，目的端口 6428；回复时目的端口为 5775。
- 无论客户是哪个 IP、使用哪个源端口，只要目的端口是 6428，报文都交付给 P1 上的同一个 `serverSocket`。

（讲解中老师口述的端口号 6248/6478 为口误，课件中服务器端口为 6428`▶ 22:54`。）

---

### TCP 套接字：监听套接字与连接套接字

TCP 是面向连接的协议，一个 TCP 服务器为了同时服务很多客户，使用**两种套接字**`▶ 24:28`：

| 类型 | 作用 | 端口号 |
|---|---|---|
| **监听套接字**（listening socket） | 服务器平时在它上面等待客户的连接请求 | 具有众所周知的端口号（如 80） |
| **连接套接字**（connection socket） | 服务器 `accept` 接收连接请求后，由传输层创建；客户端实际与它通信；每个连接套接字只与一个客户通信 | **仍使用原监听套接字的端口号** |

所有连接套接字复用监听端口号，因此仅靠"目的 IP + 目的端口"无法区分它们——同一服务器上可能存在大量目的 IP、目的端口完全相同的连接套接字`▶ 25:32`。

#### 四元组标识

连接套接字使用 **`<源 IP 地址, 目的 IP 地址, 源端口号, 目的端口号>` 四元组**进行标识，服务器依据四元组将 TCP 报文段交付到正确的连接套接字。对服务器而言，四元组具体为：

- 源 IP 地址 = 客户 IP 地址
- 源端口号 = 客户套接字端口号
- 目的 IP 地址 = 服务器 IP 地址
- 目的端口号 = 服务器监听套接字的端口号

> **老师强调**：如果像 UDP 那样只用目的 IP + 目的端口两个字段，无法确定数据包属于哪个 socket；必须同时匹配源 IP 与源端口`▶ 25:32 · 26:22`。

#### 课件示例（第 15 页）

服务器 IP 地址为 B，监听 80 端口；主机 A、C 分别与它建立连接：

- 主机 A（IP A）的进程 P3，端口 9157：报文 `源 A,9157 → 目的 B,80`，回程 `源 B,80 → 目的 A,9157`。
- 主机 C（IP C）的进程 P3，端口 5775：报文 `源 C,5775 → 目的 B,80`。
- 主机 C 的进程 P4，端口 9157：报文 `源 C,9157 → 目的 B,80`。

这三个报文的**目的 IP、目的端口都是 B、80**，仅靠两个字段无法区分归属；服务器必须再看源 IP（A 还是 C）和源端口（9157 还是 5775），才能交付给对应的连接套接字`▶ 26:22`。注意 C 上两个不同进程使用不同端口，因此即使 IP 相同也能区分。

---

### 报文边界：UDP 报文 vs TCP 字节流

TCP 与 UDP 的另一显著区别是**传输粒度**和**报文边界的可见性**，该差异源于二者套接字实现方式的不同`▶ 28:19`。

| | UDP | TCP |
|---|---|---|
| 传输单位 | 以**报文**为单位传输 | **字节流**传输 |
| 应用能否感知报文边界 | 能 | 不能 |
| 处理方式 | 对每个报文独立发送，原样、依次交付 | 可能划分、合并报文 |
| 接收方每次读取 | `receive()`/`recv` 完整收到**一个报文**，不合并、不拆分 | `recv` 读出**若干字节**，与发送方写入次数无对应关系 |
| 套接字与远端的关系 | 单个套接字可与多个远端套接字通信 | 每个连接套接字只对应一个远端 |

**UDP 侧的原因**：单个套接字可与多个远端套接字通信，来自不同远端的数据包没有合并的依据，传输层只能原样、依次地把每个数据包交付给应用进程；应用每次调用 `receive()` 都会完整收到一个数据包，交付过程中既不会合并也不会拆分，因此应用可以感知报文边界`▶ 28:59`。

**TCP 侧的原因**：TCP 为每个远端连接单独使用一个连接套接字，不同连接的数据相互隔离；但在同一连接内部，数据在传输过程中可能被 TCP 划分或合并，应用只能看到处理后的字节流，无法感知原始报文的边界`▶ 30:44`。

---

### 本节小结

- **UDP 套接字**：用 `<IP 地址, 端口号>` 二元组标识；服务器用**一个套接字**服务所有客户；面向数据报文，应用可感知报文边界`▶ 31:53`。
- **TCP 套接字**：连接套接字用 `<源 IP, 目的 IP, 源端口, 目的端口>` 四元组标识；服务器用**一个监听套接字 + 多个连接套接字**服务多个客户，每个连接套接字服务一个客户；基于字节流，应用无法感知报文边界`▶ 32:28`。
- 标识方式的不同（二元组 vs 四元组）根源在于 TCP"监听套接字 + 每连接一个套接字"的模式，也进一步导致了二者在报文边界可见性上的差异`▶ 32:28`。

## 5. UDP服务、报文格式与校验和

> 课件 第三讲_传输层(1)基本概念、UDP.pdf 第 19–26 页 · 讲解从 `32:56` 开始

### UDP 概述

网络层提供的是尽最大努力服务（best-effort service）：尽最大努力将数据包交付到目的主机，但不保证投递的可靠性和顺序，也不保证带宽及延迟要求。

UDP 在网络层之上做了最简单的封装，提供的服务包括：
- **网络层 + 多路复用与分解**：把网络层"主机到主机"的数据交付，扩展为传输层"进程到进程"的数据交付。
- **报文完整性检查（可选）**：检测出错报文并丢弃。

UDP 的实现由两部分组成：
- 复用和分用：**必须实现**；
- 报文检错：**可选实现**。

> **老师强调**：UDP 仅对网络层做最简单的封装，必须实现复用与分用，报文错误检测是可选的；正因功能简单，UDP 报文首部只有 4 个字段`▶ 32:56`。

### UDP 报文格式

UDP 报文由**报头**和**载荷（payload）**两部分组成：报头携带协议处理所需信息，载荷携带上层应用数据。

报头共 8 字节，4 个字段各占 16 比特：

| 字段 | 长度 | 作用 |
|---|---|---|
| 源端口号（source port #） | 16 bit | 用于复用/分用，标识发送进程 |
| 目的端口号（dest port #） | 16 bit | 用于复用/分用，标识接收进程 |
| 报文长度（length） | 16 bit | 指示整个 UDP 报文的字节数（首部 + 数据） |
| 校验和（checksum） | 16 bit | 检测报文传输过程中是否出错 |

报文结构示意：

```text
 32 bits
┌───────────────────┬───────────────────┐
│  source port #    │   dest port #     │
├───────────────────┼───────────────────┤
│      length       │     checksum      │
└───────────────────┴───────────────────┘
│        Application data (message)       │
```

> **老师强调**：源端口号和目的端口号各 16 比特，合起来正好 32 比特；长度字段以字节数表示报文长度；4 个字段之后就是上层应用数据`▶ 33:55`。

### UDP 校验和的基本思想

校验和字段的作用是对传输的报文段进行**检错**，但并非所有错误都能检出。

- **发送方**：
  1. 把报文段看成由若干 16 比特整数组成的序列；
  2. 对这些整数计算校验和；
  3. 将结果填入 UDP 报文段的 checksum 字段。
- **接收方**：
  1. 对收到的报文段执行相同的计算；
  2. 将计算结果与报文中 checksum 字段比较：
     - 不相等：报文段一定有错误；
     - 相等：认为没有检测到错误，但仍可能存在漏检。

> **老师强调**：接收方比较结果不相等则确认传输出错；相等只是"未检测到错误"，是否存在隐藏错误要交由应用层进一步判断`▶ 34:31`。

### 校验和的计算规则

具体步骤：

1. **划分**：将数据划分为一系列 16 比特整数。
2. **求和（带回卷，one's complement sum）**：
   - 每次把一个 16 比特整数与当前和（sum）相加；
   - 若相加结果最高位产生进位（16 比特溢出），就把溢出的 `1` 加回到低位 16 比特（wraparound）；等价地，把相加结果右移 16 位得到进位，再把该进位加回求和结果。
3. **取反**：对最终的 16 比特和逐位取反，得到校验和。

课件示例（两个 16 比特整数相加）：

```text
  1111 0011 0011 0011 0
+ 1110 1010 1010 1010 1
= 1101 1101 1101 1101 1   ← 最高位产生进位
                          ↓ 将进位 1 回卷加回低位
  1101 1101 1101 1110 0   ← wraparound 后的 sum
  0010 0010 0010 0001 1   ← 取反得到 checksum
```

> **老师强调**：发生溢出时一定要把溢出的 1 回加到低位 16 比特，最后再对求和结果取反`▶ 36:44`。

### 校验和的计算范围与伪首部

UDP 校验和的计算对象包括三部分：

1. **UDP 伪首部（pseudo header）**；
2. **UDP 首部**（4 个字段）；
3. **应用数据**。

伪首部的信息取自 IP 报头，主要包括：

| 伪首部内容 | 长度（IPv4） | 说明 |
|---|---|---|
| 源 IP 地址 | 32 bit | 取自 IP 头 |
| 目的 IP 地址 | 32 bit | 取自 IP 头 |
| 协议号 | 8 bit | UDP 取值 **17**；其余位填 0 |
| UDP 报文段总长度 | 16 bit | UDP 首部 + 数据的总长度 |

计算时的规则：
- checksum 字段先填 **0**，不参与求和；
- 协议字段中 8 比特协议号之外的部分填充全 0；
- 若数据部分长度不是 16 比特的整数倍，在末尾补 0 凑齐后再参与计算；
- 校验时，接收方对"UDP 报文（含校验和）+ 伪首部"整体按同样规则求和，若结果为 **0xFFFF**，则认为没有检测到错误。

> **老师强调**：协议号 17 代表 UDP；计算时校验和字段先置 0；数据不是 16 比特整数倍时末尾补 0`▶ 39:41`。

**为什么要包含伪首部？** 计算校验和时加入源/目的 IP 地址等信息，可以检测 IP 层是否把 UDP 报文投递到了错误的主机，避免因 IP 地址错误等造成误投递。

> **老师强调的计算示例**：伪首部含源 IP、目的 IP、全 0 填充、协议号 17；UDP 总长度为 15 字节（首部 8 字节 + 数据 7 字节），数据末尾补 0 凑成 16 比特；按 16 比特为单位依次求和，进位回卷，最后取反得到校验和`▶ 41:05`。

### 校验和的可选性与局限性

- UDP 校验和的使用是**可选**的；若不计算校验和，checksum 字段填入 `0`。
- 校验和仍可能**漏检**错误：例如两个 16 位整数恰好在同一个比特位都发生 0↔1 翻转，它们对求和结果的影响相互抵消，总和不变，错误无法被发现。
- 对这类漏检错误，UDP 不做处理，直接把数据交给应用层，由应用层负责发现和处理错误。

> **老师强调**：两个 16 位分组在同一比特位同时发生翻转，会导致求和结果不变而漏检；此时由应用层负责检测处理`▶ 42:40`。

### 为什么仍然使用校验和

尽管校验和存在漏检可能，但它被广泛使用，原因包括：

- **计算开销小**：只需简单的加法和取反，实现代价极低；
- **到达传输层的错误概率非常小**：物理层、数据链路层通常已经具备检错/纠错能力，过滤掉了网络传输过程中的大部分比特反转错误；
- **剩余错误多属小概率事件**：能到达传输层的错误一般来自主机软件 bug 或硬件故障，没有必要为这类事件设计复杂的检错纠错方案，校验和已经足够。

## 6. UDP缓冲区与适用应用

> 课件 第三讲_传输层(1)基本概念、UDP.pdf 第 27–29 页 · 讲解从 `45:26` 开始

### UDP 缓冲区：典型端系统实现

UDP 协议本身对收发端的缓冲区实现没有严格规定，但在 Linux、Windows 等主流操作系统中，通常采用"**无发送缓冲区、有接收缓冲区**"的实现方式`▶ 45:26`。

#### 发送方：无发送缓冲区

- 应用程序调用 `send` 后，通过系统调用进入内核`▶ 45:26`。
- UDP 从应用层获取数据，加上 UDP 头部后，**直接交给网络层**处理，不会在传输层缓存。
- 数据最终"穿透"到网卡缓冲区排队发送`▶ 45:26`。
- 长消息的**分片与缓冲依赖网络层、链路层**来提供，UDP 自身不负责。

#### 接收方：每个 socket 一个接收缓冲区

- 接收端必须为每个 socket 设置独立的接收缓冲区：因为同一个 socket 在同一时刻可能收到来自**多个不同主机（发送方）**的报文`▶ 46:43`。
- 传输层收到网络层交付的报文后进行**分用**，识别报文所属的 socket，并放入对应缓冲区`▶ 46:43`。
- 每次调用 `receive` 只从缓冲区中取出**一个具有完整边界的报文**，不会读到该报文之后的内容，从而避免混入其他发送方的报文`▶ 46:43`。
- 因此，一次接收得到一个报文，下一次接收可能来自另一个发送方；**应用层可以明确感知到报文边界**（保留报文边界，面向报文）。

```text
发送方                              接收方
process ──► UDP(无发送缓冲区)       process
              │加头部后直接          ▲ receive 每次取一个完整报文
              ▼ 交给网络层          │
socket ───► internet ──────►  socket(每个socket一个接收缓冲区)
                                缓冲区中存放来自不同发送方的报文
```

### 为什么需要 UDP

UDP 功能简单，带来三方面优势：

- **应用可以尽可能快地发送报文**
  - 无建立连接的延迟（无需握手）。
  - 不限制发送速率：不进行拥塞控制和流量控制。
- **报头开销小**：UDP 头部仅 8 字节。
- **协议处理简单**：实现开销低、传输性能高`▶ 47:44`。

### UDP 适合哪些应用

| 应用类型 | 典型例子 | 原因 |
|---|---|---|
| 容忍丢包但对延迟敏感 | 流媒体 | 数据量大，对丢包不敏感；人眼每秒最多识别几十帧画面，偶尔丢失少量数据包完全可接受`▶ 48:40` |
| 以单次请求/响应为主 | DNS | 请求或响应丢失后可再次重发，只要最终收到一次响应即可正常工作；相比服务器维护大量连接，开销低很多`▶ 48:58` |
| 需要可靠传输但仍想用 UDP | 应用层自行实现可靠性 | 在 UDP 基础上由应用层实现所需的可靠性功能，无需使用设计复杂的 TCP；具体可靠传输方法后续课程介绍`▶ 49:34` |

> **老师强调**：流媒体之所以用 UDP，是因为它"容忍丢包、对延迟敏感"；而 DNS 这类单次请求/响应应用，丢了重发即可，UDP 还能避免服务器维护大量连接的开销。

### 本章小结

- **传输层基本概念**
  - 服务：进程到进程的传输。
  - 实体：套接字（socket）。
  - 协议：UDP 与 TCP。
  - 实现：通过**多路复用与分用**实现进程到进程传输。
- **UDP**：可理解为"网络层 + 多路复用与分用"，仅在网络层服务之上增加了端口机制。
  - 校验和：可选（用于差错检测）。
- **阅读**：教材 3.1、3.2、3.3 节。

## 7. TCP服务模型与可靠传输问题引入

> 课件 第三讲_传输层(2)可靠传输.pdf 第 2–9 页 · 讲解从 `50:00` 开始

### TCP 服务模型

TCP 在一对通信进程之间提供一条**理想的字节流管道**。具体特性如下：

- **点到点通信**：一条 TCP 连接仅涉及一对 socket，通道只对这一对 socket 开放，其他 socket 无法干涉通道内的数据。这与 UDP 不同——UDP 的一个 socket 可以同时与多个 socket 通信`▶ 50:34`。
- **全双工**：连接两端可以同时双向传输数据，双方无需轮流等待`▶ 51:28`。
- **可靠、有序的字节流**：只要底层网络没有发生故障，发送的所有字节最终都会交付给接收方，且交付顺序与发送顺序完全一致`▶ 51:28`。
- **不保留报文边界**：应用程序多次写入的数据在接收方看来是连续的字节流，TCP 不保留每次写入的报文分界。

为支持上述服务，通信双方在发送数据前需要**建立连接**，即建立本次通信所需的状态，包括套接字、缓存、连接变量等。

TCP 发送/接收数据的基本过程：

```text
应用层写数据 → TCP 发送缓存（send buffer）→ 封装成报文段 → 网络
网络 → 报文段 → TCP 接收缓存（receive buffer）→ 应用层读数据
```

### 实现服务所需的机制

| 机制 | 作用 |
|---|---|
| 建立连接 | 双方建立通信所需的状态（套接字、缓存、变量等） |
| 可靠数据传输 | 通过流水线式发送、报文段检错、丢失重传等保证数据正确到达 |
| 流量控制 | 限制发送方速率，避免接收方缓存溢出 |
| 拥塞控制 | 限制发送方速率，避免向网络注入过多数据而造成拥塞 |

其中流量控制和拥塞控制都是对发送方速率的约束：前者保护接收方，后者保护网络`▶ 51:28`。本节首先讨论其中的**可靠传输**问题`▶ 52:42`。

### 问题背景：底层信道不可靠

可靠传输的前提是：网络核心（底层通信信道）是**不可靠信道**。其典型表现有三类：

1. **数据损坏（比特错误）**：传输过程中某个比特发生翻转，例如 `0` 变成 `1`。比特通常以电信号或光信号表示，硬件损坏或强电磁场、电磁波等外界信号干扰都可能导致比特反转`▶ 52:42 · 53:29`。
2. **数据报丢失**：数据包在网络中被丢弃，接收方收不到。
3. **数据报乱序**：数据报可能沿多条路径传输，到达接收方的顺序与发送顺序不同，例如发送顺序为 1、2、3，接收顺序可能为 2、3、1`▶ 53:29`。

可靠传输机制正是针对这三类问题的"反向设计"：即使底层信道会出错、丢失、乱序，最终仍要向上层提供完整、正确、有序的数据传送`▶ 1:04:35`。

### 可靠传输是跨层次的通用问题

可靠传输并非 TCP（传输层）独有，在网络的各个层次和多种技术中都需要考虑：

- **OSI 链路层**：链路层本身提供可靠传输功能。
- **基于 UDP 的应用层协议**：UDP 不保证可靠，应用层可自行实现。例如 DNS 通过简单重传应对丢包；TFTP 在 UDP 之上实现了数据块丢失后的恢复机制`▶ 1:05:09`。
- **5G 通信**：在物理层和链路层提供一定的可靠性保障`▶ 1:05:09`。
- **时延敏感网络（TSN）**：在网络层及以下保障传输时延。像工业控制、远程机器人手术这类场景，一旦出现时延或因丢包引发重传，可能造成灾难性后果，因此对可靠性要求极高`▶ 1:05:09`。
- **远程直接内存访问（RDMA）**：借助可靠传输机制，使远程内存访问的延迟与本地内存访问处于同一数量级`▶ 1:05:09`。

> **老师强调**：各类可靠传输方案之间存在共性。课程会先介绍可靠传输的共性机制，再讲解 TCP 可靠传输的特殊设计`▶ 1:05:09`。

### 本课程对不可靠信道的假设

**考虑的情况：**

- 通信链路会丢失信息（丢包）；
- 消息会发生乱序（多路径传输导致）；
- 通信数据在传输过程中可能出现随机的、偶发的错误，但这类错误能够通过校验技术检测出来。

**不考虑的情况：**

- 数据在通信中遭到**有意的篡改**，且这种篡改无法通过校验检测；
- 收到的数据并非来自真正的发送方，而是由第三方伪造。

> **老师强调**：故意篡改、伪造数据等有意攻击属于**信息安全与密码学**的研究范畴，本课程的可靠传输不处理这类问题`▶ 1:08:25`。

## 8. 可靠传输的形式化接口与分析方法

> 课件 第三讲_传输层(2)可靠传输.pdf 第 10–15 页 · 讲解从 `1:09:53` 开始

### 可靠传输的形式化模型

可靠传输问题的基本场景由三部分组成：发送方、接收方，以及连接二者的**不可靠信道**。可靠传输机制构建在不可靠信道之上，分别位于发送方和接收方两端，目的是在不可靠的底层通信基础上向上层提供可靠的数据传输服务`▶ 1:09:53`。

数据的实际流向为：

- **发送方向**：发送方上层应用的数据先交给可靠传输协议（发送方）处理，再通过 `udt_send()` 交付底层不可靠信道传输。
- **接收方向**：接收方从不可靠信道收到数据后，先由可靠传输协议（接收方）进行校验、修复、排序等处理，再通过 `deliver_data()` 交付上层应用`▶ 1:10:33 · 1:11:16`。

```text
发送方上层应用                         接收方上层应用
      │                                     ▲
      │ rdt_send()                  deliver_data()
      ▼                                     │
可靠传输协议（发送方）            可靠传输协议（接收方）
      │                                     ▲
      │ udt_send()                    rdt_rcv()
      ▼                                     │
        ────────── 不可靠信道 ──────────
```

### 四个接口函数

可靠传输协议在收发双方各有 1 个面向上层应用的接口函数和 1 个与底层不可靠信道交互的函数，共涉及 4 个函数：

| 函数 | 调用者 | 作用 |
| --- | --- | --- |
| `rdt_send()` | 上层应用程序 | 上层调用该函数，将待发送数据交给可靠传输协议的发送方处理 |
| `udt_send()` | 可靠传输协议（发送方） | 发送方完成处理后调用，将数据包交给不可靠信道传输 |
| `rdt_rcv()` | 下层不可靠信道 | 当信道上有数据到达时自动调用，将数据交给可靠传输协议的接收方处理 |
| `deliver_data()` | 可靠传输协议（接收方） | 接收方完成校验、修复、排序后调用，将数据交付上层应用 |

> 课件中写作 `udt_send()`，其中 udt 表示 **unreliable data transfer**；老师讲解时口述为 "udp_send"，指的是同一个函数，含义都是将数据交给不可靠信道`▶ 1:11:16`。

从协议设计者的角度，可以把这 4 个函数分成两类：

- **由协议自身主动调用的函数**：`udt_send()` 和 `deliver_data()`。设计协议时需要决定在什么时机调用它们。
- **由协议自身实现、供外部调用的函数**：`rdt_send()` 和 `rdt_rcv()`。前者处理上层传来的待发送数据，后者处理底层到达的数据；在这两个函数的实现过程中，往往会触发前两个函数的调用`▶ 1:13:07`。

### 由简到繁的场景递进

可靠传输涉及多种不可靠情况，以及收发双方之间复杂的交互，直接设计完整协议难度较大。因此课程采用**逐步增强**的思路：先在最简单的信道假设下达成可靠性，再逐步弱化信道条件、加入性能优化`▶ 1:14:15`。

| 阶段 | 信道假设 | 对应协议 |
| --- | --- | --- |
| 场景 1 | 不出错，也不丢包（完美信道） | rdt 1.0 |
| 场景 2 | 可能出错，但不丢包 | rdt 2.0、rdt 2.1、rdt 2.2 |
| 场景 3 | 可能出错，也可能丢包 | rdt 3.0 |
| 性能优化 | 在保证可靠性的基础上提高效率，并处理乱序 | 流水线传输、GBN、SR |

整体路线为：

1. 先假设信道完全可靠；
2. 引入比特出错的情况；
3. 再引入丢包；
4. 解决可靠性之后，进行流水线传输等性能优化，并处理乱序等更复杂的问题`▶ 1:14:15`。

> **老师强调**：设计原则是"先达成可靠性，然后优化性能"，不要一开始就同时解决所有问题`▶ 1:14:15`。

### 用有限状态机（FSM）描述协议

可靠传输协议本质上是一种**分布式算法**：发送方和接收方是各自独立运行的两个程序，它们必须遵循共同约定的规则、通过交换报文相互配合，才能共同保证可靠性。因此描述协议时，需要分别给出发送方和接收方的行为规则`▶ 1:15:46`。

课程使用**有限状态机（Finite State Machine, FSM）**来描述收发双方。

FSM 的基本要素包括：

- **状态（state）**：FSM 由一系列状态组成，其中有一个指定的**初始状态**；程序在任意时刻处于且仅处于一个状态。
- **事件（event）**：触发状态变化的外部或内部事情，状态的变化只能由事件引起。
- **动作（action）**：事件发生时执行的处理操作。
- **有向边（状态转移）**：从一个状态指向另一个状态，边上标注引起转移的事件以及要执行的动作`▶ 1:16:29 · 1:17:52`。

FSM 的一般表示形式：

```text
        事件 / 动作
状态1 ───────────────▶ 状态2
```

转移规则为：当某个事件发生，并且 FSM 当前正处于对应有向边的起始状态时，就执行该边所标注的动作，并转移到边所指向的新状态`▶ 1:17:52`。

> 后续介绍的每一个可靠传输协议，都会分别用**发送方 FSM** 和**接收方 FSM** 两个有限状态机共同描述，体现可靠传输的分布式特性`▶ 1:17:52`。

### 数据单元的术语约定

网络各层次对所传输的数据单元有不同的正式术语：

| 层次 | 正式术语 |
| --- | --- |
| 应用层 | 消息（message） |
| 传输层 | 报文段（segment） |
| 网络层 | 数据包 / 分组（IP 数据报） |
| 数据链路层 | 帧（frame） |

由于可靠传输是一种跨层通用技术，本章不严格区分上述术语，统一使用 **packet** 来指代传输的数据单元；课程的其他章节会尽量按照层次区分使用。在现代前沿学术与技术文献中，链路层、网络层、传输层通常也统一使用 packet，而应用层多使用 message、request 等术语`▶ 1:18:39`。

  - 有错且丢包信道：rdt 3.0

## 9. 完美信道上的RDT 1.0

> 课件 第三讲_传输层(2)可靠传输.pdf 第 16–18 页 · 讲解从 `1:20:21` 开始

### 基本假设

RDT 1.0 是可靠数据传输（rdt）协议设计的起点，它建立在"完美信道"的理想化假设之上：

- **完美信道**：报文在传输过程中既不会丢失，也不会受损（比特出错）。
- **始终就绪**：发送方和接收方的网络层始终处于就绪状态，不会出现发送方发送过快而接收方来不及处理的情况。
- **瞬间完成**：发送方/接收方能够生成/处理无穷多的数据，没有处理能力上的瓶颈。

> **老师强调**：现实中并不存在完美信道，RDT 1.0 只是一个理想化的起点，后续协议会逐步去掉这些假设`▶ 1:24:36`。

### RDT 1.0 的特点

在上述假设下，这个协议被称为"乌托邦"（Utopia）协议：

- 不处理任何**流量控制**工作（因为双方始终就绪）。
- 不处理任何**纠错**工作（因为信道不会出错或丢失）。
- 接近于**无确认的无连接服务**：发送方发出数据后不需要等待任何确认，接收方也不发回反馈。

### 发送方与接收方的行为

由于没有任何异常情况需要应对，发送方和接收方各自只需要一个状态，在无限循环中重复简单的操作。

**发送方**（在循环中不停发送）：
1. 从上一层获得数据；
2. 封装成数据包；
3. 交给下一层；
4. 完成一次发送。

```c
while (true) {
    from_upper_layer(&data);
    packet = make_pkt(data);
    to_lower_layer(packet);
}
```

**接收方**（在循环中持续接收）：
1. 等待数据到达；
2. 从下一层获得数据包；
3. 解封装，取出数据；
4. 将数据传递给上一层；
5. 完成一次接收。

```c
while (true) {
    wait_for_event(&event);
    from_lower_layer(&packet);
    extract_data(packet, &data);
    to_upper_layer(data);
}
```

### 有限状态机（FSM）描述

RDT 1.0 的发送方和接收方都只有**唯一的一个状态**，不存在状态迁移。

**发送方 FSM**：
- 状态：`Wait for call from above`（等待上层调用）。
- 触发事件：`rdt_send(data)`，即上层应用请求发送数据。
- 执行动作：
  - `packet = make_pkt(data)`：将数据封装成数据包；
  - `udt_send(packet)`：通过不可靠数据传输服务（此处实际表现为完美信道）将数据包发出。
- 动作完成后仍停留在原状态，等待下一次上层调用。

**接收方 FSM**：
- 状态：`Wait for call from below`（等待底层数据包到达）。
- 触发事件：`rdt_rcv(packet)`，即底层信道有数据包到达。
- 执行动作：
  - `extract(packet, data)`：从数据包中提取出数据；
  - `deliver_data(data)`：将数据交付给上层。
- 动作完成后仍停留在原状态，等待下一个数据包。

> **老师强调**：这个简单示例完整演示了可靠传输形式化描述中的四个核心接口/函数：`rdt_send()`、`udt_send()`、`rdt_rcv()`、`deliver_data()``▶ 1:23:02`。

### 四个核心接口的含义

| 接口 | 所在位置 | 作用 |
|---|---|---|
| `rdt_send(data)` | 发送方 | 上层调用，请求 rdt 协议发送数据（触发事件） |
| `udt_send(packet)` | 发送方 | rdt 协议调用底层不可靠传输服务发出数据包 |
| `rdt_rcv(packet)` | 接收方 | 底层有数据包到达时触发（触发事件） |
| `deliver_data(data)` | 接收方 | rdt 协议将提取出的数据交付给上层 |

其中 `udt` 表示 *unreliable data transfer*（不可靠数据传输），在 RDT 1.0 的理想假设下它恰好表现为完美信道，但在后续更现实的协议中需要通过确认、重传、序号等机制来弥补它的不可靠性。

## 10. 出错信道与ARQ、RDT 2.0

> 课件 第三讲_传输层(2)可靠传输.pdf 第 20–28 页 · 讲解从 `1:24:52` 开始

### 信道模型：比特可能翻转，但不丢包

本场景在完全可靠信道（RDT 1.0）的基础上进一步贴近现实：数据包通过不可靠信道传输时，其中某些比特可能发生 0—1 翻转，但这些错误都能被接收方通过校验和等差错检测技术发现。

- 信道只引入比特差错，不考虑数据包丢失。
- 接收方能够判断收到的数据包是否损坏。
- 核心问题：在这种“会出错、但错误可检测”的信道上，如何实现可靠数据传输。`▶ 1:24:52`

生活中的类比是打电话时信号很差：

- 语音中带有杂音，听不清时会说“喂？请再说一遍”，对方就重复刚才的内容。`▶ 1:25:45`
- 如果语音正常、听得清楚，就回应“嗯，好！”，然后对方继续说下一句。`▶ 1:25:45`

RDT 在该场景下的处理逻辑与此类似：接收方检查数据，并把接收结果反馈给发送方，发送方据此决定重传旧数据还是发送新数据。`▶ 1:25:45`

### 自动重传请求 ARQ

**自动重传请求（ARQ, Automatic Repeat reQuest）**是一种基于反馈的重传机制，用于在可能出错的信道上实现可靠传输。`▶ 1:27:29`

ARQ 的三要素为：

1. **（接收方）差错检测**：接收方利用校验和等机制判断数据包是否出错。
2. **（接收方）反馈**：接收方向发送方返回接收结果。
3. **（发送方）重传**：发送方收到反馈后，决定重传出错的数据包还是发送新数据包。`▶ 1:27:29`

#### 两类反馈

| 反馈 | 全称 | 含义 |
|---|---|---|
| **ACK** | acknowledgement | 接收方告诉发送方：数据包已正确收到 |
| **NAK** | negative acknowledgement | 接收方告诉发送方：收到的数据包有错误 |

ACK 和 NAK 本身不需要携带实际数据，因此称为**哑帧（dummy frame）**。协议只需能区分这两种反馈类型即可，例如用 1 比特表示 ACK/NAK。`▶ 1:28:28`

### RDT 2.0 协议

RDT 2.0 是基于 ARQ 思想设计的最简单协议。`▶ 1:28:28`

#### 接收方规则

- 如果检测到数据包有错，返回 **NAK**。
- 如果数据包正确，则：
  1. 从数据包中提取数据；
  2. 将数据交付上层；
  3. 向发送方回复 **ACK**。`▶ 1:28:28 · 1:33:11`

#### 发送方规则

- 从上层得到数据后，封装数据包并计算校验和，然后发送。
- 发送一个数据包后立即暂停，进入等待 ACK 或 NAK 的状态。
- 收到 **ACK**：说明该数据包已被正确接收，可以发送下一个新数据包。
- 收到 **NAK**：说明数据包出错，重传同一个数据包。`▶ 1:28:28 · 1:30:33 · 1:33:11`

### 停—等式协议

RDT 2.0 又称为**停—等式协议（stop-and-wait）**：发送方每发送一个报文后就停下来，等待接收方反馈，然后才继续发送。`▶ 1:29:56`

基本时序如下：

```text
发送方                          接收方
  |  数据帧                        |
  |------------------------------>|
  |                               | 校验
  |                               |
  |  ACK（正确）/ NAK（出错）       |
  |<------------------------------|
  |                               |
  |  ACK：发新数据                 |
  |  NAK：重传旧数据               |
```

老师用聊天的例子说明：只要接收方持续返回 ACK，发送方就可以持续发送新消息，类似于聊天对象不断回复“然后呢”，说话方便会继续讲下去；但在协议中，ACK 的具体内容并不重要，它只表示“已正确接收”。`▶ 1:31:33`

> **老师强调**：停—等协议的关键特征是“发送一个数据包后必须等待反馈”，不是拿到发送机会就连续不断地发送数据。`▶ 1:29:56`

### RDT 2.0 的有限状态机

#### 发送方状态

发送方有两个状态：

1. **Wait for call from above**：等待上层调用发送数据，是初始状态。
2. **Wait for ACK or NAK**：已发送数据包，等待接收方反馈。`▶ 1:33:11`

发送方状态转移如下：

| 当前状态 | 事件 | 动作 | 下一状态 |
|---|---|---|---|
| Wait for call from above | `rdt_send(data)` | `sndpkt = make_pkt(data, checksum)`；`udt_send(sndpkt)` | Wait for ACK or NAK |
| Wait for ACK or NAK | 收到 ACK：`isACK(rcvpkt)` | 无需重传 | Wait for call from above |
| Wait for ACK or NAK | 收到 NAK：`isNAK(rcvpkt)` | `udt_send(sndpkt)`，重传原数据包 | 仍为 Wait for ACK or NAK |

其中：

- `make_pkt(data, checksum)`：把上层数据和校验和封装成数据包。
- `udt_send(...)`：通过不可靠信道发送。
- 收到 NAK 时发送方**不发生状态转移**，仍停留在等待反馈状态，并重发刚才的数据包。`▶ 1:33:11 · 1:35:50`

#### 接收方状态

接收方只有一个状态：

- **Wait for call from below**：等待来自下层信道的数据包。`▶ 1:33:11`

接收方状态转移如下：

| 当前状态 | 事件 | 动作 | 下一状态 |
|---|---|---|---|
| Wait for call from below | 收到完好数据包：`rdt_rcv(rcvpkt) && notcorrupt(rcvpkt)` | `extract(rcvpkt, data)`；`deliver_data(data)`；`udt_send(ACK)` | 仍为 Wait for call from below |
| Wait for call from below | 收到损坏数据包：`rdt_rcv(rcvpkt) && corrupt(rcvpkt)` | `udt_send(NAK)` | 仍为 Wait for call from below |

接收方处理完数据包并返回 ACK 或 NAK 后，继续等待下一个到达的数据包，因此始终保持在同一个状态。`▶ 1:33:11`

### 正常流程与出错重传流程

#### 正常流程

1. 发送方处于等待上层数据的状态。
2. 应用层调用 `rdt_send(data)`。
3. 发送方计算校验和并封装数据包，调用 `udt_send(sndpkt)` 发送。
4. 发送方切换到等待 ACK/NAK 的状态。
5. 数据包完好到达接收方。
6. 接收方提取数据、交付上层，并返回 ACK。
7. 发送方收到 ACK 后不做额外数据处理，切换回等待上层数据的初始状态。`▶ 1:35:50`

#### 比特出错流程

1. 发送方发送数据包并进入等待 ACK/NAK 状态。
2. 数据包在传输过程中损坏。
3. 接收方通过校验检测到错误，返回 NAK。
4. 发送方收到 NAK 后不切换状态，而是重传同一个数据包。
5. 如果重传的数据包正确到达，接收方提取并交付数据，然后返回 ACK。
6. 发送方收到 ACK 后，才回到等待新数据的初始状态。`▶ 1:35:50`

### 小结

- RDT 2.0 处理的是**比特可能翻转、但不丢包，且错误可检测**的信道。
- 它采用 ARQ：接收方差错检测并反馈，发送方依据反馈重传。
- ACK 表示正确接收，NAK 表示接收出错；二者都是不需要携带数据的哑帧。
- RDT 2.0 是最简单的停—等式 ARQ 协议：发送一包，等待确认，再决定重传或发送下一包。
- 该协议仍建立在 ACK/NAK 反馈本身能够正确传输的前提上，尚未处理反馈帧损坏或丢失的问题。

## 11. 反馈帧出错与RDT 2.1

> 课件 第三讲_传输层(2)可靠传输.pdf 第 29–34 页 · 讲解从 `1:38:18` 开始

### 问题背景：ACK/NAK 反馈帧出错

RDT 2.0 高度依赖接收方返回的 ACK/NAK 反馈，但传输信道本身可能出错，因此 ACK/NAK 也可能损坏。发送方检测到反馈帧出错后，无法判断此前的数据传输究竟成功还是失败：接收方可能已正确收到数据，也可能没有收到`▶ 1:38:18`。

针对这一问题，有三种可选方案：

| 方案 | 做法 | 缺陷 |
|---|---|---|
| 方案 1 | 发送方通知接收方重传 ACK/NAK | 该“通知”本身也可能出错，又需要对通知进行确认，从而陷入无限循环，不可行`▶ 1:38:57` |
| 方案 2 | 采用既能检错又能纠错的复杂编码 | 每个 ACK/NAK 都要进行复杂编解码，计算与传输开销大；而 ACK/NAK 数量多、出错概率低，为小概率错误付出高代价不划算`▶ 1:38:57` |
| 方案 3 | 发送方不判断之前是否成功，直接重传数据 | 接收方可能收到多份相同的数据，需要去重`▶ 1:40:07` |

现实中通常选择**方案 3**：去重开销可以接受，而且只在真正出错时才执行额外操作；方案 2 则无论是否出错都要承担复杂纠错机制的开销`▶ 1:40:07`。

### 序号机制

方案 3 选定后，需要增加的额外操作是：

- **发送方**：在数据包中加入序号 `Seq`，用于区分不同数据包；
- **接收方**：忽略（丢弃）序号重复的数据包。

> **老师强调**：序号需要用比特表示、占用带宽，因此序号范围要合理设计，并非越大越好`▶ 1:42:00`。

在停等协议下，发送方每次只发一个包并等待反馈，序号只需区分“当前收到的包是不是前一个包的重传”，因此 **1 bit 序号（0、1）足够**：

- 前一次发送 `seq=0`，重传仍用 `seq=0`，下一个新数据包用 `seq=1`；
- 前一次发送 `seq=1`，重传仍用 `seq=1`，下一个新数据包用 `seq=0``▶ 1:42:00`。

这套在 RDT 2.0 基础上增加 1 bit 序号以处理 ACK/NAK 出错的协议，就是 **RDT 2.1**。

### RDT 2.1 的总体变化

**发送方：**
- 每个数据包加入序列号 `Seq`（取值 0 或 1）；
- 检查收到的 ACK/NAK 是否正确；
- 若反馈损坏或收到 NAK，则重传；只有收到正确的 ACK 才发送新数据；
- 相比 RDT 2.0，FSM 状态数翻倍：需要区分当前要发送的数据包序号是 0 还是 1`▶ 1:43:11`。

**接收方：**
- 需要检查到达数据包的序号，丢弃序号重复的包；
- 接收方并不知道自己上次发出的 ACK/NAK 是否被发送方成功收到，因此也要用状态记录“下一个等待的包序号”；
- 相比 RDT 2.0，FSM 状态数也翻倍：分别等待序号 0 和序号 1 的数据包；
- 若到达包序号与等待序号不一致，则判定为重复包`▶ 1:43:11`。

### 发送方状态机

发送方共有 4 个状态：等待上层调用 0、等待 ACK/NAK 0、等待上层调用 1、等待 ACK/NAK 1。

**发送序号 0 的数据包：**

1. 初始处于“等待上层 call 0”状态；
2. 收到上层数据后：`sndpkt = make_pkt(0, data, checksum)`，调用 `udt_send(sndpkt)` 发送，进入“等待 ACK/NAK 0”状态；
3. 在等待反馈状态：
   - 若 `corrupt(rcvpkt)`（反馈损坏）或 `isNAK(rcvpkt)`（收到 NAK）：判定此前数据包传输失败，执行 `udt_send(sndpkt)` **重传同一个序号 0 的包**，继续等待；
   - 若 `notcorrupt(rcvpkt) && isACK(rcvpkt)`（收到正确的 ACK）：确认成功，转移到“等待上层 call 1”状态，无需额外动作`▶ 1:44:28 · 1:45:18`。

**发送序号 1 的数据包（与上面对称）：**

1. 在“等待上层 call 1”状态收到数据：`sndpkt = make_pkt(1, data, checksum)`，`udt_send(sndpkt)` 发送，进入“等待 ACK/NAK 1”状态；
2. 在等待反馈状态：
   - 反馈损坏或收到 NAK：重传序号 1 的包；
   - 收到正确的 ACK：回到“等待上层 call 0”状态，准备发送下一个新数据`▶ 1:45:48`。

### 接收方状态机

接收方有 2 个状态：“等待来自下层的 0 号包”和“等待来自下层的 1 号包”，初始为等待 0 号包。

**等待 0 号包状态：**

| 到达情况 | 条件 | 接收方动作 | 状态变化 |
|---|---|---|---|
| 包损坏 | `corrupt(rcvpkt)` | 发送 NAK：`make_pkt(NAK, chksum)` 并 `udt_send` | 继续等待 0 |
| 正确但序号为 1（重复包） | `notcorrupt && has_seq1` | 不提取、不交付，**重发 ACK**（说明之前的 ACK 可能在途中损坏，发送方才重传了旧包） | 继续等待 0 |
| 正确且序号为 0（期望包） | `notcorrupt && has_seq0` | `extract` 提取数据、`deliver_data` 向上交付，发送 ACK | 转移到等待 1 |

> **老师强调**：等待 0 时收到序号 1 的正确包，说明它是此前数据包的重传，大概率是之前发的 ACK 被破坏了；此时接收方要重传一个 ACK，但因收到的不是期望包，状态保持不变`▶ 1:47:21`。

**等待 1 号包状态（逻辑完全对称）：**

| 到达情况 | 接收方动作 | 状态变化 |
|---|---|---|
| 包损坏 | 发送 NAK | 继续等待 1 |
| 正确但序号为 0（重复包） | 重发 ACK，不提取数据 | 继续等待 1 |
| 正确且序号为 1（期望包） | 提取并向上交付数据，发送 ACK | 转移到等待 0 |

`▶ 1:46:39 · 1:48:12`

### 小结与后续演化

- RDT 2.1 通过“**数据帧加 1 bit 序号 + 出错直接重传 + 接收方按序号去重**”解决了 ACK/NAK 反馈帧损坏的问题。
- 至此，RDT 2.1 已能在**丢包率为 0、仅可能出现比特差错**的信道上正常工作`▶ 1:49:05`。
- 可优化点：RDT 2.1 的 ACK 与 NAK 本身不携带额外信息，实现上只需 1 bit 即可区分这两种反馈；由此进一步演化出去掉 NAK、仅用 ACK 的 **RDT 2.2**`▶ 1:49:05`。

## 12. 用带序号ACK优化的RDT 2.2

> 课件 第三讲_传输层(2)可靠传输.pdf 第 35–37 页 · 讲解从 `1:49:49` 开始

### rdt 2.2：用带序号 ACK 取代 NAK

#### 改进动机

在 rdt 2.1 中，接收方的反馈分为 ACK（肯定确认）和 NAK（否定确认）两种，但 ACK 和 NAK 本身**不携带任何信息**（即不指明确认的是哪个分组）`▶ 1:49:49`。

rdt 2.2 做了如下改进：

- **在 ACK 中加上最近成功接收的分组序号（seq）**。
- 发送方通过**比较 ACK 携带的序号与自己刚发送分组的序号**，就能判断最近一次发送是否成功，因此 **NAK 不再需要**。
- 当出现以下任一情况时，发送方重传当前分组：
  1. ACK 损坏；
  2. ACK 未损坏，但其携带的序号 `ACK.seq != seq`（与期望不符）`▶ 1:49:49`。

#### 发送方状态机

发送方仍有四个状态：等待上层调用 0/1、等待 ACK 0/1。与 rdt 2.1 的区别体现在"等待 ACK"状态中的处理逻辑。

**等待分组 0 的 ACK（Wait for ACK 0）**：

| 事件 | 动作 |
|---|---|
| 收到未损坏且 `isACK(rcvpkt, 0)` 的 ACK | 确认成功，转移到"Wait for call 1 from above" |
| 收到损坏的 ACK，**或** 收到 `isACK(rcvpkt, 1)` | `udt_send(sndpkt)` 重传分组 0，留在本状态继续等待 |

即发送方会一直重传并等待，直到收到序号为 0 的正确 ACK 才完成状态转移`▶ 1:50:38`。

**发送分组 1 的过程与之对称**：

- 在"Wait for call 1 from above"状态调用 `rdt_send(data)` 时：`sndpkt = make_pkt(1, data, checksum)` 并发送，进入"Wait for ACK or NAK 1"。
- 在等待 ACK 1 时：
  - 收到未损坏且 `isACK(rcvpkt, 1)` → 转移回"Wait for call 0 from above"；
  - 收到损坏的 ACK **或** `isACK(rcvpkt, 0)` → 重传分组 1，继续等待`▶ 1:50:38`。

发送方伪代码逻辑（以分组 0 为例）：

```text
Wait for call 0 from above:
    rdt_send(data)
        sndpkt = make_pkt(0, data, checksum)
        udt_send(sndpkt)
        → Wait for ACK 0

Wait for ACK 0:
    rdt_rcv(rcvpkt) && notcorrupt(rcvpkt) && isACK(rcvpkt,0)
        → Wait for call 1 from above
    rdt_rcv(rcvpkt) && (corrupt(rcvpkt) || isACK(rcvpkt,1))
        udt_send(sndpkt)        // 重传分组0
        留在本状态
```

#### 接收方状态机

接收方仍只有两个状态：等待来自下层的分组 0 / 分组 1。核心改动是：**不再发送 NAK，遇到异常情况时重发上一次的 ACK**。

**等待分组 0（Wait for 0 from below）**：

| 事件 | 动作 |
|---|---|
| 收到未损坏且 `has_seq0(rcvpkt)` 的分组 | `extract` 提取数据 → `deliver_data` 交付上层 → 发送 `make_pkt(ACK, 0, chksum)` → 转移到"Wait for 1 from below" |
| 收到损坏的分组 **或** 收到 `has_seq1(rcvpkt)` 的分组 | `udt_send(sndpkt)`，即**重传上一次发出的 ACK（ACK 1）**，留在本状态 |

初始时接收方等待分组 0，此时若收到序号为 1 的分组，说明这是重复的旧分组（分组 1 此前已被接收确认过），于是重发上一次的反馈 ACK 1`▶ 1:51:34`。

**等待分组 1（Wait for 1 from below）**：

| 事件 | 动作 |
|---|---|
| 收到未损坏且 `has_seq1(rcvpkt)` 的分组 | 提取并交付数据 → 发送 `make_pkt(ACK, 1, chksum)` → 转移到"Wait for 0 from below" |
| 收到损坏的分组 **或** 收到 `has_seq0(rcvpkt)` 的分组 | 重传上一次的 ACK（ACK 0），留在本状态 |

接收侧的反馈逻辑与发送侧对称：**序号不一致或分组损坏时触发反馈重传，否则返回携带正确序号的新 ACK**`▶ 1:52:32`。

#### 为什么"重发上一个 ACK"等价于 NAK

- 发送方收到序号与当前分组不符的 ACK（例如正在等 ACK 0 却收到 ACK 1），就知道当前分组没有被正确接收，从而重传。
- 这样，接收方即使不显式发送 NAK，也能通过"重复旧 ACK"让发送方推断出需要重传，实现了与 NAK 相同的效果，同时把反馈类型从两种简化为一种。

> **老师强调**：rdt 2.2 的核心是**取消 NAK**，只靠带序号的 ACK 完成全部确认；无论是 ACK 损坏还是 ACK 序号不匹配，发送方一律重传；接收方在异常情况下则重发上一次的 ACK，两侧逻辑完全对称`▶ 1:49:49 · 1:50:38 · 1:52:32`。

### 本讲内容回顾

本讲围绕可靠数据传输（rdt）协议的逐步演进展开，主要分为三大部分：

#### 1. 一般的可靠性方案

按照信道质量由理想向现实逐步恶化的顺序，介绍了不同版本的可靠数据传输协议：

| 协议版本 | 信道假设 | 主要解决的问题 |
|---|---|---|
| rdt 1.0 | 完美信道 | 不需要差错控制，发送方直接发送、接收方直接接收 |
| rdt 2.0 | 信道会产生比特差错，但不丢包 | 通过校验和、确认帧 ACK、否定确认 NAK 等机制处理出错数据 |
| rdt 2.1 | 信道会产生比特差错，但不丢包 | 引入序号，解决 ACK/NAK 本身出错或损坏带来的问题 |
| rdt 2.2 | 信道会产生比特差错，但不丢包 | 在 rdt 2.1 基础上进一步完善，通常使用序号和 ACK 机制，不再依赖 NAK |

rdt 2.2 所假设的仍然是“只可能出错、不会丢包”的信道，因此并不是现实中真正存在的信道模型`▶ 1:52:46`。

#### 2. 一般可靠性方案的性能优化

在基本可靠传输机制的基础上，进一步提高信道利用率：

- **流水线传输**：发送方不必每发送一个分组就停下来等待确认，而是可以连续发送多个分组。
- **回退 N 算法（GBN, Go-Back-N）**：
  - 发送方可以连续发送窗口内的多个分组；
  - 接收方一般只按序接收；
  - 某个分组出错或丢失时，发送方需要重传该分组及其之后的所有分组。
- **选择重传算法（SR, Selective Repeat）**：
  - 发送方和接收方都维护窗口；
  - 接收方可以缓存乱序到达的正确分组；
  - 发送方只重传真正出错或丢失的分组，而不必回退重传一批分组。

#### 3. TCP 可靠性方案

在理解通用可靠传输原理之后，进一步讨论 TCP 如何在实际网络中实现可靠传输。

### 后续内容说明

真实信道除了会产生数据包比特错误外，还可能出现**丢包**问题，包括：

- 发送方发往接收方的数据包丢失；
- 接收方返回给发送方的 ACK 丢失。

这些问题无法由 rdt 2.2 完整处理，需要由后续的 **rdt 3.0** 协议解决。rdt 3.0 面向“**既可能出错、又可能丢包**”的信道，通常会引入超时重传等机制`▶ 1:52:46`。
